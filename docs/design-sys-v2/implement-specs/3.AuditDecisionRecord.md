# 4. Core Boundary Decision

The most important correction to the raw Audit Report is:

> **Shared visual anatomy does not imply shared product semantics.**

Design System V2 should aggressively reuse:

- tokens;
- primitives;
- layout anatomy;
- accessibility behavior;
- responsive mechanics;
- interaction mechanics.

It must **not** aggressively merge domain components simply because they look similar.

Canonical model:

```text
DOMAIN COMPONENT
      ↓ composes
GENERIC PATTERN
      ↓ composes
CORE COMPONENT
      ↓
PRIMITIVE / TOKEN
```

Example:

```text
WeddingGuestRow
      ↓
DataRow
```

NOT:

```text
WeddingGuestRow
      ↓ replace
GenericDataRow configured with all Wedding semantics
```

---

# 5. PRODUCT-SPECIFIC Rule

`PRODUCT-SPECIFIC` is a first-class disposition.

It does **not** mean:

- temporary;
- poorly designed;
- not reusable;
- should eventually disappear.

It means:

> The component owns meaningful product/domain semantics and should remain in its product/module layer while composing Design System primitives and patterns.

A `PRODUCT-SPECIFIC` component MAY use:

```text
Metric
MetricGroup
DataRow
EntityList
FilterBar
Section
StatusBadge
Dialog
ResponsiveModal
```

without being replaced by them.

## 5.1 Generic component boundary

Generic Design System components MUST NOT own:

- Wedding Guest semantics;
- Travel Activity semantics;
- Debt semantics;
- Finance calculations;
- Member roles;
- permission resolution;
- PlanType-specific business rules;
- invitation state;
- settlement calculation;
- business entity lifecycle.

Product components resolve those semantics first, then compose generic presentation.

# 8. Inspector / Master-Detail — OVERRIDE

Existing Finance/Planning implementations may provide evidence for extracting a reusable master-detail layout mechanism.

Canonical decision:

> **Extract the mechanism only after proven use cases are understood. Adoption is opt-in per product flow.**

Possible Design System pattern:

```text
MasterDetailLayout
```

It may own:

- desktop list/detail layout;
- selected-row presentation;
- responsive transition mechanics;
- mobile detail surface;
- focus/layout behavior.

It MUST NOT determine:

- what entity is selected;
- edit permissions;
- product actions;
- business detail content.

## 8.1 Adoption rule

Do NOT automatically extend Inspector/MasterDetail to:

- Wedding Guest;
- Debt;
- Todo;
- Members;

just because those screens contain a list and detail information.

Each adoption requires Product UX justification.

## 8.2 Pilot dependency

Wedding Guest Pilot does **not** require Inspector/MasterDetail as a prerequisite.

Inspector remains:

```text
REVIEW / OPT-IN
```

until a concrete Pilot/product flow demonstrates that it improves the UX.

# 13. Finance Color Semantics — RESOLVED

Human decision:

> **Monetary amounts are neutral by default.**

Do NOT automatically map:

```text
Income → green
Expense → red
```

for normal financial amounts.

Example:

```text
Tổng chi
12.500.000đ
```

should normally be neutral.

Semantic color is reserved for actual meaning such as:

```text
success
danger
warning
overdue
budget exceeded
positive outcome
negative outcome
attention state
```

Examples:

```text
Vượt ngân sách
+2.500.000đ
→ danger
```

```text
Bạn được nhận lại
1.200.000đ
→ success
```

```text
Còn phải trả
850.000đ
→ warning/danger depending on product context
```

## 13.1 Directional tokens

Income/Expense-specific colors MAY remain as narrow-use directional tokens where the UI explicitly needs transaction direction.

They are not the default color of all monetary values.

## 13.2 Severity override

Finance semantic color inconsistency:

```text
Raw Audit: P0
Canonical: P1 High
```

P0 is reserved for actual release-critical correctness/security/data failures.

```text

Tablet + Desktop
```

## 15.1 Audit severity override

Current implementation behaving mostly as a two-tier system is:


# 17. ErrorState / Retry — RESOLVED

Design System V2 should provide a reusable `ErrorState`.

Recommended anatomy:

```text

- title
- description?
- visual?
- action?       // optional
```

`Retry` is a possible action recipe.

It is NOT mandatory for every error.

Examples where retry may make sense:

```text

```

Examples where retry may not make sense:

```text
validation error
permission denied
duplicate guest
invalid CSV format
```
