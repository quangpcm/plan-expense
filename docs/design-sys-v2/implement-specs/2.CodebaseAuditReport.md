## 1. Executive Summary

### Current UI architecture

Go Plan is a Next.js 16 / React 19 / Tailwind CSS v4 App Router application with a **modular monolith** structure:

- `src/modules/<domain>/{components,hooks,services,repositories,schemas,types,utils}` — 15 domain modules (plan, member, invitation, milestone, todo, planning, expense, income, settlement, statistic, wedding-guest, travel-activity, debt-tracking, storage, auth, user, category).
- `src/shared/{components/ui, components/layout, hooks, lib, stores, types, utils, validation}` — cross-cutting, meant-to-be-generic layer.
- A single route `src/app/(authenticated)/plans/[planId]/page.tsx` renders the entire Plan-detail experience (all tabs: Overview, Planning, Finance, Wedding Guests, Members, Travel Itinerary, Debt Tracking) via tab-switch, not separate routes.
- Styling: Tailwind v4, theme defined in `src/styles/globals.css` via a single `@theme` block (no `tailwind.config.*` file exists — confirmed).

Two architectural instincts already present in the codebase closely match the target V2 philosophy, and materially de-risk migration:

1. **Plan Overview is genuinely widget/config-driven.** `src/modules/plan/components/overview-renderer.tsx` resolves an ordered, `enabled`-flagged widget list from `getResolvedPlanTypeConfig(plan)` and looks each ID up in `overview-widget-registry.tsx`/`overview-widget-registry.wedding.tsx` — a flat `Record<WidgetId, Definition>` map, not a `switch(planType)`. Confirmed zero `planType` branches inside the renderer itself.
2. **PlanCard already uses "shared anatomy + per-type config," not per-type conditional JSX.** `src/modules/plan/components/plan-card.tsx` has zero `planType` conditionals; all variance is pushed into `plan-card-config.ts` (metric/progress/footer functions per type) and `plan-card-visuals.ts` (icon/color per type) — precisely the "config map, not `if`" pattern V2 wants for `MetricGroup`/`DataRow` recipes.

### Readiness for Design System V2

**Medium readiness.** Architecture boundaries (UI→Hook→Service→Repository→Firebase, permission resolution, PlanType-as-configuration) mostly hold. Foundation tokens exist but are thin (2-tier, not 3-tier) and are bypassed constantly by ad-hoc Tailwind arbitrary values. Component-level duplication is high but mostly **visual**, not business-semantic, meaning consolidation is mechanical rather than risky. Two concrete, contained defects (finance color semantics, and a parallel non-accessible dialog system) need resolving before or during Foundation/Primitive migration.

### Top 5 risks

1. **Finance color semantics violate the (proposed) neutral-by-default rule** — `--color-income`/`--color-expense` tokens are applied by transaction **type**, not by state, in `modules/expense/components/timeline-list.tsx:290,347`, `modules/income/components/income-detail-card.tsx:40`, `modules/debt-tracking/components/debt-tracking-tab.tsx:71` (a *repaid* debt amount — a good outcome — is rendered in red), and `modules/plan/constants/overview-widget-registry.tsx:1166-1310`. A competing, correct neutral+state-based convention already exists side-by-side in `modules/statistic/components/finance-summary-hero.tsx:15-38` and `expense-detail-card.tsx:54` — this is a real, resolvable inconsistency, not a green-field decision.
2. **Two parallel dialog/sheet systems, one without accessibility.** `shared/components/ui/dialog.tsx` and `bottom-sheet.tsx` are hand-rolled `<div>`s with **no focus trap, no `aria-modal`, no Escape handling, no focus restore** — actively used in 3 and 11 files respectively, including one real Transaction form (`debt-tracking/components/debt-native-tab.tsx:299-345` wraps `DebtTransactionForm` in the non-accessible `BottomSheet` instead of the project's own mandated `ResponsiveModal`). A correct Radix/vaul-based pair (`responsive-modal.tsx`, `confirm-dialog.tsx`) exists but is under-adopted and independently re-derives the same chrome rather than composing.
3. **9 of 10 destructive actions use native `window.confirm()`** instead of the already-built, correctly-designed `ConfirmDialog` (`shared/components/ui/confirm-dialog.tsx`), including guest/group/invitation deletion in the Wedding Guest module (`wedding-guest-panel.tsx:357,510,592`) — the exact "destructive action must be visually distinct and hard to misclick" principle the target spec cares most about.
4. **Wedding Guest CSV Import/Export is completely unreachable below 1024px** (`wedding-guest-panel.tsx:673-688`, `hidden ... lg:*` with zero fallback) — a full capability loss on tablet and mobile that pre-emptively fails the "responsive recomposition preserves capability" rule for the highest-dependency Pilot screen.
5. **No typography scale, no shadow/elevation scale, single radius token.** ~930 Tailwind arbitrary-bracket occurrences, 90+ arbitrary `rounded-[Npx]` values (clustering at 18/20/24/26/28/32px, no relation to any scale), 41 distinct arbitrary shadow strings, 140 hex-color occurrences outside the theme file. High-volume but mechanical Foundation debt.

### Top 5 opportunities

1. **PlanCard + Overview widget registry are already the target pattern** (config/registry, not conditional JSX) — reusable directly as the template for `MetricGroup`/`DataRow` "recipe" APIs.
2. **Wedding Guest business-invariant discipline is excellent**, independently verified at the data layer: `guestCount`/`attendeeCount`/`moneyGiftTotal`/`goldGiftTotal` are computed and displayed as four separate numbers everywhere sampled (`wedding-guest-statistic.ts:23-50`, `wedding-guest-stat-tiles.tsx:29-54`, `wedding-guest-group-table.tsx:75-98`), and duplicate-guest handling is suggest-only end-to-end including through CSV import (`guest-duplicate-suggest-list.tsx`, `wedding-guest-import-preview-table.tsx:169-219`) — no auto-merge anywhere. This is the highest-stakes Pilot screen and it has the lowest business-regression risk.
3. **Zero role/permission checks found inside `shared/components/ui/*` or `shared/components/layout/*`.** All role logic lives in `modules/member/services/permission.service.ts` and is consumed via hooks that resolve booleans before handing off to components — the permission architecture boundary the spec requires already holds today.
4. **Several primitives are already close to the V2 target shape**: `badge.tsx` (dimension-based `tone` variant, fully tokenized), `input.tsx`/`textarea.tsx` (fully tokenized, correct focus-ring replacement), `section-heading.tsx` (19 consumers, matches the target `SectionHeader` anatomy), `dropdown-select.tsx` (18 consumers, tokenized, decent a11y base).
5. **Most "duplicate" patterns are visual, not semantic**, and business logic is cleanly separated from these presentational files — MetricGroup-shaped stat strips (5 independent implementations), DataRow-shaped rows (5 implementations), EmptyState blocks (6+ implementations) can be consolidated with low business risk.

### Estimated migration complexity: **Medium**

Foundation tokenization and component consolidation are broad in surface area but mechanical and low-risk (mostly visual-only changes, L0/L1 per the Impact Classification model). The two genuine "hard" items — dialog/overlay accessibility unification and finance color semantics — are now precisely scoped and contained, not open-ended.

### Module UI directories

`src/modules/{auth,category,debt-tracking,expense,income,invitation,member,milestone,plan,planning,settlement,statistic,storage,todo,travel-activity,user,wedding-guest}/components/*` — each module owns its own `components/hooks/services/repositories/schemas/types/utils`. Confirmed no shared UI directory contains a `repositories/` or direct `firebase`/`firestore` import (see Section 8).

### Component ownership pattern

- **Primitive/Component layer** (`shared/components/ui`) — generic, reusable, largely domain-blind (one confirmed leak, see DD-016/Section 8).
- **Pattern-ish layer** — not formally separated today; recurring anatomies (metric strips, list rows, filter bars, empty states) are re-implemented per module rather than centralized (see Sections 5–6).
- **Product Composition layer** — `modules/*/components/*`, e.g. `WeddingGuestPanel`, `MemberManagementPanel`, `PlanCard`. These correctly own domain semantics and (mostly) correctly avoid importing each other across module boundaries (verified: zero `wedding-guest` references inside `modules/member/**`, and `wedding-guest/**` only imports `modules/member` for identity/permission types, never UI components).

### Where business UI and generic UI currently sit

- Business UI: `src/modules/*/components/*` (correct location).
- Generic UI: `src/shared/components/ui/*`, `src/shared/components/layout/*` (correct location, mostly clean of domain leakage — see Section 8).
- Grey zone: `src/shared/lib/firestore/recalculate-estimated-amounts.ts` and `sync-user-plans.ts` — these are **not UI**, but they are `shared/lib` files containing Plan/Milestone/Todo business logic with direct Firestore writes, imported by 6 different module repositories. Out of Design System scope to fix, but recorded as Architecture Debt (Section 13) because it affects how confidently future UI work can trust the "UI → Hook → Service → Repository → Firebase" boundary.

## 5. Pattern Inventory

### PageHeader
No shared `PageHeader` exists. Four top-level screens, four independent implementations: `app/(authenticated)/plans/page.tsx:57-110` (bespoke greeting header), `app/(authenticated)/plans/[planId]/page.tsx:2100-2238` (bespoke title + ad-hoc KPI row), `app/(authenticated)/plans/archived/page.tsx:19-31` (Card+SectionHeading), `app/(authenticated)/settings/page.tsx:5-13` (Card+SectionHeading only). Common anatomy = eyebrow?/title/description?/actions?, i.e. exactly `SectionHeading`'s shape, but the two highest-traffic screens reinvent it. **Differences**: title size (VISUAL), presence of KPI row on plan-detail (BUSINESS SEMANTIC), presence of search/sort on plans list (actually a FilterBar, not header). **Decision: MERGE** header shell into a `PageHeader`; keep slotted content as Product Composition.

### SectionHeader
`shared/components/ui/section-heading.tsx` — **already unified**, 19 consumers across plan/debt-tracking/expense/member/planning/settlement/travel-activity/wedding-guest/settings. Matches the V2 target almost exactly. **Decision: KEEP**, layer `PageHeader` above it for the missing top-level cases.

### MetricGroup (4-stat strip)
Five independent implementations, three visual treatments:
- Single-Card strip (closest to target): `statistic/components/statistic-overview.tsx:11-38`, `plan/constants/overview-widget-registry.tsx:631-673` (`PlanSummaryWidget`), `:802-827` (`TravelFinanceKpiRow`) — near byte-identical class strings independently retyped 3 times.
- Per-metric bordered boxes (**the literal anti-pattern V2 forbids**): `statistic/components/completed-plan-overview.tsx:114-123`.
- Standalone tile grid: `wedding-guest/components/wedding-guest-stat-tiles.tsx:56-76`.

Common anatomy = label (uppercase/muted/tracked) + value (bold) + optional icon, 2/4-col responsive grid. **Differences**: wrapping chrome (VISUAL), icon presence (VISUAL), labels/content (BUSINESS SEMANTIC). **Decision: MERGE** into one `MetricGroup` (no default per-cell border), content stays Product Composition.

### Section grouping vs. Card-as-layout
No `Section` (chrome-free grouping) primitive exists. `Card` (`shared/components/ui/card.tsx`, 58 consumers) is used as the default wrapper for nearly everything, including content with no need for elevation (e.g. every entity row in `DebtList`/`DebtNativeList` individually wrapped in `Card`, `settings-group.tsx:14` reusing `Card` purely as a divider-list container). Correct chrome-free sections do exist (`overview-widget-registry.tsx:768-795` `FinanceSummaryWidget` — plain `<div className="space-y-3">` + `SectionHeading`). **Decision: introduce `Section`** as the default; demote `Card` to explicit opt-in for genuinely elevated content.

### DataRow / EntityList
No shared row primitive. Five independent row implementations sharing the same conceptual anatomy (leading?/title/metadata/status?/trailing?): `wedding-guest-list.tsx:50-119`, `debt-tracking/debt-list.tsx:31-64`, `debt-native-list.tsx:45-107`, `settlement-list.tsx:37-76`, and `todo-list.tsx`'s card-based rows. **Decision: MERGE** the row shell into `DataRow`; PRODUCT COMPOSITION for domain-specific metadata slotted in.

### FilterBar
Two real, structurally similar but independently built implementations: `wedding-guest-filter-bar.tsx:74-160` (search + dropdown grid, has an active-filter *dot* but **no reset control** despite computing `isFiltersActive`) and `todo-list-controls.tsx:21-107` (hand-rolled sort dropdown reimplementing listbox behavior the app already has via `DropdownSelect`, no search, no active-count, no reset). Neither implementation has a working "Xóa bộ lọc" reset — a genuine product gap, not just a dedup opportunity. **Decision: MERGE/build out** a proper `FilterBar` (search?/filters/activeCount/onReset).

### EmptyState
**No `EmptyState` component exists** (`grep -rn "EmptyState\|empty-state" src` → 0 hits). At least 6 bespoke inline implementations found, none distinguishing first-use/filter/permission-empty via a shared `variant` prop: `todo-list.tsx:29-33`, `wedding-guest-list.tsx:42-48`, `debt-list.tsx:21-29`/`debt-native-list.tsx:35-43`, `timeline-list.tsx:99-128`, `plans/page.tsx:129-136` (branches to `CreatePlanCard` instead of using a variant), `plans/archived/page.tsx:46-50`. One instance (`finance-tab.tsx:228-241`, the "nothing selected" inspector placeholder) already has the full target anatomy (icon+eyebrow+title+description) — use as the model. No mechanism anywhere lets a caller suppress a CTA for users without permission. **Decision: MERGE** into one `EmptyState` with a `variant` prop.

### LoadingState / Skeleton
`shared/components/ui/skeleton.tsx`, 14 consumers, well-adopted, skeleton shapes generally approximate real content (`plans/[planId]/page.tsx:838-842`). One exception: `route-loading-screen.tsx:23` uses a full-screen spinner for route *transitions* (defensible, distinct from data loading). **Decision: KEEP SEPARATE**, already matches spec direction.

### ErrorState
`modules/auth/components/auth-form-message.tsx` (`AuthFormMessage`) is the de-facto shared field/section error banner, used pervasively. **Gap: zero occurrences of retry/recovery affordance anywhere in the codebase** (`grep -rln "Thử lại\|onRetry\|retry" src` → 0 hits) — every error is a dead-end message, at every level. No distinct page-level error treatment exists. **Decision: MERGE** the banner visual, **add** an optional `onRetry` slot + page-level variant (net-new capability, not just dedup).

### DestructiveConfirmation
`shared/components/ui/confirm-dialog.tsx` is well-built (Radix AlertDialog / vaul Drawer, destructive styling, cancel/confirm separated) but used in exactly **1** place (`plans/[planId]/page.tsx:2673-2698`). **9 other destructive actions bypass it via native `window.confirm()`**: `plans/[planId]/page.tsx:863,1292,1408,1509,1560,1616` and `wedding-guest-panel.tsx:357,510,592`. Separately, `plans/[planId]/page.tsx:2616-2647` places "Hoàn thành kế hoạch" (safe), "Đóng kế hoạch" (soft-destructive) and "Xóa kế hoạch" (destructive) as three adjacent same-styled `secondary` buttons — the exact "sits next to a safe action, easy to misclick" anti-pattern the spec warns against. **Decision: MERGE — replace all 9 `window.confirm()` calls with `ConfirmDialog`.** Highest ROI, lowest risk fix in the entire audit (component already exists and is correct).

### Inspector (desktop master-detail vs. mobile sheet)
Exists, independently implemented twice: **Finance** (`expense/components/finance-tab.tsx:180-243`, `grid-cols-[1fr_1fr]` + `hidden lg:block` detail pane, media-query-driven mobile fallback to `ResponsiveModal`) and **Planning/Milestone** (`planning/components/planning-tab.tsx:199-259`, same shape, mobile fallback to `BottomSheet`). Structural mechanism (media query + `hidden lg:block` + sheet fallback) is duplicated; state shape is domain-specific (expected). No other list/detail flow in the app (Todo, Debt, Wedding Guest) has this desktop split — they all degrade to a centered modal even on wide viewports. **Decision: MERGE** into a shared `Inspector`/`MasterDetail` layout primitive, then extend adoption to Todo/Debt/Wedding Guest.

- **WeddingGuest identity ≠ GuestInvitation state**: type-level split confirmed — `WeddingGuestDocument` (`types/wedding-guest.ts`) carries only `name/sideId/relationshipId/invitedById`; `GuestInvitationDocument` (`types/guest-invitation.ts`) carries only `guestId/groupId/rsvp/attendeeCount/moneyGiftAmount/goldGiftAmount/note`. `guest-invitation-form.tsx:101-127` renders identity and invitation-state fields in visually separated sections with explicit copy clarifying identity is plan-wide ("Áp dụng cho khách này trên toàn kế hoạch, không riêng nhóm này", lines 106-108).
- **RSVP/attendee count per invitation**: `wedding-guest-group-table.tsx:75-98` shows guestCount and attendeeCount as two adjacent, separately-labeled columns; money/gold shown as two separate columns, never summed.
- **Money gift ≠ gold gift**: `wedding-guest-statistic.ts:23-50` computes `moneyGiftTotal` and `goldGiftTotal` as independent accumulators; every consumer (`wedding-guest-stat-tiles.tsx:29-54`, composition cards) renders them as separate figures.
- **No auto-merge**: `guest-duplicate-suggest-list.tsx` only exposes a "Chọn" button firing `onSelectGuest(guest)` — caller decides; confirmed no merge logic. Extends through CSV import: `wedding-guest-import-preview-table.tsx:169-219` blocks commit until the user makes an explicit per-row decision (`use_existing_sync`/`create_new`/`skip`) for any `name_only` match — no silent default.
- **Permission behavior**: authorization enforced at the service layer (`WeddingGuestService.assertManageWeddingGuestPermission`, `services/wedding-guest.service.ts:32-40`, throwing `AppError(...,'WEDDING_GUEST_PERMISSION_DENIED',403)`), not just gating UI visibility.

**V2 dependencies**: PageHeader, MetricGroup (replace `wedding-guest-stat-tiles.tsx`), FilterBar (complete the missing reset control, DD-010), EntityList/DataRow (replace `wedding-guest-list.tsx`'s hand-rolled row), StatusBadge (ready via Badge), Inspector (currently: `BottomSheet`-based forms, not a true desktop Inspector), Dialog/Sheet (needs migration off raw `Dialog`/`BottomSheet`), FormField (needs extraction), Empty/Error/Loading (EmptyState missing — DD-008).

**Blockers**:
- DD-002/DD-006 (overlay a11y) — Import/Export dialogs use the non-accessible `Dialog` primitive, not `ResponsiveModal`.
- DD-012 (responsive capability) — Import/Export entirely unreachable below 1024px; a real capability regression risk once "responsive recomposition preserves capability" becomes a locked invariant.
- DD-003 (destructive confirmation) — guest/group/invitation delete flows (`wedding-guest-panel.tsx:357,510,592`) use `window.confirm()`, not the app's own `ConfirmDialog`.
- DD-010 (FilterBar incomplete) — no reset control.
- DD-009 (no DataRow) — guest list row is a bespoke implementation.
- PD-003 (terminology overlap "khách") — a copy/IA decision needed before finalizing V2 labels, not a code defect.

**Relevant design debt**: DD-002, DD-003, DD-006, DD-008, DD-009, DD-010, DD-012, DD-013 (partial — group table duplication), DD-020 (DropdownSelect keyboard nav, used in filter bar).

**Expected impact level**: Mostly **L1/L2** (layout + interaction presentation — e.g. moving forms onto ResponsiveModal, adding desktop Inspector) with the business-logic layer entirely out of scope and already well-isolated, which is why the invariant risk is low despite the pattern-fragmentation being the highest of the three pilots.

**Readiness: PARTIAL.** Business-invariant correctness is the best of all three screens (verified, not assumed) — the blockers are entirely presentational/architectural (overlay accessibility, missing shared patterns, one responsive capability gap), not domain-risk.

## 19. Recommended Migration Order

Adjusted from the specification's generic order based on concrete evidence gathered in this audit (not a copy of the spec's default sequence):

1. **Foundation lock** — 3-tier color tokens (resolve the finance-color conflict, DD-001, as part of this step since it's a token-semantics decision, not a component decision), typography scale, radius scale (absorb the existing de-facto `rounded-[24px]`), elevation scale, one focus-ring convention.
2. **Highest-leverage primitives first, by consumer count**: `Button` (51), `Card`/`Section` (58 — but do the Section split *before* touching Card usage sites, since Section is the actual fix for DD-005), `Input`/`Textarea` (retokenize only, low risk), `Badge` (retokenize only), `DropdownSelect` (add keyboard nav — needed before FilterBar).
3. **Overlay unification** (DD-002/DD-006) — before any Pilot work touches a dialog/sheet, since Wedding Guest's pilot readiness is currently blocked on this. Migrate `dialog.tsx`'s 3 consumers and `bottom-sheet.tsx`'s form-usage consumers onto `ResponsiveModal`; make `ConfirmDialog` compose `ResponsiveModal` instead of re-deriving chrome; fix `date-field.tsx`/`date-time-input.tsx` focus indicator in the same pass (same root component family, same consumers).
4. **DestructiveConfirmation adoption** (DD-003) — mechanically replace the 9 `window.confirm()` call sites now that ConfirmDialog is the composition target; very low risk, high trust-signal payoff, unblocks Wedding Guest.
5. **MetricGroup** (DD-007) — needed by all 3 Pilots; build once, migrate `statistic-overview.tsx`, `completed-plan-overview.tsx` (removing the anti-pattern), the two `overview-widget-registry.tsx` instances, and `wedding-guest-stat-tiles.tsx`.
6. **PageHeader** (DD-011) — needed by Dashboard and Wedding Overview; build once `SectionHeading` is confirmed stable (it already is).
7. **EmptyState + ErrorState-with-retry** (DD-008, ErrorState gap) — needed by all 3 Pilots; model on the one already-correct instance (`finance-tab.tsx:228-241`).
8. **DataRow/EntityList** (DD-009) — needed specifically by Wedding Guest; do after MetricGroup/EmptyState since Wedding Guest's readiness depends on all three.
9. **FilterBar** (DD-010) — complete the missing reset control; depends on DropdownSelect keyboard-nav fix (step 2) and is required specifically for the Wedding Guest pilot.
10. **Plan Accent tokens** (DD-017) — retokenize `plan-card-visuals.ts`/`plan.constants.ts`; do after Foundation color lock (step 1), needed for Dashboard.
11. **Pilot: Wedding Overview** — lowest risk, architecture already correct; migrate widget anatomy onto MetricGroup/SectionHeader/PageHeader from steps 5-6.
12. **Pilot: Dashboard** — migrate PlanCard visuals (step 10) + page header (step 6) + MetricGroup (step 5).
13. **Pilot: Wedding Guest** — last, because it depends on the most new patterns (MetricGroup, EmptyState, DataRow, FilterBar, overlay unification) — but its business-invariant risk is already verified low, so once its Pattern dependencies land, the migration itself should be comparatively safe.
14. **Inspector/MasterDetail formalization + responsive capability fix for Guest Import/Export** (DD-012) — can happen either just before or just after the Wedding Guest pilot proper, since it's more of an "extend an existing pattern to new consumers" task than a pilot-blocking dependency; recommend doing it as part of the Wedding Guest pilot itself since the pilot already touches this module.
15. **Remaining P2/P3 polish items** (icon-scale outliers, reduced-motion gating, Toast decision, placeholder-as-label fixes, Switch touch target) — batch after the 3 Pilots are validated, per the "don't fix everything before Pilot" principle.

## 20. Unknowns / Human Decisions Required

1. **Finance color semantics — which convention wins?** The codebase currently has two real, live conventions (type-based green/red-by-default vs. neutral+state-based). This audit surfaces the conflict with precise evidence (DD-001) but does **not** decide the outcome — that is a Design/Product decision, not something to infer from code frequency.
2. **`--color-income`/`--color-expense` tokens — keep for compact/badge use only, or remove entirely?** If the neutral-default rule is adopted, these tokens may still have a legitimate narrow use (small directional dots/icons) as seen in `timeline-list.tsx:239`. Needs an explicit design decision on where color-by-type is still allowed.
3. **2-tier vs. 3-tier breakpoint reality.** Actual code overwhelmingly implements a 2-tier system (`<1024`/`≥1024`); the documented contract is 3-tier (Mobile/Tablet/Desktop). Decide whether to (a) formally adopt 2-tier and update the spec, or (b) invest in real Tablet-tier treatment where it currently collapses into Mobile (most consequentially, Wedding Guest Import/Export).
4. **`Card` usage pattern at all 58 call sites** — this audit sampled representative usages and confirmed the "Card as layout strategy" anti-pattern exists, but a full site-by-site classification (which of the 58 should become `Section`, which should stay `Card`) was out of this pass's scope and needs either a follow-up audit or a case-by-case decision during migration.
5. **`Toast` component** — built, tokenized, zero consumers, no toast mechanism exists in production at all today. Product decision needed: is toast feedback actually wanted (and if so, wire it up + add `aria-live`), or should the component be removed as dead code?
6. **`currency-field.tsx` vs. `amount-input.tsx`** — two different currency-entry UX patterns exist with only 1 and 7 consumers respectively. Decide whether both are intentionally serving different contexts or should converge.
7. **PD-002 (PlanCard wedding label ambiguity) and PD-003 (member "khách" / wedding "khách mời" terminology overlap)** — both are copy/IA decisions that touch business semantics (guest vs. member distinction) and should not be resolved unilaterally during a presentation-only migration; flagged for Product/Design review per the Business Invariant Registry's own escalation rule (Section 13.27 of the specification).
8. **PD-001 (business logic in `shared/lib/firestore/*`)** — out of Design System scope entirely, but the audit surfaces it because future UI work in this area should not assume the documented UI→Hook→Service→Repository→Firebase layering is airtight everywhere. Needs an Architecture-level decision on whether/when to relocate these two files.
9. **Contrast ratios, screen-reader behavior, 200% zoom behavior, and full heading-hierarchy correctness** — none of these can be verified by static code reading. All are marked `NEEDS HUMAN REVIEW` throughout Section 11 and require manual/automated runtime testing before the Accessibility Pilot Exit Criterion can be honestly marked PASS.
10. **Whether Wedding Guest Import/Export should genuinely stay desktop-only as an intentional product decision** (similar to the CSV import/export precedent noted in the specification for other flows) or whether this is an unintentional gap that should be fixed as part of the Pilot. The audit found no explicit product requirement stating Import/Export must be desktop-only (unlike the specification's own noted precedent for a different CSV flow) — this needs confirmation, not assumption.
