# 1. Purpose

This document defines how Go Plan Design System V2 is governed after the initial architecture, Pilot, and rollout process.

The goal is not merely to keep a component library working.

The goal is to preserve:

```text
visual consistency
architectural boundaries
product trust
accessibility
responsive quality
business safety
maintainability
reuse quality
documentation accuracy
```

while Go Plan continues to add:

```text
new Plan types
new modules
new workflows
premium capabilities
new product surfaces
```

The Design System must evolve without becoming either:

```text
a frozen library that blocks product development
```

or:

```text
an uncontrolled collection of one-off variants
```

---

# 2. Governance Principle

The canonical governance principle is:

> **Product needs may evolve the Design System, but product-specific meaning must not leak into the Design System merely for convenience.**

Every proposed Design System change should answer:

```text
Is this a reusable UI need?
Is it stable across product contexts?
Is the correct layer being changed?
Does it preserve existing contracts?
What regression risk does it introduce?
```

---

# 3. Governance Begins Before Rollout Ends

Governance rules apply as soon as V2 components become shared dependencies.

During rollout:

```text
migration governance
+
component governance
```

operate together.

After rollout:

```text
migration-specific processes decrease
governance becomes permanent
```

Do not wait until every screen has migrated before controlling V2 changes.

---

# 4. Design System Is Product Infrastructure

Treat Design System V2 as shared product infrastructure.

Changes to canonical:

```text
tokens
primitives
overlays
structural components
core patterns
```

may affect many modules.

Therefore shared UI changes require more discipline than a local product composition change.

---

# 5. Governance Layers

Governance applies across:

```text
Foundation
Core Primitives
Overlay Architecture
Structural Components
Core Patterns
Product Composition boundaries
Documentation
Regression coverage
Legacy retirement
```

Each layer has different acceptable responsibilities.

---

# 6. Dependency Direction Remains Permanent

The permanent dependency direction is:

```text
Product / Domain Composition
        ↓
Core Patterns
        ↓
Structural Components
        ↓
Core Primitives
        ↓
Foundation
```

Overlay infrastructure is shared at the appropriate primitive/infrastructure boundary.

Lower layers must never import upward.

---

# 7. Permanent Domain Boundary

Canonical Design System code must remain unaware of product concepts such as:

```text
Wedding
Travel
Debt
Finance
Guest
Member
Expense
Income
RSVP
Milestone
Todo
Shared Fund
Owner
Editor
Viewer
premium entitlement
```

unless a concept has genuinely become a product-wide generic UI semantic and has been explicitly approved through change control.

Similarity alone is not enough.

---

# 8. Product Composition Remains First-Class

Product-specific components are not considered architectural failure.

Components such as:

```text
WeddingGuestRow
MemberRow
DebtRow
TravelActivityTimeline
FinanceSummary
PlanOverviewHeader
```

may remain permanently product-specific.

They should compose shared V2 layers where useful.

Do not measure Design System quality by eliminating product components.

---

# 9. Ownership Model

Every canonical Design System area must have clear ownership.

At minimum ownership responsibilities include:

```text
API integrity
visual consistency
accessibility
documentation
regression awareness
deprecation decisions
review of new variants
```

If the repository does not formally assign individuals/teams, ownership may be process-based.

The important requirement is:

> Shared UI changes must have an explicit review responsibility.

---

# 10. Source of Truth

The source of truth consists of:

```text
approved Design System specifications
approved implementation specifications
canonical implementation
tests
documented examples
approved decision records
```

When documentation and implementation diverge:

```text
do not silently choose one
```

Determine whether:

```text
implementation is wrong
documentation is stale
or an approved evolution occurred without documentation update
```

Then reconcile explicitly.

---

# 11. Documentation Is Part of the Contract

A canonical component is not considered fully maintained if its implementation changes but its contract documentation does not.

Relevant changes should update:

```text
responsibility
API
variants
responsive behavior
accessibility behavior
migration notes
deprecation status
```

where applicable.

---

# 12. Change Categories

Every Design System change should be classified before implementation.

Canonical categories:

```text
G0 — Documentation only
G1 — Internal implementation / no public behavior change
G2 — Additive compatible capability
G3 — Existing visual/interaction contract change
G4 — Breaking API or architecture change
G5 — Foundation/system-wide semantic change
```

---

# 13. G0 — Documentation Only

Examples:

```text
clarify usage guidance
fix inaccurate example
document existing accessibility behavior
add migration note
```

Requirements:

```text
verify documentation matches implementation
no code regression gate beyond normal documentation checks
```

---

# 14. G1 — Internal Compatible Change

Examples:

```text
refactor internal markup
reduce duplicated classes
performance cleanup
internal helper extraction
```

Requirements:

```text
public API unchanged
visual behavior unchanged
accessibility unchanged
relevant tests pass
```

---

# 15. G2 — Additive Compatible Capability

Examples:

```text
new generic slot
new genuinely reusable size
new generic visual tone
additional supported composition
```

Requirements:

```text
real consumer evidence
genericity test
API review
responsive verification
accessibility verification
tests
documentation update
```

Do not add capability only because it may be useful someday.

---

# 16. G3 — Contract Change

Examples:

```text
default padding changes
default Card surface changes
Button hierarchy changes
FilterBar responsive behavior changes
overlay close behavior changes
```

These may not break TypeScript but can change many screens.

Requirements:

```text
impact search
consumer review
visual regression review
accessibility review
migration plan if needed
```

---

# 17. G4 — Breaking Change

Examples:

```text
remove prop
rename canonical variant
change component composition contract
remove legacy alias still in use
replace overlay API
```

Requirements:

```text
consumer inventory
migration strategy
compatibility decision
explicit approval
regression plan
documentation
zero-usage proof before removal where applicable
```

---

# 18. G5 — Foundation/System Change

Examples:

```text
semantic color meaning
spacing scale contract
radius roles
typography hierarchy
breakpoint/density strategy
focus system
status color semantics
```

This is the highest governance level because effects are system-wide.

Requirements:

```text
design rationale
repository impact analysis
representative surface review
accessibility review
Pilot-like validation if material
migration strategy
explicit decision record
```

---

# 19. Change Request Minimum

A proposed shared V2 change should state:

```text
Problem
Current limitation
Real consumers affected
Proposed layer
Proposed change
Why composition cannot solve it
Compatibility impact
Responsive impact
Accessibility impact
Migration impact
```

For small G0/G1 changes this may be concise.

For G3–G5 it must be explicit.

---

# 20. Consumer Evidence Rule

New shared capability requires evidence.

Preferred evidence:

```text
2+ real unrelated consumers
```

or:

```text
1 strong consumer + clearly established cross-product requirement
```

Do not create generic APIs from speculative future reuse.

---

# 21. Two-Consumer Rule Is Guidance, Not Dogma

Two consumers do not automatically justify abstraction.

Ask whether the repeated need is:

```text
structural
interaction-level
stable
domain-neutral
```

Two visually similar domain components may still need to remain separate.

---

# 22. Correct Layer Test

Before changing a component, ask:

```text
Foundation problem?
Primitive problem?
Overlay problem?
Structural problem?
Pattern problem?
Product composition problem?
```

Fix at the lowest correct reusable layer.

Do not patch Foundation for a one-screen issue.

Do not patch product CSS repeatedly for a real primitive defect.

---

# 23. Composition Before API Expansion

Before adding a prop or variant, attempt:

```text
existing composition
existing slot
product wrapper
existing semantic token
```

If composition solves the problem cleanly:

> do not expand the shared API.

---

# 24. Variant Governance

A new variant is justified only when it represents a recurring generic role.

Good candidates:

```text
interaction hierarchy
semantic tone
stable density
surface role
```

Bad candidates:

```text
wedding
finance
travel
dashboard-special
guest-list
premium-purple
```

---

# 25. Boolean Prop Governance

Avoid boolean accumulation.

Warning:

```text
compact
dense
bordered
elevated
highlighted
interactive
selected
mobile
special
...
```

If a component needs many booleans to satisfy unrelated screens:

```text
STOP
reassess component responsibility
```

---

# 26. God Component Detection

Review shared components for symptoms:

```text
many domain-neutral-looking but unrelated modes
large conditional render tree
dozens of props
product-specific branches
complex config objects
multiple layout systems
permission awareness
data awareness
```

A God Component should be decomposed before more consumers depend on it.

---

# 27. Configuration Engine Prohibition

Do not evolve Design System V2 into:

```text
schema-driven page builder
entity renderer
generic dashboard engine
generic CRUD framework
domain filter DSL
permission-aware UI engine
```

unless such architecture is separately designed and approved as a product platform capability.

That is not normal Design System evolution.

---

# 28. Foundation Governance

Foundation tokens should represent stable semantic roles.

Before adding a token ask:

```text
Is this a reusable semantic role?
Or merely a literal value needed by one screen?
```

Avoid token explosion such as:

```text
wedding-card-padding
travel-header-gap
finance-special-green
```

---

# 29. Color Governance

Permanent rule:

```text
semantic meaning > decorative preference
```

Do not add arbitrary colors to make individual modules more visually exciting.

Plan-Type expression should remain restrained and follow the approved theme specification.

---

# 30. Financial Color Governance

For Go Plan finance-related UI:

```text
ordinary monetary value
→ neutral by default
```

Use success/warning/danger only when the value represents an actual semantic state.

Do not automatically map:

```text
income → green
expense → red
```

unless a specific product context explicitly requires state meaning and is approved.

---

# 31. Typography Governance

New typography roles require strong evidence.

Prefer approved roles:

```text
page-title
section-title
component-title
body
body-strong
metadata
metric-sm
metric-md
metric-lg
```

Avoid per-feature font-size recipes.

---

# 32. Spacing Governance

Use the canonical spacing system.

Do not add arbitrary spacing tokens for isolated layout problems.

Product compositions may use existing scale values without every spacing combination becoming a semantic token.

---

# 33. Radius Governance

Canonical radius should remain role-based and restrained.

Do not increase radius globally to follow temporary visual trends.

A product surface should not create a new shared radius simply because it wants a softer appearance.

---

# 34. Elevation Governance

Elevation remains scarce.

Default surfaces should not gain shadows during routine polish.

New elevation roles require a clear layering/interaction purpose.

Trust and clarity take precedence over decorative depth.

---

# 35. Responsive Governance

Any shared component change must consider:

```text
Mobile
Tablet
Desktop
```

A desktop-only improvement that breaks mobile is not acceptable.

Go Plan remains mobile-first.

---

# 36. Capability Parity Governance

Responsive presentation may differ.

Capability should remain equivalent unless a product decision explicitly says otherwise.

Example:

```text
Desktop inline filters
Mobile modal filters
```

is valid.

Example:

```text
Desktop filters available
Mobile filters hidden
```

requires explicit justification.

---

# 37. Density Governance

Density is a system-level quality.

Avoid both:

```text
overly spacious mobile UI
```

and:

```text
desktop layouts that waste horizontal space
```

New density variants should use a small shared vocabulary and real evidence.

---

# 38. Accessibility Governance

Accessibility is a release criterion for canonical shared components.

Changes must preserve:

```text
keyboard access
focus-visible
semantic structure
accessible names
contrast
touch target intent
screen-reader order
non-color-only meaning
overlay focus lifecycle
```

A canonical accessibility regression blocks approval.

---

# 39. Overlay Governance

All normal modal workflows should continue using canonical overlay architecture.

Do not reintroduce local:

```text
Dialog
BottomSheet
portal
scroll lock
focus trap
```

implementations without explicit architecture review.

---

# 40. Confirmation Governance

Consequential/destructive confirmation must preserve AlertDialog-style semantics through `ConfirmDialog`.

Do not downgrade confirmation semantics to a normal modal for visual consistency.

---

# 41. New Overlay Needs

If a product needs a new overlay type, first determine whether it is:

```text
ResponsiveModal composition
ConfirmDialog composition
Popover/menu/tooltip primitive
truly new interaction pattern
```

Do not add a new overlay primitive for one workflow without review.

---

# 42. Structural Component Governance

Structural components remain anatomy-only.

Permanent boundaries:

```text
Metric → no calculation
MetricGroup → no aggregation
DataRow → no domain entity meaning
EmptyState → no permission decision
ErrorState → no backend recovery policy
Section → no business state
Card → no domain mode
```

---

# 43. Core Pattern Governance

Core Patterns remain product-neutral interaction compositions.

Permanent boundaries:

```text
EntityList → no fetching/sorting/domain actions
FilterBar → no domain filter execution
PageHeader → no route/permission/product semantics
```

---

# 44. Product Wrapper Governance

When a new feature needs shared UI, prefer:

```text
ProductComponent
    ↓
V2 composition
```

Do not push domain semantics downward simply to reduce wrapper count.

Product wrappers are the correct location for:

```text
business copy
permissions
domain state mapping
actions
formatting
route destinations
```

---

# 45. Permission Governance

Design System components must not resolve:

```text
Owner
Editor
Viewer
manage_all
module access
```

Product/application capability resolution occurs before rendering shared components.

Generic presentation states such as:

```text
disabled
selected
readOnly
```

are acceptable only after business capability has been resolved.

---

# 46. Premium Governance

Future premium/unlock functionality must not be implemented by teaching generic Design System components subscription rules.

Avoid:

```text
<Button requiresPremium />
<Card premium />
<EntityList premiumLimit={...} />
```

Product entitlement layer decides capability.

Design System presents supplied state/action.

If locked-feature presentation becomes recurring, specify it separately as a generic product pattern before extraction.

---

# 47. Business Invariant Governance

Design System maintenance must respect the Business Invariant Registry.

Shared UI refactors must not change:

```text
financial calculations
debt rules
guest/invitation semantics
member permissions
task/milestone ownership
travel activity behavior
```

If a shared change appears to require business logic modification:

> classify separately and review.

---

# 48. Finance Governance

Finance-related Design System migrations require particular care because visual presentation can obscure calculation regressions.

For shared changes affecting finance surfaces verify representative:

```text
totals
balances
fund state
settlement
payer/member display
currency overflow
```

The Design System remains calculation-neutral.

---

# 49. Wedding Governance

Preserve distinctions among:

```text
Member
Guest
Invitation
Expected attendee count
Guest Group
Milestone
```

Shared components must not collapse these into one generic product concept.

---

# 50. Members Governance

Members represent actual participation in a Plan.

Role and invitation actions remain product semantics.

Generic list/row/header components may present them but must not own role behavior.

---

# 51. Debt Governance

Debt direction and repayment rules remain entirely outside shared UI.

A generic tone or row layout must not infer debt semantics.

---

# 52. Travel Governance

Travel timeline/activity presentation may remain specialized even if EntityList exists.

Do not force a shared pattern where it harms timeline semantics.

---

# 53. New Plan Type Governance

When adding a new Plan type:

1. Use existing Foundation.
2. Use canonical primitives.
3. Reuse structural components where semantically correct.
4. Reuse Core Patterns where interaction matches.
5. Keep Plan-specific meaning in product composition.
6. Add new shared capability only after the governance test passes.

Do not fork the Design System per Plan type.

---

# 54. Plan-Type Expression Governance

Plan-Type expression should remain presentation-only and restrained.

Do not allow Plan types to redefine:

```text
Button semantics
status meanings
radius system
spacing system
typography system
overlay behavior
```

Plan identity may influence approved accent/expression, not fundamental interaction grammar.

---

# 55. New Component Proposal

Before adding a new canonical component, document:

```text
Problem
Existing alternatives
Why composition is insufficient
Known consumers
Responsibility
Non-responsibility
Layer
Accessibility contract
Responsive contract
Expected API
```

This may be concise for small components.

---

# 56. Component Admission Criteria

A new canonical component should satisfy:

```text
reusable
domain-neutral
stable responsibility
clear layer
testable
accessible
responsive
simpler than repeated local solutions
```

If it fails these:

> keep it product-local.

---

# 57. Component Rejection Is Healthy

Not every repeated visual should enter the Design System.

Rejecting premature abstractions protects:

```text
API quality
maintainability
product flexibility
```

A local product component can later become shared when evidence improves.

---

# 58. Experimental Components

If the team needs to test a possible abstraction, keep it outside the canonical Design System namespace/status until validated.

Mark clearly:

```text
experimental
not canonical
subject to change
```

Do not encourage broad adoption before responsibility stabilizes.

---

# 59. Promotion to Canonical

An experimental component may become canonical after:

```text
real usage
API stability
responsive verification
accessibility verification
domain-neutrality review
documentation
tests
```

---

# 60. API Stability

After rollout, canonical APIs should favor stability.

Avoid churn for naming perfection alone.

Breaking changes require material benefit.

Compatibility aliases may be preferable during migration.

---

# 61. Compatibility Policy

When changing shared APIs, choose explicitly among:

```text
preserve
alias
deprecate
migrate
break
```

Do not accidentally create breaking changes through cleanup.

---

# 62. Deprecation Policy

A deprecated API/component must have:

```text
replacement
reason
migration guidance
status
consumer inventory
```

where relevant.

Deprecation means:

```text
no new usage
```

not immediate deletion.

---

# 63. Legacy Registry

Maintain a registry for Design System legacy items during and after rollout.

Recommended fields:

```text
Legacy item
Canonical replacement
Status
Active consumers
Migration owner/wave
Removal condition
Notes
```

---

# 64. Removal Rule

Remove a legacy shared component only when:

```text
repository search confirms zero active consumers
replacement is stable
tests/build pass
no dynamic/indirect usage remains
documentation references are updated
```

Zero-usage proof is mandatory.

---

# 65. Do Not Keep Legacy Forever

Compatibility is useful during migration.

Permanent duplicate systems are not.

Once safe removal conditions are met:

```text
remove legacy
```

to prevent future accidental reuse.

---

# 66. Deprecated Import Prevention

Where practical, use existing lint/import-boundary mechanisms to prevent new imports from deprecated Design System paths.

Do not introduce heavy tooling solely for this unless justified.

Documentation alone is insufficient if deprecated imports repeatedly reappear.

---

# 67. Code Review Checklist

Shared V2 changes should review:

```text
Correct layer?
Domain-neutral?
API minimal?
Composition considered?
Responsive?
Accessible?
Uses semantic tokens?
No arbitrary colors?
No unnecessary elevation?
No permission/business logic?
Tests?
Docs?
Migration impact?
```

---

# 68. Product Review Checklist

Product components adopting V2 should review:

```text
Business behavior unchanged?
Permission behavior unchanged?
Data values unchanged?
Actions/routes unchanged?
Correct V2 layer used?
Product wrapper retained where needed?
Mobile capability preserved?
```

---

# 69. AI-Assisted Implementation Governance

AI may implement Design System work, but the same boundaries apply.

AI must be given:

```text
relevant V2 specs
Audit Decision Record
current implementation specs
Business Invariant Registry
scope/stop conditions
```

Do not ask AI simply to:

```text
"make the UI consistent"
```

across the repository.

That invites uncontrolled abstraction and business regression.

---

# 70. Required AI Pre-Code Report

For non-trivial shared changes, AI should report:

```text
CHANGE CLASSIFICATION
Affected V2 layer
Expected files
Consumers
Business logic touched?
Permissions touched?
Data model touched?
Compatibility risk
Stop conditions
```

before implementation.

---

# 71. AI Boundary Violation

Stop AI implementation when it proposes:

```text
moving business logic into shared UI
new generic config framework
PlanType branches in canonical components
permission-aware Design System components
mass codemod without semantic classification
Service/Repository changes for visual work
```

Review before proceeding.

---

# 72. Testing Governance

Use the repository's existing test architecture.

Canonical components should have tests focused on their contracts.

Product regression tests should remain product-aware.

Do not put Wedding/Finance fixtures into generic component unit tests unless the fixture is purely display text and has no semantic dependency.

---

# 73. Test Pyramid

Prefer:

```text
Foundation/static contract checks
        ↓
Component unit tests
        ↓
Pattern interaction tests
        ↓
Product integration/regression tests
        ↓
Manual responsive/accessibility verification
```

Not every visual detail needs a brittle snapshot.

---

# 74. Visual Regression Governance

For high-impact G3–G5 changes, verify representative product surfaces.

Choose surfaces that stress:

```text
mobile
desktop
large currency
long Vietnamese copy
lists
filters
overlays
empty/error states
```

Do not validate only a component sandbox.

---

# 75. Representative Surface Set

Maintain a small representative review set over time.

It should include examples from different product pressures, such as:

```text
one data/list-heavy surface
one finance-heavy surface
one collaboration/permission surface
one overlay/form-heavy surface
one mobile-dense surface
```

Exact surfaces may evolve.

---

# 76. Accessibility Regression Governance

Changes to canonical interactive components require explicit accessibility verification.

High-risk examples:

```text
Button
Input
Select
Dropdown
Modal
ConfirmDialog
interactive DataRow
FilterBar
```

Accessibility failures block release of the shared change.

---

# 77. Performance Governance

Shared components can amplify performance problems across the app.

Review changes that introduce:

```text
new context providers
large client boundaries
expensive runtime configuration
unnecessary effects
frequent rerender chains
```

Do not optimize prematurely, but avoid systemic overhead.

---

# 78. Client Boundary Governance

Presentation-only components should remain server-compatible where possible.

Do not add `"use client"` to canonical components without a real interaction need.

A shared client boundary can increase bundle cost across many consumers.

---

# 79. Dependency Governance

Do not add major UI dependencies casually.

A new dependency proposal should explain:

```text
problem solved
why existing stack is insufficient
bundle/runtime impact
accessibility implications
maintenance risk
```

---

# 80. CSS Governance

Prefer canonical tokens and component recipes.

Avoid:

```text
global overrides for one screen
!important escalation
deep selectors into component internals
duplicated raw color values
```

Product-local layout styles are acceptable when they express product composition rather than recreating shared components.

---

# 81. Escape Hatch Governance

Occasional customization is necessary.

An escape hatch is acceptable when:

```text
generic contract remains intact
customization is local
accessibility is preserved
it does not create hidden domain behavior inside shared UI
```

Repeated escape-hatch usage is evidence that a shared contract may need review.

---

# 82. `className` Governance

If canonical components support `className`, it should enable local composition, not encourage overriding core semantics.

Do not rely on `className` to routinely undo:

```text
focus behavior
disabled behavior
interaction semantics
critical responsive behavior
```

---

# 83. Design Drift Detection

Periodically inspect for:

```text
new arbitrary colors
new local shadows
new radius values
duplicate buttons
duplicate cards
duplicate modal implementations
duplicate filter bars
one-off page headers
```

Drift should be corrected early.

---

# 84. Drift Is Not Automatically a DS Defect

When drift is found, classify:

```text
product-local valid exception
missed reuse opportunity
Design System gap
legacy residue
incorrect implementation
```

Do not force every exception into shared components.

---

# 85. Maintenance Review Cadence

Use a practical review cadence based on development volume.

Recommended triggers include:

```text
after major rollout wave
before/after new Plan type
after repeated UI exceptions
before significant premium UI expansion
when multiple legacy items accumulate
```

A fixed calendar ceremony is optional.

---

# 86. Governance Metrics

Useful qualitative/quantitative signals:

```text
deprecated component usage
duplicate canonical primitive implementations
number of arbitrary token exceptions
accessibility regressions
shared component breaking changes
migration backlog
repeated escape hatches
```

Avoid vanity metrics such as:

```text
percentage of JSX using Design System components
```

More shared-component usage is not always better.

---

# 87. Success Metric

A healthy Design System means:

```text
new product UI is faster to build
common interactions feel consistent
product-specific complexity remains expressible
shared changes are predictable
regressions are rare
accessibility is built in
mobile and desktop remain coherent
```

---

# 88. Trust Metric

Because Go Plan handles important planning and financial information, visual trust is a core quality measure.

Review whether shared evolution preserves:

```text
clarity
predictability
calmness
readability
stable interaction
```

Do not chase visual novelty at the cost of confidence.

---

# 89. Animation Governance

Animation should support:

```text
state change
orientation
feedback
continuity
```

not decoration for its own sake.

Avoid adding broad motion systems until there is a clear product need.

Respect reduced-motion preferences for meaningful animation.

---

# 90. Trend Governance

Do not rewrite the system to follow temporary design trends such as:

```text
heavy glassmorphism
extreme gradients
excessive rounded cards
large floating shadows
novel navigation patterns
```

A trend may be adopted only when it improves Go Plan's product goals.

---

# 91. Brand Governance

Go Plan's brand expression should remain recognizable but restrained inside the application.

Primary identity:

```text
GO
violet/indigo → blue → cyan
```

does not imply every surface needs the brand gradient.

Use brand expression strategically.

---

# 92. White-Label / Future Template Reuse

Design System V2 should remain reusable enough to serve as a strong foundation for future products/templates.

However:

> Do not weaken Go Plan semantics or over-generalize today's system solely for hypothetical white-label reuse.

Reusable architecture comes from:

```text
semantic tokens
clean layers
domain-neutral primitives
composition
```

not from a giant configuration engine.

---

# 93. Template Extraction Rule

If Go Plan later becomes the source for another website/app template:

```text
extract Foundation
extract generic primitives
extract proven structural components
extract proven patterns
```

Then create product-specific compositions separately.

Do not copy Go Plan domain components into the generic template layer.

---

# 94. Premium UI Evolution

When premium is introduced, maintain trust and consistency.

Premium differentiation should not require a parallel visual system.

Potential premium expression may use:

```text
restrained badge
lock/upgrade affordance
feature explanation
plan comparison
```

but entitlement logic stays outside Design System.

A dedicated specification should precede broad premium UI extraction.

---

# 95. New Feature Workflow

For a normal new feature:

```text
1. Identify product requirements
2. Compose existing V2 components
3. Keep domain behavior product-local
4. Identify genuine DS gaps
5. Propose shared changes only if justified
6. Verify responsive/accessibility
7. Update docs/tests when DS changes
```

---

# 96. New Module Workflow

For a new module:

```text
Product architecture first
↓
Existing Design System composition
↓
Local product components
↓
Observe repeated generic needs
↓
Governed Design System evolution
```

Do not design a new module by first adding many generic variants.

---

# 97. Bug Fix Workflow

When a UI bug appears, classify:

```text
shared component defect
product composition defect
business defect
responsive defect
accessibility defect
```

Fix at the correct layer.

Do not patch a shared primitive for a product-only issue.

---

# 98. Shared Regression Incident

If a canonical component change causes regressions across multiple modules:

```text
stop further rollout of the change
identify affected contract
revert or fix at shared layer
verify representative surfaces
document the cause
```

Do not apply many product-local patches to compensate for a shared defect.

---

# 99. Emergency Fixes

Urgent production fixes may bypass normal documentation sequencing when necessary.

However after stabilization:

```text
document the change
reconcile specs
add regression coverage
review whether architecture was compromised
```

Emergency does not mean permanent undocumented divergence.

---

# 100. Decision Records

Create/update a decision record for material changes such as:

```text
new foundational semantic
major component responsibility change
new shared interaction pattern
breaking API
significant responsive convention
major accessibility architecture change
```

Small implementation details do not require formal ADR-style records.

---

# 101. Decision Record Minimum

Record:

```text
Context
Decision
Alternatives
Reason
Impact
Migration
Regression considerations
```

Keep decisions discoverable.

---

# 102. Documentation Structure

Maintain a clear distinction among:

```text
Design principles/specification
Implementation specifications
Decision records
Migration/rollout records
Component usage documentation
```

Do not let one giant document become the only source of truth.

---

# 103. Documentation Versioning

When a material contract changes, update:

```text
version/status
affected sections
migration notes
```

Do not create new V3 naming for every small evolution.

Major version changes should represent genuine system-level incompatibility.

---

# 104. Naming Governance

Canonical component names should describe generic responsibility.

Prefer:

```text
MetricGroup
DataRow
FilterBar
PageHeader
```

Avoid names tied to visual fashion:

```text
BeautifulCard
ModernPanel
GlassContainer
PremiumBox
```

---

# 105. Prop Naming Governance

Props should describe stable generic intent.

Prefer:

```text
tone
size
density
selected
disabled
```

Avoid domain aliases in generic APIs.

---

# 106. Semantic HTML Governance

Use native semantics whenever possible.

Do not add ARIA roles unnecessarily.

Interactive components should use appropriate native elements or proven accessible primitives.

---

# 107. Icon Governance

Continue using the approved icon system/conventions.

Icons should support recognition, not replace important text everywhere.

Icon-only controls require accessible names.

Do not add multiple icon libraries for visual preference.

---

# 108. Empty/Error Governance

EmptyState and ErrorState remain semantically distinct.

Product composition owns:

```text
cause
copy
recovery action
permission-aware action availability
```

Do not merge them into a universal state engine.

---

# 109. Loading Governance

Keep:

```text
loading
empty
error
content
```

distinct.

Do not display empty content before loading resolves.

Do not teach generic components domain loading logic.

---

# 110. Filter Governance

FilterBar remains a UI composition pattern.

Product owns:

```text
filter model
defaults
search semantics
sort semantics
URL synchronization
backend query
```

Do not gradually move these into FilterBar.

---

# 111. EntityList Governance

EntityList remains a collection pattern.

Product owns:

```text
data
fetching
sorting
filtering
selection meaning
row actions
pagination semantics
```

Do not turn EntityList into generic CRUD.

---

# 112. PageHeader Governance

PageHeader remains page hierarchy/action presentation.

Product owns:

```text
permission
route targets
Plan context
business metadata
premium state
```

Rich Plan headers may remain separate compositions.

---

# 113. Metric Governance

Metric receives display-ready value/context.

Product owns calculation and formatting policy where domain-specific.

Do not let convenience pressure turn Metric into a statistics engine.

---

# 114. DataRow Governance

DataRow remains row anatomy.

Product wrappers own entity semantics.

If multiple domain rows need radically different anatomy, do not keep adding DataRow slots indefinitely.

A specialized product row is acceptable.

---

# 115. Card Governance

Card is a contained surface, not a universal content component.

Avoid:

```text
Card variants per feature
nested Card proliferation
shadow-heavy hierarchy
```

Use Section/plain grouping when containment is unnecessary.

---

# 116. Section Governance

Section represents logical content grouping.

It should remain lightweight and should not become:

```text
data loader
permission boundary
automatic Card
analytics section engine
```

---

# 117. Button Governance

Button hierarchy should remain predictable across the app.

New product features should not invent new primary/secondary semantics.

Product chooses action priority; Button expresses it.

---

# 118. Form Primitive Governance

Inputs/selects should preserve:

```text
label
error
disabled
focus
keyboard
touch
```

behavior.

Domain validation remains outside generic primitives.

---

# 119. ResponsiveModal Governance

ResponsiveModal provides adaptive presentation while preserving modal capability.

Product owns workflow.

Do not add product-specific footer/action logic into the overlay primitive.

---

# 120. ConfirmDialog Governance

ConfirmDialog is reserved for consequential confirmation.

Do not use it as a generic information modal merely for styling.

Keep destructive intent explicit.

# 123. Regression Manifest

For material shared changes explicitly state:

```text
Business logic changed: NO
Data model changed: NO
Permissions changed: NO
Routes changed: NO
Financial calculations changed: NO
Domain semantics changed: NO
Existing capability changed: NO
```

Any `YES` means the work is not solely a Design System maintenance change and requires appropriate product review.

---

# 124. Stop Conditions

STOP and request architectural review if a proposed V2 change requires:

```text
domain imports in canonical components
permission resolution in Design System
business calculations in shared UI
Service/Repository/Firestore changes for presentation
PlanType branching throughout primitives
premium entitlement inside generic components
new generic CRUD/config engine
mass breaking change without migration
removing legacy before zero-usage proof
accessibility regression
mobile capability regression
```

---

# 125. Rollback Governance

Material shared changes must be reasonably rollbackable.

Avoid combining:

```text
Design System breaking change
+
business feature rewrite
+
data model change
```

in one inseparable migration.

Smaller boundaries improve safety.

---

# 126. Maintenance Backlog

Maintain a visible backlog for:

```text
deprecated components
known DS gaps
repeated escape hatches
accessibility improvements
documentation drift
legacy cleanup
potential abstractions awaiting evidence
```

Do not convert every backlog item into immediate shared work.

# 127. Debt Classification

Design System debt should be classified:

```text
D1 — cosmetic inconsistency
D2 — repeated local duplication
D3 — accessibility/responsive weakness
D4 — architectural boundary violation
D5 — business/regression risk caused by shared UI
```

Prioritize D4/D5 above cosmetic polish.

---

# 128. Maintenance Priority

Recommended priority:

```text
1. Regression/business safety
2. Accessibility
3. Broken architecture boundaries
4. Responsive capability
5. Repeated inconsistency
6. Visual polish
```

This reflects Go Plan's trust-oriented product direction.

# 135. Practical Decision Rule

For routine development:

```text
Can existing V2 composition solve it cleanly?
→ Use existing V2.

Is the need product-specific?
→ Keep it product-local.

Is the need recurring and domain-neutral?
→ Propose V2 evolution.

Would the change affect many consumers?
→ Raise governance level.

Would it change business behavior?
→ It is not only a Design System change.
```
