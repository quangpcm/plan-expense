# 1. Purpose

This specification defines the first controlled migration of a real Go Plan product surface onto Design System V2.

Phases 1–5 establish reusable infrastructure.

Phase 6 answers a different question:

> **Does the Design System actually work when applied to real Go Plan product complexity without changing business behavior?**

The Pilot is therefore not merely a visual redesign.

It is an architectural validation exercise.

---

# 2. Pilot Objective

The Pilot must validate the complete V2 stack:

```text
Foundation
    ↓
Core Primitives
    ↓
Overlay Architecture
    ↓
Structural Components
    ↓
Core Patterns
    ↓
Product Composition
```

The Pilot should prove that:

```text
visual hierarchy improves
responsive behavior improves
accessibility improves
composition remains readable
domain logic remains outside Design System
business behavior remains unchanged
migration remains manageable
```

---

# 3. Pilot Is a Gate, Not a Rollout

Do not interpret Phase 6 as permission to migrate all modules.

Correct sequence:

```text
Infrastructure
    ↓
One controlled Pilot
    ↓
Review
    ↓
Correct Design System problems
    ↓
Approve rollout
    ↓
Progressive module migration
```

Incorrect:

```text
Infrastructure
    ↓
Pilot begins
    ↓
simultaneously migrate entire repository
```

---

# 4. Pilot Surface Selection

The exact Pilot surface MUST follow the approved Audit Decision Record and migration strategy.

Do not choose a Pilot merely because:

```text
it is visually attractive
it is easy
it has few components
it makes screenshots look impressive
```

A useful Pilot must exercise enough V2 architecture to expose weaknesses.

---

# 5. Recommended Pilot Characteristics

The chosen surface should ideally contain several of:

```text
PageHeader or rich product header interaction
Section
Card
Metric / MetricGroup
EntityList / DataRow
FilterBar
Empty/Error states
Button/Input/Select
ResponsiveModal or ConfirmDialog
mobile + desktop differences
real permission-gated actions
real product state
```

It does not need every V2 component.

It must be representative enough to validate the system.

---

# 6. Pilot Risk Balance

Avoid both extremes.

Too simple:

```text
static settings page
one form
one empty screen
```

does not validate the system.

Too complex:

```text
entire Finance reconciliation architecture
all Wedding Guest workflows at once
multi-module dashboard redesign
```

creates too much regression risk.

Select a bounded but meaningful product surface.

# 9. Product Semantics Are Frozen

During Pilot migration, existing product semantics are treated as frozen unless an upstream approved specification explicitly changes them.

Frozen includes:

```text
feature availability
business calculations
permissions
action outcomes
data model
data ownership
sorting semantics
filter semantics
route destinations
validation rules
domain terminology
```

Visual hierarchy may change.

Product meaning must not.

---

# 10. No Opportunistic Product Redesign

Do not use the Pilot to “clean up” unrelated product behavior.

Examples of prohibited opportunistic changes:

```text
rename domain fields without approved copy decision
change Guest/Member meaning
change finance formulas
change task ownership
change permissions
change filters
change route architecture
change mobile feature availability
```

If a product issue is discovered:

```text
record it
classify it
defer it
```

unless it blocks V2 migration.

# 17. Disposition Per Existing Component

Each existing Pilot component must receive one disposition:

```text
KEEP
ADAPT
COMPOSE
REPLACE
DEPRECATE
DEFER
```

Definitions:

```text
KEEP
→ already correct; minimal/no change

ADAPT
→ same component/responsibility, migrate to V2

COMPOSE
→ retain product component but use V2 internals

REPLACE
→ generic duplicate safely replaced by canonical V2 layer

DEPRECATE
→ keep temporarily, stop new use

DEFER
→ outside Pilot scope
```

---

# 18. Prefer COMPOSE for Product Components

For domain-aware components, default preference is:

```text
COMPOSE
```

Example:

```text
WeddingGuestRow
→ remains WeddingGuestRow
→ internally composes DataRow
```

not:

```text
WeddingGuestRow
→ deleted
→ generic DataRow receives Guest object
```

This protects product boundaries.

# 21. Migration Strategy

Migrate inside-out:

```text
1. Confirm product behavior
2. Replace local visual tokens
3. Adopt primitives
4. Adopt structural components
5. Adopt patterns
6. Adapt overlays
7. Refine responsive composition
8. Verify accessibility
9. Remove now-unused local presentation duplication
```

Do not begin by deleting existing product components.

---

# 22. One Concern at a Time

Prefer small commits/changesets by concern:

```text
foundation adoption
primitive adoption
structural composition
pattern composition
overlay migration
responsive refinement
cleanup
```

Do not combine all Pilot changes into one opaque rewrite if the workflow supports incremental implementation.

---

# 23. Foundation Adoption

Pilot should eliminate local presentation decisions when canonical Foundation semantics exist.

Examples:

```text
raw slate text
→ semantic text token

arbitrary radius
→ canonical radius

local shadow
→ canonical elevation or none

local spacing
→ spacing scale where repeated
```

Do not change product status mapping solely because token names changed.

---

# 24. Primitive Adoption

Replace local generic control styling with canonical primitives where semantic behavior matches.

Examples:

```text
local button
→ Button

local text input
→ Input

local select
→ DropdownSelect
```

Do not replace specialized domain controls if canonical primitives cannot preserve behavior.

---

# 25. Structural Adoption

Use:

```text
Section
Card
Metric
MetricGroup
DataRow
EmptyState
ErrorState
```

only where their Phase 4 responsibilities fit.

Do not optimize for maximum component usage.

A successful Pilot may intentionally leave some custom product layout intact.

---

# 26. Pattern Adoption

Use:

```text
EntityList
FilterBar
PageHeader
```

only where their Phase 5 boundaries fit.

Product wrappers should remain.

Example:

```text
WeddingGuestFilters
    ↓
FilterBar
```

not:

```text
FilterBar understands wedding guest filters
```

---

# 27. Overlay Adoption

Normal modal workflows:

```text
→ ResponsiveModal
```

Consequential/destructive confirmation:

```text
→ ConfirmDialog
```

Do not downgrade AlertDialog semantics.

Do not change mutation behavior while migrating overlay presentation.

---

# 28. Responsive Migration

Pilot must be verified as one responsive product, not desktop UI plus a later mobile patch.

Evaluate:

```text
Mobile
Tablet
Desktop
```

For each section ask:

```text
What remains visible?
What wraps?
What stacks?
What moves into overlay?
What becomes denser?
What stays identical?
```

Capability should remain available unless explicitly approved otherwise.

---

# 29. Mobile-First Priority

Go Plan is mobile-first/PWA.

Pilot must not improve desktop at the expense of mobile.

Mobile should prioritize:

```text
scanability
touch reach
clear primary action
efficient vertical density
usable filters
usable overlays
keyboard behavior
```

Avoid oversized cards and excessive whitespace.

---

# 30. Desktop Priority

Desktop should improve:

```text
information density
alignment
use of horizontal space
action placement
comparison/scanning
```

Do not simply stretch mobile cards across a wide viewport.

---

# 31. Tablet

Tablet should remain usable without requiring a unique layout everywhere.

Use the Foundation breakpoint contract.

Add tablet-specific composition only when actual layout evidence justifies it.

---

# 32. Information Hierarchy

Pilot migration should make priority visible through:

```text

```

```text

```

---

# 76. Pilot Feedback Loop

Expected process:

```text
Pilot migration
↓
Find V2 weakness
↓
Classify layer
↓
Update relevant implementation spec/component
↓
Re-run Pilot
↓
Approve
```

This is the purpose of a Pilot.

Finding Design System issues is not failure.

Scaling them before correction is failure.

---

# 77. Breaking Design System Changes

If Pilot evidence shows a V2 API is wrong, it may still be changed because broad rollout has not started.

Prefer correcting the architecture now.

Record:

```text

problem
new contract
affected proof consumers
migration
```

Do not preserve a bad abstraction merely to avoid small early migration cost.

---

# 78. Pilot Completion Does Not Freeze Everything

# 98. Regression Manifest

Must explicitly state:

```text
Business logic changed: NO
Data model changed: NO
Permissions changed: NO
Routes changed: NO
Financial calculations changed: NO
Filtering semantics changed: NO
Sorting semantics changed: NO
Validation semantics changed: NO
Existing feature capability changed: NO
```

Any `YES` requires explicit review and cannot be hidden inside Pilot completion.

---

# 99. Rollout Recommendation

The Pilot report must end with one disposition:

```text
APPROVE ROLLOUT

APPROVE WITH REQUIRED DS FIXES

HOLD — DESIGN SYSTEM REVISION REQUIRED

HOLD — PRODUCT REGRESSION FOUND
```

Do not automatically proceed because the page looks better.

---

# 100. Approve Rollout

Use:

```text
APPROVE ROLLOUT
```

only when:

```text
business invariants pass
accessibility baseline passes
responsive baseline passes
V2 boundaries hold
no significant generic architecture issue remains
```

Minor product-local visual polish may remain.

---

# 101. Approve With Required DS Fixes

Use only when:

```text
Pilot is fundamentally sound
small Design System corrections are known
corrections do not require architectural rethink
```

Required fixes must be listed and completed before broad migration reaches affected components.

---

# 102. Hold — Design System Revision Required

Use when Pilot exposes problems such as:

```text
generic APIs too rigid
prop explosion
domain leakage
responsive model insufficient
overlay architecture breaks real workflows
structural components force poor hierarchy
```

Fix the relevant V2 layer first.

---

# 103. Hold — Product Regression Found

Use when:

```text
permissions changed
values changed
actions changed
routes changed
filters changed
data behavior changed
```

Revert/fix the Pilot before rollout.

---

# 104. Rollback Strategy

Pilot migration must be independently rollbackable.

Keep business code untouched where possible.

Prefer changes in:

```text
presentation components
product composition
shared V2 components
styles
tests
```

Avoid mixing unrelated feature work into the Pilot branch/change set.

---

# 105. Stop Conditions

STOP and request review if Pilot requires:

```text
Service changes
Repository changes
Firestore changes
permission redesign
business calculation changes
data model changes
route redesign
new major UI framework
new state-management framework
new form architecture
premium entitlement changes
domain props added to Design System
mass repository migration
```

Also STOP if preserving existing behavior is impossible with the current V2 architecture.

That is a Design System finding and must be reviewed rather than bypassed.

# 109. Rollout Must Remain Incremental

Even after Pilot approval:

```text
do not mass rewrite
```

Recommended model:

```text
one bounded surface/module
↓
verify
↓
stabilize
↓
next surface/module
```

High-risk Finance/permission-heavy areas should receive stricter regression gates than low-risk presentation screens.

---

# 110. Canonical Pilot Principle

The Pilot answers:

```text
Can Go Plan use this Design System on real product UI?
Does the architecture survive real domain complexity?
Does V2 improve UI without changing behavior?
Is the system ready to scale?
```

The Pilot must never become:

```text
an excuse for feature redesign
a repository-wide rewrite
a place to hide business changes
a screenshot-only exercise
```

> **Validate the Design System against the product before scaling the Design System across the product.**
