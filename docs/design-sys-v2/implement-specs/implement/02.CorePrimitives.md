# 1. Purpose

This specification defines how Go Plan migrates its **Core UI Primitives** onto Design System V2 Foundation.

Core Primitives are the smallest reusable interactive/presentation building blocks that:

- are shared across product modules;
- do not understand business/domain semantics;
- consume Foundation semantic tokens;
- own their generic visual and interaction states;
- provide stable contracts to higher-level components and patterns.

The objective is:

> Establish a small, consistent, accessible primitive layer that later V2 structural components, patterns and product compositions can safely reuse.

This wave is not a product redesign.

It is not a domain component consolidation wave.

# 6. Implementation Philosophy

Prefer:

> **ADAPT existing primitives over replacing them when their public semantics are already valid.**

The goal is not to create `ButtonV2`, `InputV2`, etc.

The goal is to make the canonical existing primitive become V2-compatible while minimizing consumer breakage.

Avoid parallel permanent APIs such as:

```text
Button
ButtonV2
NewButton
```

Temporary compatibility layers are allowed only when required for safe migration.

# 9. Shared Primitive Rules

All interactive primitives must follow the same baseline contract where applicable.

## 9.1 Foundation consumption

Use semantic Foundation roles for:

```text
color
text
border
radius
spacing
focus
motion
disabled states
```

Do not introduce arbitrary raw palette values when a semantic token exists.

## 9.2 Native semantics first

Prefer native HTML semantics whenever possible.

Examples:

```text
button → <button>
text input → <input>
textarea → <textarea>
```

Do not recreate native interaction using generic `<div>` elements unless the underlying accessible primitive/library requires it.

## 9.3 Ref forwarding

Preserve existing ref behavior.

If the current primitive forwards refs, V2 must continue to do so.

Do not break form libraries or imperative focus behavior.

## 9.4 Consumer attributes

Preserve/pass through appropriate native attributes:

```text
aria-*
data-*
name
value
defaultValue
required
disabled
readOnly
autoComplete
placeholder
```

as appropriate for the primitive.

## 9.5 Controlled/uncontrolled behavior

Do not silently change controlled/uncontrolled semantics.

If current component supports both, preserve both unless separately approved.

# 10. State Grammar

Core Primitives should share a predictable state grammar where applicable:

```text
default
hover
active
focus-visible
disabled
invalid
loading
selected / checked
read-only
```

Not every primitive implements every state.

Do not add meaningless states merely for API symmetry.

---

# 11. Disabled vs Read-Only

Do not treat `disabled` and `readOnly` as identical.

### Disabled

Typically:

```text
not interactive
not submitted by native form behavior where applicable
visually de-emphasized
```

### Read-only

Typically:

```text
value remains readable/selectable
not editable
may remain focusable depending on native semantics
```

Preserve native semantics.

Do not use disabled styling merely to represent a permission-denied business state if the product should instead hide an action.

Permission decisions remain outside primitives.

---

# 12. Invalid State

Generic form primitives may expose a generic invalid/error visual state.

Preferred integration:

```text
aria-invalid
```

and/or a small generic variant when required.

The primitive must not own the actual error message business logic.

Example:

```tsx
<Input aria-invalid={Boolean(error)} />
```

Higher-level form composition owns:

```text
label
description
error message
validation semantics
```

unless an existing field component already owns those responsibilities and is separately classified.

---

# 13. Focus

Every interactive primitive must use the canonical Foundation focus-visible treatment.

Requirements:

```text
keyboard-visible
consistent
high enough contrast
not clipped by ordinary container overflow where avoidable
not shown unnecessarily for pointer interaction when focus-visible is supported
```

Do not create a unique focus ring per primitive.

---

# 14. Touch Target

Interactive controls should support the approved minimum touch target intent of approximately:

```text
44 × 44px
```

This does not require every visual element to visibly occupy 44px if a safe hit-area strategy exists.

Compact desktop density must not make mobile interaction difficult.

---

# 15. Motion

Primitive state transitions should use Foundation motion tokens where transition adds clarity.

Avoid animation for:

```text
ordinary text input
every hover state
pure decoration
```

Respect reduced-motion behavior.

---

# 16. Class Composition

Use the repository's existing class composition utility/pattern.

Do not introduce a new styling abstraction solely for Core Primitives.

If variant management already uses an approved utility, continue it.

If no variant utility exists, do not automatically add one unless repeated variant complexity clearly justifies it and the dependency impact is approved.

---

# 17. Public API Stability

Core Primitive migration should minimize breaking changes.

Preferred strategy:

```text
existing valid prop
→ preserve

legacy visual prop with clear V2 mapping
→ temporarily map/deprecate

invalid/domain-leaking prop
→ classify before removal
```

Do not rename props simply for aesthetic API consistency.

A breaking API change must have a concrete benefit and migration plan.

---

# 18. Compatibility Strategy

When a public API must evolve:

```text
1. Add V2-compatible behavior
2. Preserve old API where safe
3. Mark legacy path
4. Migrate consumers progressively
5. Remove compatibility only at zero usage
```

Do not force broad repository migration inside this wave merely to achieve a cleaner primitive signature.

# 19. Button — Canonical Responsibility

Button owns:

```text
button visual hierarchy
size
generic interaction states
disabled
loading where supported
icon alignment
focus
```

Button does not own:

```text
permission

business confirmation

PlanType
```

# 20. Button Variants

Minimum canonical variants:

```text
primary
secondary
ghost
destructive
```

Do not create core variants:

```text
wedding
travel
finance
debt
success-action
premium-purple
```

If an existing variant has a legitimate semantic role not covered above, classify it rather than deleting it automatically.

---

# 21. Button Sizes

Canonical target:

```text
sm
md
lg
icon
```

Exact dimensions must follow the approved V2 Foundation/density system and current usability constraints.

Avoid a large size matrix.

Do not encode viewport names into Button size variants such as:

```text
mobile
desktop
```

Responsive composition should decide which size to use when necessary.

---

# 22. Button Loading

If Button currently supports loading, preserve it.

If loading is introduced/normalized:

```text
button remains disabled from duplicate activation
accessible state remains understandable
label should remain available to assistive technology
width should remain stable where practical
spinner must not be the only semantic signal
```

Do not introduce asynchronous business behavior into Button.

Button only renders the supplied state.

---

# 23. Button Icons

Support common composition:

```text
icon + label
label + icon
icon-only
```

Icon-only buttons MUST have an accessible name, e.g.:

```text
aria-label
```

or equivalent accessible text.

Do not infer accessible names from icon type.

---

# 24. Button Destructive Semantics

`destructive` communicates destructive visual intent.

It does NOT automatically:

```text
open confirmation
delete data
check permissions
```

Confirmation remains the responsibility of the product/overlay flow.

Input owns:


# 26. Input Types


# 27. Input Placeholder

Placeholder is supporting input guidance, not a replacement for a field label.

V2 styling should keep placeholder lower-emphasis but readable.

Do not globally use placeholder text as the only accessible name.

---

# 28. Input Invalid State

Input should support:

```text
aria-invalid
```

and canonical danger/error presentation when invalid.

Do not automatically render an error icon or message inside every Input unless approved by the higher-level field pattern.

---


Textarea-specific responsibilities:

```text

resize behavior
minimum height
```

Do not add domain-specific character-count behavior to the primitive.

A generic `maxLength` remains native behavior.

# 40. DateField — Boundary

DateField is a generic date-entry primitive/component, not a scheduling business component.

It may own:



# 41. DateTimeInput — Boundary

DateTimeInput follows the same principle.

It may compose:

```text
date input

generic date/time interaction
```

Preserve current timezone/data serialization semantics.

A Design System migration must not silently change stored date/time meaning.

# 42. Date/Time Regression Guard

Date/time components are presentation-sensitive but can accidentally affect data.

If visual migration requires changing any of these:

> STOP and classify as higher-impact work.

# 49. Browser Autofill

Input styling should remain usable under browser autofill.

Do not aggressively override autofill in a way that reduces readability or creates browser-specific visual defects.

Only normalize autofill if existing implementation has a demonstrated problem.

---

# 50. Mobile Input Behavior

For mobile:

```text

avoid tiny touch targets
avoid focus styles being clipped

```

Do not change business input type merely to summon a different mobile keyboard.

# 51. Responsive Primitive Strategy

Most primitives should not have separate Mobile/Tablet/Desktop component architectures.

Responsive differences should normally be limited to:

```text

width

```

Higher-level composition owns major layout changes.

# 52. Plan-Type Expression in Primitives

Default rule:

> Core Primitives do not receive `planType`.

Avoid:

```tsx
<Button planType="wedding" />
<Badge planType="travel" />
<Input planType="debt" />
```

If product expression needs an accent, resolve a generic presentation variant/tone outside the primitive.

---

# 53. Permission Boundary

Never add:

```text
role
permissions
canEdit
canDelete
moduleAccess
```

as authorization semantics inside primitives.

Valid generic props:

```text

```

# 54. Domain Copy Boundary

Core primitives do not own domain labels such as:

```text

Thêm thành viên

```

Product composition supplies copy.

Generic primitive copy should be limited to unavoidable accessibility/internal UI behavior and preferably configurable.

---

# 55. Hard-Coded Style Migration

When touching a primitive, migrate its internal presentation to Foundation semantics.

Do not simultaneously migrate every consumer's surrounding styles.

Primitive-owned hard-coded styles:

```text
IN SCOPE
```

Consumer-owned hard-coded styles:

```text
DEFER unless required for compatibility
```

---

# 56. Duplicate Primitive Implementations

If repository verification finds multiple generic implementations of the same primitive:

```text
classify consumers
identify canonical implementation
identify semantic differences
```

Do not merge solely by name.

Safe consolidation is allowed only when behavior and semantics are truly equivalent and migration remains within Core Primitive scope.

Otherwise document for a later wave.

---

# 57. Underlying UI Libraries

If a primitive wraps Radix, shadcn-style primitives, browser native controls or another existing accessible library:

> preserve the underlying accessible behavior unless there is a demonstrated defect.

Do not replace the library to achieve visual consistency.

Design System V2 should primarily adapt styling/API boundaries around proven interaction primitives.

---

# 58. Deprecated Props

When a visual prop becomes obsolete under V2:

```text
keep temporarily if widely consumed
map to canonical V2 semantics
document deprecation
avoid new usage
```

Remove only when consumer usage reaches zero.

Do not maintain ambiguous deprecated props indefinitely.

It does NOT mean every consumer in Go Plan has migrated to V2 styling.

# 77. Canonical Core Primitive Principle

Core Primitives should answer:

```text
How does this generic control look?
How does it focus?
How does it disable?
How does it expose native/accessibility semantics?
How does it consume Foundation?
```

They should never answer:

```text
Can this user edit?
What does this debt mean?
Is this guest confirmed?
Should this expense be green?
What PlanType is active?
```

> **Core Primitives standardize interaction mechanics and visual grammar; Product Composition owns meaning.**
