# 1. Purpose

This specification defines how Go Plan migrates from a validated Design System V2 Pilot to broad product adoption.

The objective is not to migrate as quickly as possible.

The objective is:

> **Migrate progressively, preserve business invariants, reduce visual inconsistency, retire legacy UI safely, and keep every rollout wave independently verifiable and rollbackable.**

---

# 2. Rollout Entry Gate

Phase 7 MUST NOT begin merely because `06.PilotMigration.md` exists.

The Pilot must have completed with one of:

```text
APPROVE ROLLOUT
```

or:

```text
APPROVE WITH REQUIRED DS FIXES
```

where all rollout-blocking Design System fixes have already been completed and re-verified.

Do not proceed from:

```text
HOLD — DESIGN SYSTEM REVISION REQUIRED
HOLD — PRODUCT REGRESSION FOUND
```

---

# 3. Rollout Is Not a Mass Rewrite

Forbidden model:

```text
V2 approved
↓
replace UI across repository
↓
fix regressions afterward
```

Required model:

```text
V2 approved
↓
Inventory remaining surfaces
↓
Risk classify
↓
Select bounded wave
↓
Migrate
↓
Verify
↓
Stabilize
↓
Retire proven legacy
↓
Next wave
```

---

# 4. Primary Rollout Principles

Every wave follows these principles:

```text
Business invariants first
Capability parity first
Product semantics remain product-owned
Generic UI remains domain-neutral
Small blast radius
Evidence before cleanup
Verification before next wave
Rollback remains possible
```

Visual consistency is important, but never outranks correctness.

---

# 5. Scope

Phase 7 governs migration of remaining product surfaces that should consume the validated V2 stack.

It includes:

```text
migration inventory
surface classification
risk tiers
wave planning
dependency ordering
migration manifests
per-wave verification
legacy retirement
cross-module regression
rollout reporting
```

---

# 6. Explicit Non-Scope

Phase 7 does NOT authorize:

```text
new business features
premium/paywall implementation
permission redesign
data model redesign
service/repository refactor
Firestore migration
route redesign
finance formula changes
Guest/Member semantic changes
Debt model changes
Travel workflow redesign
new state-management framework
new UI framework
```

If such work is desired, create separate product/architecture specifications.

---

# 7. V2 Stack Is the Baseline

After Pilot approval, the canonical dependency direction is:

```text
Product Composition
        ↓
Core Patterns
        ↓
Structural Components
        ↓
Core Primitives / Overlay Architecture
        ↓
Foundation
```

New product UI should default to this stack unless a documented exception exists.

---

# 8. No Forced Maximum Reuse

Rollout success is not measured by how many V2 components appear in a screen.

Correct migration may retain:

```text
WeddingGuestRow
TravelActivityTimeline
Debt-specific summaries
Finance reconciliation compositions
Plan-specific headers
```

when they own real product semantics.

V2 should standardize stable presentation anatomy beneath them.

---

# 9. Rollout Inventory

Before the first broad wave, inventory remaining UI surfaces.

For each surface record:

```text
Module
Route/screen
Primary components
Current shared components
Overlay usage
List/filter usage
Business complexity
Permission complexity
Responsive complexity
Known legacy UI
Test coverage
Migration dependencies
```

Do not plan rollout from folder names alone.

---

# 10. Migration Unit

The preferred migration unit is a **bounded product surface**.

Examples:

```text
Members tab
Wedding Guest list surface
Travel Activity overview surface
Debt overview surface
Finance statistics section
Todo/Milestone management surface
```

Avoid migration units that are either:

```text
too small → meaningless verification
```

or:

```text
too broad → impossible regression isolation
```

---

# 11. Surface Risk Model

Each migration unit must be assigned a risk tier.

Use:

```text
R1 — Low risk
R2 — Moderate risk
R3 — High risk
R4 — Critical / invariant-heavy
```

Risk is based on product behavior, not visual complexity alone.

---

# 12. R1 — Low Risk

Typical characteristics:

```text
mostly presentation
few/no mutations
no financial calculations
simple permissions
no complex overlay workflow
strong existing V2 fit
```

Examples may include simple informational/summary surfaces, subject to repository evidence.

R1 is suitable for early rollout waves.

---

# 13. R2 — Moderate Risk

Typical characteristics:

```text
forms or common mutations
filters/lists
normal permission gating
responsive overlays
multiple UI states
```

Requires functional regression plus permission verification where applicable.

---

# 14. R3 — High Risk

Typical characteristics:

```text
complex domain workflow
multiple permission levels
significant list/filter behavior
cross-component state
important destructive actions
high user impact
```

Examples may include Members management or complex Wedding Guest workflows depending on current implementation.

R3 requires narrower waves and stronger manual regression.

---

# 15. R4 — Critical / Invariant-Heavy

Typical characteristics:

```text
financial calculations
settlement/reconciliation
shared fund behavior
debt balances
business invariants where wrong UI/data interpretation can cause material user harm
```

R4 migration must be presentation-only unless separately approved.

Use explicit before/after value fixtures and invariant verification.

---

# 16. Risk Escalation Rules

A surface must be escalated at least one tier when migration unexpectedly requires:

```text
permission resolver changes
calculation-adjacent code edits
route behavior changes
shared state changes
large client-boundary changes
multiple legacy component replacements at once
```

If it reaches prohibited business change territory:

> STOP rollout for that surface.

---

# 17. Recommended Migration Ordering

Default ordering principle:

```text
V2 fit + lower business risk
↓
common collaboration/product surfaces
↓
complex domain surfaces
↓
financial/invariant-heavy surfaces
```

Do not interpret this as a fixed module order without repository evidence.

The actual order must be generated from the migration inventory and approved Pilot findings.

---

# 18. Dependency-Based Ordering

Prioritize surfaces that remove duplicated legacy infrastructure used by later surfaces.

Example:

```text
shared list/filter shell
↓
several product wrappers can migrate safely afterward
```

But do not migrate a high-risk business surface early merely because it contains a common component.

Extract/adapt the generic layer separately where possible.

---

# 19. Module Boundary

A wave may contain multiple surfaces from one module when they share:

```text
same product wrapper architecture
same risk profile
same regression fixtures
```

Do not bundle unrelated modules solely to increase throughput.

---

# 20. Wave Size

Default wave size should be small enough that a reviewer can answer:

```text
What changed?
Why?
Which behaviors are at risk?
How were they verified?
How do we roll it back?
```

If those answers become unclear, the wave is too large.

---

# 21. One High-Risk Surface Per Wave

For R3/R4 work, prefer one major surface per wave.

Do not combine:

```text
Finance reconciliation migration
+
Members permission-heavy migration
+
Wedding Guest redesign
```

into one rollout unit.

---

# 23. Baseline Before Every Wave

Capture current behavior before editing.

At minimum:

```text

actions

loading
empty
```

---

# 24. Component Disposition

Each touched legacy/shared/product component receives:

```text
KEEP
ADAPT
COMPOSE
REPLACE
DEPRECATE
REMOVE
DEFER
```

`REMOVE` is allowed only after zero active usage and equivalent capability are proven.

---

# 25. Product Components Default to COMPOSE

Domain-aware components should normally remain product-owned.

Examples:

```text
MemberRow
WeddingGuestRow
DebtRow
TravelActivityItem
FinanceSummary
```

may adopt V2 internally.

Do not delete them merely because generic anatomy now exists.

---

# 26. Generic Duplicate Default to REPLACE/DEPRECATE

Purely generic duplicate UI is a stronger consolidation candidate.

Examples:

```text
local generic card shell
local generic modal wrapper
local generic list separator shell
local generic page-title/action wrapper
```

Replacement still requires consumer verification.

---

# 27. Migration Sequence Per Surface

Recommended order:

```text
1. Freeze behavior baseline
2. Adopt Foundation tokens
3. Adopt Core Primitives
4. Adopt Structural Components
5. Adopt Core Patterns
6. Adopt Overlay Architecture
7. Refine responsive layout
8. Verify accessibility
9. Verify product behavior
10. Remove proven local duplication
11. Mark legacy disposition
```

Do not lead with deletion.

---

# 28. Foundation Migration Rule

Replace arbitrary presentation values where canonical semantic roles exist.

Do not convert every literal mechanically.

Semantic classification comes first:

```text
What role does this text/surface/spacing/status serve?
```

then choose the V2 token.

---

# 29. Primitive Migration Rule

Use canonical primitives where behavior matches.

Do not weaken specialized controls merely to achieve visual consistency.

If canonical primitive cannot preserve behavior:

```text
classify gap
fix generic layer if truly generic
or retain product control
```

---

# 30. Structural Migration Rule

Use the Phase 4 semantic boundaries:

```text
logical grouping → Section
contained surface → Card
single high-signal value → Metric
metric arrangement → MetricGroup
row anatomy → DataRow
absence → EmptyState
persistent failure → ErrorState
```

Do not optimize for replacing maximum markup.

---

# 31. Core Pattern Migration Rule

Use:

```text
EntityList
FilterBar
PageHeader
```

through product wrappers where meaning exists.

Never pass domain models into patterns merely to reduce product code.

---

# 32. Overlay Migration Rule

Use:

```text
ResponsiveModal
```

for normal modal workflows and:

```text
ConfirmDialog
```

for consequential/destructive confirmation.

Legacy `Dialog`/`BottomSheet` may only be removed after active usage reaches zero.

---

# 33. Responsive Capability Parity

Every wave must verify that mobile and desktop expose equivalent intended capability.

Presentation may differ:

```text
inline desktop filters
↔ mobile modal filters
```

Capability must not disappear accidentally.

---

# 34. Density Strategy During Rollout

Do not migrate into an overly spacious “component showcase” aesthetic.

Go Plan needs efficient scanning for:

```text
members
guests
tasks
activities
transactions
debts
```

Use restrained Card surfaces and row-based density where appropriate.

---

# 35. Trust-Oriented Visual Standard

Rollout should converge toward:

```text
neutral base
clear typography
restrained brand accents
semantic status colors
limited elevation
consistent radius
predictable interaction
```

Avoid introducing visual novelty per module.

---

# 36. Plan-Type Expression During Rollout

Plan-type personality may remain visible through the approved Plan-Type Expression system.

It must not cause generic components to branch on:

```text
wedding
travel
debt
finance
```

Product composition resolves expression and supplies generic presentation inputs where needed.

---

# 37. Business Invariant Gate

Every R3/R4 wave must explicitly map relevant invariants from the Business Invariant Registry.

For each:

```text
Invariant
Affected surface
Before value/behavior
After value/behavior
Verification
PASS/FAIL
```

A failed invariant blocks the wave.

---

# 38. Finance Guardrail

Finance-related rollout must not change:

```text
income/expense meaning
Shared Fund model
fund balance calculation
member-paid vs fund-paid semantics
settlement/reimbursement rules
statistics calculations
```

Display-ready values enter V2 components after calculation.

---

# 39. Debt Guardrail

Debt rollout must preserve:

```text
loan vs repayment
directionality
outstanding balance
repayment limits
due-date semantics
```

Do not make generic Metric/DataRow understand these concepts.

---

# 40. Wedding Guardrail

Wedding rollout must preserve distinctions including:

```text
Member
Guest
Invitation
Expected attendee count
Guest Group
Milestone
```

Do not merge concepts because their UI is visually similar.

---

# 41. Members Guardrail

Members rollout must preserve:

```text
real plan membership
Owner / Editor / Viewer
invitation lifecycle
module access
Editor own/manage-all behavior
```

Design System receives already-resolved capabilities only.

---

# 42. Travel Guardrail

Travel rollout must preserve:

```text
activity chronological ordering
timeline meaning
activity category meaning
time/duration behavior
```

Do not force timeline architecture into EntityList when it weakens product semantics.

---

# 43. Todo/Milestone Guardrail

Task rollout must preserve current permission meaning across:

```text
Todo
Milestone
```

where the approved Work access applies to both.

Do not split permissions during UI migration.

---

# 44. Permission Verification

For permission-sensitive waves verify representative:

```text
Owner
Editor — own content
Editor — manage all where configured
Viewer — allowed modules
Viewer — denied modules
```

Verify both visibility and actual mutation capability where applicable.

---

# 45. Premium Boundary

Rollout prepares visual consistency for future Premium, but must not couple generic components to entitlement logic.

Do not add to Design System:

```text
isPremium
planLimit
featureLocked
subscriptionTier
```

Product entitlement architecture remains separate.

---

# 46. Accessibility Gate

Each wave must preserve or improve:

```text
heading hierarchy
keyboard navigation
focus-visible
control labels
modal focus lifecycle
touch targets
contrast
non-color-only meaning
```

Accessibility regression blocks rollout acceptance.

---

# 47. Responsive Gate

Verify at minimum:

```text
Mobile
Tablet
Desktop
```

R2–R4 waves should include realistic narrow-mobile stress.

Do not verify only desktop screenshots.

---

# 48. Content Stress

Use realistic Vietnamese content:

```text
long names
long plan titles
long descriptions
long labels
large currency values
multiple badges/statuses
```

Do not tune V2 around placeholder data.

---

# 51. Filter Matrix

# 52. List Matrix

```text

```

---

# 53. Financial Value Comparison

For R4 financial surfaces, compare exact representative values before/after.

Examples:

```text
total income
total expense
fund balance
member balance
settlement amount
debt outstanding
```

Presentation changes are acceptable.

Value changes are not.

---

# 54. Automated Verification

Run existing applicable repository commands:

```text
typecheck
lint
tests
build
```

Do not introduce a new test framework as part of rollout.

Record pre-existing failures separately.

---

# 55. Manual Verification

Every wave requires manual verification appropriate to its risk.

R1:

```text
visual + responsive + primary interactions
```

R2:

```text
R1 + state/overlay/filter behavior
```

R3:

```text
R2 + permissions + broader functional matrix
```

R4:

```text
R3 + explicit invariant/value verification
```

---

# 56. Test Coverage Strategy

Do not chase arbitrary coverage percentage.

Prioritize tests around:

```text
business-critical behavior
permission gates
overlay semantics
filter/list behavior
regression-prone compositions
```

Design System unit tests should remain domain-neutral.

Product regression tests may use domain fixtures.

---

# 57. Visual Review

Review each wave for:

```text
hierarchy
spacing
typography
surface nesting
density
action hierarchy
responsive composition
status color discipline
```

A wave may be functionally correct but still fail visual acceptance if it introduces inconsistency.

---

# 58. Architecture Review

Review changed code for:

```text
domain imports into Design System
prop explosion
PlanType branching
generic config engines
business calculations in presentation components
permission resolution in generic UI
router/data fetching ownership in patterns
```

Any of these require correction before scaling.

---

# 59. Cross-Wave Consistency

Do not solve the same recurring problem differently in each module.

When a second wave reveals a generic gap:

```text
classify it
update the correct V2 layer
verify prior consumers
then continue
```

Do not create module-local workarounds by default.

---

# 60. Design System Change During Rollout

V2 is more stable after Pilot but not immutable.

A generic change during rollout requires:

```text
problem evidence
affected V2 layer
current consumers
proposed contract change
compatibility impact
regression plan
```

The broader the consumer set, the higher the change-control burden.

---

# 61. Change Classification During Rollout

Use the approved Impact Classification & Change Control system.

Presentation-only changes may remain low impact.

Changes touching:

```text
permissions
calculations
data model
routing
business capability
```

must be escalated and cannot hide inside a rollout wave.

---

# 62. Legacy Registry

Maintain a rollout legacy registry with:

```text
Legacy component
Replacement
Current consumers
Disposition
Deprecation date/wave
Removal condition
Status
```

Possible statuses:

```text
ACTIVE
DEPRECATED
ZERO-USAGE
REMOVABLE
REMOVED
BLOCKED
```

---

# 63. Deprecation Rule

Mark a legacy generic component `DEPRECATED` when:

```text
canonical replacement exists
new usage should stop
existing consumers can migrate progressively
```

Do not remove it immediately unless zero usage is proven.

---

# 64. Zero-Usage Proof

Before removal:

```text
repository search
import search
runtime/route awareness where needed
tests/build
```

must confirm no active consumer.

Do not rely on memory or folder inspection alone.

---

# 65. Legacy Removal Rule

Remove only when:

```text
zero active usage
replacement semantics equivalent
no capability lost
regression suite passes
rollback no longer depends on the file
```

For `Dialog`/`BottomSheet`, preserve Phase 3 removal rules.

---

# 66. Product Wrapper Retirement

Do not retire a product wrapper merely because it contains little JSX after migration.

If it still owns:

```text
product naming
status mapping
permissions
actions
data formatting
business composition
```

it remains architecturally valuable.

---

# 67. Dead CSS Cleanup

Remove legacy styles only after consumer migration is proven.

Avoid broad CSS deletion in the same wave as high-risk product migration unless usage is clear.

---

# 68. No Big-Bang Token Cleanup

Do not block product migration on eliminating every legacy raw color/spacing value repository-wide.

Use progressive cleanup:

```text
touched surface
↓
semantic migration
↓
verified
```

Track remaining hotspots separately.

---

# 69. No Big-Bang Import Rewrite

Do not restructure the entire shared UI directory during rollout.

Migration should primarily change component usage, not repository architecture, unless a separate approved refactor exists.

---

# 70. No New Parallel V3

If V2 needs correction, correct V2.

Do not create:

```text
ButtonV3
CardNew
EntityList2
```

as local escape hatches.

Parallel systems recreate the inconsistency this project is trying to remove.

---

# 71. Rollback Strategy Per Wave

Each wave must be independently rollbackable.

Avoid mixing:

```text
feature work
business refactor
schema migration
UI migration
```

in one changeset.

Rollback should restore prior presentation without requiring data repair.

---

# 72. Stop Conditions

STOP a wave if migration requires:

```text
business formula changes
permission redesign
data model changes
Service/Repository changes
Firestore changes
route redesign
premium entitlement changes
new major framework
domain props in Design System
loss of mobile capability
unresolved accessibility regression
```

Do not bypass the Design System boundary to keep schedule.

---

# 73. Wave Acceptance Dispositions

Each wave ends with exactly one:

```text
APPROVE
APPROVE WITH FOLLOW-UP
HOLD — DS ISSUE
HOLD — PRODUCT REGRESSION
ROLLBACK
```

Do not automatically start the next wave until disposition permits it.

---

# 74. APPROVE

Use when:

```text
all required gates pass
no rollout-blocking issue remains
legacy dispositions are recorded
```

The next planned wave may begin.

---

# 75. APPROVE WITH FOLLOW-UP

Use only for non-blocking issues such as:

```text
minor local polish
non-critical legacy cleanup
additional test hardening
```

Follow-ups must be recorded with ownership/status.

Do not use this to waive accessibility, permissions, invariant or capability failures.

---

# 76. HOLD — DS ISSUE

Use when the wave reveals a reusable Design System defect:

```text
API too rigid
responsive pattern insufficient
overlay problem
structural boundary problem
accessibility defect
```

Fix at the canonical layer and re-test affected prior consumers.

---

# 77. HOLD — PRODUCT REGRESSION

Use when migration changes:

```text
behavior
permission
value
route
filter semantics
validation
capability
```

Fix before continuing.

---

# 78. ROLLBACK

Use when the wave cannot be stabilized safely within its intended scope.

Rollback is preferable to expanding scope into uncontrolled business refactoring.

Document the blocker for later redesign.

---

---

# 82. Completion Metrics

Track useful migration health, not vanity metrics.

Useful:

```text
verified surfaces migrated
legacy generic components remaining
zero-usage legacy candidates
open DS blockers
open product regressions
R3/R4 surfaces verified
```

Less useful by itself:

```text
percentage of JSX using V2
number of components replaced
```

Maximum reuse is not the objective.

---

# 83. Rollout Quality Metric

A successful wave should reduce at least one of:

```text
visual inconsistency
local generic CSS
repeated generic markup
responsive divergence
accessibility inconsistency
legacy component dependency
```

without increasing business coupling in the Design System.

---

# 84. Module Completion Gate

A module may be marked V2-migrated when:

```text
all intended surfaces migrated
module-specific regression passes
remaining legacy usage is explicitly justified or zero
responsive verification passes
accessibility baseline passes
no unresolved DS workaround remains
```

Do not require deletion of legitimate product-specific components.

---

# 85. Repository Completion Gate

Design System V2 rollout is complete when:

```text
all in-scope product surfaces have verified disposition
canonical V2 stack is the default for new UI
legacy generic duplicates are removed or explicitly retained with reason
R3/R4 invariants pass
mobile/desktop capability parity is verified
no rollout-blocking accessibility issue remains
regression suite/build pass
```

---

# 86. Post-Rollout Legacy Freeze

After completion, legacy generic components that remain only for justified exceptional cases should be clearly marked.

New feature work must not reintroduce deprecated legacy UI.

Enforce through:

```text
documentation
code review
lint/import restriction only if repository architecture justifies it
```

Do not add tooling merely for ceremony.

---

# 87. New Feature Rule During Rollout

New features developed while migration is ongoing should use V2 by default when the required canonical layers are stable.

Do not intentionally build new UI on deprecated components merely because surrounding old screens still use them.

If V2 cannot support the new feature cleanly:

```text
record a DS gap
review at correct layer
```

---

# 88. Parallel Product Development

If product feature work and V2 migration touch the same surface:

Prefer sequencing:

```text
stabilize business feature
↓
update baseline
↓
migrate UI
```

or isolate changes cleanly.

Avoid debugging business and visual migrations simultaneously.

---

# 89. Conflict Resolution

When rollout encounters a conflict between:

```text
visual consistency
```

and:

```text
existing proven product behavior
```

preserve behavior first.

Then determine whether the Design System needs extension or the product composition should remain specialized.

---

# 90. Design Review Cadence

Perform review after each meaningful wave, not only at repository completion.

This catches drift early:

```text
new one-off variants
nested-card recurrence
inconsistent FilterBar usage
product props leaking into generic components
responsive shortcuts
```

---

# 91. Architecture Drift Checks

Periodically search for:

```text
raw domain imports in Design System
new *V2/*New duplicate components
new hard-coded status colors
new arbitrary radius/shadow recipes
direct legacy Dialog/BottomSheet usage
new generic clickable divs
```

Treat findings as review signals, not automatic errors without context.

# 92. Documentation Synchronization

If rollout changes a canonical V2 contract, update:

```text
relevant implementation specification
component documentation
migration notes
legacy registry
```

Implementation and specification must not drift silently.

# 93. Business Invariant Registry Synchronization

If rollout discovers an undocumented invariant:

```text
STOP assuming
verify existing behavior
record it in the Business Invariant Registry through the approved change-control process
then continue
```

Do not encode newly discovered rules only in UI tests.

# 96. Final Rollout Disposition

Use one:


# 97. V2 ROLLOUT COMPLETE

Requires:

```text
all in-scope surfaces verified
critical invariants pass
no blocking accessibility issue
no unresolved product regression
legacy generic duplication controlled
V2 is default for new UI
```

---

# 98. COMPLETE WITH DOCUMENTED DEBT

Allowed when remaining items are explicitly non-blocking, such as:

```text
low-value legacy visual cleanup
specialized product component intentionally retained
additional non-critical test coverage
```

Each item must have a reason.

---

# 99. PARTIAL — BLOCKERS REMAIN

Use when:

```text
R3/R4 surfaces remain unverified
business regression remains
critical accessibility issue remains
Design System architecture issue blocks safe migration
```

Do not hide these behind a completion percentage.

# 101. Canonical Rollout Principle

Rollout answers:

```text
Which surface migrates next?
How risky is it?
Which V2 layers should it consume?
Which business invariants must remain unchanged?
How do we verify it?
When may legacy UI be retired?
When is it safe to proceed?
```

It must never answer by shortcut:

```text
Replace everything that looks old.
Make every product component generic.
Rewrite all screens at once.
Fix business behavior while we are here.
```

> **Migrate in bounded, evidence-driven waves. Standardize presentation aggressively only where semantics remain intact; preserve product meaning and business correctness without compromise.**
