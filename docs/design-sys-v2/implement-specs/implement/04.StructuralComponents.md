# 1. Purpose

This specification defines the canonical Design System V2 structural component layer for Go Plan.

Phase 4 covers:

```text
Section
Card
Metric
MetricGroup
DataRow
EmptyState
ErrorState
```

These components sit between low-level primitives and higher-level product patterns/compositions.

The objective is:

> Reuse repeated visual anatomy without moving product meaning, business calculation, permissions or domain state into generic components.

This is the phase with the highest risk of accidental over-generalization.

Therefore the primary architectural requirement is:

> **Extract stable anatomy, not business concepts.**

---

# 2. Why This Layer Exists

Go Plan contains many modules with visually similar structures:

```text
Wedding
Travel
Finance
Debt
Members
Tasks
Dashboard
```

Examples of repeated anatomy include:

```text
section heading + content
contained surface
label + metric value
group of metrics
leading icon/avatar + main content + trailing action
empty content message
error/retry presentation
```

These repetitions justify shared structural components.

They do NOT justify merging product components simply because screenshots look similar.

Phase 4 canonical components:


Possible small supporting pieces may be created only when they clearly belong to one canonical anatomy, for example:


Do not expand this wave into all patterns.

# 6. Structural Component Boundary

A structural component may know:

```text
layout
spacing
surface
generic visual hierarchy
generic presentation slots
generic interaction state where structurally required
responsive arrangement
```

It MUST NOT know:

```text
how a value was calculated
whether a user has permission
what a Guest means
what Debt direction means
what an Expense means
what RSVP means
which PlanType business rule applies
which records should be fetched
how records are sorted
```

---

# 7. Dependency Direction

Required dependency:

```text
Product Composition
        ↓
Core Pattern
        ↓
Structural Component
        ↓
Core Primitive
        ↓
Foundation
```

Structural components may compose primitives.

They must never import product modules.

---

# 8. Anti–God Component Rule

A structural component is becoming a God Component when its API begins accumulating unrelated product concepts.

Warning signs:

```text
planType
role
permissions
statusType
expenseType
guestStatus
debtDirection
showWeddingMode
financeMode
activityMode
```

or large boolean matrices:

```text
compact
highlighted
bordered
elevated
interactive
selected
warning
finance
mobileCard
...
```

When this happens:

> STOP and reassess whether composition should remain in the product/pattern layer.

---

# 9. Generic Prop Test

Before adding a prop to a structural component, ask:

1. Does this prop describe generic visual/layout behavior?
2. Is the concept meaningful across unrelated modules?
3. Can the component remain understandable without knowing product semantics?
4. Will at least multiple real consumers benefit?
5. Could composition solve the need more cleanly?

If the answer points to domain meaning:

> keep it outside the structural component.

---

# 10. Implementation Philosophy

Prefer adapting existing shared components when their responsibility already matches V2.

Do not automatically create:

```text
SectionV2
CardV2
MetricV2
```

alongside existing canonical components.

Preferred migration:

```text
existing component
↓
inspect API and consumers
↓
adapt safely
↓
compatibility where needed
↓
progressive consumer migration
```

# 13. Section — Purpose

`Section` represents a logical grouping of related content.

It exists to solve:

```text
section rhythm
heading/content relationship
consistent vertical spacing
optional section actions
```

It does NOT automatically create a card.

This distinction is central to V2.

---

# 14. Section Philosophy

Many Go Plan screens currently risk becoming:

```text
Page
└── Card
    └── Card
        └── Card
```

V2 should instead support:

```text
Page
├── Section
│   ├── Heading
│   └── Content
│
├── Section
│   ├── Heading
│   └── Content
```

with Card used only when a contained surface is actually useful.

---

# 15. Section Anatomy

Canonical conceptual anatomy:

```text
Section
├── Header?
│   ├── Eyebrow? / supporting context?
│   ├── Title
│   ├── Description?
│   └── Action?
│
└── Content
```

Exact API should remain minimal.

Do not add every possible slot unless repository evidence demonstrates recurring need.

---

# 16. Section Responsibilities

Section may own:

```text
vertical rhythm
header-to-content gap
section-to-section spacing
basic header alignment
responsive action wrapping
```

Section should generally NOT own:

```text
background
border
shadow
business state
data fetching
empty state automatically
```

unless a clearly named visual variant is approved.

Default Section should remain structurally light.

---

# 17. SectionHeader

`SectionHeader` may be extracted if:

```text
the same header anatomy recurs independently
Section becomes cleaner through composition
multiple consumers need header without full Section wrapper
```

Do not create it merely to split one component into more files.

Potential responsibility:

```text
title
description
action
alignment
```

No product semantics.

---

# 18. Section Actions

Section may accept generic action content through composition.

Correct:

```tsx
<Section
  title="Công việc sắp tới"
  action={<Button ...>Xem tất cả</Button>}
>
```

The Section does not know what “Xem tất cả” does.

Do not add:

```text
onViewAllTasks
onOpenFinance
```

to Section.

---

# 19. Section Responsive Behavior

On narrow screens:

```text
title/description remain readable
actions may wrap or move below title
content remains full-width
```

Do not introduce separate mobile Section architecture.

The product content inside Section controls its own complex responsive behavior.

---

# 20. Card — Purpose

`Card` represents a contained surface.

Card owns:

```text
surface
border
radius
optional approved elevation
generic padding where variant/recipe requires it
```

Card does NOT define page hierarchy.

Card does NOT mean “section.”

---

# 21. Card Default

Canonical default should be visually restrained.

Conceptually:

```text
surface.default / raised as approved
subtle border
approved radius
elevation.none by default
```

Do not make every Card float with shadow.

---

# 22. Card Variants

Keep variants minimal.

Potential generic variants may include:

```text
default
subtle
interactive
```

only if repository evidence supports them.

Do NOT create:

```text
finance
wedding
travel
debt
metric
guest
premium
```

as Card variants.

Metric presentation belongs to Metric/MetricGroup or product composition.

---

# 23. Card Padding

Card may own a small canonical padding set if recurring needs justify it.

Example conceptual:

```text
sm
md
lg
```

Avoid dozens of padding combinations.

If a product needs unusual internal layout, composition may use Card as surface and own its inner spacing.

---

# 24. Interactive Card

An interactive Card must use appropriate semantics.

Do not make a `<div>` clickable without keyboard semantics.

Depending on intent:

```text
link-like card
→ anchor/link semantics

action-like card
→ button semantics or contained button/action
```

Do not put invalid nested interactive elements inside a card-level button/link.

This may require product-level composition rather than a generic `interactive=true`.

---

# 25. Card vs Section Decision Rule

Use `Section` when the primary need is:

> group related page content.

Use `Card` when the primary need is:

> visually contain a unit/object or separate a surface.

Use both only when justified:

```text
Section
└── Card(s)
```

Avoid:

```text
Card as page section
└── Card as group
    └── Card as row
```

---

# 26. Card Nesting

Nested Cards should be uncommon.

Before nesting, ask whether inner content could instead use:

```text
divider
surface.subtle
spacing
DataRow
plain grouping
```

Do not ban nesting globally; some product structures may justify it.

But nested-card usage should be reviewed during Pilot migrations.

---

# 27. Metric — Purpose

`Metric` presents one high-signal value with context.

Canonical conceptual anatomy:

```text
Metric
├── Label
├── Value
├── Supporting?
└── Leading/Trailing presentation?
```

Metric is presentation.

It is NOT a calculation engine.

---

# 28. Metric Boundary

Metric may know:

```text
label
formatted value
supporting text
generic tone
size
alignment
optional icon/leading visual
```

Metric MUST NOT know:

```text
expense totals
income totals
budget calculations
guest counts
RSVP math
settlement
debt balance
progress calculation
currency conversion
```

Values must be resolved before reaching Metric.

---

# 29. Metric Example

Correct:

```tsx
const totalExpense = calculateElsewhere(...);

<Metric
  label="Tổng chi"
  value={formatCurrency(totalExpense)}
/>
```

Incorrect:

```tsx
<Metric
  expenses={expenses}
  incomes={incomes}
  calculateBalance
/>
```

---

# 30. Metric Value Type

Prefer Metric receiving display-ready presentation:

```text
ReactNode / formatted string
```

rather than raw domain values that force it to understand formatting rules.

Generic number formatting may be acceptable only if a current shared formatting contract already exists and does not introduce product semantics.

Default architecture:

> product/presentation composition formats the value.

---

# 31. Metric Tone

Metric may support a small generic tone system when semantically justified:

```text
default
success
warning
danger
brand
```

Use tone for actual meaning, not decoration.

Finance invariant remains:

```text
ordinary money amount
→ default / neutral
```

Do not map expense to danger or income to success automatically.

---

# 32. Metric Sizes

Canonical metric typography roles come from Foundation:

```text
metric-sm
metric-md
metric-lg
```

Metric may expose a small corresponding size API if real layouts need it.

Do not create per-screen sizes.

---

# 33. Metric Supporting Content

Supporting content may include:

```text
short explanatory text
delta/status text
time/context
```

It should remain secondary.

Do not turn Metric into a mini dashboard card containing arbitrary lists, charts and actions.

When content becomes complex:

> use product composition around Metric.

---

# 34. Metric Card Boundary

Metric should not automatically render Card chrome.

This allows:

```text
Metric inside plain Section
Metric inside Card
Metric inside MetricGroup
Metric inside product summary
```

without forced nested surfaces.

If a visual “stat card” is needed:

```text
Card
└── Metric
```

or a product-specific composition.

---

# 35. MetricGroup — Purpose

`MetricGroup` arranges multiple Metrics.

Its responsibility is:

```text
layout
columns
gap
alignment
density
responsive arrangement
```

Nothing more.

---

# 36. MetricGroup Hard Guardrail

Audit Decision Record explicitly protects this boundary.

MetricGroup MUST NOT calculate:

```text
total expense
total income
balance
guest totals
progress
settlement
budget
```

It must not receive domain collections just to derive Metrics.

---

# 37. MetricGroup API

Prefer composition:

```tsx
<MetricGroup>
  <Metric ... />
  <Metric ... />
  <Metric ... />
</MetricGroup>
```

rather than configuration objects that grow into a generic dashboard engine.

A small generic layout API may include:

```text
columns
density
alignment
```

if needed.

---

# 38. MetricGroup Responsive Behavior

MetricGroup may own responsive column behavior.

Example conceptual:

```text
Mobile → 2 columns / stacked depending on count
Tablet → 2–3
Desktop → 3–4
```

Do not hard-code one layout solely from metric count if product context requires a different emphasis.

Allow controlled generic layout options rather than domain-specific variants.

---

# 39. Unequal Metric Importance

Not all product metrics have equal importance.

MetricGroup should not force equal visual hierarchy if product composition needs one primary metric.

Possible solution:

```text
product composition outside MetricGroup
```

or a very small generic span/layout mechanism if recurring.

Do not add:

```text
primaryFinanceMetric
featuredGuestMetric
```

props.

---

# 40. DataRow — Purpose

`DataRow` provides reusable list-row anatomy.

Canonical conceptual anatomy:

```text
DataRow
├── Leading?
├── Main
│   ├── Title
│   ├── Supporting?
│   └── Metadata?
├── Status?
└── Trailing?
```

DataRow is not a domain entity component.

---

# 41. DataRow Boundary

DataRow may know:

```text
layout
spacing
leading slot
title/content slots
supporting content
status slot
trailing slot
hover
focus
selected
disabled if genuinely generic
```

It MUST NOT know:

```text
Guest
Member
Debt
Expense
Income
Todo
Activity
RSVP
role permissions
```

---

# 42. DataRow Example

Correct:

```tsx
<DataRow
  leading={<Avatar ... />}
  main={<MemberIdentity ... />}
  status={<Badge ... />}
  trailing={<MemberActions ... />}
/>
```

Product composition resolves:

```text
role
permission
copy
actions
status mapping
```

DataRow only arranges them.

---

# 43. DataRow Main Content

Prefer composition/slots over a large semantic prop list.

Avoid turning DataRow into:

```text
title
subtitle
description
date
amount
category
owner
location
role
rsvp
progress
...
```

A few generic convenience props may be acceptable if existing consumers repeatedly share identical anatomy.

But slot composition is safer when product content varies.

---

# 44. DataRow Status

Status is presentation content supplied by the consumer.

DataRow should not map domain states to Badge tones.

Correct:

```tsx
status={<Badge tone="success">Đã xác nhận</Badge>}
```

mapping happens outside DataRow.

---

# 45. DataRow Trailing Actions

Trailing may contain:

```text
text
amount
icon
menu
button
chevron
```

depending on product composition.

DataRow does not decide whether actions are allowed.

Permission resolution remains outside.

---

# 46. DataRow Interaction

A row may be:

```text
non-interactive
selectable
navigational
actionable
```

Do not collapse all modes into a clickable `<div>`.

If whole-row interaction is needed, semantics must be correct.

Avoid nested-interactive conflicts with trailing menus/buttons.

Product composition may need to keep row itself non-interactive and expose explicit actions.

---

# 47. DataRow Selected State

Selected state may be generic for controlled selection patterns.

DataRow may receive:

```text
selected
```

only as presentation state.

It must not manage selection collections.

`EntityList` or product composition will own selection mechanics later.

---

# 48. DataRow Density

DataRow may support a small generic density contract if real consumers need it:

```text
comfortable
compact
```

Do not create density per module.

Dense Wedding Guest and normal Members may share the same generic density vocabulary while retaining product-specific content.

---

# 49. DataRow Mobile Behavior

On mobile, DataRow should support content wrapping without destroying hierarchy.

Possible behavior:

```text
main content grows
metadata wraps
trailing remains reachable
secondary content may move below
```

Do not make DataRow itself decide which product metadata should disappear.

Product composition decides information priority.

---

# 50. DataRow Desktop Behavior

Desktop may use more horizontal alignment.

Do not turn DataRow into a table replacement.

If data requires column alignment across many rows, that may belong to a later responsive table/list pattern.

---

# 51. EmptyState — Purpose

`EmptyState` communicates absence of content and provides an optional next action.

Canonical anatomy:

```text
visual?
title
description?
primary action?
secondary action?
```

---

# 52. EmptyState Boundary

EmptyState owns:

```text
layout
visual hierarchy
generic action placement
responsive spacing
```

It does NOT decide:

```text
why data is empty
which entity to create
whether user has permission
what CTA should do
```

Product supplies content and actions.

---

# 53. Empty State Categories

The same structural EmptyState may be used for different product causes:

```text
first-use empty
filtered empty
search empty
permission-limited empty
archived/no-active-data
```

But the generic component should not encode all causes as business enums unless a real cross-product need exists.

Often product copy/action composition is enough.

---

# 54. EmptyState Action Guard

If user lacks permission to create content:

```text
product layer should omit or replace create CTA
```

Do not pass role/permission to EmptyState so it can decide.

---

# 55. EmptyState Visual

Visual may be:

```text
icon
small illustration
```

but should remain restrained.

Do not require large illustrations for every empty state.

Trust/productivity UI should keep empty states informative rather than decorative-heavy.

---

# 56. ErrorState — Purpose

`ErrorState` communicates a recoverable or terminal UI-level failure.

Canonical anatomy:

```text
visual?
title
description?
action?
secondary action?
```

It shares some visual anatomy with EmptyState but has different semantics.

---

# 57. ErrorState Must Remain Distinct

Do not merge EmptyState and ErrorState into one generic `State` component merely because the layout is similar.

Semantic distinction matters:

```text
Empty
→ nothing to show / no matching content

Error
→ expected content/action failed
```

They may share internal visual recipe if useful.

Their public intent should remain clear.

---

# 58. ErrorState Boundary

ErrorState does NOT own:

```text
API retry implementation
error parsing
logging
business recovery
permission recovery
navigation policy
```

Product supplies an action.

Correct:

```tsx
<ErrorState
  title="Không thể tải dữ liệu"
  action={<Button onClick={refetch}>Thử lại</Button>}
/>
```

---

# 59. ErrorState Retry

Do not hard-code a Retry button into every ErrorState.

Some failures require:

```text
Thử lại
Quay lại
Đóng
Yêu cầu quyền truy cập
Mở cài đặt
```

Product composition chooses the recovery.

---

# 60. ErrorState vs Toast

ErrorState is for a persistent content-area failure where the user needs context/recovery.

Toast is transient feedback.

Do not convert all errors into ErrorState or all ErrorStates into Toast.

Toast remains outside this wave.

---

# 61. Loading State Boundary

This phase does not create a universal LoadingState unless upstream specifications explicitly require it.

Existing Skeleton remains the primary loading presentation primitive/pattern where appropriate.

Do not force EmptyState/ErrorState to handle loading.

Keep:

```text
loading
empty
error
content
```

semantically distinct.

---

# 62. Structural Composition Example

Correct architecture:

```tsx
<Section
  title="Cân đối thành viên"
  action={<Button variant="ghost">Xem đối soát</Button>}
>
  <Card>
    <MetricGroup>
      <Metric ... />
      <Metric ... />
    </MetricGroup>
  </Card>
</Section>
```

Business values and actions are resolved outside these structural components.

---

# 63. Product Composition Example

Wedding Guest may eventually compose:

```text
WeddingGuestStats
    ↓
MetricGroup
    ↓
Metric
```

This does NOT mean replacing `WeddingGuestStats` with MetricGroup.

`WeddingGuestStats` remains the domain-aware composition.

---

# 64. Product Components Must Survive

Examples that should remain product-specific:

```text
WeddingGuestStats
WeddingGuestRow
TravelFinanceSummary
DebtRow
MemberRow
PlanCard
```

They may internally adopt V2 structural components.

Do not delete product components merely because their markup becomes smaller.

---

# 65. Product-Specific Is Not Duplication

Two components may both use:

```text
DataRow
Badge
Avatar
```

while remaining separate:

```text
WeddingGuestRow
MemberRow
```

because their semantics/actions/permissions differ.

This is correct architecture.

---

# 66. Presentation Duplication vs Semantic Duplication

Extract when duplication is:

```text
spacing
surface
row anatomy
metric anatomy
empty/error layout
```

Do not extract merely because two modules both have:

```text
status
amount
name
date
```

Those fields can have different meaning.

---

# 67. Card/Section Migration Rule

When migrating a consumer, classify each existing container:

```text
A — logical page grouping
→ Section

B — contained entity/surface
→ Card

C — both
→ Section + Card

D — decorative wrapper only
→ remove / plain layout

E — unclear product hierarchy
→ REVIEW
```

Do not mechanically replace every existing Card with Section.

---

# 68. Nested Container Audit

For each Pilot later, inspect:

```text
Card inside Card
bordered container inside Card
shadowed sub-card
metric card inside summary card
```

and ask whether hierarchy can be expressed through:

```text
spacing
divider
surface.subtle
MetricGroup
DataRow
```

Phase 4 creates the tools; Pilot phases make product-specific decisions.

---

# 69. Metric Migration Classification

Existing statistic UI should be classified:

```text
A — one label + one value
→ Metric candidate

B — group of independent values
→ MetricGroup + Metric candidate

C — calculated/domain summary widget
→ product component composing Metrics

D — chart/complex analysis
→ NOT Metric replacement
```

Do not turn charts or reconciliation widgets into Metric.

---

# 70. DataRow Migration Classification

Existing list items:

```text
A — generic row anatomy
→ product row may compose DataRow

B — strong custom visual object
→ KEEP product layout

C — true tabular alignment
→ later responsive table/list pattern

D — timeline item
→ timeline/product pattern, not DataRow automatically
```

Do not force Travel Activity timeline into DataRow merely because it is a list.

---

# 71. Empty/Error Migration Classification

Existing empty/error surfaces should be classified by semantic state.

Do not replace:

```text
permission denied
loading
filtered empty
fatal page error
```

with identical copy/actions.

Shared structure is allowed; product semantics remain explicit.

---

# 72. Typography

Structural components must use Foundation semantic typography roles.

Examples:

```text
Section title
→ section-title

Metric value
→ metric-* role

DataRow title
→ body-strong / component-title depending on anatomy

supporting metadata
→ metadata
```

Do not create local arbitrary typography recipes unless the approved roles cannot represent a real shared need.

---

# 73. Color

Structural components use semantic colors only.

Do not hard-code:

```text
blue
green
red
slate
```

for domain meaning.

Status color enters through generic tone/presentation props or composed Badge/content.

Finance neutral-by-default remains mandatory.

---

# 74. Radius

Use canonical Foundation radius roles.

Do not preserve `24px` merely because existing stat cards use it.

Migration should classify the component role and apply the appropriate canonical radius.

---

# 75. Elevation

Default:

```text
Section → no elevation
Metric → no elevation
MetricGroup → no elevation
DataRow → no elevation
EmptyState → no elevation
ErrorState → no elevation
Card → none unless raised variant/role requires it
```

Do not add shadows to make V2 “premium.”

---

# 76. Border

Use borders intentionally.

Examples:

```text
Card → subtle border where approved
DataRow → separators may belong to parent list/pattern
Metric → generally no border by itself
Section → generally no border
```

Avoid each child drawing its own border and creating visual noise.

---

# 77. Responsive Philosophy

Structural components should adapt gracefully but not own product information-priority decisions.

They may control:

```text
gap
columns
wrapping
stacking
padding
alignment
```

They should not decide:

```text
hide wedding metadata
hide finance amount
show different business fields
```

---

# 78. Mobile Density

Mobile-first does not mean oversized cards and excessive vertical whitespace.

V2 should preserve efficient scanning.

Use:

```text
clear hierarchy
adequate touch spacing
compact supporting metadata
controlled card padding
```

Avoid turning every row into a large standalone card.

---

# 79. Desktop Density

Desktop should use available width without stretching content unnaturally.

MetricGroup may expand columns.

DataRow may use horizontal alignment.

Section actions may sit beside title.

But do not create desktop-only information architecture inside generic structural components.

---

# 80. Accessibility — Section

Use semantic sectioning elements where appropriate, but do not automatically render every visual Section as `<section>` if it creates meaningless document landmarks.

If Section has a meaningful heading, semantic association is encouraged.

HTML element strategy should remain configurable or context-aware without API over-complexity.

---

# 81. Accessibility — Card

Card itself usually has no special ARIA role.

Do not add:

```text
role="group"
role="region"
```

to every Card.

Use semantics only when the consumer context warrants them.

---

# 82. Accessibility — Metric

Metric label/value relationship should remain understandable.

Avoid visual-only arrangements where screen reader order becomes confusing.

For financial values, formatting must remain understandable as text.

Metric should not rely on color alone for positive/negative meaning.

---

# 83. Accessibility — DataRow

DataRow semantics depend on its parent pattern.

It may appear in:

```text
list
navigation
selection list
plain stack
```

Do not hard-code one ARIA role that is wrong for other contexts.

Parent pattern/product composition owns list/listbox/table semantics where applicable.

---

# 84. Accessibility — Empty/Error

Titles and descriptions should be read in logical order.

Action controls must have clear names.

Do not hide important failure information only in icons/colors.

---

# 85. Ref Behavior

Where structural components expose refs today, preserve behavior.

Do not introduce refs unnecessarily.

If polymorphic semantics are needed, prefer a small proven pattern over an overly generic `as` system.

---

# 86. Polymorphism Guardrail

Do not make every structural component support arbitrary:

```text
as
asChild
component
```

unless current architecture already relies on it or there is a concrete accessibility/composition need.

Over-polymorphic APIs increase complexity.

Use the simplest contract that serves real consumers.

---

# 87. Slot Guardrail

Composition slots are useful, but too many named slots can create a generic page-builder component.

For each slot ask:

```text
Is this stable anatomy?
Or are we moving product layout into a generic API?
```

If the latter:

> keep composition in product layer.

---

# 88. Variant Guardrail

A new variant must represent a recurring generic visual/interaction role.

Do not add a variant because one Pilot needs a one-off appearance.

One-off product expression can remain composition-level until repeated evidence justifies extraction.

---

# 89. Plan-Type Expression

Structural components should generally not receive `planType`.

Correct:

```text
product composition resolves accent
↓
passes generic tone/accent presentation if necessary
```

Avoid:

```tsx
<Card planType="wedding" />
<Metric planType="travel" />
<DataRow planType="debt" />
```

Plan-Type Expression remains controlled and presentation-only.

---

# 90. Permission Boundary

Structural components do not receive authorization semantics.

Avoid:

```text
canEdit
canDelete
role
accessLevel
```

when these props mean permission.

A generic disabled/interactive state is acceptable after product capability resolution.

---

# 91. Business Calculation Boundary

No structural component may import:

```text
statistic.service
finance calculators
debt calculators
guest aggregation
settlement logic
```

Metric values and status content are supplied ready for presentation.

---

# 92. Data Fetching Boundary

Structural components do not fetch.

No:

```text
React Query hooks
Firebase reads
repositories
server actions
```

inside Section/Card/Metric/DataRow/EmptyState/ErrorState.

Product/pattern layer supplies data.

---

# 93. Error Parsing Boundary

ErrorState does not parse arbitrary backend errors into user copy.

Product/application layer maps technical error → presentation content.

This avoids leaking backend concepts into Design System.

---

# 94. Localization Boundary

Structural components should not hard-code Vietnamese product copy.

Generic accessibility labels should follow the app's current localization/copy mechanism if one exists.

Product-facing titles/actions are supplied by consumers.

---

# 95. Testing Philosophy

Test structural contracts, not every CSS detail.

Use the existing repository test framework.

Prioritize:

```text
content rendering
slot rendering
variant behavior
interaction semantics where applicable
ref/attribute forwarding where applicable
responsive class/behavior contract when practical
```

Avoid fragile snapshots that make every visual refinement expensive.

---

# 96. Section Tests

Representative:

```text
renders title/content
renders optional description/action
works without header
preserves semantic/custom attributes if supported
does not inject Card chrome by default
```

---

# 97. Card Tests

Representative:

```text
renders children
canonical variant/padding behavior
no elevation by default
interactive semantics only when explicitly composed/supported
```

Do not test product behavior.

---

# 98. Metric Tests

Representative:

```text
label/value
supporting content
size
generic tone
no calculation behavior
```

A test should not need Finance/Wedding fixtures.

If it does, boundary is wrong.

---

# 99. MetricGroup Tests

Representative:

```text
renders composed metrics
layout options
responsive contract where practical
```

No calculation fixtures.

No domain fixtures.

---

# 100. DataRow Tests

Representative:

```text
leading
main
status
trailing
selected presentation
density
non-interactive default
```

If interactive modes are supported, verify keyboard/native semantics.

---

# 101. EmptyState Tests

Representative:

```text
title
description
visual
primary action
secondary action
works without actions
```

No permission fixtures.

---

# 102. ErrorState Tests

Representative:

```text
title
description
action
secondary action
works without retry
```

Do not assume action label is “Thử lại.”

# 108. Consumer Migration Strategy

Phase 4 should NOT broadly migrate product screens.

Allowed:

```text
canonical shared component adaptation
small proof consumers
low-risk generic surfaces
```

Major product adoption begins in Core Patterns and Pilot waves.

---

# 109. Proof Consumer Selection

Choose a small set that demonstrates:

```text
Section
Card
Metric/MetricGroup
DataRow
EmptyState/ErrorState
```

without requiring product architecture changes.

Do not choose consumers that force:

```text
permission redesign
complex Wedding Guest behavior
Finance settlement logic
route redesign
```

---

# 110. Existing Product Component Adaptation

If a product component can internally replace repeated markup with a structural component without changing its public API or behavior, that may be a valid proof migration.

Example:

```text
MemberRow
before: custom generic row shell
after: DataRow composition
```

only if semantics fit cleanly.

Do not force it if the product row has specialized anatomy.

---

# 111. No Generic Config Engine

Do not build structures like:

```tsx
<UniversalCard
  type="metric"
  domain="finance"
  fields={[...]}
  actions={[...]}
  statusMapping={...}
/>
```

or:

```tsx
<DataRow entity={entity} schema={...} />
```

This is explicitly outside the Design System V2 direction.

Composition should remain readable in code.

---

# 112. Readability of Composition

A successful structural layer should make product components easier to understand.

Preferred:

```tsx
<MetricGroup>
  <Metric label="Tổng chi" value={totalExpenseText} />
  <Metric label="Dự kiến" value={expectedText} />
</MetricGroup>
```

not a deeply generic configuration DSL.

---

# 113. API Compatibility

When adapting existing shared components:

```text
preserve valid props
map legacy visual props where safe
document deprecated props
migrate progressively
```

Do not require repository-wide migration just to clean names.

---

# 114. Legacy Alias Strategy

Temporary aliases may be used for visual variants or prop names when semantic mapping is unambiguous.

Do not alias ambiguous concepts.

Example:

```text
legacy "outline" Card variant
```

must be inspected before mapping to V2 `default` or `subtle`.

---

# 115. Duplicate Structural Components

If audit finds multiple Card/StatCard/ListItem implementations:

```text
compare responsibility
compare semantics
compare consumers
```

Consolidate only stable generic anatomy.

Keep product wrappers when they own meaning.

---

# 116. File Ownership

Exact paths follow repository evidence.

Preferred conceptual ownership:

```text

or existing shared UI directory
```

depending on current architecture.

Do not restructure the whole UI folder in Phase 4.

---

# 117. Import Boundary

Structural component files must not import:

```text
modules/wedding
modules/travel
modules/debt
modules/finance
repositories
services
Firebase
permission resolvers
business entity types
```

Generic React/types/utilities and Core Primitives/Foundation are allowed.

---

# 118. Performance

Structural components should remain lightweight.

Avoid:

```text
unnecessary context providers
runtime schema engines
heavy memoization abstractions
large configuration parsing
```

Simple composition should stay simple.

---

# 119. SSR / Client Boundary

Structural presentation components should remain server-compatible where possible.

Do not add `"use client"` unless interaction/state genuinely requires it.

Examples:

```text
Section
Card
Metric
MetricGroup
EmptyState
ErrorState
```

should generally not require client state.

Interactive DataRow behavior may be composed through client-side product controls rather than forcing DataRow itself to become stateful.

# 127. Stop Conditions

STOP and request review if implementation requires:

```text
moving calculations into Metric/MetricGroup
moving permission logic into DataRow/EmptyState
adding domain enums to structural components
adding PlanType branching
creating a universal config-driven component
changing Service/Repository
changing Firestore
changing routing
broadly redesigning product screens
deleting product-specific wrappers solely due to visual similarity
```

Also STOP if a structural component requires a rapidly growing prop matrix to satisfy unrelated modules.

That is evidence the boundary is wrong.

# 131. Canonical Structural Principle

Structural components answer:

```text
How is content grouped?
What is a contained surface?
How is a metric presented?
How are metrics arranged?
How is row anatomy arranged?
How is empty content presented?
How is a persistent error presented?
```

They must never answer:

```text
How is finance calculated?
What does RSVP mean?
Can this Editor delete?
Which Guest action is available?
How should Debt settlement work?
What data should be fetched?
```

> **Standardize stable visual anatomy. Keep business meaning in product composition.**
