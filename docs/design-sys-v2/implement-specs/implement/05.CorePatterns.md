# 1. Purpose

This specification defines the reusable **Core Pattern** layer of Go Plan Design System V2.

Core Patterns sit above primitives and structural components and below product/domain compositions.

Phase 5 focuses on recurring interaction/composition problems that appear across multiple Go Plan modules while remaining independent of business meaning.

Canonical Phase 5 patterns:

```text
EntityList
FilterBar
PageHeader
```

Additional pattern extraction is allowed only when repository evidence and the approved Audit Decision Record clearly justify it.

The objective is:

> Standardize recurring composition and interaction grammar without turning the Design System into a generic product engine.

---

# 2. Core Pattern Definition

A Core Pattern is larger than a primitive or structural component.

It may coordinate multiple generic pieces such as:

```text
Input
Button
DropdownSelect
Badge
Avatar
Section
Card
DataRow
EmptyState
ErrorState
```

but it still does not own domain rules.

Example:

```text
EntityList
├── list structure
├── row spacing
├── selection presentation
├── empty/error/loading composition
└── responsive list behavior
```

It does not know whether the entities are:

```text
Guests
Members
Expenses
Debts
Todos
Activities
```

---

# 3. Layer Boundary

Required architecture:

```text
Product / Domain Composition
        ↓
Core Pattern
        ↓
Structural Components
        ↓
Core Primitives
        ↓
Foundation
```

Core Patterns must not import upward from product modules.

---

# 4. Why This Layer Is Separate

Patterns have more behavioral responsibility than structural components.

For example:

```text
DataRow
→ arranges one row

EntityList
→ coordinates a collection of rows
```

and:

```text
Input / DropdownSelect
→ individual controls

FilterBar
→ coordinates filtering controls visually
```

Because of this increased responsibility, patterns carry a greater risk of accidentally absorbing product logic.

Therefore:

> **Core Patterns may coordinate generic UI state, but product/domain state remains outside.**

# 10. Pattern Extraction Test

Before extracting a pattern, confirm:

1. The anatomy/interaction repeats across unrelated modules.
2. The repeated behavior is generic.
3. Domain-specific copy and decisions can remain outside.
4. The API does not need product enums.
5. Composition remains easier to read after extraction.
6. The abstraction reduces inconsistency rather than merely reducing line count.

If these conditions are not met:

> keep the implementation product-specific.

---

# 11. Anti-Framework Rule

Core Patterns must not become an internal low-code framework.

Explicitly avoid:

```tsx
<EntityList
  entityType="guest"
  schema={...}
  query={...}
  permissions={...}
  columns={...}
  actions={...}
  filters={...}
/>
```

or:

```tsx
<PageHeader
  planType="wedding"
  module="finance"
  role="editor"
  autoActions
/>
```

Go Plan should remain composition-driven.

---

# 12. EntityList — Purpose

`EntityList` provides generic collection presentation for repeated entity rows.

It may coordinate:

```text
row stack
row separators/gaps
list density
selection presentation
empty state
error state
loading placeholder integration
responsive collection spacing
```

It does not know entity semantics.

---

# 13. EntityList Anatomy

Conceptual anatomy:

```text
EntityList
├── Content state
│   ├── Loading
│   ├── Error
│   ├── Empty
│   └── Rows
│       ├── Row
│       ├── Row
│       └── ...
└── Optional generic footer/pagination slot
```

Exact API should adapt repository needs.

Do not build every state into one mandatory monolithic prop object.

---

# 14. EntityList vs DataRow

`DataRow`:

```text
one row anatomy
```

`EntityList`:

```text
collection-level structure
```

EntityList may compose DataRow, but must not require every child to be DataRow.

This allows product rows with specialized anatomy to remain valid.

---

# 15. EntityList Child Strategy

Prefer composition:

```tsx
<EntityList>
  {members.map(member => (
    <MemberRow key={member.id} member={member} />
  ))}
</EntityList>
```

over:

```tsx
<EntityList
  data={members}
  entityType="member"
  renderAutomatically
/>
```

A generic `renderItem` API may be acceptable if existing architecture strongly benefits from it, but plain children composition is preferred when simpler.

---

# 16. EntityList Data Boundary

EntityList should not:

```text
fetch
query
sort
filter
aggregate
paginate from backend
resolve permissions
map domain status
```

Product/pattern composition supplies the resulting collection.

---

# 17. EntityList Loading

EntityList may accept a generic loading presentation or loading slot.

It should not infer loading from query libraries.

Correct:

```tsx
<EntityList loading={isLoading} ... />
```

or composition equivalent.

Incorrect:

```text
EntityList imports React Query/Firebase and fetches data.
```

---

# 18. EntityList Empty State

Product determines why the list is empty and what action is appropriate.

Correct:

```tsx
<EntityList
  empty={
    <EmptyState
      title="Chưa có thành viên"
      action={canInvite ? <Button>Thêm thành viên</Button> : undefined}
    />
  }
/>
```

EntityList does not receive `canInvite` or Member permissions.

---

# 19. EntityList Error State

Product/application layer maps technical errors into presentation.

EntityList may render a supplied `ErrorState`.

It does not parse backend errors or call refetch itself unless a generic callback is explicitly supplied by composition.

---

# 20. EntityList Selection

EntityList may support generic controlled selection presentation only if multiple real modules need it.

Allowed conceptual inputs:

```text
selected IDs / selected state
selection mode
selection callback
```

only if the implementation remains domain-neutral.

Preferred boundary:

```text
product owns selection state
pattern coordinates generic selection mechanics/presentation
```

Do not let EntityList decide what selected entities mean.

---

# 21. EntityList Bulk Actions

Bulk action semantics belong outside EntityList.

Correct:

```text
product selection state
↓
product decides available bulk actions
↓
renders toolbar/action region
```

EntityList may expose a generic slot for selection controls if repeated evidence justifies it.

Do not add:

```text
bulkDelete
bulkInvite
bulkSetRole
```

props.

---

# 22. EntityList Row Actions

EntityList does not own row actions.

Rows/product composition provide them.

This avoids permission/business leakage.

---

# 23. EntityList Density

A small generic density contract may be supported:

```text
comfortable
compact
```

if Phase 4 DataRow density uses the same vocabulary.

Do not introduce:

```text
guestDense
financeDense
desktopTable
```

variants.

---

# 24. EntityList Dividers

Collection separators belong at the collection level where practical.

This prevents every DataRow from drawing independent borders.

EntityList may support generic presentation such as:

```text
divided
spaced
```

only if these are real recurring list treatments.

Keep the variant set small.

---

# 25. EntityList Accessibility

Parent semantics depend on usage.

Possible contexts:

```text
list
navigation list
selection list
plain collection
```

Do not force `role="listbox"` or another specialized role for every EntityList.

If a generic semantic element/role option is needed, keep it narrow and documented.

Product patterns own specialized semantics.

---

# 26. EntityList Mobile Behavior

Mobile lists should prioritize scan efficiency.

Avoid automatically converting every row into a separate large Card.

Preferred:

```text
compact rows
clear separators
sufficient touch targets
natural wrapping
```

Product-specific information priority remains outside EntityList.

---

# 27. EntityList Desktop Behavior

Desktop may use denser row layout and wider content.

EntityList does not become a table automatically.

When strong cross-row column alignment is required, defer to a later table/list pattern rather than overloading EntityList.

---

# 28. FilterBar — Purpose

`FilterBar` provides generic composition for:

```text
search
filter controls
sort controls
filter reset
active filter summary/chips where approved
responsive filter access
```

It standardizes interaction layout.

It does NOT own domain filtering rules.

---

# 29. FilterBar Boundary

FilterBar may know:

```text
layout
control grouping
responsive wrapping
generic search slot
generic filter slots
generic action/reset slot
active state presentation
```

It MUST NOT know:

```text
Guest status
Expense category
Debt direction
Member role
Travel category
Wedding group
```

---

# 30. FilterBar Composition

Prefer composition:

```tsx
<FilterBar
  search={<SearchInput ... />}
  filters={
    <>
      <DropdownSelect ... />
      <DropdownSelect ... />
    </>
  }
  actions={<Button ...>Đặt lại</Button>}
/>
```

rather than a universal filter schema.

---

# 31. No Filter DSL

Do not build:

```tsx
<FilterBar
  filters={[
    { field: 'rsvp', type: 'select', ... },
    { field: 'groupId', type: 'multi-select', ... }
  ]}
/>
```

as a Design System requirement.

A product-level data/filter framework may exist separately, but Core Patterns should not invent one.

---

# 32. Search Boundary

FilterBar may host a search input.

It does not define:

```text
debounce policy
backend query syntax
search fields
accent-insensitive matching
server/client search strategy
```

Those remain product/application concerns.

---

# 33. Sort Boundary

FilterBar may host a generic sort control.

It does not determine valid sort options or execute sorting.

Product supplies:

```text
options
selected value
change handler
```

---

# 34. Reset Boundary

FilterBar may expose an action region or generic reset presentation.

The product decides:

```text
what default filters are
whether reset is available
what reset changes
```

Do not embed product filter defaults in FilterBar.

---

# 35. Active Filter Count

A generic active-filter count may be displayed if product composition provides the count.

FilterBar must not calculate domain filter activity from arbitrary filter objects unless a stable generic filter state model already exists and is explicitly approved.

Preferred:

```text
activeCount={3}
```

over domain introspection.

---

# 36. Filter Chips

If approved and repeated, FilterBar may host generic active-filter chips.

The product supplies:

```text
label
remove action
```

The pattern does not translate domain filter values into copy.

Do not require chips in Phase 5 if repository evidence does not justify them.

---

# 37. Mobile Filter Strategy

Mobile filter UX may differ from desktop.

Typical pattern:

```text
Desktop
→ inline search + controls

Mobile
→ search + compact filter trigger
→ filters may open in an overlay
```

The exact behavior must follow repository evidence and approved V2 responsive strategy.

Do not force all desktop controls into one cramped mobile row.

---

# 38. Filter Overlay Boundary

If mobile filters use an overlay:

```text
FilterBar
↓ may trigger product/generic filter content
↓ ResponsiveModal provides surface
```

FilterBar should not recreate BottomSheet/Dialog mechanics.

Use Phase 3 overlay architecture.

---

# 39. Mobile Filter Apply Behavior

Whether filters apply:

```text
immediately
on Apply
```

is a product interaction decision unless a cross-product convention has already been approved.

Do not silently change filtering behavior while migrating layout.

---

# 40. FilterBar Sticky Behavior

Do not make FilterBar sticky by default.

Sticky filtering can be useful for long lists but changes page behavior and available viewport space.

Product/pattern composition should opt in only where justified.

---

# 41. FilterBar Accessibility

Requirements:

```text
search input has accessible label
filter controls have accessible names
mobile filter trigger communicates active state/count where relevant
reset/apply actions are explicit
keyboard order remains logical
```

Do not rely on icon-only filters without accessible naming.

---

# 42. FilterBar URL State Boundary

FilterBar does not own URL/query-string synchronization.

Product/application routing layer owns it.

Do not import router hooks into the generic pattern solely for convenience.

---

# 43. PageHeader — Purpose

`PageHeader` defines consistent page-level hierarchy and action placement.

It may coordinate:

```text
title
description
metadata/context
primary action
secondary actions
back/breadcrumb/navigation slot where genuinely generic
responsive wrapping
```

It does not own Plan business semantics.

---

# 44. PageHeader vs Plan Header

A generic `PageHeader` is NOT automatically the same thing as the product-specific Plan Overview header.

Go Plan currently has rich Plan headers that may include:

```text
Plan name
status
description
financial summary
members
PlanType expression
```

Those are product compositions.

They may use PageHeader internally where appropriate, but must not be flattened into a generic PageHeader API.

---

# 45. PageHeader Anatomy

Conceptual anatomy:

```text
PageHeader
├── Context / navigation?
├── Main
│   ├── Title
│   ├── Description?
│   └── Metadata?
└── Actions?
```

Keep optional areas minimal.

Do not build a universal hero component.

---

# 46. PageHeader Title

Page title is the highest page-level content heading.

Use the Foundation `page-title` role.

Preserve semantic heading structure.

PageHeader should support a meaningful heading element strategy without forcing invalid hierarchy.

---

# 47. PageHeader Actions

Product supplies actions.

Correct:

```tsx
<PageHeader
  title="Thành viên"
  actions={<Button>Thêm thành viên</Button>}
/>
```

PageHeader does not know:

```text
who may add members
what the action does
whether premium is required
```

---

# 48. PageHeader Permission Boundary

Permission resolution happens before composition.

Correct:

```tsx
<PageHeader
  title="Thành viên"
  actions={canManageMembers ? <AddMemberButton /> : undefined}
/>
```

Incorrect:

```tsx
<PageHeader
  title="Thành viên"
  role={role}
  module="members"
  autoActions
/>
```

---

# 49. PageHeader Metadata

Generic metadata/context may be composed.

Do not add domain-specific props:

```text
memberCount
totalExpense
weddingDate
debtBalance
```

Use product composition.

---

# 50. PageHeader Plan-Type Expression

Default PageHeader should remain neutral.

If a product header needs Plan-Type expression, resolve that in product composition or through a narrowly approved generic accent presentation.

Do not add PlanType branching to PageHeader.

---

# 51. PageHeader Responsive Behavior

Desktop:

```text
title/context left
actions may align right
```

Mobile:

```text
content stacks/wraps
primary action remains reachable
description does not compete with controls
```

Do not hide important actions merely because the viewport is narrow.

Product may move secondary actions into a menu when justified.

---

# 52. PageHeader Action Priority

PageHeader may provide layout for:

```text
one primary action
secondary action region
```

but it does not decide which action is primary.

Product composition owns action hierarchy.

Avoid filling headers with many equally prominent buttons.

---

# 53. PageHeader Back Navigation

If multiple modules share a recurring back-navigation presentation, PageHeader may accept a generic navigation slot.

It should not decide route targets.

No router/domain logic inside PageHeader.

---

# 54. PageHeader Breadcrumbs

Breadcrumb support is optional and should only be added if repository evidence shows a recurring desktop need.

Do not introduce breadcrumbs simply because they are common in SaaS templates.

Go Plan is mobile-first; navigation must reflect actual product hierarchy.

---

# 55. PageHeader vs Section

Use:

```text
PageHeader
→ page-level identity/action

Section
→ grouping inside page
```

Do not use Section as a substitute for page heading.

Do not repeat the same title in PageHeader and first Section without a semantic reason.

---

# 56. Pattern State Ownership

Core Patterns may coordinate local generic UI state when that state is purely presentational.

Examples that may be acceptable:

```text
mobile filter overlay open/closed
generic collapsible control state if approved
```

They must not own domain state such as:

```text
selected Guest Group business filter model
Member permissions
Finance reconciliation state
```

---

# 57. Controlled State Preferred at Product Boundaries

When pattern state affects product behavior, prefer controlled contracts.

Example:

```text
searchValue
onSearchChange

filter trigger
selected values supplied externally
```

Do not hide meaningful state transitions inside a generic pattern.

---

# 58. Loading / Empty / Error / Content

Patterns should preserve clear state separation:

```text
loading
error
empty
content
```

Do not conflate them.

EntityList may coordinate rendering, but product/application layer determines which state is active.

---

# 59. Skeleton Boundary

Existing Skeleton may be composed for loading.

Phase 5 does not redesign Skeleton unless required by approved upstream disposition.

Do not make EntityList invent domain-shaped skeletons.

Product may supply specialized skeleton rows.

---

# 60. Pagination Boundary

EntityList may expose a generic footer slot that can host pagination/load-more controls.

It does not own:

```text
page number
cursor
backend pagination
infinite query
```

A future pagination primitive/pattern should only be extracted with evidence.

---

# 61. Infinite Scroll

Do not add infinite scroll to EntityList as a generic capability in this phase.

It has meaningful UX/data implications.

If a product currently uses it, preserve that product behavior outside the generic pattern.

---

# 62. Virtualization

Do not add list virtualization unless current scale/performance evidence requires it.

Virtualization changes accessibility, measurement and interaction behavior.

It is not a Design System default.

---

# 63. Drag and Drop

EntityList does not own drag-and-drop/reordering.

Todo/Milestone ordering or other domain reorder semantics remain product-specific.

A future generic sortable pattern requires separate approval.

---

# 64. Responsive Pattern Philosophy

Core Patterns may change arrangement across:

```text
Mobile
Tablet
Desktop
```

but should preserve product capability.

Responsive changes may affect:

```text
layout
control grouping
wrapping
surface presentation
density
```

They must not silently remove features.

---

# 65. Capability Parity

Responsive adaptation must distinguish:

```text
same capability, different presentation
```

from:

```text
feature unavailable
```

Example:

```text
Desktop filters inline
Mobile filters in modal
```

is capability parity.

Simply hiding filters on mobile is not.

Any intentional capability difference requires product approval.

---

# 66. Accessibility — Shared

Core Patterns must preserve:

```text
logical reading order
keyboard order
visible focus
accessible control names
semantic headings
touch targets
non-color-only state
```

Patterns must not override accessible behavior from underlying primitives.

---

# 67. EntityList Accessibility

Verify:

```text
row order
interactive row semantics
selection semantics if supported
empty/error state announcement/readability
trailing actions reachable
```

Avoid nested interactive traps.

---

# 68. FilterBar Accessibility

Verify:

```text
search label
filter labels
sort label
mobile filter trigger name
active count meaning
keyboard navigation
overlay focus behavior when mobile filters open
```

---

# 69. PageHeader Accessibility

Verify:

```text
page title heading hierarchy
actions named
back/navigation action named
description/metadata reading order
```

Do not create multiple competing H1s through generic defaults.

---

# 70. Typography

Patterns consume Foundation roles.

Typical mapping:

```text
PageHeader title
→ page-title

PageHeader description
→ body / text-secondary

FilterBar supporting labels
→ metadata/body

EntityList
→ delegates row typography to child composition/DataRow
```

Do not create a separate typography system in patterns.

---

# 71. Surface and Elevation

Patterns should remain visually restrained.

Typical:

```text
EntityList
→ no forced Card

FilterBar
→ plain or subtle surface depending on approved composition

PageHeader
→ no Card/elevation by default
```

Do not wrap every pattern in Card.

---

# 72. Border Ownership

Avoid double borders.

Examples:

```text
EntityList may own row separators
DataRow should not also draw them by default

FilterBar surface may own boundary
individual controls own their own control borders
```

Clarify parent/child ownership.

---

# 73. Spacing Ownership

Pattern owns spacing between its major generic parts.

Children own their internal spacing.

Avoid both parent and child adding equivalent margins.

Prefer:

```text
gap
```

over child-specific external margins where possible.

---

# 74. Plan-Type Expression

Core Patterns should generally not receive:

```text
planType
```

Product composition resolves any accent before passing generic presentation.

Do not create:

```text
<EntityList planType="wedding">
<FilterBar planType="travel">
<PageHeader planType="debt">
```

---

# 75. Permission Boundary

No Core Pattern may resolve:

```text
Owner
Editor
Viewer
module access
manage_all
canEditAllExpenses
```

Product layer determines:

```text
which actions render
which controls are disabled
which filters exist
```

---

# 76. Premium Boundary

Core Patterns do not resolve premium entitlement.

Do not add:

```text
isPremium
requiresPremium
locked
```

as product entitlement semantics.

If a premium feature uses a pattern, product composition decides whether to render:

```text
normal action
locked affordance
upgrade flow
```

A future premium/entitlement pattern requires separate specification.

---

# 77. Business Copy Boundary

Patterns should not hard-code domain copy.

Examples that remain product-supplied:

```text
Thêm thành viên
Mời khách
Tổng chi
Đã xác nhận
Lọc theo nhóm khách
```

Generic accessibility copy may use the app's approved copy/localization mechanism where necessary.

---

# 78. Data Formatting Boundary

Patterns do not format:

```text
currency
dates
guest counts
percentages
debt balances
```

Product/presentation composition supplies display-ready content.

---

# 79. Domain Status Boundary

Patterns do not map:

```text
RSVP → Badge tone
Debt direction → color
Plan status → label
Member role → action
```

Those mappings remain product-specific.

---

# 80. Routing Boundary

PageHeader navigation slots and EntityList row interactions may trigger routing through consumer-supplied elements/callbacks.

Patterns must not import route maps or construct product URLs.

---

# 81. Data Fetching Boundary

No Core Pattern may import:

```text
React Query domain hooks
Firebase
repositories
services
server actions for domain data
```

Data enters from product/application composition.

---

# 82. Form Boundary

FilterBar may compose form controls but is not a general form framework.

Do not introduce form library coupling unless existing generic controls already require it.

Filtering forms and business edit forms remain separate concepts.

---

# 83. URL/Filter Synchronization

If a product stores filters in URL parameters:

```text
product/application layer
↓ parses/synchronizes URL
↓ supplies state to FilterBar controls
```

FilterBar remains router-neutral.

---

# 84. API Design — Prefer Slots

Core Patterns should prefer meaningful composition slots over large product-oriented prop matrices.

Good:

```text
search
filters
actions
children
empty
error
```

Potentially bad:

```text
guestStatusOptions
memberRoleOptions
showDebtSort
financeSearchMode
```

---

# 85. API Design — Avoid Boolean Explosion

Warning:

```text
compact
bordered
sticky
mobileSheet
showReset
showCount
collapsible
searchable
selectable
divided
cardMode
...
```

A few orthogonal generic options may be valid.

A growing boolean matrix means the abstraction needs review.

---

# 86. API Design — Avoid Premature Genericity

Do not solve hypothetical future modules.

Design APIs from:

```text
approved V2 needs
current repository evidence
known Pilot requirements
```

Future extension should be possible, but speculative complexity is not a goal.

---

# 87. Existing Product Wrappers

Product wrappers should survive when they own meaning.

Examples:

```text
WeddingGuestList
MemberList
DebtList
TravelActivityList
```

may compose EntityList but remain separate.

Correct:

```text
WeddingGuestList
    ↓
EntityList
    ↓
WeddingGuestRow
```

---

# 88. Product Filter Wrappers

Similarly:

```text
WeddingGuestFilters
FinanceFilters
DebtFilters
```

may compose FilterBar.

Do not replace them with a universal domain-aware FilterBar.

---

# 89. Product Header Wrappers

Rich product headers may compose PageHeader.

Examples:

```text
PlanOverviewHeader
WeddingOverviewHeader
```

remain product-specific if they own domain information.

PageHeader standardizes only the generic page hierarchy/action shell.

# 93. Proof Consumer Strategy

Proof consumers should:


# 94. Pilot Separation

Core Pattern implementation is still infrastructure.

Do not start broad Pilot redesign during Phase 5.

The purpose is to ensure that when Pilot begins, the reusable layers are ready and stable.

---

# 95. No Visual Redesign by Accident

Adopting EntityList/FilterBar/PageHeader may normalize spacing and hierarchy.

It must not silently change:

```text
what information is shown
action availability
filter semantics
sort order
list order
pagination
navigation destination
```

Those are product behaviors.

---

# 96. Search Input Reuse

If a canonical Input/search primitive exists, FilterBar should compose it.

Do not create a separate styled search input unless search-specific anatomy genuinely requires a small wrapper such as icon/clear action.

Any wrapper must remain generic.

---

# 97. Clear Search

A generic clear-search affordance may be supported when reusable.

It must:

```text

clear only through supplied state callback
not own query logic
```

Do not add search history/suggestions in Phase 5.

---

# 98. Filter Count on Mobile

If mobile collapses filters behind a trigger, displaying active count is useful.

Product supplies the count or generic controlled filter model if explicitly approved.

The count must not rely on color alone.

---

# 99. Filter Control Overflow

Desktop FilterBar should handle realistic control widths.

Prefer:

```text
wrap
responsive grouping
controlled min/max widths
```

over tiny compressed selects.

Do not create horizontal overflow that hides actions unless intentionally designed.

---

# 100. PageHeader Long Title Stress

Verify realistic long Plan/page names.

Header should:

```text

preserve action reachability
avoid overlap
```

Do not truncate primary page identity aggressively by default.

# 101. Vietnamese Copy Stress

```text
Thêm và quản lý những người tham gia kế hoạch

```

Patterns must not be optimized only for short English mock copy.

---

# 102. Large Dataset Stress

EntityList architecture should remain structurally sound with many rows.

Phase 5 does not require virtualization.

Check:

```text
consistent separators
stable row keys supplied by product
no unnecessary pattern-level rerender architecture
```

Do not add complex optimization without evidence.

---

# 103. Empty Search Results

A filtered/search-empty result is semantically different from first-use empty.

Product should supply appropriate EmptyState content.

FilterBar + EntityList must allow:

```text
active filters remain visible
reset action remains available
empty message explains no matching results
```

The generic patterns do not write that copy.

---

# 104. Error With Active Filters

If data loading fails while filters are active, product decides whether filters remain editable.

EntityList/ErrorState should not reset filters automatically.

Preserve user state unless product behavior says otherwise.

---

# 105. Selection + Filtering

If a product supports selection and filtering, the product owns semantics of selected hidden items.

EntityList must not automatically clear selection on filter changes.

That is a product decision.

---

# 106. Responsive Filter Overlay Integration

If implemented:

```text

    ↓
```

```text

```

Do not duplicate overlay mechanics.

---

# 107. Sticky PageHeader

PageHeader should not be sticky by default.

Sticky page-level actions may be useful in some workflows but can conflict with mobile navigation/header layers.

Treat stickiness as product layout behavior requiring evidence.

---

# 108. Header Actions on Mobile

When actions do not fit:

```text
preserve primary action
move lower-priority actions into an explicit menu if product approves
or stack/wrap
```

PageHeader should not automatically hide secondary actions without a replacement path.

---

# 109. Icon Usage

Use Lucide through existing conventions.

Patterns may accept icon content but should not map product states to icons internally.

Avoid decorative icon overload in FilterBar/PageHeader.

---

# 110. Color Usage

Patterns consume semantic Foundation tokens.

Default should remain neutral.

Brand/status colors should be used only when the supplied generic state warrants them.

Do not make PageHeader or FilterBar gradient-heavy.

---

# 111. Elevation

Default:

```text
EntityList → none
FilterBar → none
PageHeader → none
```

If mobile FilterBar opens an overlay, overlay elevation comes from ResponsiveModal.

Do not add shadows simply to distinguish pattern boundaries.

---

# 112. Radius

Patterns should use canonical Foundation radius only when they actually own a surface.

A plain PageHeader does not need radius.

A plain EntityList does not need outer Card radius by default.

---

# 113. Density

Patterns should align with the approved responsive/density system.

Avoid a separate pattern-specific density scale.

If EntityList uses `compact/comfortable`, it should align with DataRow and spacing tokens.

---

# 114. Client/Server Boundary

Keep patterns server-compatible where possible.

`PageHeader` and basic `EntityList` should not require `"use client"` merely because some consumers are interactive.

`FilterBar` may require client-side composition depending on current implementation, but avoid pulling product data trees into client boundaries unnecessarily.

---

# 115. Ref and DOM Boundary

Do not expose imperative refs unless real consumers require them.

Patterns should not encourage consumers to manipulate internal DOM structure.

Stable composition APIs are preferred.

---

```text

Can this Editor invite Members?
How should expenses be sorted?

Which route should this entity open?
```
