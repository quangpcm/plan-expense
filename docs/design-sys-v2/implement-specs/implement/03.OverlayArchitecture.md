# 1. Purpose

This specification defines the canonical Design System V2 overlay architecture for Go Plan.

The overlay layer includes:

```text
ResponsiveModal
ConfirmDialog

legacy:
Dialog
BottomSheet
```

The objective is:

> Consolidate overlay presentation and responsive behavior while preserving the correct accessibility semantics of each interaction type.

The most important architectural rule is:

> **Visual similarity does not justify collapsing Dialog, AlertDialog and Sheet semantics into one generic interaction primitive.**

V2 may share visual recipes, tokens and responsive policies.

It must preserve semantic differences.

---

# 2. Audit Decision

Canonical dispositions:

```text

→ KEEP / ADAPT

ConfirmDialog
→ KEEP / ADAPT

Dialog
→ DEPRECATE after migration coverage

BottomSheet
→ DEPRECATE after migration coverage
```

`ConfirmDialog` must NOT be replaced by an ordinary `ResponsiveModal` merely because the surfaces look similar.

The existing accessible confirmation semantics remain protected.

# 4. Scope

Phase 3 may:

- adapt `ResponsiveModal`;
- adapt `ConfirmDialog`;
- normalize overlay visual anatomy;
- normalize modal/sheet responsive policy;

# 6. Overlay Semantic Families

Go Plan should distinguish at least three conceptual overlay families:

```text
Dialog / Modal
Alert / Confirmation
Sheet / Drawer presentation
```

These may share appearance but not necessarily accessibility semantics.

## 6.1 Dialog / Modal

Used for:

```text
forms
detail editing
non-destructive focused tasks
contained workflows
```

## 6.2 Alert / Confirmation

Used when the user must explicitly acknowledge or confirm a consequential action.

Examples:

```text
delete
remove
discard
irreversible action
high-impact state transition
```

## 6.3 Sheet / Drawer

Primarily a presentation/layout form factor.

A Sheet does not automatically imply different business semantics.

It may be the mobile rendering of a normal modal workflow.

---

# 7. ResponsiveModal Responsibility

`ResponsiveModal` owns generic responsive overlay presentation.

Conceptually:

```text
Desktop
→ centered Dialog/Modal

Mobile
→ Bottom Sheet / Drawer-like surface

Tablet
→ choose the treatment that best fits the approved responsive policy
```

The exact breakpoint mapping must use Foundation.

ResponsiveModal may own:

```text
open/close presentation
responsive surface selection
overlay/backdrop
generic header
generic body
generic footer/action region
close affordance
focus lifecycle through underlying accessible primitives
```

It MUST NOT own product/business semantics.

---

# 8. ResponsiveModal Does Not Mean One DOM Primitive

The name `ResponsiveModal` describes the **product-facing contract**, not necessarily one underlying primitive.

Implementation may use:

```text
Dialog semantics on desktop
Sheet/Dialog-derived semantics on mobile
```

if accessibility behavior remains correct.

Do not force one implementation mechanism across all viewport sizes if doing so harms usability or semantics.

---

# 9. ConfirmDialog Responsibility

`ConfirmDialog` represents an explicit confirmation interaction.

It owns:

```text
confirmation surface
title
description
confirm action
cancel action
destructive/attention visual hierarchy
accessible confirmation semantics
focus behavior
```

It does NOT own:

```text
delete API call
permission check
business mutation
business entity naming
domain-specific copy
```

Product composition supplies these.

---

# 10. ConfirmDialog Semantic Protection

If current `ConfirmDialog` uses `AlertDialog` or an equivalent accessible primitive:

> preserve that semantic behavior.

Do not rewrite it as ordinary Dialog solely to share ResponsiveModal code.

Allowed sharing:

```text
tokens
surface recipe
spacing
radius
typography
button layout
motion values
responsive visual policy where safe
```

Semantic implementation may remain separate.

---

# 11. Destructive Confirmation Recipe

The Design System may define a reusable destructive-confirmation recipe.

It should standardize:

```text
danger emphasis
action hierarchy
cancel placement
confirm placement
loading state
disabled state
copy hierarchy
```

It must not automatically determine when confirmation is required.

Product flows decide whether an action is destructive/high-impact enough to require confirmation.

---

# 12. Dialog vs ConfirmDialog Decision Rule

Use normal modal/dialog when the primary intent is:

```text
create
edit
inspect
configure
choose
complete a contained workflow
```

Use ConfirmDialog when the primary intent is:

```text
confirm consequential action
acknowledge destructive action
prevent accidental irreversible/high-impact action
```

Do not use ConfirmDialog merely because a modal has two buttons.

---

# 13. Overlay Anatomy

Canonical generic anatomy:

```text
Overlay
├── Backdrop
└── Surface
    ├── Header
    │   ├── Title
    │   ├── Description?
    │   └── Close?
    │
    ├── Body
    │
    └── Footer / Actions?
```

Not every overlay must render every slot.

Avoid wrappers that exist only for visual nesting.

---

# 14. Header Contract

Overlay header may contain:

```text
title
description
close action
```

Title should be accessible and programmatically associated with the overlay where required by the underlying primitive.

Description should also be associated where appropriate.

Do not render hidden placeholder titles merely to silence accessibility warnings unless the product genuinely has an accessible name.

---

# 15. Close Affordance

Normal ResponsiveModal should generally support an explicit close affordance unless the workflow intentionally requires completion/decision.

Close affordance must have an accessible name.

Example:

```text
aria-label="Đóng"
```

or equivalent localization strategy.

ConfirmDialog should normally expose explicit cancel/confirm actions rather than relying only on an `X`.

Do not make destructive confirmation dismissible only through an unlabeled icon.

---

# 16. Escape Key

For ordinary modal workflows, Escape should normally close the overlay when supported by the underlying accessible primitive.

For high-impact confirmation flows, preserve the current accessible primitive's expected dismiss behavior unless product requirements explicitly prevent it.

Do not implement custom global key handlers when the underlying primitive already handles Escape correctly.

---

# 17. Backdrop Interaction

Backdrop click/tap behavior must be intentional.

Normal editing/creation modal:

```text
may dismiss if product flow is safe
```

Dirty form / high-risk workflow:

```text
may require discard protection
```

ConfirmDialog:

```text
follow underlying AlertDialog semantics / approved confirmation behavior
```

The generic overlay component must not independently infer whether unsaved data exists.

Product composition resolves that state.

---

# 18. Unsaved Changes Boundary

ResponsiveModal does NOT own business dirty-state detection.

Correct:

```text
Product form
↓ determines dirty state
↓ decides whether close is allowed / needs confirmation
↓ controls overlay
```

Incorrect:

```text
ResponsiveModal
↓ introspects form state
↓ decides discard behavior
```

A future generic discard-confirmation pattern may be composed externally.

---

# 19. Controlled Open State

Preserve current controlled/uncontrolled behavior.

Preferred product contract should support controlled state where existing architecture uses it:

```text
open
onOpenChange
```

or equivalent current API.

Do not change state ownership merely for V2 consistency.

---

# 20. Portal

If the current accessible overlay primitive uses a portal:

> preserve it.

Do not move overlay DOM into local layout containers unless there is a proven issue.

Portal behavior helps avoid:

```text
overflow clipping
stacking context bugs
layout interference
```

---

# 21. Focus Lifecycle

Overlay focus behavior is release-important.

On open:

```text
focus moves into the overlay appropriately
```

While open:

```text
keyboard focus remains within the modal interaction context where modal semantics require it
```

On close:

```text
focus returns to the logical trigger when possible
```

Do not manually reimplement focus trapping if the underlying accessible library already provides it.

---

# 22. Initial Focus

Initial focus should be intentional.

Normal form modal:

```text
first meaningful field/action may receive focus
```

Confirmation:

```text
avoid defaulting focus to destructive confirm when that increases accidental activation risk
```

Prefer the safe action/cancel or the underlying accessible primitive's approved behavior when appropriate.

Do not create one global initial-focus rule for every overlay.

---

# 23. Focus Return

After closing an overlay, focus should return to:

```text
the trigger
```

or another logical nearby element if the trigger no longer exists because of the confirmed action.

Example:

```text
Delete row
↓ row disappears
↓ focus should move to a logical list/context target
```

That product-specific fallback is owned by the consumer.

The overlay primitive should preserve default trigger restoration where possible.

---

# 24. Nested Overlays

Avoid nested overlays unless the workflow genuinely requires them.

Examples of risky nesting:

```text
Dialog
  → ConfirmDialog
```

may be valid for destructive confirmation from an edit form, but focus/stack behavior must be tested.

Do not build arbitrary:

```text
Dialog → Sheet → Dialog
```

chains as a normal UX pattern.

If nested overlays are required, preserve underlying library stacking/focus semantics.

---

# 25. Z-Index

Use Foundation layering roles.

Do not add arbitrary:

```text
z-[9999]
```

inside individual overlays.

Required layering should account for:

```text
backdrop
overlay surface
dropdown/popover inside overlay
toast if product requires it above/beside overlay
```

Exact ordering should follow the existing architecture and Foundation convention.

---

# 26. Backdrop

Use the canonical Foundation backdrop token.

Backdrop should:

```text
separate modal context
retain enough page context
avoid excessive darkness
avoid decorative blur unless approved
```

Do not introduce heavy glassmorphism as a default V2 behavior.

---

# 27. Surface

Overlay surface consumes:

```text
surface.overlay
border if needed
radius
elevation.overlay
text semantic tokens
```

Do not hard-code a separate white/gray/shadow system inside each overlay.

---

# 28. Desktop Modal Geometry

Desktop modal should use a constrained width strategy.

Prefer semantic sizes rather than arbitrary per-consumer pixel widths where recurring patterns exist.

Possible conceptual size roles:

```text
sm
md
lg
xl
```

Do not create a large size matrix.

Consumers with genuinely complex content may provide an approved max-width override.

---

# 29. Mobile Sheet Geometry

Mobile presentation should prioritize:

```text
thumb reach
content readability
safe area
keyboard behavior
scrollability
clear dismissal
```

Sheet may use:

```text
bottom anchored surface
top radius
viewport-aware max height
```

Do not require full-screen height for every modal.

---

# 30. Tablet Behavior

Three-tier Foundation does not require a unique Tablet overlay.

Tablet may use:

```text
desktop-style centered modal
```

or:

```text
mobile-style sheet
```

depending on width/content/usability.

Choose one canonical default based on current V2 responsive contract and existing implementation evidence.

Do not create tablet-specific behavior solely to satisfy the existence of a breakpoint.

---

# 31. Safe Area

Mobile sheet/footer actions must respect device safe-area insets where the current PWA/browser environment requires them.

Do not hard-code bottom padding that conflicts with existing safe-area handling.

Reuse current platform/layout utilities if available.

---

# 32. Scrolling

Overlay architecture must clearly separate:

```text
fixed/stable header where appropriate
scrollable body
stable footer/actions where appropriate
```

without creating nested scroll traps.

For simple content, allow natural surface scrolling.

For long forms, ensure:

```text
actions remain reachable
keyboard does not permanently hide actions
body can scroll
```

Do not globally force sticky headers/footers for every overlay.

---

# 33. Mobile Keyboard

Input-heavy mobile overlays must be verified with virtual keyboard behavior.

Check:

```text
focused field remains reachable
content can scroll
footer does not cover field
sheet height responds acceptably
close/submit actions remain reachable
```

Do not solve keyboard issues by changing form business behavior.

---

# 34. Action Footer

Generic footer may support:

```text
primary action
secondary/cancel action
additional content where justified
```

Default action hierarchy should remain predictable.

For normal forms:

```text
primary action
secondary cancel
```

For destructive confirmation:

```text
destructive confirm
safe cancel
```

Exact visual/order conventions must follow approved V2 and locale/product behavior.

---

# 35. Mobile Action Layout

On narrow mobile widths, action buttons may:

```text
stack
stretch
```

if required for usability.

Do not shrink labels below readable/touch-safe sizes merely to keep actions on one row.

Higher-level overlay composition may choose action layout when generic auto behavior is insufficient.

---

# 36. Loading Actions

When an overlay submit/confirm action is loading:

```text
prevent duplicate submission
preserve understandable label/state
keep close behavior intentional
```

Do not automatically lock the entire overlay unless product flow requires it.

ConfirmDialog may prevent repeated confirm activation while mutation is in progress.

Business mutation state remains consumer-controlled.

---

# 37. Error Presentation Boundary

Overlay component does not own business error handling.

Product content may render:

```text
FieldError
InlineError
ErrorState
Toast
```

as appropriate.

Do not make ResponsiveModal automatically convert errors into Toast.

Do not make ConfirmDialog know API failure semantics.

---

# 38. Confirm Failure

If a destructive action fails:

```text
do not falsely close the overlay as if successful
```

unless current product behavior explicitly handles failure elsewhere.

The product consumer controls close-on-success behavior.

ConfirmDialog only exposes actions/state.

---

# 39. Accessible Naming

Every modal/confirmation must have an accessible name.

Preferred source:

```text
visible title
```

If a visible title is intentionally absent, the consumer must provide an equivalent accessible label through the supported underlying API.

Do not ship unnamed modal surfaces.

---

# 40. Accessible Description

Description is optional.

When present, it should be programmatically associated where supported.

Avoid verbose repeated screen-reader content if the body already communicates the same information.

---

# 41. ARIA Boundary

Prefer ARIA generated/managed by the underlying accessible primitive.

Do not manually add conflicting roles such as:

```text
role="dialog"
```

on top of an existing library component that already handles semantics.

Avoid duplicated IDs and conflicting `aria-labelledby`/`aria-describedby`.

---

# 42. Screen Reader Behavior

Verify representative overlays for:

```text
title announced
description announced when relevant
focus enters correctly
actions have names
close control has name
disabled/loading state understandable
```

ConfirmDialog must clearly communicate the consequential action.

---

# 43. Reduced Motion

Overlay enter/exit motion must respect Foundation reduced-motion policy.

Do not remove state visibility when motion is reduced.

A modal should still clearly appear/disappear without relying on animated travel to communicate state.

---

# 44. Overlay Animation

Use restrained motion.

Normal goals:

```text
communicate appearance
communicate sheet direction
avoid abrupt visual context switch
```

Avoid:

```text
bounce
overshoot
large scale effects
long premium animation
```

for routine product workflows.

Trust and speed take priority.

---

# 45. ResponsiveModal API Philosophy

Keep the API small.

Potential generic responsibilities:

```text
open
onOpenChange
title
description?
children
footer/actions?
size?
close affordance?
```

Exact API should adapt the current component rather than forcing this literal shape.

Avoid accumulating props such as:

```text
isWedding
isFinance
isGuestForm
deleteMode
permission
hasDirtyForm
```

---

# 46. Composition Preferred Over Prop Explosion

Prefer slots/composition when content differs substantially.

Example conceptual:

```tsx
<ResponsiveModal ...>
  <ProductForm />
</ResponsiveModal>
```

rather than adding generic props for every product field.

Similarly, footer composition may be preferable when action requirements vary.

Keep enough structure to preserve consistent anatomy without creating a God component.

---

# 47. ConfirmDialog API Philosophy

Generic conceptual inputs:

```text
open
onOpenChange
title
description?
confirm label
cancel label
confirm tone / destructive
loading?
disabled?
onConfirm
```

Exact current API should be preserved where valid.

Do not pass the entity itself merely so ConfirmDialog can derive copy.

Product layer derives:

```text
"Xóa khách mời Nguyễn Văn A?"
```

and passes presentation content.

---

# 48. Domain Leakage Cleanup

The Audit identified inappropriate domain leakage in existing generic confirmation implementation.

During `ConfirmDialog` ADAPT:

```text
remove unrelated domain-specific dependency
```

only if this can be done safely within presentation/component scope.

Do not expand into unrelated auth/business refactoring.

If removing the dependency requires behavioral changes:

> STOP and report.

---

# 49. Legacy Dialog

Canonical status:

```text
Dialog → DEPRECATE
```

Deprecation means:

```text
no new V2 usage
existing consumers continue temporarily
migrate progressively
remove only at zero active usage
```

Do not delete the component at the beginning of Phase 3.

---

# 50. Legacy BottomSheet

Canonical status:

```text
BottomSheet → DEPRECATE
```

Same rules:

```text
no new V2 usage
existing consumers remain until migrated
remove at zero usage
```

Do not replace every BottomSheet consumer automatically.

Some consumers may represent patterns that need separate Product UX review.

---

# 51. Deprecation Signaling

Use the repository's normal deprecation mechanism where useful.

Possible:

```text
JSDoc @deprecated
code comment
lint/import boundary if already supported
documentation
```

Do not add a new lint plugin solely for deprecation enforcement.

The implementation report must list remaining legacy consumers.

---

# 52. Migration Classification

Each legacy overlay consumer should be classified:

```text
A — normal modal workflow
→ ResponsiveModal candidate

B — destructive/confirmation workflow
→ ConfirmDialog candidate

C — presentation sheet / special mobile interaction
→ REVIEW

D — product-specific complex workflow
→ migrate during product wave
```

Do not mass migrate category C/D.

---

# 53. Proof Consumers

Phase 3 may migrate a small number of consumers to validate architecture.

Choose consumers that:

```text
have simple business behavior
exercise desktop/mobile presentation
exercise normal modal
exercise confirmation
have low regression risk
```

Avoid using the most complex Wedding Guest/Finance workflow as the first proof.

---

# 54. Product-Specific Dialogs

Components such as:

```text
ImportDialog
ExportDialog
Wedding Guest forms
Member dialogs
Finance forms
```

remain product-specific even if they compose ResponsiveModal.

Correct:

```text
ImportDialog
    ↓
ResponsiveModal
```

Incorrect:

```text
ResponsiveModal
    ↓ contains CSV business logic
```

---

# 55. Import/Export Boundary

CSV Import/Export mobile capability is a Product UX decision and not an Overlay Architecture decision.

Overlay migration must not silently:

```text
add mobile CSV capability
remove mobile CSV capability
change import/export workflow
```

It may only provide the responsive surface needed when the product flow is explicitly migrated.

---

# 56. Permission Boundary

Generic overlays never resolve:

```text
Owner
Editor
Viewer
canDelete
canManageAll
module access
```

Product composition decides whether an action is available.

Example:

```tsx
{canDelete ? (
  <ConfirmDialog ... />
) : null}
```

Do not pass role data into ConfirmDialog to decide authorization.

---

# 57. Business Mutation Boundary

Generic overlays do not import:

```text
services
repositories
Firebase
business mutation hooks
domain entities
```

They expose events.

Product composition performs mutations.

---

# 58. Route Boundary

ResponsiveModal does not decide whether a detail should be:

```text
route
modal
sheet
```

at the product architecture level.

It only provides overlay mechanics for flows already approved as overlays.

Do not convert route-based details into modals during this wave.

---

# 59. Overlay and Toast

Toast remains:

```text
ADAPT / DEFER
```

Overlay Architecture should not redesign Toast.

Ensure z-index/layering does not make existing Toast unusable.

Whether Toast appears above an overlay should follow current product feedback needs and Foundation layering.

---

# 60. Overlay and Dropdown/Popover

Dropdowns/select menus inside an overlay must remain usable.

Verify:

```text
portal stacking
focus
click interaction
z-index
scroll
```

Do not solve stacking issues with arbitrary z-index escalation.

Fix layering at the appropriate semantic layer.

---

# 61. Overlay and Date Picker

Date/date-time controls inside overlays are a required integration check.

Verify:

```text
calendar/popover visible above surface
keyboard/focus works
mobile behavior usable
no clipping
```

Do not change DateField data semantics to solve overlay layout.

---

# 62. Overlay and File Upload

File upload flows may appear inside product dialogs.

Overlay Architecture must not alter:

```text
file validation
upload limits
storage behavior
business import rules
```

Only presentation/scroll/focus behavior is in scope.

---

# 63. Overlay Width Ownership

Generic modal sizes may cover common use cases.

Product-specific dialogs may request a supported size.

Avoid arbitrary consumer classes like:

```text
max-w-[873px]
```

when a canonical size fits.

But do not force a complex product workflow into an unsuitable width merely to eliminate one-off values.

Classify true exceptions.

---

# 64. Full-Screen Overlay

Do not introduce full-screen modal as a default variant.

A full-screen workflow is a significant UX mode and requires demonstrated need.

Mobile bottom sheet and full-screen mobile page are not interchangeable.

---

# 65. Confirmation Copy

Design System does not own product copy.

Product should provide clear confirmation language.

Preferred pattern:

```text
Title:
specific action

Description:
consequence/context

Confirm:
explicit verb
```

Avoid generic product copy such as:

```text
Bạn có chắc không?
OK
```

when a specific action can be stated.

This is a composition guideline, not domain logic inside ConfirmDialog.

---

# 66. Destructive Button Placement

Use one canonical V2 confirmation action hierarchy.

Do not allow every module to arbitrarily swap visual prominence/order unless there is a product-specific accessibility/usability reason.

Exact order should follow the approved Go Plan V2 convention and existing locale behavior.

---

# 67. Close During Mutation

Do not define a universal rule that every overlay must remain open or closeable during mutation.

Generic components expose state.

Product flows decide whether:

```text
close disabled
cancel disabled
backdrop dismissal disabled
```

is necessary.

Avoid trapping users unnecessarily.

---

# 68. Form Submission

ResponsiveModal must not intercept native/product form submission unless its current API explicitly supports a generic mechanism.

Preferred:

```text
ProductForm
↓ owns submit
ResponsiveModal
↓ owns surface
```

Footer buttons may use native form association where appropriate.

Do not duplicate submit handlers across modal and form.

---

# 69. Semantic HTML

Overlay content should preserve semantic HTML:

```text
heading
form
fieldset where appropriate
labels
buttons
```

Do not replace semantic content with generic clickable containers during visual migration.

---

# 70. Scroll Lock

If the underlying overlay library manages body scroll lock:

> preserve it.

Do not add a second independent scroll-lock mechanism.

Verify mobile Safari/PWA behavior if relevant to current supported browsers.

---

# 71. Browser Back

Do not introduce browser-history integration into generic overlays unless current architecture already uses it.

Opening/closing a modal should not unexpectedly alter routes/history in Phase 3.

Route-modal architecture is outside scope.

---

# 72. SSR / Hydration

If Go Plan uses Next.js client/server rendering boundaries, preserve current overlay client-component requirements.

Do not move large product trees to client components merely because an overlay primitive needs client-side state.

Keep client boundaries as narrow as practical.

---

# 73. Performance

Overlay implementation should not eagerly render expensive hidden product content when current architecture avoids it.

Preserve lazy/conditional rendering where appropriate.

Do not optimize prematurely with a new abstraction that complicates accessibility.

---

# 74. Testing Strategy

Use the existing repository test stack.

Prioritize interaction contracts.

Representative tests:

```text
opens
closes
Escape behavior
backdrop behavior where supported
title/description semantics

focus returns
confirm action fires once
cancel action
loading prevents duplicate confirm
disabled confirm
responsive rendering behavior where testable
```

Do not introduce a new test framework.

---

# 75. ConfirmDialog Tests

At minimum verify:

```text
confirm callback
cancel callback
accessible title
destructive action semantics
loading/disabled state
no duplicate confirm
focus behavior where test tooling supports it
```

Business mutation success/failure belongs to product tests.

# 76. ResponsiveModal Tests

At minimum verify:

```text
close affordance
title/description
```


and specifically:

```text

safe area
scroll

virtual keyboard
long content
```

# 80. Business Regression Contract

Overlay migration must not alter:

```text
mutation behavior
save behavior
delete behavior
permission behavior
validation
data serialization
financial calculations
Wedding Guest invariants
Debt semantics
member lifecycle
routing
CSV business rules
```

A dialog looking different is expected.

The action behind it behaving differently is a regression unless separately approved.

# 88. Stop Conditions

```text

changing permission logic
```

# 89. Rollback Strategy

Overlay Architecture must be independently rollbackable.

Prefer:

```text
adapt canonical overlay components
add compatibility
migrate small proof consumers
deprecate legacy imports
```

Avoid deleting legacy implementations before replacement coverage is proven.

# 92. Canonical Overlay Principle

Overlay architecture should answer:

```text
How is focused content presented?
How does it adapt between mobile and desktop?
How is focus managed?
How is the surface dismissed?
How are actions arranged?
Which accessibility semantic is required?
```

It must never answer:

```text
Can this user delete?
How is this guest removed?
How is this expense saved?
Should CSV import exist on mobile?
What business mutation should run?
```

> **Share overlay mechanics and visual grammar; preserve interaction semantics and product ownership.**
