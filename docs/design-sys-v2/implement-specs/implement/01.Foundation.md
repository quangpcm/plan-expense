# Go Plan — Design System V2

# 01. Foundation Implementation Specification

**Version:** 1.0
**Status:** APPROVED SPEC — Ready for Wave 1 Implementation
**Phase:** Design System V2 / Foundation
**Scope:** Presentation foundation only

## 1. Purpose

This specification defines how the approved Design System V2 Foundation is introduced into the existing Go Plan codebase.

Foundation includes:

- Color
- Typography
- Spacing
- Radius
- Border
- Elevation
- Focus
- Motion
- Responsive breakpoints
- Base surface/body treatment

The objective is:

> Establish one canonical semantic presentation foundation without changing existing product behavior.

This is infrastructure for later primitives, components, patterns and Pilot migrations. It is not a broad UI redesign.

## 2. Source of Truth

Implementation precedence:

Business invariants / existing behavior → Design System V2 Sections 1–16 → `3.AuditDecisionRecord.md` → `2.CodebaseAuditReport.md` → existing style implementation.

The Audit Report is authoritative for what currently exists. The Audit Decision Record is authoritative for disposition, boundary, severity and migration decisions.

## 3. Scope

Wave 1 may implement or normalize semantic color tokens, semantic text/surface/border tokens, brand/status/focus tokens, spacing, typography roles, radius, elevation, motion, reduced-motion behavior, responsive breakpoint contract, and base body/background/text treatment.

Wave 1 may update central styling/theme configuration needed to expose those tokens.

Only small representative consumer migrations are allowed when needed to verify the foundation.

## 4. Non-Scope

Do not use Foundation implementation to redesign Dashboard, Wedding Overview or Wedding Guest; replace Card usages globally; build MetricGroup/DataRow/EntityList/FilterBar; replace Dialog/BottomSheet; refactor modules; change business logic, Service, Repository, Firestore schema/rules, permissions, routing, PlanType behavior, terminology or financial calculations.

## 5. Mandatory Repository Verification

Before modifying code, inspect the actual repository and identify:

- global CSS entry;
- Tailwind/theme configuration;
- CSS variable definitions;
- existing theme helpers;
- font setup;
- radius/shadow variables;
- animation utilities;
- breakpoint configuration;
- dark-mode scaffolding if any;
- shared class utilities such as `cn()`.

Use the existing styling stack. Do not introduce a new CSS-in-JS library, theme library, Tailwind plugin, component framework or token package unless separately approved.

## 7. Token Architecture

Use:

```text
RAW / REFERENCE VALUES
        ↓
SEMANTIC TOKENS
        ↓
COMPONENT / PATTERN USAGE
```

Consumers should prefer semantic meaning over raw color identity.

## 8. Token Naming

Token names describe role, not appearance.

Preferred roles include:

```text
background / foreground
surface / surface-subtle / surface-raised
text-primary / text-secondary / text-muted
border / border-strong
brand / brand-foreground
interactive-hover / interactive-active
success / warning / danger / info
focus-ring
overlay
```

Avoid product-facing canonical names such as `blue`, `green`, `red`, `gray-card`, `wedding-pink` or `travel-blue`. Raw palette/reference variables may use color names internally.

## 9. Color Architecture

Minimum semantic groups:

```text
brand.*
surface.*
text.*
border.*
interactive.*
status.*
focus.*
overlay.*
```

An optional `plan.*` expression layer is allowed only when required by approved Plan-Type Expression.

## 10. Brand

Go Plan brand direction is violet/indigo → blue → cyan. The gradient is identity, not a default fill for ordinary surfaces.

Use brand expression selectively for identity, approved primary CTA, active/selected identity and small premium emphasis.

Do not apply gradients to every card, header, metric, icon container, list row or large content background.

Minimum conceptual roles:

```text
brand.primary
brand.primary-hover
brand.primary-active
brand.foreground
brand.accent
brand.subtle
brand.gradient-start
brand.gradient-middle
brand.gradient-end
```

Exact raw values must come from the approved Design System V2 source. If exact numeric values are not specified, preserve compatible existing values or flag the unresolved value; do not invent a new palette.

## 11. Surface

Support:

```text
surface.page
surface.default
surface.subtle
surface.raised
surface.overlay
```

Use spacing, typography, surface and border before reaching for elevation. Do not make every section boxed.

## 12. Text

Support:

```text
text.primary
text.secondary
text.muted
text.disabled
text.inverse
text.link
```

Migrated V2 consumers should use semantic roles rather than raw slate/blue/emerald classes when an equivalent semantic role exists.

## 13. Borders

Support:

```text
border.default
border.subtle
border.strong
border.focus
```

Default borders should remain quiet. Strong borders are for explicit separation/state, not ordinary decoration.

## 14. Status

Canonical semantics:

```text
status.success
status.warning
status.danger
status.info
```

Where useful, expose foreground/surface/border roles. Do not create domain tokens such as `status.rsvpConfirmed` or `status.expense`.

## 15. Finance Color Invariant

Normal monetary values are neutral by default.

Do not implement `Income = green` and `Expense = red` as a global rule.

Examples:

```text
Tổng chi — 12.500.000đ → neutral
Tổng thu — 20.000.000đ → neutral
Vượt ngân sách +2.500.000đ → danger
Bạn được nhận lại 1.200.000đ → success
```

Directional income/expense colors may remain for narrow transaction-direction use. Do not mass-replace existing green/red classes without semantic inspection.

## 16. Interactive and Focus

Foundation should support consistent interactive states: default, hover, active, disabled and selected.

Focus visibility is P1 and mandatory. Provide a canonical `focus-visible` treatment with ring color, width and offset semantics. It must be visible on normal and brand surfaces. Never remove outline without a replacement.

## 17. Overlay Foundation

Provide the semantic values later overlays need, such as backdrop, overlay surface and overlay elevation. Do not migrate overlay components in this wave.

## 18. Plan-Type Expression

Potential roles such as `plan.travel.accent`, `plan.wedding.accent`, etc. are presentation-only and must come from current supported PlanTypes/configuration.

They may influence accent, small decorative highlight, icon emphasis and selected identity.

They must not affect spacing, typography, radius, component architecture, permission, business behavior or accessibility. Do not add PlanType branching to core primitives.

## 19. Dark Mode

Dark Mode is not a Foundation Wave deliverable unless already active. Preserve existing scaffolding and avoid token naming that makes future dark mode difficult. Do not add a theme switcher or full dark palette in this wave.

## 20. Typography

Keep the approved/current font family (Inter unless upstream V2 explicitly changes it). Formalize semantic roles rather than introducing a decorative font.

Minimum roles:

```text
page-title
section-title
component-title
body
body-strong
metadata
caption
metric-lg
metric-md
metric-sm
```

Use CSS utilities, Tailwind extensions, recipes or variables according to the existing stack. Do not create React wrappers for every typography role.

Typography roles define visual hierarchy; consuming components remain responsible for semantic HTML headings.

Do not mass-replace every existing text utility in Wave 1. Define and verify the canonical roles; broad migration occurs with component/pattern waves.

## 21. Spacing and Density

Use a 4px base grid and the approved practical scale, including values equivalent to 4, 8, 12, 16, 20, 24, 32, 40 and 48 where approved.

Use tokens for repeated component padding, section rhythm, control/list/layout gaps. Genuine one-off geometry may remain local.

Density differences should primarily use spacing, control height, row padding and grouping—not a second typography/color/component system.

## 22. Radius

Canonical roles:

```text
radius.sm  = 8px
radius.md  = 12px
radius.lg  = 16px
radius.xl  = 20px
radius.full
```

If the approved V2 source specifies different exact values, that source wins.

Legacy `rounded-[24px]` must not automatically become a canonical token. Classify the surface and migrate toward an approved role later.

Do not globally rewrite radius values in Wave 1.

## 23. Elevation

Elevation is semantic hierarchy, not decoration.

Minimum roles:

```text
elevation.none
elevation.raised
elevation.overlay
```

Ordinary content surfaces generally use none. Raised surfaces use elevation intentionally; overlays use overlay elevation.

Do not preserve a large arbitrary legacy shadow scale merely because it exists. Define canonical elevation now and migrate consumer shadows progressively.

## 24. Motion and Reduced Motion

Keep the motion vocabulary small, e.g. fast/normal durations and standard/enter/exit easing where required.

Motion communicates state change, spatial transition, feedback and overlay lifecycle—not generic “premium” animation.

Support `prefers-reduced-motion: reduce`. Minimize decorative animation while preserving understandable essential state transitions.

## 25. Responsive Foundation

Canonical model:

```text
Mobile   0–767
Tablet   768–1023
Desktop  >=1024
```

Map this contract to the existing Tailwind/CSS breakpoint system.

Three supported tiers do not require every component to have three layouts. Distinct Tablet treatment is only needed when it solves an actual usability/layout problem.

Do not rewrite all responsive classes in Wave 1. Verify/document the mapping and use it for future V2 work.

## 26. Base Application Treatment

Define the canonical body/page background, default foreground, font family and focus/selection compatibility.

Do not add large decorative gradients to the global body.

Go Plan manages money, wedding, debt, shared planning and travel. Foundation should prioritize clarity, trust, hierarchy, scanability and predictability over glassmorphism, heavy gradients, excessive shadow/color or decorative animation.

Premium perception should come from consistency and refinement.

## 27. CSS Variable / Tailwind Integration

Prefer the repository's existing styling mechanism.

If semantic CSS variables integrated with Tailwind already exist, extend that model. If Tailwind theme config is canonical, integrate there.

Avoid two manually duplicated sources such as `tokens.ts` plus unrelated CSS variable values unless the current architecture requires and documents the mapping.

The implementation report must state:

- where canonical values are defined;
- how Tailwind consumes them;
- how plain CSS consumes them;
- how legacy consumers coexist.

Do not create TypeScript token objects merely for completeness when all consumers are CSS/Tailwind. Runtime token exports are justified only by real runtime needs.

## 28. Charts and Icons

Charts may need explicit series colors. Chart colors are not automatically status semantics. Product chart composition remains responsible for meaningful mapping.

Lucide remains the canonical icon family. Foundation may define sizing guidance but should not wrap every Lucide icon or introduce another icon library.

## 29. Z-Index

If repository evidence shows inconsistent z-index usage, define only the minimal roles required for future work, such as base, sticky, dropdown, overlay and toast. Do not create a large layering scale without need.

## 30. Legacy Compatibility

Wave 1 must allow V1 and V2 consumers to coexist.

Temporary aliases are acceptable when they prevent broad breakage, have an unambiguous semantic mapping and a clear V2 target. They must not become a second permanent system.

If one legacy variable means different things in different contexts, do not alias it blindly; migrate those consumers contextually later.

## 31. No Mass Codemod

Do not run repository-wide replacements such as:

```text
text-blue-* → text-brand
text-green-* → text-success
rounded-[24px] → rounded-xl
shadow-* → elevation-raised
```

Visual similarity does not prove semantic equivalence.

## 32. Representative Verification

If real UI consumers must be changed to verify Foundation, choose only a small number of low-risk, business-neutral/shared surfaces.

Changes must be small, reversible and presentation-only. List every representative consumer changed and why.

Do not begin Pilot migration under the name of Foundation verification.

## 33. Accessibility Foundation

Foundation must enable later components to meet WCAG AA intent, visible focus, sufficient contrast, reduced motion, touch-target guidance and non-color-only status semantics.

Check semantic foreground/background combinations for contrast where practical. Do not add a dependency solely for contrast tooling unless approved.

Touch target guidance remains minimum 44×44px, with safe hit-area expansion allowed.

Color alone must not be the only carrier of product status.

## 34. File Ownership and New Files

Exact paths must follow repository evidence. Prefer editing existing central theme/foundation files rather than creating parallel systems.

Create a new file only when it has a clear ownership role that does not already exist. “Cleaner folder structure” is not sufficient reason.

Do not move unrelated files in Wave 1.

## 35. Import Boundary

Foundation must not import Wedding, Travel, Debt or Finance business types; Member roles; repositories; Firebase; or product entities.

Presentation-level PlanType expression may consume an existing approved presentation/configuration identifier only when architecture supports it. Avoid business-module imports into Foundation.

## 36. Business and Permission Protection

Foundation must not affect financial totals, settlement, fund balance, debt calculations, guest invitation/attendee/gift semantics, Todo/Milestone behavior, Travel Activity behavior, member lifecycle or permissions.

No Foundation token/component may resolve Owner/Editor/Viewer, `canEditAllExpenses` or module access.

Product/domain layers resolve capability; Foundation only presents the resulting state.

## 38. Required Verification

Run the repository's existing applicable commands for typecheck, lint, tests and build. Inspect repository scripts rather than inventing command names.

If a command fails because of a pre-existing issue, record it and determine whether Wave 1 caused it.

Visually verify representative Mobile, Tablet and Desktop widths for app rendering, base background/text, brand token resolution, focus visibility, global contrast and absence of accidental global radius/shadow rewrites.

Accessibility verification should include keyboard focus visibility, contrast of new semantic combinations, reduced-motion CSS behavior and confirmation that no global outline is removed without replacement.

## 39. Regression Manifest

The implementation report must explicitly state:

```text

Existing feature capability changed: NO
```

Any YES means the Foundation wave exceeded approved scope and requires review.

Distinguish implemented, verified, deferred and not applicable.

Do not claim “Design System V2 migration complete.” Correct wording is “Foundation Wave complete.”

## 41. Rollback Strategy

Keep Foundation independently rollbackable. Prefer central token/config changes and minimal consumer edits.

Do not mix Foundation with large component rewrites.

If a global visual regression occurs, Foundation should be revertible without reverting unrelated product work.

## 42. Stop Conditions

STOP and request review if Foundation appears to require:

- business logic changes;
- data model changes;
- permission changes;
- Firestore changes;
- major component API rewrites;
- broad consumer migration;
- a new styling framework/component library;
- a new PlanType architecture;
- arbitrary resolution of conflicting approved token values.

## 43. Completion Gate

When Wave 1 passes the acceptance criteria:

```text
FOUNDATION ✓
```

the next specification is `02.CorePrimitives.md`, covering the approved primitive migration such as Button, Input, Textarea, Badge, Avatar, Switch, DropdownSelect and Date/DateTime controls.

## 44. Canonical Principle

Later V2 layers should be able to answer:

```text
What color should this mean?      → semantic color
What hierarchy is this text?      → typography role
How separated should this be?     → spacing scale
What kind of surface is this?     → surface + radius + elevation
How does keyboard focus appear?   → focus foundation
How should it respond?            → responsive contract
```

without inventing a local visual language.

> **Centralize visual decisions; preserve product semantics.**

Foundation should make Go Plan feel like one coherent product without forcing Wedding, Travel, Finance, Debt, Members and future modules into the same generic product semantics.
