## Fix 1 — Member nested interactive DOM: **APPROVED, IMPLEMENTED**

**Original analysis (unchanged, kept for the record):**

Traced two ways to make the avatar-change button and `Collapsible`'s own trigger button separate
DOM siblings instead of nested:

1. **Move the avatar button entirely outside `<Collapsible>`** (as a flex sibling of the whole
   component instance) — achievable with **zero** change to `Collapsible`'s public API. Rejected:
   this would nest `Collapsible`'s own wrapper (including its expand/collapse content area) one
   level deeper, inside a `flex-1` div next to the avatar — so the expanded edit form
   (`Input`/`DropdownSelect`/`ModuleAccessEditor`/buttons) would be indented and narrowed by the
   avatar's width instead of spanning the full card width, exactly as it does today. That is a
   real, visible regression to "expanded/collapsed behavior," which the instructions require
   preserving.
2. **Add an optional `leading?: ReactNode` prop to `Collapsible`**, rendered as a sibling
   immediately before the trigger `<button>` but still inside `Collapsible`'s own full-width
   wrapper. This keeps the collapsed row's avatar position and the expanded form's full width
   pixel-identical to today, and fully eliminates the nested-button structure (avatar and trigger
   become true DOM siblings — no nesting, so no event-bubbling double-action is possible either).
   Backward-compatible: `Collapsible`'s 3 other consumers (`members-tab.tsx`,
   `member-management-panel.tsx` ×2) never pass `leading`, so their rendered output is unchanged.

Option 2 is the only one that preserves the existing UX exactly, but it is a public prop addition
to a shared Design System component. Per explicit instruction — "If preserving the existing UX
requires changing the shared Collapsible public API: STOP and report the proposed API change
before implementing it" — this is a STOP condition. Proposed change, not yet applied:

```tsx
// collapsible.tsx — additive prop, no change to existing behavior when omitted
type CollapsibleProps = {
  title?: string;
  description?: string;
  icon?: ReactNode;
  header?: ReactNode;
  leading?: ReactNode; // NEW — optional interactive sibling rendered before the trigger button
                        // (not inside it), so a consumer's own interactive element never nests
                        // inside Collapsible's own trigger.
  defaultOpen?: boolean;
  className?: string;
  children: ReactNode;
};

// render: wrap the trigger button in a flex row with `leading` as its sibling; button's own
// className changes from `w-full` to `flex-1` (visually identical when `leading` is absent).
<div className="flex items-center gap-3">
  {leading}
  <button type="button" className="flex min-h-11 flex-1 items-center justify-between gap-3 text-left" ...>
    {/* unchanged */}
  </button>
</div>
```

`member-list.tsx` would then split `summary` into `avatarButton` (unchanged markup) and
`nameBlock` (unchanged markup, minus the avatar), and use
`<Collapsible header={nameBlock} leading={avatarButton}>{editForm}</Collapsible>` — no other
change to permissions, avatar editing, member actions, or mobile/desktop behavior.

**Implementation (this pass), exactly as proposed and approved:**

- `collapsible.tsx`: added `leading?: ReactNode` to `CollapsibleProps`. The trigger `<button>` is
  now wrapped in `<div className="flex items-center gap-3">{leading}<button ...>`, with the
  button's own className changed from `w-full` to `flex-1`. When `leading` is omitted — all 3 other
  consumers (`members-tab.tsx`, `member-management-panel.tsx` ×2) — a single `flex-1` child of a
  flex row with no siblings renders at the exact same width as `w-full` did, so their output is
  unchanged. No other prop, behavior, or export was touched.
- `member-list.tsx`: `summary` split into `avatarButton` (the exact same `<button aria-label=...>`
  markup, byte-identical) and `nameBlock` (the exact same name/badges/secondary-line markup,
  byte-identical, minus the avatar). The non-collapsible branch
  (`!canManageMembers || member.role === 'owner'`) still renders `summary` (now composed as
  `avatarButton` + `nameBlock` inside the same wrapping `flex items-center gap-3` div it always
  used) — unaffected by this change, since it never used `Collapsible` in the first place. The
  collapsible branch changed from `<Collapsible header={summary}>{editForm}</Collapsible>` to
  `<Collapsible header={nameBlock} leading={avatarButton}>{editForm}</Collapsible>`. No change to
  `canManageMembers`/`disabled` gating on the avatar button, no change to `editForm`, no change to
  any handler, service call, or menu item.

## Fix 2 — Settlement confirmation: **IMPLEMENTED**

Added `ConfirmDialog` gating to both actions, using the request/perform pattern proven across
Wave 0/4:

- **`SettlementSuggestionCard`** ("Xác nhận đã chuyển"): the `Button` now opens a local
  `showConfirm` state instead of calling `onConfirm` directly. `ConfirmDialog` description reads
  `{fromName} → {toName} · {amount}. Khoản chuyển này sẽ được ghi nhận là đã hoàn tất.` —
  `confirmVariant="default"`, matching the original button's own un-overridden (primary) color,
  per the instruction not to make every action destructive-red. Confirm calls the existing
  `onConfirm` prop exactly once, then closes; Cancel/backdrop/Escape close with zero calls.
- **`SettlementList`** ("Hủy" on a completed settlement): the per-row "Hủy" button now sets a
  local `pendingCancel` (the full `SettlementDocument`) instead of calling `onCancel` directly. One
  `ConfirmDialog` at the list level (not per-row) reads `{fromMember} → {toMember} · {amount}. Xác
  nhận đã hoàn tất trước đó sẽ bị hủy.` — `confirmVariant="destructive"`, since this reverses
  already-recorded financial history (a more consequential action than recording a new transfer),
  matching the original "Hủy" link's own hover-to-rose-600 cue. Confirm calls the existing
  `onCancel` prop exactly once with the same `SettlementDocument`, then clears; Cancel/backdrop/
  Escape clear with zero calls.
- **`SettlementSuggestionCard`'s `onConfirm` prop type** changed from `MouseEventHandler<HTMLButtonElement>`
  to `() => void` — confirmed safe: every existing caller (`settlement-suggestion-list.tsx`,
  `settlement-workspace.tsx`) already wires it as `onConfirm={() => onConfirm(suggestion)}`, a
  zero-argument closure that never used the click event. This is a local prop-type correction on a
  non-exported type, not a shared API change.
