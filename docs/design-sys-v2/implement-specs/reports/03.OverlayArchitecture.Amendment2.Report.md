## 2. Bug 1 implementation/result

Added `data-vaul-no-drag` to `ResponsiveModal`'s mobile content-scroll wrapper (the
`overflow-y-auto` div wrapping `children` inside `Drawer.Content`) — vaul's own supported opt-out,
checked directly in its `shouldDrag()`. Nothing else in the mobile branch changed: no
`VisualViewport` JS, no `setTimeout`, no `useEffect` repositioning, no body-scroll hacks, no global
touch handlers, and no per-consumer `TodoVendorForm` patch. The drag handle and header sit outside
this wrapper and are unaffected.

## 3. Bug 2 implementation/result

Migrated exactly the two named consumers in `plans/[planId]/page.tsx` —
`statisticMemberDrilldown` and `statisticMilestoneMemberDrilldown` — from `BottomSheet` to
`ResponsiveModal`. `onClose={...}` became `onOpenChange={(next) => { if (!next) setX(null); }}`;
`showCloseButton` was dropped (redundant — `ResponsiveModal` always renders a close button).
`TimelineList`'s props, the drilldown state variables, the title logic, and `onSelectExpense`/
`onSelectIncome` wiring to `setDetailExpense`/`setDetailIncome` are byte-for-byte unchanged. Both
migrated modals were given `size="sm"` — this preserves `BottomSheet`'s own previous desktop width
(`md:max-w-md`, read from `bottom-sheet.tsx`'s own JSX) rather than leaving them newly-unconstrained
after the migration, which would have reintroduced the exact "excessively wide" problem this same
amendment fixes elsewhere. This wasn't explicitly requested but was necessary to avoid a
self-inflicted regression; flagged here rather than done silently.

No other `BottomSheet` consumer was touched (Header menu, `PlanningTab`'s drilldown,
`member-actions-menu.tsx`'s "⋮" menu all remain `BottomSheet`, per their unaffected KEEP
disposition).

`docs/ui-modal-conventions.md` §4 now includes the required rule (§4.1): a `BottomSheet` may only
remain for menu/read-only-drilldown use when it cannot coexist with, contain, or be contained in a
`ResponsiveModal` interaction chain; otherwise it must migrate. The two migrated drilldowns are
cited as the applied example; the three untouched KEEP `BottomSheet`s are cited as the reason the
rule doesn't apply to them (none ever opens a `ResponsiveModal` from inside itself).

## 4. Bug 3 API contract

```ts
type ResponsiveModalProps = {
  open: boolean;
  onOpenChange: (open: boolean) => void;
  title: string;
  description?: string | undefined;
  children?: ReactNode;
  className?: string | undefined;
  size?: 'sm' | 'md' | 'lg' | 'xl' | undefined; // NEW
};
```

Approved mapping applied exactly: `sm → max-w-md`, `md → max-w-xl`, `lg → max-w-2xl`,
`xl → max-w-4xl`. Applied only to the desktop `Dialog.Content` class list; the mobile
`Drawer.Content` branch is untouched and was already always full-width by construction (confirmed
unaffected — see §9). Class merge order is exactly base → size → caller `className`, so an existing
consumer's own `className` (e.g. `max-w-2xl overflow-y-auto`) still wins over `size` for any
conflicting utility, per `tailwind-merge`'s last-wins rule — existing `className`-based consumers
needed zero changes and remain fully in control. Omitting `size` changes nothing: no default
max-width was introduced.

## 8. Mobile drawer scroll verification (Bug 1)

Same temp route, a form modeled on `TodoVendorForm`'s field shape (short text input, a "Link tham
khảo"-equivalent input, a "Mô tả ngắn"-equivalent textarea, tall enough to require scrolling) inside
a mobile `ResponsiveModal`, at 390×844 with touch emulation enabled.

```
data-vaul-no-drag present on the content wrapper                    PASS
Content scrollTop confirmed at 0 before the gesture                 PASS
A drag/scroll gesture starting inside the form at scrollTop=0       PASS — form remained open
  does NOT dismiss the drawer
Dragging the visible drag handle down still dismisses intentionally PASS
Console/runtime errors                                              0
```

One limitation, disclosed rather than glossed over: the synthetic mouse-based drag used to emulate
a touch-scroll did not itself produce a nonzero `scrollTop` afterward — Chromium/Playwright's
synthetic pointer events don't reliably reproduce native touch-scroll momentum on an
`overflow-y-auto` element the way a real finger gesture does. The relevant, provable claim — **the
gesture no longer dismisses the drawer** — was verified directly; whether the content visibly
scrolls under a real finger is part of the required manual check below.

**REAL IPHONE MANUAL CHECK REQUIRED** — this automated pass cannot exercise vaul's `isIOS()`-gated
Safari-specific keyboard workarounds (`preventScrollMobileSafari()`) at all, confirmed by reading
vaul's source: that entire code path is skipped outside real iOS. The following must be confirmed
on a real iPhone before this bug is considered fully closed:
- Focused input ("Link tham khảo") remains visible when the keyboard opens.
- Typing multiple lines into "Mô tả ngắn" keeps the textarea visible and usable.
- Scrolling the form while the keyboard is open reaches every field and the submit button.
- The footer (submit/cancel) remains reachable once the keyboard is open.
