## 3. Candidates rejected and why

**`WeddingGuestList` → `DataRow`: not adopted.** Evaluated against the real implementation, not
assumed. The row's two independent interaction zones — a large clickable area (guest name +
subtext + badges + attendee/gift summary → opens edit) and a separate trailing delete icon button
— are exactly the case `DataRow`'s own contract flags as *not* its interactive mode: "If trailing
already contains its own buttons/menu, prefer leaving the row non-interactive with explicit
trailing actions instead." Building this with `DataRow` would mean passing the entire existing row
markup as one opaque `main` node with `trailing={deleteButton}`, which does not simplify anything
— `DataRow` would only contribute the same `flex items-center gap-2` wrapper the row already has
today. No structural change made; **kept as-is**, matching the Pre-Code's own framing that
"not adopting Metric/DataRow is an acceptable Pilot result."

**Import CSV dialog: not migrated, per approval.** Legacy `Dialog` kept unchanged. Recorded as
deferred migration debt (§8) — its 3-step wizard + wide preview table doesn't cleanly fit
`ResponsiveModal`'s current size contract (no `size` prop, className-override only).

**`WeddingGuestGroupTable`, `RsvpDonutChart`, `WeddingGuestCompositionCard`/`Rows`, `ShareBar`,
`WeddingGuestImportPreviewTable`, `WeddingGuestGroupNav`: kept product-specific, per approval.**
None of these were touched. `WeddingGuestGroupNav`'s chip selector was reviewed against `Badge`
during implementation and found not "trivially clean" (chip has selected/hover states and an
inline manage-groups trigger baked into one row — not a simple label+tone swap), so left alone per
the "unless trivially clean" qualifier.

## 7. Findings / deferred debt

```text
1. Import CSV dialog (legacy Dialog) — deferred per approval. Still uses the legacy, deprecated
   Dialog component. Structural blocker: ResponsiveModal has no `size` prop for its wide 3-step
   preview table. Revisit during Rollout once ResponsiveModal's size contract is addressed, or if
   a specific approved width-override pattern emerges from another consumer first.

2. WeddingGuestExportDialog's desktop-only gating is now enforced by exactly one mechanism (the
   trigger button's `hidden lg:inline-flex` class) instead of two (trigger + the dialog's own
   `hidden lg:flex` wrapper, which had no equivalent in ResponsiveModal and was removed). This is
   a deliberate simplification, not a gap: the trigger gate is the one that actually determines
   real user-facing availability; the second gate was pure redundancy. Recorded for visibility,
   not as an open risk.

3. Metric/MetricGroup adoption for WeddingGuestStatTiles trades a small amount of pixel fidelity
   for consistency, disclosed explicitly: (a) icon (`leading`) now sits beside the full label+value
   stack rather than beside the label only, a minor layout shape change; (b) `Metric`'s single
   `size` prop can't reproduce the original's responsive `text-lg → text-2xl` scale-up at `lg:`,
   so the tile value stays one size (`sm`) across breakpoints; (c) `MetricGroup`'s `density="compact"`
   (`gap-3`) doesn't have a tighter mobile option matching the original's `gap-2` below `lg:`. None
   of these affect the four values' distinctness or correctness (§4) — purely presentational,
   consistent with "presentation may improve" migration guidance.

4. WeddingGuestList/DataRow rejection (§3) is a second data point — after Pilot #2's PlanCard/Metric
   rejection — that DataRow's "trailing already has its own actions → don't force interactivity"
   guidance is a real, recurring pattern worth keeping in mind for any future row-anatomy migration
   in this codebase, not just this Pilot's own evidence.

5. Design System backlog — no new items added this Pilot; all items already carried forward from
   the STOP/GO review remain untouched (Progress, Plan-Type tokens, TextAction, NotificationBadge,
   bottom-panel abstraction, global radius migration, Button size="icon"). No new ad hoc radius
   value was introduced — no radius-related code was touched in this Pilot at all.
```
