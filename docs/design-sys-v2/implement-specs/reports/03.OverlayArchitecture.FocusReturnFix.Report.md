## 1. Confirmed root cause

The STOP/GO review's Presence/animation-timing hypothesis was **not confirmed** — re-investigation
this pass found the actual, simpler mechanism by reading Radix's `Dialog.Content` implementation
directly (`node_modules/@radix-ui/react-dialog/dist/index.mjs`):

```js
// DialogContentModal (used whenever Dialog.Root's `modal` is true — the default, and the value
// AlertDialog.Root hardcodes unconditionally):
onCloseAutoFocus: composeEventHandlers(props.onCloseAutoFocus, (event) => {
  event.preventDefault();
  context.triggerRef.current?.focus();
}),
```

Radix's modal `Dialog`/`AlertDialog` does **not** use the generic `document.activeElement`-based
"restore to whatever was previously focused" behavior that `@radix-ui/react-focus-scope`'s
`FocusScope` provides generically (that fallback exists, but only runs when nothing overrides
`onCloseAutoFocus` — see `03.OverlayArchitecture.FocusReturnFix` investigation notes below). For
**modal** dialogs specifically, Radix always calls `event.preventDefault()` and then
`context.triggerRef.current?.focus()` — where `context.triggerRef` is a ref that only
`Dialog.Trigger`/`AlertDialog.Trigger` register themselves into.

**`ResponsiveModal` and `ConfirmDialog` are both fully controlled components that never render a
`Trigger` subcomponent** (`03.OverlayArchitecture.md` §19 explicitly requires preserving this
controlled `open`/`onOpenChange` architecture rather than forcing `Trigger` usage) — they are
opened from arbitrary external elements (a FAB, a menu item, a delete button). Because of this,
`context.triggerRef.current` is **always `null`**, so `null?.focus()` is a guaranteed no-op, on
every close, unconditionally. `event.preventDefault()` had already run by that point too, which
blocks `FocusScope`'s own generic `previouslyFocusedElement` fallback from ever getting a chance to
run instead. This is a deterministic, 100%-reproducible structural mismatch between our
architecture (controlled, Trigger-less) and Radix's default modal behavior (Trigger-based) — not a
timing race, not a StrictMode artifact, not an animation-interaction bug.

**Empirical confirmation (before the fix), via an in-page `focusin`/`focusout` event log:**

```text
focusout  BUTTON[aria-label=Đóng]   dt=6ms
(no further focus events — nothing ever received focus after this)
final focus: <body>
```

Zero `focusin` events after the `focusout` confirms no `.focus()` call on a real, focusable element
ever ran — consistent with `context.triggerRef.current` being `null` and `.focus()` being called on
`null` (a no-op producing no event at all), not with a focus attempt landing on a since-removed
element (which would still fire a `focusin`/`focusout` pair or leave different traces).

**`vaul`'s `Drawer` inherits the identical mechanism.** `node_modules/vaul/dist/index.mjs` confirms
`Drawer.Content` renders `DialogPrimitive.Content` directly (`import * as DialogPrimitive from
'@radix-ui/react-dialog'`), with `modal` defaulting to `true` (`Root`'s destructured default,
`node_modules/vaul/dist/index.mjs:879`) and no `onCloseAutoFocus` interception of its own (vaul
only intercepts `onOpenAutoFocus`, to implement its own `autoFocus` default-`false` behavior —
confirmed unrelated and untouched by this fix). So the mobile branch fails for exactly the same
reason as desktop.

**`ConfirmDialog` was also affected — verification proved it, per the task's explicit
condition.** `@radix-ui/react-alert-dialog`'s `AlertDialogContent`
(`node_modules/@radix-ui/react-alert-dialog/dist/index.mjs:44-68`) is built directly on
`DialogPrimitive.Content` with `Root`'s `modal: true` hardcoded
(`node_modules/@radix-ui/react-alert-dialog/dist/index.mjs:21`), and only overrides
`onOpenAutoFocus` (to focus Cancel safely) — `onCloseAutoFocus` passes straight through to the same
`DialogContentModal` default. Since `ConfirmDialog` never uses `AlertDialog.Trigger` either, it has
the identical `triggerRef.current === null` no-op. Confirmed empirically before fixing:

```text
Desktop (AlertDialog), Cancel-button close: focus → <body>
Mobile (Drawer), Cancel-button close:       focus → <body>
```

## 2. Exact fix

Both `responsive-modal.tsx` and `confirm-dialog.tsx` now:

1. Capture the element that had focus at the moment the overlay opens, via React's documented
   ["adjusting state during render"](https://react.dev/learn/you-might-not-need-an-effect#adjusting-some-state-when-a-prop-changes)
   pattern — comparing the `open` prop against a previous-value `useState`, and calling
   `setTrigger(document.activeElement)` conditionally, during render, only on the exact render
   where `open` transitions to `true`:

```tsx
const [trigger, setTrigger] = useState<HTMLElement | null>(null);
const [wasOpen, setWasOpen] = useState(open);
if (open !== wasOpen) {
  setWasOpen(open);
  if (open) {
    setTrigger(document.activeElement as HTMLElement | null);
  }
}
```

2. Pass an `onCloseAutoFocus` handler to `Dialog.Content`/`Drawer.Content`
   (`AlertDialog.Content`/`Drawer.Content` in `confirm-dialog.tsx`) that calls the library's own
   documented override mechanism — `event.preventDefault()` to stop Radix's internal
   `triggerRef`-based attempt, then focuses the captured element directly:

```tsx
function restoreFocusToTrigger(event: Event) {
  event.preventDefault();
  trigger?.focus();
}
```

No `setTimeout`, no `useEffect`-based restoration, no `document.activeElement` polling, no global
event listeners, no product-specific trigger IDs, and no consumer-facing API change.

## 3. Why this is a supported mechanism, not a hack

- `onCloseAutoFocus` is Radix's own public, documented prop on `Dialog.Content`/`AlertDialog.Content`
  (confirmed in `node_modules/@radix-ui/react-dialog/dist/index.d.mts:78` and
  `@radix-ui/react-alert-dialog/dist/index.d.mts:23`, typed `(event: Event) => void`) —
  it exists specifically so consumers can override the library's default close-focus behavior.
  `confirm-dialog.tsx` already used the equivalent open-side extension point
  (`onOpenAutoFocus`) for exactly this kind of override before this fix; this is the same pattern
  applied to the close side.
- `composeEventHandlers(props.onCloseAutoFocus, radixInternalHandler)` inside Radix's own source
  means **our** handler runs first; calling `event.preventDefault()` inside it stops Radix's
  internal `triggerRef.current?.focus()` from running at all, so there is no double-focus race —
  our handler is the only one that executes.
- The state-capture uses React's own documented pattern for deriving state from a prop change
  during render — not a `useRef` mutation during render (which this project's React Compiler lint
  rule, `react-hooks/refs`, explicitly disallows and initially caught during this fix — see §9) —
  and not a `useEffect`, which would run one tick after commit and risk capturing focus that has
  already moved.

One implementation note worth recording: the first fix attempt used a `useRef` write during
render (the more commonly-seen version of the "capture previous value" pattern) and was caught by
this project's React Compiler lint rule (`react-hooks/refs`, "Cannot access refs during render") —
switched to the `useState`-based variant of the same pattern, which is React's actual documented
form of "adjusting state during render" and is compiler-safe. Recorded here since it's a concrete,
reusable lesson for any future fix needing this same "capture something at prop-transition time,
without an effect" shape in this codebase.
