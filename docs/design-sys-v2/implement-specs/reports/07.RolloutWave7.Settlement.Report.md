## 3. MIGRATE / KEEP / DEFER

| `SettlementList`'s history row | MIGRATE → `DataRow` | Leading(status icon)/main(from→to text + amount + timestamp, single line)/trailing(conditional "Hủy" button) — a plain text row, not an avatar-based identity visual. |

## 5. Rejected candidates + reason

Covered inline in §3. The one candidate most worth calling out: `SettlementSuggestionCard` was
seriously considered for `DataRow` (it does have a nominal leading/trailing shape if forced), but
rejected because its "main" content is not a single piece of information — it's two independently
meaningful identities (payer, payee) connected by a directional arrow that IS the semantic point of
the row. Cramming that into `DataRow`'s single `main` slot would not simplify anything and risks
this wave's explicit P0 concern (transfer-direction fidelity) for no real gain. This mirrors the
named precedent (`WeddingGuestList`/`PlanCard`/Wave 6's `MemberBalanceTable` rejections) rather than
inventing a new justification.

## 7. Settlement before/after equivalence

Method: a mock-props harness (`src/app/wave7-verify-temp/page.tsx`, deleted after use, no
Firestore) with two members named `Alice_RECEIVER`/`Bob_PAYER` and clearly distinct amounts
(777.777₫ balance, 555.555₫ completed settlement, 222.222₫ cancelled settlement) — chosen
specifically so a transposition or reversed direction would be immediately visible, per this
wave's instruction. Driven by Playwright, checked via both text content and a full-page screenshot.

Confirmed exact, correct output:
- `MemberBalanceRowItem`: `Alice_RECEIVER` (adjustedBalance = +777,777) rendered `+777.777 ₫` in
  `rgb(5, 150, 105)` (`--color-success`) with label "Còn được nhận"; `Bob_PAYER`
  (adjustedBalance = −777,777) rendered `−777.777 ₫` in `rgb(220, 38, 38)` (`--color-danger`) with
  label "Cần trả" — sign, magnitude, color, and label all correctly paired per member, not swapped.
- `SettlementSuggestionCard` (unchanged, rendered as part of the same page for context): correctly
  showed `Bob_PAYER → Alice_RECEIVER · 777.777 ₫` — matches `{fromMemberId: 'bob', toMemberId:
  'alice', amount: 777_777}` exactly, confirming the untouched sibling component still works
  correctly alongside the migrated rows.
- `SettlementList` history: a `status: 'completed'` settlement (`fromMemberId: 'bob'`,
  `toMemberId: 'alice'`, amount 555.555) rendered `Bob_PAYER -> Alice_RECEIVER 555.555 ₫` with a
  green check icon, normal (non-strikethrough) text, and a visible "Hủy" button. A
  `status: 'cancelled'` settlement (`fromMemberId: 'alice'`, `toMemberId: 'bob'`, amount 222.222)
  rendered `Alice_RECEIVER -> Bob_PAYER 222.222 ₫` with a gray X icon, **strikethrough** text, and
  **no** "Hủy" button — direction not reversed between the two rows, and the
  `canCancel && isCompleted` gate on the cancel button verified working in both directions (present
  only on the completed one).

## 8. Shared Fund / direction verification

No Shared Fund presentation exists in this module — `SettlementWorkspace`/`SettlementSuggestionCard`/
`SettlementList` all display **member-to-member** transfers only (`fromMemberId`/`toMemberId` are
both plan members; there is no "Fund" party in `SettlementDocument`/`SettlementSuggestion`). Fund
reimbursement/unallocated-balance presentation lives in the Statistic module's `FundBalanceCard`
(Wave 6, already reviewed, not touched again here) — `SettlementSuggestionList` only *references*
`unallocatedFundBalance` in one warning message ("Quỹ chung còn X chưa phân bổ — hãy chỉnh 'Hoàn
cho'...", unchanged, not migrated). No risk of conflating Fund→Member with Member→Member was
present because no Fund-side transfer UI exists in this module to potentially conflate.

Direction fidelity for the member-to-member transfers that do exist is covered in full in §7.

## 9. Targeted interaction verification

No overlay (`ResponsiveModal`/`ConfirmDialog`) was introduced or touched this wave — neither
migrated row passes `onClick` to `DataRow`, so both render as plain non-interactive `<div>`s (per
`DataRow`'s own `isInteractive = Boolean(onClick)` behavior); the real action buttons
("Xác nhận đã chuyển", "Hủy") remain ordinary same-level `<button>` elements inside `trailing`, not
nested inside another interactive element — confirmed this avoids the class of nested-`<button>`
hydration issue found (and left unfixed, as instructed) in Wave 4's `member-list.tsx`.
`SettlementSuggestionCard`'s confirm button and `SettlementList`'s cancel button are both
direct-call, no-confirmation-step actions today (unchanged) — not a `window.confirm`/`BottomSheet`
pattern to migrate, and adding a new confirmation gate where none exists would be a behavior change
beyond this wave's presentation-only mandate (noted in §11, not acted on).
