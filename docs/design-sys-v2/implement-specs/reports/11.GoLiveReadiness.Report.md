# Go-Live Readiness Review

**Scope:** analysis/verification only. No source code was modified. This review synthesizes
existing evidence from all Pilot reports, the STOP/GO review, Rollout Waves 0–7, the Post-Rollout
Design System Review, the Pre-Go-Live Fix Batch, and the Visual Polish report — re-testing nothing
that evidence already covers. Fresh source inspection was limited to two areas with no prior
dedicated evidence: Auth/Entry route guarding, and a final automated-gate re-run.

## 1. Executive decision

Every previously-identified real defect (member nested-button hydration/accessibility issue,
member-actions-menu desktop clipping, Settlement's missing confirmation step, Dashboard money
ellipsis, Members terminology) has been fixed and verified in the reports leading up to this one.
Fresh inspection of Auth/Entry — the one release-critical surface with no prior dedicated report —
found route guarding intact and no unauthenticated-access gap. The automated release gate
(typecheck/lint/test/build) is clean against the same pre-existing, unrelated lint baseline carried
through every prior wave. No new P0 was found in this review.

## 6. Financial trust review

- **Totals** (plan-level, statistic-level): computed exclusively by `statistic.service.ts` and
  `utils/fund-balance.ts`; confirmed zero diff to either across every Wave that touched a surface
  displaying their output (0, 2, 6, 7). Design System components only ever receive already-computed
  numbers/strings as props.
- **Member balance**: `statistic.memberBalances` — display migrated (Metric/DataRow) in Waves 6/7,
  field-by-field mapping confirmed unchanged; sign/magnitude/label triple verified together in
  Wave 7's dedicated fixture (`+777.777 ₫` / `"Còn được nhận"` vs. `−777.777 ₫` / `"Cần trả"`,
  correctly paired per member, not swapped).
- **Shared Fund**: `FundBalanceCard` → `Metric` migration (Wave 6) verified `unallocatedBalance`/
  `allocatedIncome`/`totalIncome` render exactly, including the invariant-warning banner appearing
  only when `invariant.valid: false`.
- **Settlement direction**: A→B is never reversed. Verified twice independently — Wave 7's
  dedicated `Alice_RECEIVER`/`Bob_PAYER` dataset (built specifically to expose a transposition) and
  the Pre-Go-Live Fix Batch's fresh confirm/cancel dialogs, both confirming payer→payee, amount, and
  history-row direction render correctly and are never swapped. Cancel = zero mutation, Confirm =
  exactly one mutation, confirmed via call-count spies in both reports.
- **Debt direction** (native_debt: họ nợ tôi / tôi nợ họ, loan vs. repayment): calculation code
  itself was never touched by any Wave; Wave 5's UI migration was verified via full-file diff to be
  a pure `BottomSheet`→`ResponsiveModal` wrapper swap with every prop passed to
  `DebtTransactionForm` (`fixedDirection`, `initialDirection`, `type`, `fixedCounterpartyMemberId`,
  `transaction`) character-for-character identical before and after.

**Status: no known path where a displayed financial value, balance, or direction can be wrong or
reversed.**

## 8. Premium readiness (advisory only)

- Module/feature boundaries are already reasonably clean for future gating: `plan-type-config.ts`
  defines an explicit per-plan-type list of modules (`{ moduleId, enabled, order, label }`), and
  `resolveModuleAccess(currentMember, moduleId)` already gates per-member, per-module visibility
  independent of role. Overview widgets are individually declared with their own `isAvailable()`
  check and `moduleId`. Adding a `requiresPremium` condition alongside the existing `enabled`/
  `isAvailable` checks looks structurally additive, not a rewrite.
- No core Plan/permission/business logic appears to need rewriting to introduce a paywall later —
  the gating mechanism (module-level, not scattered per-component) is the same shape a premium lock
  would need.
- The one area that could be structurally awkward later: several Overview widgets and Statistic
  components assume full data is always available once a module is "enabled" (no partial/preview
  rendering mode exists anywhere). A future "preview then upsell" pattern would need new UI, not
  just a new boolean check — but that is an additive future task, not a blocker or a sign of
  current architectural debt.
- Premium is not implemented and is not required for this release; this section is advisory only,
  per instruction.

## 9. Launch checklist

For the product owner, immediately before deployment:

1. Confirm production Firebase project config (API keys, project ID, security rules) — not the dev/
   test project used during this initiative's verification.
2. Confirm Firestore security rules match the current permission model (Owner/Editor/Viewer,
   module access) — this review verified application-level gating, not Firestore rules themselves.
3. Send one real invitation end-to-end (create → email/link → accept as a new user) on the
   production environment.
4. Run one real financial test plan manually: create a plan, add an expense and an income, confirm
   totals/statistics match expectations, then delete the test plan.
5. Run one real Settlement confirm + one real Settlement cancel on a disposable test plan, confirm
   history reflects both correctly.
6. Smoke-test on one real mobile device (not just a resized desktop browser): create-plan flow,
   member management, and the expense payer picker.
7. Confirm environment variables (Storage bucket, any API keys) are set for production, not
   pointing at a dev/staging bucket.
8. Confirm a rollback plan exists (previous deploy/tag reachable) before promoting to production.
9. Confirm error/monitoring reporting (if any) is wired to a channel someone actually watches
   post-launch.
10. Take a fresh Firestore backup/export immediately before the first real production writes.

## 10. Final disposition

**READY TO GO LIVE WITH NON-BLOCKING FOLLOW-UPS**

No P0 release blocker exists. The three P1 items in §3 are worth near-term attention (Settlement
confirmation is new and would benefit from one more round of real-world usage before being
considered as battle-tested as the rest of the app; debt repayment-limit validation and the
invitation long-email composition were not part of this review's fresh verification scope) but none
of them block release.
