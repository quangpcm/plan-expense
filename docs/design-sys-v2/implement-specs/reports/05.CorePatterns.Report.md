## 6. EntityList boundary decisions

This is the section the review asked to see most clearly (data/query-engine risk), so stated
plainly:

- Full prop type: `{ loading?: ReactNode; error?: ReactNode; empty?: ReactNode; divided?: boolean;
  density?: 'comfortable'|'compact'; children?: ReactNode } & Omit<HTMLAttributes<HTMLDivElement>,
  'children'>`. That is the complete surface. There is no `data`, `query`, `entityType`, `schema`,
  `columns`, `fetch`, `sortBy`, or `filter` prop, and none could be added without visibly
  contradicting the "just a `ReactNode` slot" shape everything else already has.
- **EntityList does not decide which state is active.** It does not check `children.length`, call
  `React.Children.count`, or introspect its children at all — the exact anti-pattern that would
  have made it start "knowing" about data. Instead, per the spec's own example (§18), the *product*
  decides which slot is truthy at the call site (`empty={plans.length === 0 ? <EmptyState .../> :
  undefined}`), and `EntityList` just renders whichever of `loading`/`error`/`empty` is present, in
  that priority order, falling through to `children` only when none are. This keeps the "is the
  list empty" decision — which requires knowing what the product's data even is — entirely on the
  product side.
- No sorting, filtering, aggregation, pagination, or fetching code exists anywhere in the 55-line
  implementation. There is no `useEffect`, no `useState`, no hook of any kind — it's a pure
  function of its props.
- `divided`/`density` are the only two "generic" behavioral props, both closed enums/booleans
  (`density` uses the same `'comfortable'|'compact'` vocabulary as Wave 4's `DataRow`, per §23's
  explicit instruction to reuse that vocabulary rather than invent a parallel one).
- Proof consumer: `plans/archived/page.tsx`'s existing three-way `isLoading ? ... : plans.length >
  0 ? ... : ...` conditional became `<EntityList loading={...} empty={...}>{plans.map(...)}
  </EntityList>`. `useArchivedPlans()`'s data/loading/error state, and the `plans.map(...)` row
  rendering (still `ArchivedPlanListItem`, Wave 4's `DataRow`-composing product row, untouched)
  are byte-for-byte the same — only the outer conditional's markup source changed.

## 7. FilterBar boundary decisions

- Full prop type: `{ search?: ReactNode; filters?: ReactNode; actions?: ReactNode; className?:
  string } & ...native div attributes`. Three content slots, no filter schema, no filter DSL, no
  domain option arrays. Compare against §11's explicit anti-example
  (`<EntityList entityType="guest" schema={...} query={...} />`-style prop explosion) — FilterBar
  has nothing resembling that shape.
- FilterBar owns zero state. `searchQuery`/`sortBy` remain exactly where they were —
  `useState` calls inside `plans/page.tsx` — and are passed down as already-resolved `value`/
  `onChange` props on the real `Input`/`select` controls composed *into* FilterBar's `search`/
  `filters` slots. FilterBar never sees `searchQuery` or `sortBy` as values; it only receives
  already-built `ReactNode`s.
- No debounce policy, no search field list, no sort-option list, no filter-execution code exists
  anywhere in FilterBar — those all remain in `plans/page.tsx`'s existing `filteredPlans =
  useMemo(...)`, completely untouched.
- Proof consumer: `plans/page.tsx`'s existing search input (with icon) + sort `<select>` (with
  icon) row became `<FilterBar search={...} filters={...} />`. The `filteredPlans` computation,
  the `Input`/`select` elements themselves, their `value`/`onChange` wiring, and the sort option
  list (`Mới nhất`/`Ngày tạo`) are all unchanged — only the outer row wrapper's markup source
  changed. No `actions`/reset slot was used, since this page doesn't have a reset action today —
  nothing was added to justify one.

## 8. PageHeader boundary decisions

- Full prop type: `{ title: ReactNode; description?: ReactNode; metadata?: ReactNode; actions?:
  ReactNode; className?: string } & ...native div attributes`. No `role`, `module`, `planType`, or
  `autoActions` prop — the exact anti-example from §11 (`<PageHeader planType="wedding"
  module="finance" role="editor" autoActions />`) has nothing in PageHeader's shape to attach to.
- Title renders as a real `<h1>` using Foundation's `page-title` typography role (§46's explicit
  instruction), and PageHeader resolves nothing about what the title/actions *mean* — it only
  lays them out.
- **Proof consumer selection follows Audit Decision Record §10 directly**: Wedding Overview
  explicitly does *not* need PageHeader ("PageHeader dependency: NO"), but "Dashboard → PageHeader
  dependency: YES" — `/plans` (the plans list/dashboard route) is exactly that surface. Used
  `plans/page.tsx`'s existing greeting header (`h1` + description + notification bell + avatar) as
  the proof consumer, composing the bell button and Avatar — both already-existing, already-correct
  elements with their own state/logic (`isNotificationOpen`, `todayAttentionCount`, `bellTone`) —
  into PageHeader's `actions` slot completely unchanged. PageHeader does not know what the bell
  button does or what `bellTone` means; it only receives the finished `ReactNode`.
- **One visible, deliberate size change, flagged explicitly**: the original greeting used
  `text-[2rem] font-bold` (32px), a one-off value. Adopting `PageHeader` means adopting Foundation's
  canonical `page-title` role (24px/700, from Wave 1), per §46's explicit instruction to use it.
  This changes the greeting's rendered size at this one call site. This is not a silent app-wide
  cascade like Wave 4's Card situation — `PageHeader` is a brand-new component with exactly one
  consumer right now, so this is the deliberate, visible result of choosing to prove the pattern
  here, not an unreviewed side effect. Flagged in case the review wants it reconsidered.
- The rich Plan/Wedding-specific headers described in Audit Decision Record §10 (Plan Detail
  Shell's own header, Wedding Overview's header) were **not** touched — per §10, Wedding Overview
  explicitly has no PageHeader dependency, and Plan Detail Shell migration is out of this wave's
  scope (`archived-plan-list-item.tsx`/`plans/page.tsx` are the low-risk surfaces chosen instead,
  not the rich domain headers).

## 12. Responsive behavior

- `FilterBar` wraps via `flex flex-wrap` — on narrow widths the search input (`flex-1`) and the
  sort control (`shrink-0`) naturally reflow; not a mobile-specific overlay implementation in this
  wave (`plans/page.tsx`'s two controls fit on one row down to normal mobile widths already, so no
  mobile-collapse/overlay behavior was needed for this proof consumer — §37/§38's overlay pattern
  remains available for a future FilterBar consumer that actually needs it, not built speculatively
  here).
- `PageHeader` wraps via `flex flex-wrap items-start justify-between gap-4` — title/description
  stack on the left, actions cluster shrinks to its own row when space is tight, matching §51.
- `EntityList` has no responsive branching of its own (`flex flex-col`, one column) — its rows
  (`ArchivedPlanListItem`) already own their own internal responsive behavior from prior waves.
- Not independently re-verified per-breakpoint beyond the build/runtime checks in §17 — no sandbox
  headless browser available, same limitation as every prior wave's report.
