## 0. Review outcome

First submission was reviewed as **APPROVE WITH REQUIRED FIXES**. Two governance-level findings,
both a form of the same rule: don't invent a value when there's no approved/existing source to
back it, even a "restrained" or "small" one.

1. `--shadow-raised` was a brand-new value with no existing consumer to harvest it from and no
   approved exact spec value — inconsistent with how `brand.gradient-*` had correctly been left
   out for the identical reason. **Fixed: removed.** `elevation.raised` is deferred to Pilot
   evidence; `elevation.none` (native `shadow-none`) and `elevation.overlay` (harvested from
   Dialog) stand as-is.
2. `.text-caption` was locked at `11px`, a size that doesn't appear in 01.Foundation's role table
   and wasn't sourced from anything existing — a judgment call presented as if it were settled.
   **Fixed: remapped to the approved `12px` size** (same as `.text-metadata`). The role stays
   (semantic distinction between "metadata" and "caption" is still useful at the consumer layer),
   but its size is no longer an unapproved invention.

Both fixes applied, `typecheck`/`test`/`build` re-run clean (unchanged results — see §7/§9/§10).
Sections below are updated to reflect the fixed state; §13/§14 keep a record of what was removed
and why, since that's implementation knowledge worth carrying into later waves.

## 3. Canonical token source

Single source: `src/styles/globals.css`, inside the pre-existing `@theme { ... }` block (Tailwind
v4, CSS-first config — there is no `tailwind.config.js` in this repo). No second/duplicated token
source was introduced.

- Tailwind consumes `@theme` entries two ways: (a) auto-generated utility classes for names that
  don't collide with Tailwind's own reserved scale (e.g. `--color-brand-primary` → usable as
  `bg-brand-primary` if ever wanted), and (b) `var(--token-name)` inside arbitrary-value brackets
  (`bg-[var(--color-brand-primary)]`), which is the pattern already used everywhere in this
  codebase (e.g. existing `--radius-card` is consumed as `rounded-[var(--radius-card)]`, never as
  a bare `rounded-card` class) — new tokens follow that same established convention.
- Plain CSS (non-Tailwind) consumes the same variables via ordinary `var(--token-name)`, since
  `@theme` variables compile down to real `:root`/`@layer theme` custom properties.
- Legacy consumers are untouched and keep reading the original raw variable names
  (`--color-primary`, `--color-border`, etc.) directly; new semantic names are aliases layered on
  top (`--color-brand-primary: var(--color-primary);`), not replacements. Both stay in sync
  automatically because the semantic name just points at the existing variable.

## 4. Semantic tokens introduced

All added inside `@theme` unless noted. Every alias below points at an **existing** value already
shipping in the app — nothing here is an invented palette.

**Brand** — `--color-brand-primary`, `-primary-hover`, `-foreground`, `-accent`, `-subtle`.
`-primary-active` aliases `-primary-hover` (no distinct active shade exists yet — flagged, not
invented). `brand.gradient-start/middle/end` were **not** added: the codebase has no existing
gradient to preserve (verified — zero `bg-gradient-*`/violet/cyan usage found), and 01.Foundation
§10 explicitly forbids inventing new hex values when the source doesn't specify them. Deferred.

**Surface** — `--color-surface-page`, `-default`, `-subtle`, `-raised`, `-overlay`. `-raised` and
`-overlay` both alias the same white as `-default`: today's dialogs/popovers separate visually via
shadow only, not a distinct fill — confirmed by reading `dialog.tsx`/`responsive-modal.tsx`
(`bg-white`, same computed color as `--color-surface`).

**Text** — `-primary`, `-secondary`, `-muted`, `-inverse`, `-link` map to distinct existing
values. `-disabled` aliases `-muted` (no distinct disabled-text color exists yet — flagged).

**Border** — `-default`, `-subtle` (aliases `-default`, no distinct subtle tier exists yet —
flagged), `-focus`. `-strong` was **not** re-declared: the existing raw variable is already named
`--color-border-strong` — see §13 Known Issue Found And Fixed below.

**Status** — `success`/`warning`/`danger`/`info`, each with a `-surface` variant, mapped 1:1 to
the existing `success`/`warning`/`danger`/`info` (+ `-soft`) tokens.

**Focus** — `--color-focus-ring` (solid, matches Button's existing `ring-2 ring-[--color-accent]`
recipe), `--color-focus-ring-soft` (wide/soft, matches Input/DropdownSelect's existing
`ring-4 ring-[--color-accent-soft]` recipe). Both existing recipes were found in the repo and
named, not unified — unifying them would be a broad consumer migration, out of scope for
Foundation (§42 Stop Conditions).

**Overlay** — `--color-overlay-backdrop: rgb(2 6 23 / 40%)`, harvested byte-for-byte from
`ResponsiveModal`/`BottomSheet`'s existing `bg-slate-950/40`, not invented.

**Radius** — `--radius-ds-sm/md/lg/xl/full` = `8/12/16/20/9999px`. Namespaced `-ds-` — see §13.

**Elevation** — `--shadow-overlay` only (harvested from Dialog's existing shadow, not invented).
`elevation.none` needs no token — Tailwind's native `shadow-none` already covers it.
`elevation.raised` is **deferred**, not added: there is no existing "raised" surface to harvest a
value from and no approved exact value, so — per review — it is not invented provisionally. Add it
once Pilot evidence justifies a specific value.

**Focus geometry / z-index** (plain `:root`, not `@theme` — see §13) —
`--focus-ring-width: 2px`, `--focus-ring-offset: 2px` (names Button's existing recipe, doesn't
change it), `--z-index-sticky/dropdown/overlay/toast` = `10/30/40/50` (aliases the numeric ladder
already used consistently across the app).

**Typography roles** (`@layer components`, bundled recipes, no React wrappers per §20) —
`.text-page-title` (24/700), `.text-section-title` (18/700), `.text-component-title` (15/600),
`.text-body` (14/400), `.text-body-strong` (14/600), `.text-metadata` (12/400), `.text-caption`
(12/400 — same size as metadata; kept as a distinct semantic role for consumers that need to say
"this is a caption" rather than because it has a different locked size, per review — an unapproved
11px value would have been an invention, not a mapping), `.text-metric-lg/md/sm` (28/22/18, all
700). Sizes follow 6.Foundation.md §6.4.2's proposed scale; that source itself says "not
implementation-lock absolute — Pilot screens will validate."

**Motion** — no new tokens. Tailwind's numeric `duration-150/200/300` + `ease-out/ease-in`
utilities already satisfy the fast/normal/slow (100-150/150-200/200-300ms) vocabulary from
6.Foundation §6.11 — inventing named duration tokens on top would duplicate an existing scale.
Documented here instead of in CSS.

**Spacing** — no new tokens. Tailwind v4's default spacing scale is `n × 0.25rem`, which already
equals the approved 4px grid (`p-4` = 16px, `gap-2` = 8px, etc.) — nothing to add, just documented.

**Responsive breakpoints** — no changes. No custom `--breakpoint-*` override exists; Tailwind's
default `md: 768px` / `lg: 1024px` already match the approved Tablet/Desktop cut points, and
existing usage (156× `sm:`, 36× `md:`, 139× `lg:`, 16× `xl:`) is already built on this contract.
Documented, not touched.

## 13. Known remaining legacy styles / issues found during this wave

**Issue #1 — Fixed. Comment prematurely closed a CSS block.** A first draft of one comment
contained the literal substring `--color-*/--radius-*` — the `*/` inside it closed the CSS
comment early, corrupting everything after it. `next build`'s webpack CSS loader caught this as a
hard syntax error (`Unknown word entries`) before any commit. Fixed by rewording the comment to
avoid `*` immediately before `/`. This is now a real gotcha worth remembering for future waves:
**never write a Tailwind/CSS comment containing `<word>-*` followed by `/`**.

**Issue #2 — Fixed. Self-referencing circular custom property, and a broader lesson about
verifying Tailwind v4's on-demand token emission.** A first draft added
`--color-border-strong: var(--color-border-strong);` intending to alias a new semantic name onto
an existing raw value — but the existing raw variable in this codebase already happens to be
named exactly `--color-border-strong`. The duplicate declaration became a self-reference,
silently invalidating that custom property (CSS spec: a circular `var()` computes to nothing) and
clobbering the original `#cbd5e1` value. This did **not** produce a build error (circular `var()`
is syntactically valid CSS), so it was only caught by directly diffing compiled CSS output against
expectations, not by `typecheck`/`lint`/`test`/`build` passing — those all stayed green throughout.
Fixed by deleting the duplicate declaration (the existing name already satisfied the target
semantic role, so no new alias was needed at all).

While investigating why several *other*, unrelated new tokens (e.g. `--color-brand-primary`,
`--radius-ds-md`) were also missing from the compiled CSS even after that fix, confirmed empirically
(by comparing every existing token's usage count in `src/**/*.tsx` against its presence in
compiled output, and by a temporary canary consumer — see §6) that **Tailwind v4 only emits a
`@theme` variable into the shipped CSS if something in the scanned source actually references it**
(a real utility class, or the exact `var(--name)` string inside an arbitrary-value bracket).
Tokens with zero consumers exist correctly in source but are invisible in the compiled bundle —
this is expected on-demand/JIT behavior, not a defect, and it will resolve itself the moment
Wave 2 (`02.CorePrimitives.md`) writes the first real consumer. Documented here so the next wave
doesn't mistake "token not in compiled CSS yet" for "token is broken."

**Known remaining legacy styles (not fixed, correctly out of scope for Wave 1):**

- Body background is a bespoke 3-stop light gradient
  (`linear-gradient(180deg, #f8faff 0%, #f4f7fb 45%, #f6f8fc 100%)`), not the flat
  `--color-surface-page` token. 01.Foundation §26 says don't add large decorative gradients to the
  body, but doesn't say to remove an existing subtle one — flattening it would be a visible base
  treatment change beyond token-only scope, left for explicit product/design decision, not silently
  changed here.
- `focus:` vs `focus-visible:` is inconsistent across existing inputs (Button uses
  `focus-visible:`; Input/DropdownSelect/date fields use plain `focus:`, so their ring also shows
  on mouse-click focus, not just keyboard). Pre-existing, not introduced, flagged for Wave 2
  (Primitives).
- Radius is highly fragmented today: `rounded-full` (146×), `rounded-2xl` (115×), `rounded-[24px]`
  (42×), `rounded-[28px]` (33×), `rounded-xl` (5×, at Tailwind's default 12px), plus several other
  one-off bracket values (`[32px]`, `[20px]`, `[26px]`, `[18px]`). None were touched. Per
  3.AuditDecisionRecord.md §14, legacy 24px does not automatically become a new canonical token;
  mapping each of these to `radius-ds-sm/md/lg/xl` is Wave 2-4 (Primitives/Overlay/Structural)
  work, informed by this inventory.
- `--font-sans` was declared (`'Inter', 'Segoe UI', sans-serif`) but never actually loaded before
  this wave — no `@font-face`, no `next/font`, so it silently fell back to the OS default sans
  font for every user. Fixed in this wave (§2) since it's central, small, reversible, and directly
  the Typography Foundation deliverable — flagged here for visibility since it's a real, if quiet,
  pre-existing gap rather than something this wave broke.
