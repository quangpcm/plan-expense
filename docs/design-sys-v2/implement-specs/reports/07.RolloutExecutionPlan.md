# 07. Rollout Execution Plan

**Status:** PLANNING ONLY — no code changed, no wave opened. This document synthesizes
`07.RolloutStrategy.md` (the approved spec, written before any Pilot evidence existed) with actual
evidence from Pilots #1-3 and the STOP/GO review, plus a fresh app-wide inventory, into a concrete,
sequenced wave plan. It replaces "read the spec and start migrating" with "here is what the spec
means given what we now know."

**What this is not:** a wave manifest. Each wave still gets its own short manifest (§9 format,
abbreviated from `06.PilotMigration.md`'s Pre-Code discipline) immediately before it opens — this
document sequences and risk-classifies; it doesn't pre-verify per-file detail no wave has looked at
yet (`07.RolloutStrategy.md` §9 itself: "Do not plan rollout from folder names alone" — the
classifications below are first-pass, confirmed or corrected at each wave's own bounded inventory).

## 2. What the three Pilots actually proved (evidence, not repetition)

```text
Overlay migration (BottomSheet/Dialog/window.confirm → ResponsiveModal/ConfirmDialog) is now
  proven THREE times independently (Dashboard's CreatePlanForm modal was already ResponsiveModal
  pre-Pilot; Wedding Guest did 4 BottomSheets + 1 Dialog + 3 window.confirm flows) with zero
  business regression and a real accessibility defect found and fixed along the way. This is the
  single most de-risked migration pattern available — it should lead the rollout, not follow it.

Structural component adoption (Metric/MetricGroup, DataRow) is genuinely conditional, not a
  checklist. Two real rejections (PlanCard/Metric in Pilot #2, WeddingGuestList/DataRow in Pilot
  #3) each had a concrete, component-source-level reason, not a vague "doesn't feel right." This
  means future waves must budget real evaluation time per surface, not assume adoption.

FilterBar's "shell only, state stays in product layer" composition pattern worked cleanly twice
  (Dashboard, Wedding Guest) with near-zero risk — this is a second de-risked, repeatable pattern.

Radius/color drift is real and was NOT solved by the Pilots — 24/28px legacy values compounded
  across all three surfaces, plus one novel value (26px) that appeared once. The rest of the app
  (per the inventory in §4) is consistent with the SAME 24/28px pair rather than introducing new
  scattered values — meaning the drift, while real, has not gotten worse outside the Pilots. This
  is dischargeable during rollout via the token-touched-surface-at-a-time model
  (`07.RolloutStrategy.md` §68), not a dedicated cleanup wave (see §6).

Five Design System gaps remain deliberately unbuilt (Progress, Plan-Type Expression tokens,
  TextAction, NotificationBadge, bottom-panel abstraction) plus one that has crossed the evidence
  threshold (Button size="icon", now 3 data points: Dashboard's bell, Wedding Guest's delete-guest
  and delete-group icon buttons). None of these block rollout starting; §8 defines trigger
  conditions for acting on them.
```

## 6. Why there is no dedicated "visual/token normalization" wave

`07.RolloutStrategy.md` §68 is explicit: *"Do not block product migration on eliminating every
legacy raw color/spacing value repository-wide... Use progressive cleanup: touched surface →
semantic migration → verified. Track remaining hotspots separately."* The inventory in §3 shows the
drift outside the Pilots hasn't gotten *worse* (same 24/28px pair, no new scattered values) — there
is no urgency spike that would justify breaking this rule. Radius/color cleanup happens **inside**
each surface wave below, exactly as it did in Dashboard and Wedding Guest (exact-alias token swaps
where they exist, explicit non-action where they don't, radius left alone unless that wave's own
surface already needs to touch the relevant Card/Skeleton instance). `statistic`'s heavy footprint
(§4, R4) means it will absorb a large share of this cleanup simply by being migrated at all.

    1 window.confirm only. Does not touch what any tab renders.

  Why first: smallest possible wave, proven pattern, immediately shrinks the legacy registry,
    builds confidence in the lighter process model (§10) before it's used on a real domain surface
  V2 expected: ResponsiveModal, ConfirmDialog (already partially present in this file)

Wave 1 — R1 low-risk modules
  Surfaces: storage (attachment-picker BottomSheet), user, auth, invitation
  Risk: R1
  Why now: lowest business risk, good surface for the lighter process model's first real test
    against unfamiliar (to this session) code
  V2 expected: ResponsiveModal for the one BottomSheet; Button/Badge/FilterBar/EmptyState/

  Surfaces: expense (expense-form BottomSheet + finance tab presentation), milestone, planning,

  Risk: R2, isolated separately from Wave 2 because of its explicit chronological/category
    semantic guardrail (§42) — worth its own narrow verification pass rather than bundling with
    unrelated R2 modules per §19's "do not bundle unrelated modules solely to increase throughput"

Wave 4 — member (R3)
  One high-risk surface per wave, per §21. Permission-heavy: Owner/Editor/Viewer, module access,
  invitation lifecycle, Editor own/manage-all distinction (§41 Members Guardrail). 2 BottomSheet

Wave 5 — debt-tracking (R3)
  Separate wave from member, per §21. Debt directionality, outstanding balance, repayment limits,
  due-date semantics (§39 Debt Guardrail) — must not let generic Metric/DataRow understand these
  concepts, same discipline already proven in Wedding Guest's WG-RG guardrails. 3 BottomSheet
  consumers.

Wave 6 — statistic (R4)
  Heaviest Card (12) and raw-color (13) footprint in the app. Presentation-only, mandatory
  (§15/§38). Explicit before/after value fixtures for every displayed calculation (§53). This wave
  alone likely does more visual-consistency work than all prior waves combined, simply by being
  the largest untouched surface — do not let that turn it into a bigger business-logic change than
  intended.

Wave 7 — settlement (R4)
  Named directly in the Finance Guardrail (§38). One high-risk surface per wave (§21) — kept

  statistic's aggregate-display logic are different enough domains to warrant independent

## 9. Lighter process model for Wave execution (replaces the Pre-Code→review→implementation→report→review cycle used for the 3 Pilots)

```text
Wave opens
  ↓
Bounded inventory (short — file list, current V2/legacy usage, business invariants touched,
  permission-sensitive actions, expected disposition per component; NOT a full Pre-Code essay)
  ↓
Implementation
  ↓
Automated regression (typecheck/lint/test/build)
  ↓
Targeted P0/P1 verification (business-invariant-risk items get real behavior verification;
  visual/spacing/pixel differences are P2, not blockers unless they cause a real usability problem)
  ↓
Concise wave report (`07.RolloutStrategy.md` §79 format, abbreviated — no separate PreCode
  document, no giant per-component prose; a findings/disposition table plus a short narrative
  where genuinely needed)
  ↓
Next wave
```

This does not remove judgment or evidence — it removes the *ceremony* the Pilot phase needed
precisely because the Design System itself was still unproven. It is now proven three times.

### STOP conditions (unchanged from the discipline already used throughout this session — carried forward explicitly, not weakened)

```text
Business invariant risk discovered
Permission or data-model change required
Shared/Design-System API change required (new prop, new component, contract change)
New Design System abstraction would be needed to proceed cleanly
Unexpected architectural finding (domain leakage, God component pressure, prop explosion)
```

Any of these pauses the current wave for explicit review — the same threshold `07.RolloutStrategy.md`
§72 and this session's own STOP/GO review already established. Everything below that threshold
(component disposition calls, minor visual differences, which exact-alias tokens apply) proceeds
with the autonomy the lighter process model is meant to enable.
