# Wave 4 Addendum — MemberActionsMenu clipping fix

**Trigger:** Manual QA Checkpoint #2 found a blocking P1 usability bug in Member: the "..." action
trigger opened a popup that was clipped by its surrounding container, making all options
invisible/unselectable — blocking manual verification of linked-member delete-blocking, the
claim-invitation workflow, and Cancel behavior.

**Scope discipline:** Wave 4's disposition is unchanged — `member-actions-menu.tsx` remains
policy-exempt from `ResponsiveModal`/`ConfirmDialog` migration (it's a menu/popover, not a form,
per `ui-modal-conventions.md` §4). This is a targeted structural bug fix inside the exempt
component, not a reopening of that migration decision.

## 1. Root cause (confirmed by real layout measurement, not assumption)

Method: a mock-props harness rendering `MemberList` with an expanded, editable row, driven by
Playwright, reading `getBoundingClientRect()` and `getComputedStyle()` for every ancestor of the
"..." trigger.

`EditableMemberRow` renders `MemberActionsMenu` inside `editForm`, which is passed as
`Collapsible`'s `children`. `Collapsible` wraps its children in a `div.overflow-hidden` — the
mechanism its expand/collapse animation depends on (a CSS `grid-template-rows: 0fr → 1fr`
transition needs an `overflow: hidden` box so content doesn't visibly spill out while collapsed).
That wrapper's box is sized to the natural document-flow height of `editForm`'s content (measured:
204px tall, from y=441 to y=645 in one repro run).

`MemberActionsMenu`'s desktop dropdown was `position: absolute` (`top-12 right-0`), anchored to a
small `position: relative` wrapper around the trigger button. Its *containing block* for
positioning purposes is that relative wrapper — but that wrapper is itself a descendant of the
`overflow-hidden` box, so the dropdown is subject to that ancestor's clipping. Measured directly:
the dropdown rendered at y=730–770, while the clipping ancestor's box ended at y=645 — **the entire
dropdown fell ~85px past the clip boundary**, making it fully invisible and non-interactive,
exactly matching the QA report.

The mobile variant (`BottomSheet`, `position: fixed inset-0`) was unaffected — measured with real,
non-clipped bounds in the same repro. `position: fixed` establishes its containing block at the
viewport (or the nearest ancestor with a transform/filter/perspective/`contain`, none of which
exist in this chain), so it was never subject to the `overflow-hidden` ancestor's clipping. **This
is a desktop-only bug.**

## 2. Relationship to the Wave-4-reported hydration bug

**Not the cause.** The nested-`<button>` hydration mismatch reported in the Wave 4 report is a
different, unrelated mechanism (invalid HTML nesting in the row's `summary`/avatar-button markup,
causing a server/client DOM mismatch). This clipping bug is pure CSS layout: an `overflow: hidden`
ancestor clipping an `absolute`-positioned descendant, present regardless of hydration state.
Confirmed independently — the fix below resolves the clipping with the hydration warning still
present in the console (harmless to this bug, unrelated root cause, left untouched per the
instruction not to fix it opportunistically).

## 3. Fix applied

File changed: `src/modules/member/components/member-actions-menu.tsx` only. No other file touched.

- Desktop dropdown `Card` changed from `absolute top-12 right-0` to `fixed`, with its `top`/`right`
  (or `bottom`/`right` — see below) computed in viewport pixel coordinates from the trigger's
  `getBoundingClientRect()` at the moment the menu opens. `position: fixed` escapes the
  `overflow-hidden` ancestor's clipping entirely (same reason the mobile `BottomSheet` was already
  unaffected), which directly resolves the reported bug.
- Added a `triggerRef` (`useRef`) on the trigger button and a `toggleOpen` handler that computes
  the position on open — replacing the previous inline `onClick={() => setIsOpen((v) => !v)}`.
- **Viewport-edge flip, added after the base fix exposed a secondary issue in testing**: a purely
  `fixed`-positioned dropdown, once computed, cannot be scrolled into view if it lands below
  `window.innerHeight` — unlike the original `absolute` version, which (despite being clipped by
  the wrong ancestor) at least scrolled with the page. Verified this was reachable: in a synthetic
  repro with the target row pushed near the bottom of a 900px-tall viewport, the fixed dropdown
  computed a position starting at y=934 — off-screen with no way to reach it. Fixed with a small
  space check: if `window.innerHeight - rect.bottom` is less than the dropdown's estimated height,
  it opens **above** the trigger (`bottom`-anchored) instead of below. This is a minor scope
  addition beyond the literal reported bug, but was necessary for "reliably visible and selectable"
  to hold in general, not just in the one reproduction the QA report happened to hit.
- No portal was used — `position: fixed` alone was sufficient (proven by the mobile `BottomSheet`
  already relying on the exact same mechanism from the same DOM position), so no
  `createPortal`/`document.body` mounting was introduced. This keeps the diff smaller than a portal
  based fix would have required.
- The mobile `BottomSheet` branch (`md:hidden`) is **completely untouched** — it was never part of
  the bug.
- `menuItems` construction, all `onSelect` callbacks, `MenuItemButton`, the backdrop-click-to-close
  button, and every permission/ownership check upstream of this component are untouched.

## 4. Preserved (per instruction)

  `canUnlink`, `onDelete`).
- Permission/ownership behavior: no gating logic exists inside `member-actions-menu.tsx` itself
  (it only renders whatever `items` it's given), so none was touched.
- Desktop/mobile interaction model: still Card-dropdown on desktop, `BottomSheet` on mobile — same

- All Wave 4 `ConfirmDialog`/`ResponsiveModal` migrations in `member-list.tsx`: untouched, verified
  still working end-to-end below (this fix is what makes them reachable through the real UI at
  all).

No shared DS public API change, no new overlay abstraction, no permission/business change was

## 6. Targeted verification

Method: reused the Wave 4 mock-props harness (temp route, deleted after use, no Firestore) with
Playwright, this time driving **real `.click()` calls** (which fail on actionability/clipping,
unlike raw coordinate math) rather than just reading computed styles.

Desktop (1280×900):
- Menu opens on trigger click; dropdown renders fully within the viewport (previously computed
  ~85px past the clip boundary, now inside it).
- A real click on "Xóa thành viên" succeeds (previously timed out — clipped, non-actionable) and
  correctly opens the `ConfirmDialog`.
- Linked-guest scenario re-verified through the now-working menu: opening it and clicking delete
  still surfaces only the info-only "Không thể xóa thành viên" dialog with **no destructive button
  rendered** — the forbidden action still isn't exposed.
- Cancel/"Hủy"/"Đóng" close the dialog as before (exercised as part of the same pass).
- Edge case re-tested after adding the viewport flip: with the target row pushed near the bottom of
  the viewport (3 rows expanded), the menu now opens upward and remains fully clickable, instead of
  rendering off-screen.

Mobile (390×844): re-ran the same real-click scenarios — `BottomSheet` path unaffected by this fix
(as expected, it was never broken), still opens, closes, and reaches `ConfirmDialog` correctly.

Not separately re-verified in-browser this pass (already covered by Wave 4's original P0 pass, and
unaffected by this fix): unlink Cancel=0/Confirm=1 mutation counting, reactivate/deactivate flow,
claim-invitation-link mini-workflow content. This fix only changes how the menu becomes reachable,
not what happens after an item is clicked.
