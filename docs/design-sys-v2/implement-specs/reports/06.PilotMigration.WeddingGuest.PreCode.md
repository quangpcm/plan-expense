## 2. Module snapshot

`src/modules/wedding-guest/` — 56 files, ~5,900 lines. Single entry point: `WeddingGuestPanel`,
rendered as one tab inside `plans/[planId]/page.tsx`'s Plan Detail Shell (not a standalone page —
same reasoning as Wedding Overview: `PageHeader` is not a dependency here, per ADR §10's identical
ruling for the Shell-hosted Overview surface).

```text
WeddingGuestPanel (940 lines, orchestrator — owns all state/handlers/overlay wiring)
├─ WeddingGuestStatTiles          4 KPI tiles (guest/attendee/money/gold), hand-rolled
├─ Card > RsvpDonutChart          hand-rolled SVG donut
├─ WeddingGuestGroupNav           chip group selector
├─ WeddingGuestInsights           auto-text insights
├─ Card > WeddingGuestFilterBar + WeddingGuestList (preview)
├─ WeddingGuestStats
│  ├─ WeddingGuestGroupTable      dual-mode (desktop table / mobile cards)
│  ├─ WeddingGuestActionNeeded
│  ├─ WeddingGuestAttendanceSummary
│  └─ WeddingGuestCompositionCard/Rows
├─ ResponsiveModal "view all guests" > WeddingGuestListComposition + WeddingGuestList (full)  [already V2]
├─ BottomSheet "group manager" > WeddingGuestGroupList                                        [legacy]
├─ WeddingGuestImportDialog (Dialog, desktop-only, dynamic import)                             [legacy]
├─ WeddingGuestExportDialog (Dialog, desktop-only, dynamic import)                             [legacy]
├─ BottomSheet "create" > WeddingGuestCreateForm                                               [legacy]
├─ BottomSheet "edit guest" > WeddingGuestEditForm                                             [legacy]
└─ BottomSheet "edit invitation" > GuestInvitationForm                                         [legacy]
```

**The single biggest, clearest opportunity in this Pilot:** every CRUD entry point and both
CSV dialogs still use the legacy `BottomSheet`/`Dialog` components (`DEPRECATE` status since Wave
3), and every destructive action (`delete guest`, `delete group`, `remove from group`) uses plain
`window.confirm(...)` — `ConfirmDialog` is used **nowhere** in this module. This is exactly the
kind of consumer Overlay Architecture's deprecation path anticipated migrating during a Pilot.

## 3. Business invariants — mapped to current code (not re-litigated, only located)

| Invariant (ADR §34) | Where it's structurally enforced today | Migration risk |
|---|---|---|
| WG-RG-01 Guest ≠ PlanMember | Separate type modules, zero cross-import (`types/wedding-guest.ts` vs `modules/member/types/member.ts`) | LOW — presentation-only migration cannot touch this |
| WG-RG-02 Guest identity ≠ invitation state | `WeddingGuestDocument` has no RSVP/gift/group fields at all; those live only on `GuestInvitationDocument` | LOW — same reason |
| WG-RG-03 Invitation/group RSVP is invitation-owned | Invitation doc ID is `${guestId}_${groupId}` — one doc per (guest, group) pair | LOW — not touched by UI migration |
| WG-RG-04 attendeeCount ≠ guest identity count | Computed separately in `wedding-guest-statistic.ts:42-43` (`guestCount` = distinct guestIds, `attendeeCount` = sum of invitation values) | **MEDIUM** — any Metric/MetricGroup adoption for `WeddingGuestStatTiles` must keep these as two separate Metrics, never merged (identical guardrail to Wedding Overview's own guest-count invariant, already proven safe there) |
| WG-RG-05 Money gift ≠ gold gift | Separate nullable fields on `GuestInvitationDocument`; separate formatters (`formatCurrency` vs `formatGoldGift`, `utils/gold-gift.ts`) | **MEDIUM** — same reasoning as above; never combine into one Metric |
| WG-RG-06/07 Duplicate detection = suggestion only, no auto-merge | `findDuplicateGuestMatches`/`findGuestsBySimilarName` (`utils/guest-duplicate.ts`) return plain arrays; `GuestDuplicateSuggestList` has no merge action, only an optional "select existing" callback the caller wires | LOW — presentation-only; migrating the BottomSheet shell around these forms cannot introduce a merge behavior by itself |
| WG-RG-08 Permission behavior unchanged | Single capability `weddingGuests.manageGuest`, resolved via `hasPlanCapability`, enforced at both UI (`canManage` gates) and service layer (`assertManageWeddingGuestPermission` in every service) | **MEDIUM** — see §4; must survive the overlay-shell swap exactly |
| WG-RG-09 Existing data remains compatible | No data-model file in this Pilot's expected changes (§8) | N/A if scope is respected |
| WG-RG-10 No Finance coupling for gifts | Gift totals are Wedding-Guest-local values, not routed through the Finance module anywhere found | LOW — not touched |

## 4. Permission mapping

One capability, `weddingGuests.manageGuest` (view-only gate is `weddingGuests.view`, resolved
upstream in the module registry, outside this Pilot's file boundary). `canManage` computed once in
`WeddingGuestPanel:117-119`, threaded as a prop to every gated affordance:

```text
Action                          Owner   Editor (manageGuest granted)   Editor (denied)   Viewer
Create guest / add to group     shown   shown                          hidden            hidden
Edit guest / edit invitation    shown   shown                          hidden            hidden
Delete guest / group / unassign shown   shown                          hidden            hidden
Import / Export CSV             shown   shown                          hidden            hidden
Manage groups                   shown   shown                          hidden            hidden
```

Server-side defense in depth is independent of UI gating (`assertManageWeddingGuestPermission` +
`assertEditablePlan` in every service method) — **not touched by this Pilot's file boundary**
(services/repositories excluded, §8). UI migration must preserve every `canManage`/`activeGroupId`
conditional exactly; it must not move, duplicate, or loosen any of these checks.

## 5. Overlay migration (the core of this Pilot)

| Current | Target | Confidence | Why |
|---|---|---|---|
| `BottomSheet` × 4 (create, edit guest, edit invitation, group manager) | `ResponsiveModal` | **HIGH** | `ResponsiveModal` already proven in 2 Pilots and already used once in this exact module (view-all-guests list); forms already compose V2 primitives internally (Input/DropdownSelect/Textarea/CurrencyField/Button); shell swap only, no business logic touched. This is also a strong validation opportunity for the just-fixed focus-return behavior across 4 real create/edit workflows. |
| `window.confirm` × 3 (delete guest, delete group, remove from group) | `ConfirmDialog` | **HIGH** | Exactly `ConfirmDialog`'s purpose. Dynamic message text (varies by group-membership/invitation count) already exists as computed strings — moves directly into `description`, no new logic. Zero semantic ambiguity. |
| `Dialog` (legacy) — Export CSV | `ResponsiveModal`? | **OPEN QUESTION — see §11** | Simple content (one DropdownSelect + one button), but desktop-only gating must be preserved exactly if migrated. |
| `Dialog` (legacy) — Import CSV | `ResponsiveModal`? | **OPEN QUESTION — see §11** | Complex 3-step wizard with a wide preview table; desktop-only gating; `ResponsiveModal` has no `size` prop today (className override only) — forcing this into the canonical shell may need an approved width exception, not a default. Higher structural risk than any other item in this Pilot. |

## 9. Radius guardrail disclosure

`Skeleton` loading placeholders in this module already use `rounded-[28px]`
(`wedding-guest-panel.tsx:627-628`, `wedding-guest-import-dialog.tsx:260,324`) — **this is not a
new value**; it's the exact same 28px already flagged as uncontrolled drift in
`07.StopGoSystemReview.md` §5. If this Pilot's implementation touches these Skeleton instances, it
must not introduce a *fourth* distinct number — reusing 28px here is at least consistent with
existing (if undesirable) drift, not new drift, and should be called out plainly in the eventual
implementation report rather than silently carried over. **No new ad hoc radius value is proposed
by this Pre-Code.** Radius unification is explicitly not a goal of this Pilot.
