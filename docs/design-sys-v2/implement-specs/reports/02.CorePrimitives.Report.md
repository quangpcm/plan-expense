Every token rename in this wave follows one mechanical rule, applied without exception: **only
rename when the new semantic token is a byte-identical alias of the old raw variable** (verified
against Wave 1's `globals.css`). Where no exact Foundation equivalent exists yet (Badge's
`neutral`, `--color-secondary`/`-foreground` generally), the raw legacy variable was left
untouched rather than force-mapped to an inexact neighbor — same discipline the Wave 1 review
required for `--shadow-raised`/`.text-caption`, now carried forward as house rule for this wave.

## 5. API changes

**Button — additive only, zero breaking change:**

- New variant `destructive`: `bg-[var(--color-status-danger)] text-white hover:bg-red-700`.
  Harvested byte-for-byte from `confirm-dialog.tsx`'s existing manual className workaround
  (`bg-red-600 text-white hover:bg-red-700`) — `--color-status-danger` equals Tailwind's `red-600`
  exactly, confirmed in Wave 1, so the base color is a genuine semantic rename. **`hover:bg-red-700`
  is not that** — per review, this is explicitly classified as a **known Foundation semantic gap**:
  a raw Tailwind value kept as-is because no `--color-status-danger-hover` (or equivalent) token
  exists yet, not evidence that raw hover values are the intended canonical pattern. It's a
  temporary legacy state, same in kind as Badge's untouched `neutral` variant (§14) — flagged for
  Foundation to actually decide on, not silently treated as settled. No shadow was added either:
  the harvested evidence doesn't have one, and inventing a colored shadow would repeat the exact
  mistake the Wave 1 review corrected for `--shadow-raised`.
- New `size` prop (`sm` | `md`), default `md`. `md`'s classes are **byte-identical** to the
  pre-Wave-2 hardcoded base classes — every one of Button's 51 existing consumers that doesn't
  pass `size` renders pixel-identical to before.
  - `sm` harvested byte-for-byte from `settlement-suggestion-card.tsx`'s existing manual override
    (`min-h-9 px-4 py-2 text-xs`); `gap` deliberately kept at `md`'s value since the original
    override never touched it.
  - `lg` and `icon` were **not** added. Neither has a real consumer anywhere in the repo to derive
    or verify a value against. `lg` was deferred in the first submission already; `icon` was
    initially added (derived from the existing 44px height + the approved 44×44 touch-target
    floor) but removed after review — a mechanical derivation is still a guess without a real
    consumer, the same standard already applied to `lg`. Add both only when a real consumer needs
    one and its exact requirements (e.g. `icon`'s accessible-name contract) can be verified against
    it, not preemptively.
- Focus ring renamed `--color-accent` → `--color-focus-ring` (exact alias, zero visual change).

No other primitive's public API changed. No prop was renamed or removed anywhere.

## 8. Accessibility changes

- **Switch**: added `outline-none focus-visible:ring-2 focus-visible:ring-[var(--color-focus-ring)]
  focus-visible:ring-offset-2`. Previously had zero focus styling of any kind (not even a
  `outline-none` — just whatever the browser default happened to be, unstandardized). Now uses the
  same canonical ring as Button.
- **DateField / DateTimeInput**: both compose a real `<input type="date">`/`<input
  type="datetime-local">` that is absolutely positioned, full-size, and `opacity-0` — it's the
  actual focusable/interactive element, but it had `outline-none` with **no visible replacement
  at all**. Fixed using `has-[:focus-visible]:ring-2 has-[:focus-visible]:ring-[var(--color-focus-ring)]
  has-[:focus-visible]:ring-offset-2` on the visible wrapper `<div>`, since the real input is
  invisible and can't show its own ring. Verified this compiles (`has(:focus-visible)` selector
  present in compiled CSS — see §12) and is a CSS-only, zero-JS, zero-markup-restructure fix.
- No other accessibility behavior changed. Icon-only Button support was not added this wave (§5) —
  there is no accessible-name contract to verify since the API surface doesn't exist yet.

## 14. Known legacy behavior/styles

- **Button `destructive`'s `hover:bg-red-700` is a known Foundation semantic gap, not a canonical
  end-state.** Foundation (Wave 1) never defined a hover token for `status.danger` (or any status
  color) — only base + surface roles exist (`--color-status-danger`, `--color-status-danger-
  surface`). This wave harvested the raw Tailwind `red-700` value that already existed in
  `confirm-dialog.tsx`'s workaround rather than invent a new token for it. Should be revisited
  when/if Foundation adds a hover convention for status colors — until then this is a deliberately
  temporary raw value, tracked here rather than presented as settled.
- Badge's `neutral` variant and any other `--color-secondary`/`--color-secondary-foreground`
  usage (Button's `secondary` variant, AmountInput's suggestion chips) still reference the raw
  legacy tokens — Wave 1 never aliased these to a Foundation semantic name because no exact
  equivalent exists (`--color-secondary` ≠ `--color-surface-subtle`, different values). Left as
  evidence for a future Foundation addition if this tone is judged to need one, not silently
  force-mapped now.
- Avatar's decorative tone palette (6 hues) and empty-state `bg-slate-950` fallback remain raw
  Tailwind colors — correctly outside Foundation's semantic categories (see §4).
- AmountInput's focus indication is a bottom-border color change (`focus-within:border-[--color-
  brand-primary]`), not the canonical ring recipe used everywhere else. Deliberately left alone:
  it's a real, visible focus indicator (not a gap like Switch/DateField were), and AmountInput is
  explicitly flagged ADAPT-with-careful-boundary-preservation — forcing the generic ring onto this
  large hero-style money input would be an unreviewed visual change, not a token rename.
- `ConfirmDialog`'s manual `destructive`/`success` className workaround (§7) is now redundant for
  `destructive` but was correctly left alone — it's out of this wave's scope.

## 16. CurrencyField vs AmountInput evidence

No new evidence was found or acted on. Per 02.CorePrimitives.md §46, this remains an open decision

wrapper around `<Input>` sharing `AmountInput`'s `formatAmountInputValue`/`parseAmountInputValue`

presentation weight and consumer count (`AmountInput`: 7, `CurrencyField`: 1). Not a recommendation
— just what repository verification actually showed, reported per §46's instruction rather than
acted on silently.
