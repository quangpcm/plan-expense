## 0. Review outcome

First submission was reviewed as **APPROVE WITH ONE REQUIRED FIX**: the report's claim that
"Cancel appears before Confirm in the DOM, so it receives initial focus" was an unverified
DOM-order inference, not a cited library guarantee — unacceptable for a destructive-confirmation
safe-focus contract, which should be explicit, not incidental.

**What was actually verified** (by reading the installed library source directly —
`node_modules/@radix-ui/react-alert-dialog@1.1.23` and `node_modules/vaul@1.1.2` — not docs, not
memory, not assumption):

- **Desktop (Radix `AlertDialog`)**: `AlertDialogContent` *does* hardcode a safe-focus mechanism —
  but it is **not automatic in the way the original report implied**. It works by maintaining an
  internal `cancelRef` (via React context) and calling `cancelRef.current?.focus()` inside its own
  `onOpenAutoFocus`. That ref is only ever populated by the dedicated `<AlertDialog.Cancel>`
  subcomponent. **Our Cancel button was a plain `<Button>` with a manual `onClick`, never wrapped
  in `<AlertDialog.Cancel>`** — so `cancelRef.current` was always `null`, and the "guarantee" was
  never actually active. `event.preventDefault()` still fired (blocking Radix's fallback
  first-tabbable-element focus), so focus landed on the Content container itself, not on any
  button. The original report's claim was not just uncited — the actual runtime behavior didn't
  match it either. **Fixed** — see §5.
- **Mobile (`vaul` `Drawer`)**: confirmed **no equivalent mechanism exists at all**. `vaul`'s
  `Root` defaults `autoFocus = false`, and `Drawer.Content`'s `onOpenAutoFocus` handler
  unconditionally calls `event.preventDefault()` when `autoFocus` is false — meaning nothing
  receives focus on open, by design default. This needed an explicit implementation, not a
  rationale correction. **Fixed** — see §5.

Both fixes use each primitive's own documented extension point (`AlertDialog.Cancel` composition;
`Drawer.Content`'s `onOpenAutoFocus` prop) — no `setTimeout`, no `useEffect`, no custom focus
polling. `typecheck`/`test`/`build` re-run clean (unchanged results — §12/§14/§15). All other
findings from the first review (close button, proof consumer, destructive cleanup, `z-50`,
legacy-component scope, `member-list` finding, Foundation gaps) were approved as-is and are
unchanged in this revision.

## 4. ResponsiveModal changes

- **Added the missing close affordance** (§15 requires one for normal — non-confirmation — modal
  workflows; ResponsiveModal had none at all, only backdrop-click/Escape). Added `Dialog.Close`
  (desktop) / `Drawer.Close` (mobile), both accessible-named `aria-label="Đóng"`, using the exact
  position/size/color recipe already established by `bottom-sheet.tsx`'s own optional close
  button (`absolute right-4 top-4 rounded-full p-1.5 text-slate-400 hover:bg-slate-100
  hover:text-slate-600`) — harvested, not invented. Added `pr-8` to both title blocks so long
  titles don't run under the new button (a small layout-safety delta beyond what the harvested
  BottomSheet pattern does, called out explicitly since it's the one place this wave added
  something not directly copied from existing evidence — pure spacing hygiene, not a new visual
  value).
- **Token rename** (all exact, value-identical to what existed): `bg-slate-950/40` →
  `bg-[var(--color-overlay-backdrop)]`, `z-40` → `z-[var(--z-index-overlay)]`, desktop shadow
  `shadow-[0_16px_60px_rgba(15,23,42,0.1)]` → `shadow-[var(--shadow-overlay)]` (this is the exact
  value Wave 1 harvested `--shadow-overlay` from — confirmed byte-identical).
- **Not renamed** (no exact Foundation token exists — see §18): `border-slate-200`,
  `text-slate-950`, `text-slate-600`, `rounded-[28px]`/`rounded-t-[32px]`, and the mobile sheet's
  own shadow (`shadow-[0_-16px_60px_rgba(15,23,42,0.08)]` — upward-facing, 8% opacity, a
  *different* value from `--shadow-overlay`'s 10%, so not the same token).
- No change to `open`/`onOpenChange`/controlled-state behavior, Portal usage, or the underlying
  Radix Dialog / vaul Drawer primitives themselves — per §19/§20/§21, these were already correct
  and are not reimplemented.

## 5. ConfirmDialog changes

- **Removed the redundant manual `destructive` className workaround** (`bg-red-600 text-white
  hover:bg-red-700`) in favor of Button's native `variant="destructive"` (added in Wave 2, and in
  fact harvested *from* this exact line originally — the two were already byte-identical). This is
  the "known cleanup" flagged in the Wave 2 report as ready for Wave 3.
- `success` variant (`bg-emerald-600 text-white hover:bg-emerald-700`) **kept as a raw className
  override** — Button has no native `success` variant (not one of the four minimum canonical
  variants per 02.CorePrimitives.md §20), so there's nothing to switch it to. Not invented here.
- **Token rename** (exact, same rule as ResponsiveModal): backdrop → `--color-overlay-backdrop`,
  desktop shadow → `--shadow-overlay`. `z-50` (both desktop and mobile) intentionally **not**
  renamed to `--z-index-toast` even though the numbers coincidentally match — that token means
  "toast," not "alert dialog above a modal," and reusing it just because the digits match would be
  a semantic mismatch, not a rename. Flagged as a real Foundation gap instead (§18).
- **No change** to `onEscapeKeyDown`/`onPointerDownOutside` prevention (desktop AlertDialog
  already refuses outside-click dismissal by built-in AlertDialog semantics; mobile Drawer
  explicitly prevents both) — this is the correct, already-compliant "preserve AlertDialog
  semantics, don't collapse into ordinary Dialog" behavior required by §9/§10 and Audit Decision
  Record §9.1. Not touched.
- **Initial-focus behavior — corrected after review (§0).** Verified against the actual installed
  library source, not DOM-order inference:
  - **Desktop**: the Cancel button is now wrapped in `<AlertDialog.Cancel asChild>` (Radix's own
    dedicated cancel-focus component, composed via `asChild` onto our existing `<Button>` so no
    extra DOM node is introduced). This activates `AlertDialogContent`'s internal, hardcoded
    `onOpenAutoFocus` → `cancelRef.current.focus()` mechanism, which previously did nothing because
    no `AlertDialog.Cancel` was present to populate that ref. This is now a real library guarantee,
    not an inferred one, and required zero custom focus code — just correct composition.
  - **Mobile**: `vaul`'s `Drawer` has no equivalent built-in mechanism (confirmed via source:
    `autoFocus` defaults to `false`, and `Drawer.Content` explicitly calls `event.preventDefault()`
    on open when that's the case — nothing is focused by default). Implemented explicit safe focus
    using `Drawer.Content`'s own `onOpenAutoFocus` prop (the library's documented extension point
    for exactly this, the same mechanism Radix's own `AlertDialogContent` uses internally, not a
    custom hack): the handler calls `event.preventDefault()` and focuses the Cancel button, located
    via a `data-confirm-dialog-cancel` attribute on the shared Cancel `<Button>` (a plain
    synchronous DOM query inside the library's own focus-management callback — no `setTimeout`, no
    `useEffect`, no polling).
  - Both platforms are handled with primitive-supported APIs, verified separately rather than
    assuming desktop behavior generalizes to mobile, per the review's explicit instruction.

## 6. Accessibility semantics preserved

  `Drawer` with `dismissible={false}` (mobile) — the exact same underlying primitives as before.
  No semantic downgrade to ordinary `Dialog`.
- `ResponsiveModal` still renders through `@radix-ui/react-dialog` (desktop) / `vaul` `Drawer`
  (mobile) — unchanged. The new close buttons use `Dialog.Close`/`Drawer.Close`, the libraries'
  own dedicated close-trigger primitives (not a manual `onClick` reimplementation), so focus

- Focus trap, focus-on-open, and focus-return-to-trigger are all still owned by Radix/vaul,
  untouched — per §21 "do not manually reimplement focus trapping if the underlying library
  already provides it."
- Portal usage unchanged in both components.

## 17. Keyboard/focus verification

Not run interactively (see §15's runtime-smoke-test limitation) — but the initial-focus claim
specifically (the one point that most needed rigor) was verified against installed library source
rather than left as an interactive-test gap. See §0/§5 for the full detail; summary:

- `Dialog.Close`/`Drawer.Close` are the libraries' dedicated close-trigger components — clicking
  or activating them via keyboard (Enter/Space, since they render as real `<button>` elements)
  triggers the library's own close + focus-return handling, the same mechanism the backdrop-click
  path already used.
- `ConfirmDialog`'s safe-focus behavior is now backed by each primitive's own documented mechanism
  — Radix's internal `cancelRef`-via-`AlertDialog.Cancel` on desktop, an explicit
  `onOpenAutoFocus` handler on mobile — confirmed by reading `node_modules/@radix-ui/react-alert-
  dialog` and `node_modules/vaul` source directly, not inferred from DOM order or assumed to
  generalize from one platform to the other.
- Escape: `ResponsiveModal`'s desktop path has no override, so Radix Dialog's default
  Escape-closes behavior applies (unchanged). `ConfirmDialog` explicitly prevents Escape on both
  platforms (unchanged, correct per §16/Audit Decision Record §9.1).
- What's still unverified interactively: actual Tab order through the full footer, and whether
  the visible focus ring renders correctly on the programmatically-focused Cancel button. Both are
  standard browser/CSS behavior once an element has `.focus()` called on it (no custom focus-style
  suppression was added anywhere in this wave), but a real browser check remains the honest gap —
  same as noted in §15, ahead of Pilot.

## 18. Known limitations

- **Missing Foundation tokens surfaced by this wave**, none invented to fill the gap:
  - No `--z-index` role above `--z-index-overlay` (40) for "alert/confirmation stacked above a
    normal modal" — `ConfirmDialog`'s `z-50` stays a raw literal. A future Foundation addition
    (e.g. `--z-index-alert`) would resolve this properly.
  - `border-slate-200`, `text-slate-950`, `text-slate-600` used throughout every overlay have no
    matching Foundation semantic token (checked against Wave 1's exact hex values — none match).
    This is real, repo-wide overlay-specific color fragmentation from the app's main neutral scale
    (`--color-border`/`--color-foreground`/`--color-muted`), not something this wave's
    "exact-alias-only" rename rule could safely touch.
  - Overlay radius (`28px`/`32px`) has no canonical `radius-ds-*` equivalent (nearest is `xl` at
    20px, a real value change) — left as-is, consistent with the same discipline already applied
    to Button `lg`/`icon` sizes and `--shadow-raised` in prior waves.
- `Dialog`/`BottomSheet`'s internal styling was **not** token-migrated — only JSDoc-deprecated.
  Deliberate: investing migration effort into a component marked DEPRECATE contradicts "no new V2
  usage," so token work went entirely into the canonical `ResponsiveModal`/`ConfirmDialog` instead.
- `BottomSheet`, when used with a controlled `open` prop, has no Portal, no focus trap, and no
  Escape handling at all (confirmed by reading its source) — a real, pre-existing accessibility
  gap in the *legacy* component. Not fixed, by design: fixing internals of a deprecated component
  isn't a good use of this wave's effort when the fix is "migrate to ResponsiveModal, which already
  has all three."
