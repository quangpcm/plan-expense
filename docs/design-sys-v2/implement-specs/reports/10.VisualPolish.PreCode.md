## 2. Finding 1 — Dashboard money truncation

**Root presentation cause:** `PlanCard` (`src/modules/plan/components/plan-card.tsx`) renders its
`primaryMetric.value`, `primaryMetric.detail`, `secondaryMetric.value`, `secondaryMetric.detail`,
and `progress.label`/`secondaryDetail` inside a fixed two-column grid (`grid-cols-2`) with
`className="truncate ..."` on every one of those text nodes. All of these values are pre-formatted
**strings**, not numbers, computed upstream in
`src/modules/plan/constants/plan-card-config.ts`. Every monetary one of them is built through a
single local helper:

```ts
function getSafeCurrency(value: number | null | undefined) {
  return formatCurrency(getSafeNumber(value));
}
```

`formatCurrency` (`src/shared/utils/currency.ts`) produces full-precision VND
(`Intl.NumberFormat('vi-VN', { style: 'currency', currency: 'VND' })`, e.g. `315.602.000 ₫`). For
a 9-digit+ value inside a card half-width slot, this string is too wide for the available space,
and the CSS `truncate` class clips it mid-digit with an ellipsis — exactly the observed
`315.602.00...`.

**Affected file(s):**
- `src/modules/plan/constants/plan-card-config.ts` — the single file that constructs every
  monetary string PlanCard renders. `getSafeCurrency` is private to this file (confirmed via
  repo-wide grep — zero other importers).

No change needed to `plan-card.tsx`, `build-plan-card-view-model.ts`, `plan-card.ts` (types), or
`currency.ts` itself.

**Existing formatting utilities found:**
- `formatCurrency` — full-precision VND. Already used by `getSafeCurrency` (the thing causing the
  bug).
- `formatCompactCurrency` — **already exists**, already produces exactly the target shape from the
  finding (`315,6 triệu` for ≥1M, `X tỷ` for ≥1B, `X nghìn` for ≥1K, falls back to full
  `formatCurrency` below 1,000 so small/zero amounts stay exact). This is not a new utility to
  invent — it is **already the established pattern for every other space-constrained
  card/summary slot in the app**: `PlanDetailShell`'s own header totals, Milestone cards/timeline,
  Todo cards, Debt-tracking cards, the Statistic category donut, and both Overview widget files
  (`overview-widget-registry.tsx`, `overview-widget-registry.wedding.tsx`) all already use
  `formatCompactCurrency` for exactly this kind of slot. `PlanCard` is the one remaining
  card-style money display still using full-precision formatting.

**Proposed minimal solution:** change `getSafeCurrency`'s implementation from `formatCurrency` to
`formatCompactCurrency`. One function, one file, reuses an already-proven, already-widely-adopted
utility — no new formatting architecture, no PlanType-specific branching, no change to
`formatCurrency`/`formatCompactCurrency` themselves (both stay untouched, so every other consumer
of full-precision `formatCurrency` elsewhere in the app is unaffected).

This is squarely a **PlanCard PlanType-specific visual configuration** fix (`plan-card-config.ts`
is exactly that boundary — it is the per-plan-type presentation layer that already varies label/
tone/detail per plan type), not a change to `PlanCard` presentation markup or to a shared formatter.

**Other PlanCard slots affected: YES.** `getSafeCurrency` is called uniformly for every monetary
value across all 9 plan-type configs and the ended-plan summary variant — `primaryMetric.value`,
`secondaryMetric.value`, both `.detail` fields, and every `buildXProgress()`'s `label` (e.g.
`"${getSafeCurrency(totalExpense)} / ${getSafeCurrency(budgetAmount)}"`). A single-function fix
closes the truncation risk identically everywhere it exists — Wedding's "Ngân sách"/"Dự chi" is not
special-cased, it just happens to be the one already observed in a real screenshot.

**Responsive implication:** none differs by breakpoint. `PlanCard`'s metric grid is a plain
`grid-cols-2` with no responsive variant in its own JSX; the truncation risk (and the fix) applies
identically at every viewport width — mobile cards are narrower so the risk is if anything higher
there, not different in kind.

**Risk: LOW** (existing formatter usage — swap one function call to another already-exported,
already-battle-tested utility; no new code paths, no type changes).

**Verification plan:** render `/plans` with a plan whose `budgetAmount`/`totalExpense` (and, for
debt/travel/etc., the relevant field) is a 7–9 digit VND value, across a representative sample of
plan types (at least `wedding`, since it's the reported case, plus one non-monetary-progress type
like `project` to confirm no regression) and both active and ended status. Confirm: no `…` ellipsis
appears mid-number on any metric slot; `isMoneyMasked` (locked-plan masking) still renders the
`•••••••` placeholder correctly since that logic wraps the value string and never inspects its
content; small amounts (<1,000₫, e.g. a fresh plan with 0 spend) still render exact, not
compacted-to-nothing. No screenshot matrix — a handful of targeted renders is sufficient since this
is a pure string-formatting change.

## 4. Finding 3 — Overview density

Both surfaces were inspected at their actual current composition: Travel's widgets live in the
shared `overview-widget-registry.tsx` (no Travel-specific file exists — Travel has no override
registry, unlike Wedding); Wedding's widgets live in `overview-widget-registry.wedding.tsx`
(merged into the shared registry via spread). Both already route through the `Section`/`Card`
primitives established during the Pilots — the composition is not broken, per the finding's own
framing; this is a targeted refinement, not a rebuild.

### Travel

**Candidate — `TravelItinerarySummaryWidget`'s "Tổng lịch trình" stat box** (RECOMMENDED)
- **Current composition:** inside the widget's own `<Card>`, when there's an upcoming activity, a
  2-column grid renders the activity's own details on the left and, on the right, a fully-boxed
  aside: `<div className="rounded-[24px] border border-slate-200 bg-slate-50/70 p-4">` containing
  just a label ("Tổng lịch trình"), a big number, and one line of supporting text.
- **Proposed simplification:** drop the bordered/filled box; render the same
  label/number/supporting-text as plain right-aligned typography (matching how single-stat asides
  render elsewhere in the app, e.g. `PlanCard`'s footer values, with no box). The 2-column grid
  layout itself, the activity details on the left, and all data/logic stay exactly as-is.
- **Expected visual benefit:** removes one full nested bordered/filled container for a
  single number+label pairing that doesn't need its own chrome to read as distinct from its
  sibling column — spacing and typography weight (already a `text-3xl font-semibold` number) are
  sufficient on their own.
- **Risk:** LOW — local presentation only, one component, no data/props change.

**Considered, KEEP AS-IS — `TravelTripStatusWidget`'s "Hành trình" panel:** the same-shaped
`rounded-[24px] border border-white/70 bg-white/80 p-4 backdrop-blur` box also appears here, nested
inside the hero `<Card>`'s gradient background. Unlike the itinerary-summary case, this box serves
a real legibility function: the parent Card has a diagonal gradient background bleeding across the
whole surface, and the semi-opaque white panel is what keeps its own text readable against that
gradient, not decorative duplication of the same content. Flattening it would risk contrast/
legibility regressions on the gradient background. **Not proposed for this batch.**

**Considered, KEEP AS-IS — `TravelPlanningProgressWidget` / `TravelAttentionTodosWidget` item
borders:** each renders a `Card` (Level 2/3 boundary) containing individually-bordered,
individually-clickable milestone/todo buttons. These items are genuine Level-3 "actual
interactive/data items," where the finding's own hierarchy model says a border remains appropriate
— this is not redundant framing of the same content, it's the actual clickable unit. **Not
proposed for this batch.**

**Considered, KEEP AS-IS — `TravelFinanceSummaryWidget`:** `SectionHeading` → three sibling `Card`s
(KPI row + 2 side-by-side insight cards), no card-in-card anywhere in this widget. Already good
hierarchy. **Not proposed for this batch.**

### Wedding

**Candidate — `AttentionItemRow`'s desktop-only card-in-card styling** (RECOMMENDED, highest-value)
- **Current composition:** `WeddingAttentionSummaryWidget` renders one `<Card className="gap-5">`
  containing two sub-sections. In the first ("Cần xử lý ngay"), each `AttentionItemRow` is a plain
  divided row on mobile (`divide-y divide-slate-100`, no per-item border) but on desktop
  (`lg:` breakpoint) gains its own full card treatment:
  `lg:rounded-[26px] lg:border lg:border-slate-200 lg:bg-white lg:shadow-[0_10px_32px_rgba(15,23,42,0.05)]`
  plus a hover-lift shadow — a Card nested inside the parent Card, at desktop only. `26px` is also
  a non-canonical radius value (the app's scale is 8/12/16/20/full; the second sub-section
  ("Sắp tới"), two paragraphs below in the exact same widget, already correctly uses the canonical
  `20px` on its own `DataRow` items).
- **Proposed simplification:** on desktop, replace the individual
  `rounded-[26px]/border/shadow/hover-shadow` treatment with a lighter one consistent with the
  "Sắp tới" rows directly below it in the same Card — e.g. a plain `20px`-radius border with a
  subtle hover background change, no independent drop shadow layered on top of the parent Card's
  own elevation. Mobile's already-lightweight `divide-y` treatment is untouched. No content,
  click target, or data changes.
- **Expected visual benefit:** removes a genuine double-shadow/double-card effect on desktop,
  brings the widget's two sub-sections (currently styled inconsistently from each other) into a
  single coherent visual language, and incidentally resolves a previously-flagged non-canonical
  radius value (`26px`) as a side effect of fixing the actual reported density issue — not a
  separate radius-cleanup action.
- **Risk:** MEDIUM — touches a responsive (`lg:`) class list on a component used identically for
  every attention-todo item; visually verify both breakpoints since the desktop and mobile
  treatments diverge today and must be reconciled without breaking the mobile path (which is not
  being touched, but must be re-confirmed unaffected).

**Considered, KEEP AS-IS — `WeddingMilestoneSnapshotWidget`:** `Section` → grid of 2
`WeddingMilestoneCard`s, each already `rounded-[var(--radius-ds-lg)] shadow-none` — lightweight,
single-level, no nested boxes. Already good hierarchy. **Not proposed for this batch.**

**Considered, KEEP AS-IS — `WeddingGuestSummaryWidget`'s pending-RSVP alert banner:** the
`rounded-2xl border border-[var(--color-status-warning-surface)] ...` callout inside the widget's

kept alert banners (`FundBalanceCard`, `SettlementSuggestionList`). **Not proposed for this
batch.**

**Considered, KEEP AS-IS — `WeddingFinanceSummaryWidget`:** single `Card`, no nested sub-boxes,
already lightweight. **Not proposed for this batch.**

## 5. Finding 4 — Pending invitations

**Current composition:** `InvitationList`
(`src/modules/invitation/components/invitation-list.tsx`) renders one full `<Card key={...}
className="gap-3">` per invitation — Card's own default recipe (`p-5`, `rounded-[var(--radius-card)]`
24px, border, shadow) around: an identity line + role line on the left, a status `Badge` top-right,
and, when revocable, a right-aligned "Hủy lời mời" `Button` on its own row below. With N pending
invitations stacked in a `grid gap-3`, each one independently boxed and shadowed, vertical space
scales linearly and heavily with invitation count — exactly the reported problem.

**Affected file(s):** `src/modules/invitation/components/invitation-list.tsx` only. Confirmed via
grep this component has exactly 2 consumers, both in `members-tab.tsx` (the primary pending-
invitations grid, and the "Lịch sử lời mời" `Collapsible` for non-pending history) — a single fix
to `InvitationList` benefits both call sites uniformly with no per-site changes needed.

**Proposed compact composition:** replace the per-invitation `<Card>` with `DataRow`
(`leading`/`main`/`status`/`trailing` slots — no `onClick`, since this row already has its own
explicit trailing action button, matching `DataRow`'s own documented guidance to stay
non-interactive when trailing already contains a button, and the same lesson already applied to
`WeddingGuestList`'s `DataRow` reject and the recent Member nested-button fix):
- `main`: identity (email or "Liên kết mời", bold) stacked with the role label underneath (same
  two pieces of text as today, same source fields).
- `status`: the existing status `Badge`, unchanged variant logic
  (`invitation.status === 'pending' ? 'info' : 'neutral'`).
- `trailing`: the "Hủy lời mời" `Button`, only when `canRevoke && invitation.status === 'pending'`
  — identical condition to today, just moved into `DataRow`'s `trailing` slot instead of a
  separate row.
- Wrapper `className` on each `DataRow` follows the same bordered-row convention already used by
  `SettlementList` and `CategoryBreakdown` (`rounded-2xl border border-slate-200 px-4`), so this
  isn't introducing a new visual convention, just reusing the one already established for exactly
  this "compact list of short entries" shape.
- The zero-invitations empty `<Card>` message is unchanged.

The finding's own mockup shows the cancel button wrapping to its own line below status — that's
illustrative, not a strict layout requirement (the finding explicitly says "or an equivalent
compact row/card composition"). `DataRow`'s standard single-row layout (main | status | trailing,
all inline, `main` free to truncate/wrap via its own `min-w-0 flex-1`) already satisfies the actual
goal (materially less vertical space per invitation than a full Card) using the exact established
pattern, with no new wrapping logic to invent for this one component.

**Permission/action preservation:** `canRevoke` and `invitation.status === 'pending'` gate
`trailing`'s presence with the identical boolean expression used today — no permission logic
changes. `onRevoke(invitation)` is still called with the same `InvitationDocument`, unchanged.

**Mobile/desktop behavior:** `DataRow` has no breakpoint-specific behavior of its own (unlike, say,
`ResponsiveModal`) — the same single-row composition renders identically at every width, with
`main`'s `min-w-0 flex-1` handling long emails via truncation the same way `Card`'s current
`<p>` (no truncate class today, actually — worth confirming during implementation whether to add
`truncate` to match other identity rows in the app, since the current Card version can already wrap
a long email across lines; `DataRow`'s single-row layout does not wrap `main`'s internal text by
default unless the paragraph itself allows it, so implementation should keep or add appropriate
truncation, not silently change wrapping behavine — flagged for implementation-time attention, not
a design decision this manifest needs to lock down).

**Risk: LOW–MEDIUM** (local composition change, single component with 2 known call sites, no new
shared API — `DataRow` itself is untouched, already-approved, already used this exact way
elsewhere).

**Verification plan:** render Members tab with 0, 1, and 5+ pending invitations (including at
least one with a long email and one email-less "Liên kết mời" entry) as both a manageable owner
(`canRevoke=true`) and a non-owner viewing "Lịch sử lời mời" (`canRevoke=false`, non-pending
statuses only). Confirm: status badge and role text unchanged in meaning, "Hủy lời mời" is
reachable and calls `onRevoke` with the correct invitation exactly as before, non-revocable/
non-pending rows correctly show no button, and the compact rows measurably reduce total vertical
space vs. the current per-item Card at 5+ invitations. No screenshot matrix — visual confirmation
at one representative width per breakpoint is sufficient.
