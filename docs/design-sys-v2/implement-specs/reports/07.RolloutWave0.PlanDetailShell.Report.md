## 2. Bounded inventory vs. actual scope

The Rollout Execution Plan estimated this file's remaining legacy surface as "1 BottomSheet + 1
window.confirm." The real count, found at this wave's own inventory (per `07.RolloutStrategy.md`
§9 — "do not plan rollout from folder names alone"):

  todo delete, expense delete, income delete) — not 1.
- `BottomSheet`: **3** occurrences (header 3-dot menu on mobile; 2 read-only statistic drilldowns)
  — not 1.

Cross-checked against `docs/ui-modal-conventions.md` §4 ("Khi nào KHÔNG áp dụng rule này"), which
explicitly exempts two categories from the ResponsiveModal rule:
- "Menu/popover đơn giản không phải form (ví dụ menu 3-chấm của Header)"
- "Drilldown/xem dữ liệu thuần túy không có hành động tạo/sửa"

All 3 `BottomSheet` instances in this file fall squarely into those two exempted categories. This
narrowed the real wave scope to the 6 `window.confirm` flows only. This is a bounded-inventory
correction, not a STOP-triggering finding — no business/permission/API impact, just a more
accurate file-level count than the pre-wave estimate.

## 5. Business / permission / data changes

**NO.** Every migrated flow is a mechanical 1:1 port:
- Same service call (`travelActivityService.deleteActivity`, `milestoneService.deleteMilestone`,
  `todoService.deleteVendor`, `todoService.deleteTodo`, `expenseService.deleteExpense`,
  `incomeService.deleteIncome`), same arguments, same error handling/messages.
- Same `if (!user) return` early-exit guard, now on `requestDeleteX` (previously the first line of
  the combined confirm+delete handler) — preserved so a null-`user` edge case still fully no-ops
  instead of opening a dialog it can't act on.
- Same success side effects (e.g. `performDeleteExpense`/`performDeleteIncome` still close
  `detailExpense`/`detailIncome` and `desktopFinanceDetail` only after the delete succeeds;
  `performDeleteTravelActivity` still only clears `detailTravelActivity` if it matches the deleted
  activity's id).
- No permission-gating logic was touched — all `canManage*`/`hasCapability(...)` checks upstream
  of these delete affordances are unchanged.
- No Firestore/service/repository file was touched.

The only functional delta: a `window.confirm()` (synchronous, blocks the JS thread until answered)
becomes a `ConfirmDialog` (async, non-blocking). This introduces a real gap that didn't exist
before — a user could theoretically double-click "Xóa/Xoá" before the request completes — so each
flow's existing submitting flag (`isTodoSubmitting`, `isMilestoneSubmitting`,
`isDeletingExpenseInline`, `isDeletingIncomeInline`) is now wired into `ConfirmDialog`'s `loading`
prop to disable the button mid-request, and a new `isDeletingTravelActivity` flag was added for the
one flow (travel activity) that previously had no submitting state at all. This is the same
double-submit protection every other `ConfirmDialog` usage in this file already relies on.

## 7. Targeted P0/P1 verification

No new isolated browser harness was built for this wave. Reasoning:

- The business-invariant risk surface for a delete-confirmation migration is "does Confirm mutate
  data exactly once, does Cancel mutate zero times, does the dialog show the correct target." All
  six flows are structurally identical ports of the same request/perform pattern already verified
  end-to-end in a real browser 3 times over (Dashboard's `TodoNotificationScreen`, Wedding Guest's
  guest/group/invitation deletes, and the dedicated Focus Return Fix matrix) — including the exact
  "Cancel = 0 mutations, Confirm = exactly 1 mutation, focus returns to trigger" assertions via a
  `confirmCount` counter script. `ConfirmDialog` itself (the shared component) was not modified in
  this wave.
- This page pulls live state from ~13 Firestore-backed hooks (`usePlan`, `useMilestones`,
  `useTodos`, `useExpenses`, `useIncomes`, `useTravelActivities`, `useDebtTracking`,
  `useDebtTransactions`, `useSettlements`, `usePlanMembers`, `usePlanInvitations`,
  `useCurrentUserProfile`, `useUserPlans`). Building an isolated mock-data harness equivalent to the
  Pilot-era ones would mean faking all 13 — disproportionate effort for a wiring-only change with
  zero altered business logic, and exactly the ceremony the lighter process model (§9 of the
  Execution Plan) is meant to remove for a proven pattern.
- Exercising the real Confirm path against a live plan was not an option regardless — that would
  permanently delete real Firestore data, which is out of scope for verification under any
  methodology used this session.
- What was done instead: a line-by-line equivalence check of each `requestDeleteX`/`performDeleteX`
  pair against the original `handleDeleteX` it replaced (documented in §5 above), confirming
  identical service arguments, identical guards, identical success/error side effects — plus full
  `tsc`/build success, which catches any prop-wiring or type mismatch across all 6 call sites
  (`onDelete`, `onDeleteMilestone`, `onDeleteVendor`, `onDeleteTodo`, `onDeleteDesktopDetail`, the
  two `DetailPanel.onDelete`s).

If a live-data-safe way to exercise the Confirm path becomes available (e.g. a seeded dev/test
Firestore project), a follow-up pass could add real interaction verification — not required to
close this wave given the above.
