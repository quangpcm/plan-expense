## 4. Current Dashboard architecture

```text
(authenticated)/layout.tsx
 └─ AuthGuard (modules/auth/components/auth-guard.tsx)
     └─ AppShell (shared/components/layout/app-shell.tsx)
         └─ PlansPage  (app/(authenticated)/plans/page.tsx)
             ├─ PageHeader                         [already V2 Core Pattern — see §5.1]
             ├─ FilterBar                          [already V2 Core Pattern — see §5.2]
             ├─ AuthFormMessage                    [error state — see §5.3]
             ├─ Skeleton × 2                       [loading state — see §5.3]
             ├─ TodoAttentionSection (module: todo) [see §5.4]
             ├─ PlanCard × N (module: plan)         [see §5.5]
             ├─ CreatePlanCard (module: plan)       [see §5.5]
             ├─ FAB (raw <button>)                  [see §5.5]
             ├─ TodoNotificationScreen (module: todo) [see §5.6]
             └─ ResponsiveModal → CreatePlanForm (module: plan) [see §5.7]
```

**Important context not obvious from the file tree:** unlike Wedding Overview (a config → registry →
composition architecture protected by ADR §22), the Dashboard page is a single container component
(`PlansPage`) that directly composes everything — there is no widget-registry layer here, and none
is proposed by this Pre-Code package. `PageHeader` and `FilterBar` (both Wave 5 Core Patterns) are
**already imported and in production use on this exact page** — `plans/page.tsx` is currently the
*only* production consumer of `PageHeader` in the entire codebase (confirmed by
`grep -rln "PageHeader" src`, which returns only `page-header.tsx` itself and `plans/page.tsx`).
This means Dashboard is not a cold-start migration for those two components; the shell-level
composition is already there. What is **not** yet migrated is what gets passed into their slots
(the bell button, the sort `<select>`, the search `Input` wrapper) and everything below the
header/filter row (PlanCard, CreatePlanCard, the two state banners, the two overlays).

## 5. Current sections (detailed)

### 5.1 Header → `PageHeader`

`plans/page.tsx:62-87`. Already composed on the V2 `PageHeader` (`shared/components/ui/
page-header.tsx:19-30`, `title`/`description`/`actions` slots, all Foundation-token typography).

`actions` slot content is **not** itself migrated:
- Notification bell — raw `<button>` (`plans/page.tsx:65-77`) with hand-rolled tone classes
  from a **local** `getBellToneClass` (`plans/page.tsx:27-37`) that mixes Foundation tokens
  (`--color-border`, `--color-muted`, `--color-accent`) with raw Tailwind
  (`border-rose-200 bg-rose-50 text-rose-600`, `border-amber-200 bg-amber-50 text-amber-600`) —
  no exact-alias exists for rose/amber in Foundation (`--color-status-danger`/`-warning` exist but
  are not byte-identical to these specific rose-200/amber-200 shades, so per the established
  exact-alias rule from Wave 1, they cannot be silently substituted).
  Count badge (`plans/page.tsx:72-76`) is a raw `<span>` with `bg-rose-500`, same gap.
- `Avatar` (`plans/page.tsx:78-82`) — already the shared `shared/components/ui/avatar.tsx` (V2
  Core Primitive per ADR §20.3 ADAPT list), called with a per-instance inline shadow
  (`shadow-[0_10px_24px_rgba(43,94,242,0.2)]`) not present in the primitive itself; `Avatar`'s own
  fallback state uses a raw `bg-slate-950` (avatar.tsx:25), not a Foundation token — pre-existing
  gap in the primitive itself, not introduced by Dashboard.

### 5.2 Filter/search row → `FilterBar`

`plans/page.tsx:89-115`. Already composed on the V2 `FilterBar` (`shared/components/ui/
filter-bar.tsx:18-26`, `search`/`filters`/`actions` slots).

Contents are not migrated:
- Sort control (`plans/page.tsx:91-102`) — a raw `<select>`, hand-styled
  (`rounded-2xl border border-[var(--color-border)] ...`), even though `DropdownSelect`
  (`shared/components/ui/dropdown-select.tsx`) exists and is already used elsewhere on this very
  page inside `CreatePlanForm` (`create-plan-form.tsx:134-139`). `DropdownSelect`'s contract is
  `value / onValueChange / options: {value,label,icon?}[]` — a 2-option list
  (`updatedAt` → "Mới nhất", `createdAt` → "Ngày tạo") maps cleanly onto it.
- Search control (`plans/page.tsx:104-114`) — shared `Input` + a raw absolutely-positioned lucide
  `Search` icon with a `pl-10` padding hack. The *same* icon-prefix pattern is duplicated
  independently for the sort control's `ArrowUpDown` icon one block above
  (`plans/page.tsx:91-92`) — i.e. two ad hoc "icon + input/select" compositions on the same row,
  no shared recipe. No `InputWithIcon`/`SearchInput` primitive exists in the current component
  catalogue (checked `shared/components/ui/`), so this is evidence, not something to invent a
  primitive for inside this Pilot.

### 5.3 State banners

- **Error**: `AuthFormMessage` (`plans/page.tsx:118`), shown when `useUserPlans().errorMessage` is
  set. **`AuthFormMessage` (`modules/auth/components/auth-form-message.tsx`) is used in 40+ files
  across the entire app** (confirmed by `grep -rln`, spanning auth, expense, settlement, wedding-guest,
  member, debt-tracking, income, milestone, planning, travel-activity, todo, and the Wedding Overview
  widget registry that this Pilot's predecessor deliberately did not touch). It is a de facto
  shared component even though it lives in `modules/auth/`, is not itself token-based
  (`bg-rose-50 text-rose-700` / `bg-emerald-50 text-emerald-700`, raw Tailwind), and is **out of
  file boundary for this Pilot** (§14) — changing its own file would ripple into every other
  screen that imports it, including screens no V2 wave has reviewed yet. Any Dashboard-side
  migration of this error banner must happen by changing what `plans/page.tsx` renders locally
  (e.g. swap the call site to `ErrorState`), never by editing `auth-form-message.tsx` itself.
- **Loading**: two `Skeleton` blocks (`plans/page.tsx:120-124`, `h-44 rounded-[28px]`) in a plain
  `grid gap-4` with **no responsive column classes**, unlike the real grid below it
  (`sm:grid-cols-2 lg:grid-cols-3` appears at lines 126 and 140 but not at line 121) — a pre-existing
  loading-state fidelity gap (skeleton always renders as 1 column even on tablet/desktop where the
  real grid would show 2-3).
  `Skeleton` itself (`shared/components/ui/skeleton.tsx:5-7`) still renders `bg-slate-200`, a raw
  Tailwind color with no exact Foundation alias — same gap already recorded and left alone during
  Wedding Overview (`conservation-context.md` §5.3: "Badge, Skeleton (chỉ đổi radius token) → giữ
  nguyên (KEEP)"). Consistent precedent to follow here too unless new evidence changes that.

### 5.5 Plan grid: `PlanCard`, `CreatePlanCard`, FAB

**`PlanCard`** — `modules/plan/components/plan-card.tsx:37-200`, one per plan
(`plans/page.tsx:130-132`, inside `filteredPlans.map`).
- Wraps shared `Card` with heavy per-instance overrides (`plan-card.tsx:49`):

  hover:-translate-y-0.5 hover:shadow-[0_20px_70px_rgba(23,32,51,0.08)]` — a raw rgba border color
  and two raw shadow values on top of `Card`'s own already-legacy `--radius-card` +
  `shadow-[0_18px_54px_rgba(23,32,51,0.06)]` recipe (`card.tsx:19`, explicitly marked
  `TEMPORARY LEGACY COMPATIBILITY`, reverted after Wave 4 review, **still in effect** — see

- Role badge (`plan-card.tsx:70-74`, shown only when `plan.role !== 'owner'`) already uses `Badge`.
- Lock icon (`plan-card.tsx:75-79`) is a raw `<span>` pill, **not** `Badge`, styled inconsistently
  with the role `Badge` two lines above it.
- "Active" status (`plan-card.tsx:80-84`) is a bespoke inline `<span>` with a dot +
  `bg-[var(--color-success-soft)] text-[var(--color-success)]` — functionally identical to what

  value.
- Primary/secondary metric block (`plan-card.tsx:94-141`) — raw label/value/detail markup with
  `cn()` tone-branching (`default`/`success`/`warning`/`danger`, lines 100-105 and 128-133) that is

  (`label`/`value`/`supporting`/`tone`). `Metric`'s `tone` union (`default/success/warning/danger/

  accentTextClassName` is a **9-way, per-plan-type raw hex color** (`plan-card-visuals.ts:25-98`,
  e.g. `text-[#9a3412]` for debt, `text-[#0c48d7]` for all 8 other types) applied when tone is

  and does not have an existing Foundation equivalent — a genuine open question for the Manifest
  (see §13), not something to resolve by inventing a token here.
- Progress bar (`plan-card.tsx:143-150`) — raw two-`div` track+fill, styled per-plan-type via
  `visual.progressTrackClassName`/`progressFillClassName` (also raw hex,
  `plan-card-visuals.ts:31-96`). **This is the same "no Progress/ProgressBar primitive exists"
  finding already recorded and deliberately left unresolved after Wedding Overview**
  (`conservation-context.md` §5.5, item 2, "STRUCTURAL ISSUE (candidate)... chờ bằng chứng từ
  Pilot #2/#3"). Dashboard is exactly that second piece of evidence.
- Footer row (`plan-card.tsx:186-196`) — raw flex row, icon + label/value pairs, structurally

  static row (not a list) makes the fit weaker than a typical `DataRow` use case.
- Money-masking (`plan-card.tsx:15-35`, `MASKED_MONEY_VALUE = '•••••••'`, applied when

### 5.6 `TodoNotificationScreen` — full-screen/bottom-sheet overlay, NOT built on `ResponsiveModal`

`modules/todo/components/todo-notification-screen.tsx` (used only here: `plans/page.tsx:154`, and
its own file — confirmed by `grep -rln`, no other consumer exists).

This is the most structurally significant finding on this surface. It hand-rolls its own overlay
(`todo-notification-screen.tsx:172-177`, `fixed inset-0 z-50 ...`) with its own responsive split:
- Mobile: full-screen panel.
- **Desktop/tablet (`md:` and up): still bottom-anchored** (`md:min-h-[40vh] md:max-h-[78vh]
  md:rounded-t-[32px] md:border md:border-b-0`, line 72), only capped to `md:max-w-2xl` and
  centered horizontally with a backdrop click-to-close (line 174).

This is a **different responsive model from `ResponsiveModal`**, which switches to a fully
**centered** Radix `Dialog` at `≥768px` (`responsive-modal.tsx:38-46`) rather than staying
bottom-anchored. `ResponsiveModal`'s `title` prop is also typed as plain `string`
(`responsive-modal.tsx:19`), not `ReactNode` — it cannot directly accept
`TodoNotificationScreen`'s richer header (icon badge + dynamic subtitle text that changes based on
`todayAttentionCount`, lines 77-87). Per `06.PilotMigration.md` §26/§27 ("Do not force a mapping
where the semantic fit is weak" / "Do not downgrade AlertDialog semantics... do not change mutation
behavior while migrating overlay presentation"), this is flagged as **REVIEW**, not an assumed
REPLACE — the Manifest should not presuppose `TodoNotificationScreen` collapses onto
`ResponsiveModal` without a deliberate design decision, since doing so would also require either
widening `ResponsiveModal`'s `title` contract or accepting a header downgrade, and would change its
desktop positioning behavior (bottom-anchored → centered), which is a visible interaction change,
not pure token migration.

Internally: own duplicate loading (3 raw `animate-pulse` divs, lines 107-109, not `Skeleton`), own
duplicate error banner (raw rose-50/rose-700, lines 102-104, third independent copy of the same
banner pattern seen in `plans/page.tsx:118` via `AuthFormMessage` and in
`todo-attention-section.tsx:81`), and its own empty state (lines 111-120: icon badge + heading +
description) — this is the **richest, most EmptyState-shaped markup found on the whole Dashboard
surface**, a good reference/candidate pattern if `EmptyState` adoption is pursued here, per
`06.PilotMigration.md` §38.
Uses shared `Button` (line 165, `variant="secondary"`) for its mobile-only footer close action —
the one already-migrated primitive in this file.

## 6. Business invariant mapping

| Invariant | Current behavior | Affected UI | Migration risk | Verification method |
|---|---|---|---|---|
| **Plan list ordering is user-controlled, client-side** | `filteredPlans` sorts by `sortBy` (`updatedAt` default or `createdAt`), descending, via `Timestamp.toMillis()` (`plans/page.tsx:52-57`) | Sort control in FilterBar | LOW — pure client `useMemo`, no server query change; migrating the raw `<select>` to `DropdownSelect` must preserve the exact same 2 options/values/default | Value diff: same plan order before/after for a fixed dataset and sort selection |
| **Search is client-side substring match on `planName` only** | `plans.filter(p => p.planName.toLowerCase().includes(query))` (`plans/page.tsx:53-54`) | Search Input in FilterBar | LOW — no debounce, no server call, nothing to preserve beyond the filter predicate itself, which this Pilot does not touch | Functional check: same filtered set before/after for a representative query |
| **Locked-plan money masking is a real privacy behavior, not decoration** | `plan.isLocked → MASKED_MONEY_VALUE` replaces every monetary primary/secondary/detail/progress-label value across `PlanCard` (`plan-card.tsx:15-35`, applied at 5 separate call sites: 105/107, 112-113/116-119, 133/136-138, 155/158, 164/167-169) | PlanCard metrics/progress | MEDIUM — this is the first Pilot to encounter a masking behavior; any `Metric`/`Progress` composition must keep masking applied per-value (not as a whole-card blur), exactly matching today's 5 call sites | Visual + value diff: locked vs unlocked plan of the same type, confirm every monetary field masks/unmasks identically |
| **Plan-Type Expression is a real 9-way branch, not a theme swap** | `planCardVisualsByType` (icon/gradient/accent-color/progress colors) and `planCardConfigByType` (which 2 metrics, what they mean, what the progress bar represents) both keyed by all 9 `PlanType` values (`plan-card-visuals.ts:25-98`, `plan-card-config.ts:425-621`) | Every PlanCard | MEDIUM — per MG-DR-04 (ADR §30), no `planType` prop may be added to a generic Design System component to switch styling; whatever composition emerges must resolve the per-type visual/metric decision in the product layer (`PlanCard`/`plan-card-visuals.ts`/`plan-card-config.ts`), same as today, just potentially composing `Metric`/`MetricGroup`/a future Progress primitive rather than raw divs | Visual diff across all 9 plan types (icon, accent color, metric labels/values, progress) |
| **Ended-plan status changes which metrics render, independent of plan type** | `isEndedPlan` branch (`plan-card-config.ts:36-38, 301-423`, `buildEndedSummaryConfig`) swaps the metric set for an ended plan regardless of its type | PlanCard metrics | LOW — pure pass-through of an already-resolved view model into presentation | Value diff: same plan, active vs ended, confirm metric set matches pre-migration exactly |
| **Debt plans have a sub-model that changes displayed metrics** | `resolvePlanDebtModel` (referenced in `plan-card-config.ts`, `DebtModel = 'finance_aggregate' | 'native_debt'`) changes whether a debt-type PlanCard shows "Phải thu/Phải trả" or "Dòng tiền ròng" | PlanCard metrics for `planType: 'debt'` | LOW — presentation pass-through of an existing resolved value; not touched by this Pilot's file boundary | Value diff: one `finance_aggregate` debt plan and one `native_debt` plan, confirm correct label set survives migration |
| **Attention-todo aggregation only considers active plans** | `useAttentionTodos` filters `plan.planStatus === 'active'` before subscribing (`use-attention-todos.ts:32`) | Bell tone/count, TodoAttentionSection, TodoNotificationScreen | LOW — filter logic lives in the hook, untouched by this Pilot's file boundary (§14) | Functional check: an ended/archived plan with overdue todos must not affect bell count |

## 7. Permission-sensitive actions

Unlike Wedding Overview's per-widget `moduleId` gating (resolved upstream in
`overview-renderer.tsx`), Dashboard has **no module-access-based visibility gating of its own** —
every user who reaches this page sees the full header, filter bar, todo-attention section (if any
attention items exist), full plan grid, and both create-plan entry points identically. The only
permission/privacy-relevant behaviors found:

| Action/state | Owner | Editor | Viewer | Notes |
|---|---|---|---|---|
| Create plan (CreatePlanCard/FAB → CreatePlanForm) | Available | Available | Available | Not role-gated at all — creating a plan makes the creator its Owner; this screen doesn't show plans that don't exist yet, so "role" is moot for this specific action |
| Role badge on `PlanCard` | Hidden (`plan.role === 'owner' ? null : ...`, `plan-card.tsx:70`) | Shown, label "Biên tập" | Shown, label "Theo dõi" | Display-only; does not gate any action on the card itself (card is always a `next/link` to the plan, `plan-card.tsx:48`) |
| Locked-plan money masking (`plan.isLocked`) | Same masking applies regardless of role — this is a plan-level privacy flag, not a role-derived permission | | | Must be preserved exactly (§6) — the only actual visibility-affecting state on this surface |

No `hasCapability`/`resolveModuleAccess`/role-branching code was found anywhere in `plans/page.tsx`,
`plan-card.tsx`, `create-plan-card.tsx`, `create-plan-form.tsx`, `todo-attention-section.tsx`, or
`todo-notification-screen.tsx` (confirmed by grep for `role ===`, `hasCapability`, `moduleAccess`
across these files — only the one `plan.role === 'owner'` display check above exists). This is a
genuinely lower permission-complexity surface than Wedding Overview, consistent with ADR §27's

## 13. Anticipated Design System findings (flagged in advance, not yet acted on)

1. **Progress/ProgressBar primitive — now with a second piece of evidence.** Wedding Overview
   recorded this as a "STRUCTURAL ISSUE (candidate)" pending more evidence
   (`conservation-context.md` §5.5 item 2). `PlanCard`'s progress bar (`plan-card.tsx:143-150`) is
   the second independent hand-rolled progress bar found across the two Pilots so far. Per the
   established rule, this is recorded as evidence toward — not a decision to build — a Progress
   primitive. Should be raised explicitly in the STOP/GO review after this Pilot (ADR §28).
2. **Plan-type accent color system has no Foundation equivalent.** `accentTextClassName` /
   `progressTrackClassName` / `progressFillClassName` in `plan-card-visuals.ts` are 9 raw hex
   values with no exact Foundation alias, and unlike Wedding Overview's raw-color gaps (which were
   generic slate/rose/amber/sky with no domain meaning), these specifically encode **Plan-Type
   Expression** — the ADR's own vocabulary (§27, §11.3) for "a plan type should look and feel
   distinct." This is not simply "gap, leave raw" like the others; it may need an explicit Plan-Type
   Expression token layer (e.g. `--color-plan-type-{type}-accent`) as a Foundation extension, which
   is a bigger decision than this Pre-Code package should make unilaterally. Flagged for explicit
   Manifest-review discussion, not a default direction.
3. **Text-link/IconButton primitive gap — same finding, different shape.** Wedding Overview
   recorded "no text-link footprint" (Button forced to override chrome away). Dashboard's bell
   button (`plans/page.tsx:65-77`) is an icon-only trigger with a badge overlay, not a text link —
   a related but distinct gap (an "IconButton" or "IconButton + NotificationBadge" primitive, not a
   text-link one). Recorded as a second, adjacent primitive-gap data point, not assumed to be the
   same finding.
4. **Radius inconsistency has grown, not shrunk.** Wedding Overview already found Card-adjacent
   radius drift. Dashboard adds a fourth concrete value into the same visual system:
   `PlanCard` `24px`, base `Card` `--radius-card` (24px equivalent), `TodoAttentionSection`'s
   `Card` override `28px`, `CreatePlanCard` `28px`, `Skeleton` loading blocks `28px`. Worth
   surfacing at the STOP/GO review as a concrete, cross-Pilot pattern rather than two isolated
   Pilot-local issues.
5. **The three-copy urgency-tone mapping (rose/amber/sky) is now confirmed present on two
   independent files within this single Pilot** (`todo-attention-section.tsx:28-50` and
   `todo-notification-screen.tsx:34-56`), in addition to being cross-referenced by name in the
   Wedding Overview Pre-Code package. This is real duplicated-logic evidence for a shared
   "urgency tone" utility/token set, not just a presentational nit.

None of the above are proposed to be resolved inside this Pilot's implementation — they are
recorded per `06.PilotMigration.md` §74/§76 ("classify layer... do not patch every issue locally")
for the Manifest reviewer's judgment on whether Dashboard alone is enough evidence to act, or
whether the STOP/GO review (ADR §28) is the correct venue.
