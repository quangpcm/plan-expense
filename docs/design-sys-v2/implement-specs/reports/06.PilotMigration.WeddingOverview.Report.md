## 8. `AttentionItemRow → DataRow`: evaluated, kept custom

Per the conditional override ("compose only if genuinely simpler"), this was evaluated concretely
before deciding:

- `AttentionItemRow` has **no `leading` slot**, a `main` (title + metadata line), and a `trailing`
  countdown badge — anatomically DataRow-shaped on mobile.
- But its **desktop (`lg:`) presentation isn't a row transformation** — it becomes a bordered,
  shadowed, hover-lifting card arranged in a 1-3 column grid (`lg:rounded-[26px] lg:border
  lg:bg-white lg:shadow-[...] lg:hover:-translate-y-0.5 ...`). `DataRow`'s own desktop behavior
  model (Wave 4/5) is "may use more horizontal alignment," not "becomes a distinct card with its
  own elevation at a breakpoint." Composing `DataRow` here would require passing most of that
  desktop treatment back in through `className` overrides, at which point `DataRow` would
  contribute little beyond its own `flex` scaffolding while fighting its interactive default
  styles (`hover:bg-[var(--color-surface-subtle)]`, its own `rounded-[var(--radius-ds-md)]`) for
  no real simplification.
- The plain "upcoming todo" row (§7, no breakpoint-conditional treatment at all) *did* compose
  cleanly — confirming the difference is specifically the desktop card-ification, not `DataRow`
  itself being a poor fit for todo rows in general.

**Decision: `AttentionItemRow` stays custom.** Only its color tokens were left as-is (no exact
Foundation alias exists for its `slate-*`/`rose`/`amber`/`sky` palette — same "don't force an
inexact mapping" discipline applied throughout every prior wave).

## 22. Design System issues discovered

Both were anticipated in the Pre-Code package (§13) and are now confirmed by actual implementation,
not just prediction:

1. **Core Primitives has no canonical "text link" footprint.** `Button`'s only two sizes (`sm`,
   `md`) both assume real button chrome (padding, `min-h-*`, `rounded-full`). Adopting `Button` for
   `ViewAllAction` required overriding `h-auto min-h-0 gap-0 rounded-none p-0` — a substantial
   override, not a clean drop-in. Classification: `PRIMITIVE ISSUE`. Recommendation: if this
   pattern recurs in Dashboard (Pilot #2) or Wedding Guest (Pilot #3), it's real evidence for a
   `Button` "link" variant or a separate lightweight `LinkButton`/`TextAction` primitive — not
   invented here, on a single Pilot's evidence.
2. **No canonical Progress/ProgressBar primitive exists.** Confirmed unchanged — all 3 hand-built
   progress bars in this file (milestone %, RSVP multi-segment, budget %) were left as-is per
   override's explicit instruction, only their fill colors token-migrated. Classification:
   `STRUCTURAL ISSUE` (candidate). Same recommendation as the Pre-Code package: wait for Dashboard/
   Wedding Guest evidence before proposing an abstraction.

Neither was acted on beyond token migration, per 06.PilotMigration.md §76 ("classify layer, don't
patch every issue locally inside the Pilot").

### 23a. Issue found and fixed during this pass

**`WeddingMilestoneCard`'s title truncation did not actually truncate.** The `truncate` class was
already present on `milestone.title`'s `<p>` (pre-existing, not part of this Pilot's diff), but two
ancestors had no width constraint: the wrapping flex item (missing `min-w-0`) and the `Card` itself,
which is a **CSS Grid item** at `WeddingMilestoneSnapshotWidget`'s `grid gap-3 lg:grid-cols-2`
container — grid items default to `min-width: auto`, i.e. content's min-content size, exactly like
flex items, unless explicitly reset. With a long milestone name (content-stress scenario), the title
ran past the Card's right edge with no ellipsis, at every breakpoint below `lg`. Fixed by adding
`min-w-0` to both the flex item (`overview-widget-registry.wedding.tsx`, `WeddingMilestoneCard`,
the `<div>` wrapping the eyebrow label + title) and the `Card` itself
(`className="min-w-0 gap-3 rounded-[var(--radius-ds-lg)] shadow-none"`). This is a **pre-existing
bug**, not a regression introduced by this Pilot — confirmed via `git diff`, the two ancestor
elements were unchanged context lines before this fix. Both edits are inside
`overview-widget-registry.wedding.tsx`, the file already in scope for this Pilot. Re-ran
typecheck → tests → full build → full browser re-verification after the fix (§18-21, this section)
— all clean, no other regression found.
