# Post-Rollout Design System Review

**Scope:** analysis only. No source code modified. Synthesizes `1.AuditSpecification.md`,
`3.AuditDecisionRecord.md`, `implement/01–08.*.md`, `07.StopGoSystemReview.md`, all 3 Pilot reports,
and `07.RolloutWave0` through `07.RolloutWave7` reports, cross-checked against current source where
a claim needed re-verification rather than re-audited from scratch.

## 1. System health

The Design System survived 3 Pilots + 8 Rollout waves without drifting from its own stated
principles:

- **Generic components stayed domain-neutral.** `grep` across `src/shared/components/ui/` for
  `planType` returns zero hits — no shared primitive knows about Plan-Type, wedding, debt
  direction, or settlement semantics. Every domain concept (guest/attendee count, debt direction,
  settlement direction, member balance sign) stayed in product code and was passed into generic
  primitives (`Metric`, `DataRow`, `MetricGroup`) as already-resolved values/tone props, never as
  business logic embedded in the primitive.
- **No God Component emerged.** `Button` gained exactly one variant (`destructive`, harvested
  byte-for-byte from existing code) and one size (`sm`, same) across the whole rollout — `size="icon"`
  was proposed and deliberately not added twice (Wave 2, this review) for lack of a forcing
  requirement. `Card` kept a single, documented legacy-compat default throughout — no per-consumer
  prop sprawl. `ResponsiveModal`/`ConfirmDialog` still have the same minimal prop surface as when
  Overlay Architecture shipped; the one real capability gap (`ResponsiveModal` has no `size` contract)
  was **not** patched around with an ad-hoc escape hatch — it stayed a documented block on exactly
  one consumer (`WeddingGuestImportDialog`, see §5.8).
- **Business calculations and permission semantics stayed outside the DS**, verified per-wave, not
  assumed: every Wave report includes an explicit diff check confirming zero touch to
  `*.service.ts`, repositories, `statistic.service.ts`, `settlement.service.ts`,
  `debt-calculators.ts`, and every `hasCapability`/`hasPlanCapability` call site. This held even in
  the two R4 waves (statistic, settlement) that touched the app's most calculation-dense surfaces.
- **Legacy compatibility decisions stayed controlled, not diffuse.** The `Card` legacy-radius
  default is one decision made once (Wave 4) and never re-litigated per consumer. The
  `BottomSheet`→`ResponsiveModal` migration reached 0 remaining MIGRATE-classified consumers
  (everything left is either exempt-by-policy or one explicitly-tracked blocked exception — see
  §5.13 and §5.8).
- **One real defect survived the entire rollout unfixed by design**: a nested `<button>`-in-`<button>`
  hydration/HTML-validity bug in `member-list.tsx`, flagged in Wave 4, deliberately left alone at
  every subsequent checkpoint per explicit "don't fix opportunistically" instructions. Re-confirmed
  still present in current source (§2.1) — this is the one finding in this review that changes the
  system's shippability, not just its aesthetic polish.

**Overall: the system is stable enough to ship.** Ten consecutive Waves/Pilots reported
170/170 tests green, clean production builds, and zero business/permission/data regressions. The
one confirmed runtime defect (§2.1) is small, isolated, and has a narrow fix — it does not indicate
systemic instability, but it should not ship unaddressed either.

## 2. P0 — MUST FIX BEFORE GO LIVE

### 2.1 Member row: `<button>` nested inside `<button>` (hydration + accessibility defect)

- **Issue:** `member-list.tsx`'s `summary` block renders an avatar-change
  `<button aria-label="Đổi avatar của {nickname}">` (line ~155) as a descendant of `Collapsible`'s
  own toggle `<button type="button" onClick={... setIsOpen}>` (`collapsible.tsx` line 32) whenever
  `header={summary}` is used — which is every non-owner, manageable member row (`Card` → `Collapsible`
  branch in `member-list.tsx`). Confirmed still present in current source (re-read both files
  directly; not fixed at any point across Wave 4 or its addendum, both of which explicitly deferred
  it).
- **User/product risk:** Nesting interactive elements is invalid HTML — browsers auto-correct the
  parse tree, which no longer matches what React's virtual DOM expects, producing a real
  hydration-mismatch error on every render of this block (confirmed as a genuine console error in
  Wave 4's own testing, not a false alarm). Neither the inner nor outer `onClick` handler calls
  `stopPropagation()`, so tapping the avatar can also toggle the row's expand/collapse state in the
  same gesture — a real, user-visible double-action glitch on a page (Members) that every plan
  owner visits to configure access. It is also a concrete accessibility violation: nested
  interactive controls have undefined behavior for screen readers and keyboard navigation (tab
  order, activation semantics).
- **Affected files/layer:** `src/modules/member/components/member-list.tsx` (the `summary` block)
  and, if a structural fix is chosen at the shared level, `src/shared/components/ui/collapsible.tsx`.
  Product layer, not Design System core — `Collapsible` itself is used correctly elsewhere (its
  `header` prop is a general slot; the bug is in what `member-list.tsx` puts into that slot).
- **Recommended action:** restructure `member-list.tsx`'s `summary` so the avatar-change affordance
  is not itself a nested interactive element inside `Collapsible`'s trigger — e.g. render the avatar
  as non-interactive inside the collapsed header and move the "change avatar" action into the
  already-expanded `editForm` (next to "Lưu thay đổi"/the actions menu), or make it reachable via the
  actions menu. This is a product-file-only fix; no Design System API change is implied.
- **Expected blast radius:** one file (`member-list.tsx`), no other consumer of `Collapsible` is
  affected (no other `header` prop usage nests an interactive element — not re-audited exhaustively
  here, but no other wave report flagged a similar pattern). Fix is presentation-only; no
  service/permission/data touch required.

## 3. P1 — SHOULD FIX BEFORE GO LIVE

### 3.1 Settlement mutation has no confirmation step (`SettlementSuggestionCard`, `SettlementList`)

- **Issue:** "Xác nhận đã chuyển" (`settlement-suggestion-card.tsx`) and "Hủy"
  (`settlement-list.tsx`) both mutate financial settlement state immediately on click — direct
  `onClick={onConfirm}`/`onClick={onCancel}`, no `window.confirm`, no `ConfirmDialog`, confirmed via
  current source. This predates the Design System rollout (Wave 7 confirmed it, unchanged) and was
  correctly left untouched per that wave's presentation-only mandate.
- **User/product risk:** this is now the **only** consequential/financial mutation left in the app
  with zero confirmation step — every other destructive or consequential action (delete plan/member/
  guest/milestone/todo/expense/income/vendor, unlink account, reactivate/deactivate member, close/
  archive/complete plan) was migrated to `ConfirmDialog` gating across the 3 Pilots + Wave 0/4. A
  mis-tap on "Xác nhận đã chuyển" records a money transfer as having happened; a mis-tap on "Hủy"
  reverses a completed settlement. Risk is partially mitigated — "Hủy" exists specifically to reverse
  a completed settlement, so the confirm-side mistake is recoverable via a second real action, not
  silent data loss — which is why this is P1, not P0.
- **Affected files/layer:** `src/modules/settlement/components/settlement-suggestion-card.tsx`,
  `src/modules/settlement/components/settlement-list.tsx`. Presentation layer only —
  `settlement.service.ts` and both repositories are unaffected by adding a confirm step.
- **Recommended action:** wrap both actions in `ConfirmDialog`, using the exact request/perform
  pattern already proven across 3 Pilots + Wave 0/4 (`requestConfirmSettlement`/
  `performConfirmSettlement`, `requestCancelSettlement`/`performCancelSettlement`). This is a
  behavior change (net-new confirmation step), not a migration — it needs an explicit go-ahead
  before implementing, which is why it is not done as part of this review.
- **Expected blast radius:** 2 files, additive only (no existing prop/callback signature needs to
  change — `onConfirm`/`onCancel` still get called, just after a confirm step). No DS API change.

### 3.2 Duplicated bell-tone mapping (`getBellToneClass`)

- **Issue:** `getBellToneClass()` is defined identically (byte-for-byte, all 3 branches and the
  fallback) in both `todo-notification-screen.tsx` and `todo-attention-section.tsx`.
- **User/product risk:** none directly — this is pure code duplication, not a behavior gap. Flagged
  as P1 rather than P2 only because it is a correctness *trap*: the two files will silently diverge
  the next time someone tunes attention-tone colors in one and forgets the other, which is a higher-
  probability bug source than most P2 items in this review.
- **Affected files/layer:** both files above, `src/modules/todo/`. Pure presentation, no service/data
  touch needed.
- **Recommended action:** extract to one shared util (e.g. `todo/utils/attention-tone.ts`) and import
  in both. Not a Design System change — this is product-internal deduplication.
- **Expected blast radius:** 2 files edited + 1 new util file. Zero behavior change if done as a
  pure extraction.

## 4. P2 — SAFE POST-GO-LIVE

### 4.1 Progress primitive (linear single-value family)

Evidence is now substantial and spans 4+ modules: Wedding Overview (milestone %, budget %),
Dashboard `PlanCard`, Statistic (`FinanceBudgetProgress`, `FinanceMilestoneBars`,
`MemberBalanceTable`'s 2 `ComparisonBar`s/row, `MemberSpendingList`'s embedded bar), Settlement
(`SettlementProgressSummary`'s pending-state bar). All of these are the **same shape**: a single
value against a max, rendered as a filled bar with a semantic tone. This family has crossed the
evidence bar for a shared primitive.

**Segmented progress is a different, separate family and should not be folded into the same
component**: `RsvpDonutChart` (Wedding Guest) and `FinanceCategoryDonut` (Statistic) are both
multi-category donut charts with their own arc-geometry/grouping logic (top-N + "Khác" bucketing) —
structurally a chart, not a progress bar. Evidence for a shared *segmented* primitive is weaker (2
data points, both circular/donut, not linear-segmented) and should be evaluated separately from the
linear-progress decision, not bundled into one "Progress" component spec.

**Not a Go-Live blocker**: every current instance already renders correctly with its own
hand-rolled bar; building a shared primitive is a consistency/maintainability improvement, not a
correctness fix. Recommend this as the **first** item to pick up post-launch given how much evidence
has accumulated, but it does not gate release.

### 4.2 `Button size="icon"`

Real, current-source evidence of raw hand-rolled icon-only circular buttons that duplicate Tailwind
classes instead of using `Button`: the Plan Detail Shell header's "⋮" trigger, both icon actions in
`travel-activity-detail.tsx`, and both toggle buttons in `todo-list-controls.tsx` — 5 real
consumers, all currently correct and shipping fine as hand-rolled markup. Adding `size="icon"` to
`Button` is purely additive (zero existing `Button` consumer is affected), so the risk of adding it
is near-zero — but nothing is currently broken by its absence, so there is no correctness reason to
do it before Go-Live. Recommend adding the size once, then migrating the 5 known consumers
opportunistically (not as a dedicated cleanup wave, consistent with §68's progressive-cleanup rule).

### 4.3 TextAction / text-link pattern

Evidence has grown well past the original 2-data-point threshold: at least 8 "Xem thêm/Xem tất cả"
instances now exist across Dashboard (`overview-widget-registry.tsx`, 5 occurrences),
Wedding Overview, Wedding Guest (2 occurrences), Settlement, and Debt-tracking — most hand-overriding
`Button`'s chrome (`h-auto min-h-0 gap-0 rounded-none p-0`) to get a plain text-link look. This is
real, repeated friction and a good post-launch candidate (`Button variant="link"` is the more likely
fit than a brand-new `TextAction` component, since every instance is still fundamentally a clickable
text label, not a structurally distinct primitive) — but every existing instance already renders
correctly today, so there is no functional reason to block Go-Live on it.

### 4.4 Radius drift (ad-hoc 24/26/28px)

Distinguish, per instruction, three different things that all currently coexist:
- `Card`'s legacy 24px default — a single, controlled, intentional Wave 4 decision, not drift.
- Ad-hoc literal `rounded-[24px]`/`rounded-[26px]`/`rounded-[28px]` on non-`Card` containers — 74
  occurrences across 34 files, confirmed via fresh grep. Every Wave that encountered these (0, 2, 3)
  independently confirmed the same finding: no canonical token (`--radius-ds-lg`=16px,
  `--radius-ds-xl`=20px) is an exact-alias match for 24/26/28px, so forcing a mapping would violate
  the exact-alias principle, not fix drift.
- The canonical 8/12/16/20/full scale itself — correctly used wherever a Pilot/Wave did touch a
  surface needing a radius decision (e.g. Wave 0/1/2's `rounded-[var(--radius-ds-lg)]` overrides).

The drift has not worsened across 8 waves of surface-by-surface migration (same 24/26/28px pair
repeatedly, no new scattered values) — confirming `07.RolloutStrategy.md` §68's no-mass-cleanup rule
was the right call, not a deferred cost that's compounding. Recommend continuing exactly the current
policy (fix opportunistically only when a wave/feature already needs to touch that surface) rather
than opening a dedicated cleanup pass, before or after Go-Live.

### 4.5 Financial color semantics — `StatisticOverview`'s green "Tổng thu"

Reviewed and judged **not a meaningful confusion risk**, despite being a literal exception to the
internal "red/green = member's own balance only" principle: coloring a plan-wide total-income figure
green (money coming in = positive/green) is itself a near-universal, independently-intuitive fintech
convention — it does not require knowledge of the member-balance metaphor to read correctly, and
no Wave or Pilot browser-verification pass ever surfaced actual user confusion from it. This is an
internal-consistency note for the color-token documentation, not a user-facing defect. Recommend
documenting both valid uses of green/red (aggregate polarity vs. member receivable/payable) rather
than changing the rendered color.

### 4.6 Dead Statistic components

`ExpenseTimelineChart` and `CompletedPlanOverview` (`src/modules/statistic/components/`) — confirmed
via fresh repo-wide grep to have zero consumers anywhere (imports, barrel `index.ts`, tests). Safe,
zero-risk deletion whenever convenient; no urgency either way since unreachable code has no runtime
effect.

## 5. NO ACTION / INTENTIONAL EXCEPTIONS

### 5.1 Plan-Type Expression token layer

Dashboard (Pilot #2) validated that the architecture (generic components stay Plan-Type-unaware,
receiving already-resolved tone/color props) works. Raw `planType ===` branching still lives in
product configuration (`plan.constants.ts`, `plan-card-config.ts`, `edit-plan-form.tsx`,
`create-plan-form.tsx`, the Plan Detail Shell) — confirmed via fresh grep, and confirmed zero
`planType` references exist inside `shared/components/ui/`, meaning the architectural guarantee this
token layer would harden is already holding by convention, without the token layer built yet.
Extracting a formal token layer is speculative ahead of a second real surface needing it (per the
STOP/GO review's own deferral, still valid — Wave 6/Statistic did not surface Plan-Type-specific
evidence). NO ACTION before Go-Live; revisit if a future surface needs it.

### 5.2 `WeddingGuestImportDialog` (legacy `Dialog`, not migrated)

Confirmed still importing `src/shared/components/ui/dialog.tsx` directly. This is the single
remaining legacy `Dialog` consumer app-wide, tracked since Pilot #3 as an intentional, evidence-based
exception (`ResponsiveModal` has no `size` contract for a wide, multi-step CSV preview table with
exactly one consumer needing it). Per the Design System's own "don't invent, defer instead"
principle (2+ consumer evidence required before adding a new prop/contract), building a `size` API
into `ResponsiveModal` for a single consumer would be exactly the kind of speculative addition the
system has consistently avoided elsewhere. **Keeping it as an intentional exception for Go-Live is
the correct call** — it is not migration debt, it is a documented, deliberate boundary. Revisit only
if a second wide-content consumer appears.

### 5.3 `TodoNotificationScreen` bottom-anchored overlay

Reconfirmed: still exactly one data point (itself). No wave introduced a second always-bottom-
anchored overlay need. NO ACTION — stays `KEEP PRODUCT-SPECIFIC`.

### 5.4 `NotificationBadge`

Reassessed against current source, not just prior notes: the closest things to a second data point
are `todo-attention-section.tsx`'s `<Badge>{count} việc</Badge>` (a `Badge` next to a section
heading, not a count overlaid on an icon corner) and the tone-colored bell-icon treatments in both
todo files (see §3.2 — a duplication finding, not new primitive evidence). There is still no second
genuine "numeric badge overlaid on an icon" instance anywhere in the app. NO ACTION — insufficient
evidence for a dedicated primitive, unchanged from the STOP/GO review's original deferral.

### 5.5 Intentional `BottomSheet` KEEP cases

Confirmed across Waves 0, 2, and 4: the Plan Detail Shell header menu + 2 statistic drilldowns
(Wave 0), `PlanningTab`'s milestone-expense drilldown (Wave 2), and `member-actions-menu.tsx`'s "⋮"
menu (Wave 4) are all explicitly exempted by `docs/ui-modal-conventions.md` §4 (menus/popovers and
read-only drilldowns). These are not migration debt and should not be re-flagged as such in any
future audit solely because `BottomSheet` remains in the file.

## 6. Recommended execution order

```
1. Fix P0 §2.1 (member nested-button) — small, isolated, blocks Go-Live.
2. Decide on P1 §3.1 (Settlement confirmation) — needs a product decision (this changes UX, not
   just markup), then implement using the already-proven ConfirmDialog request/perform pattern.
3. P1 §3.2 (getBellToneClass dedup) — trivial, can be bundled with #1 or done independently; either
   order is fine, no dependency between them.
4. Everything in §4 (P2) — pick up post-launch, in whatever order matches available capacity;
   §4.1 (Progress) and §4.3 (TextAction) have the strongest accumulated evidence and are the most
   consistency-value-dense if you want a suggested starting point, but none are urgent.
5. §5 items — no action needed; re-open only if the stated trigger condition (a second real
   consumer/data point) actually occurs.
```

## 7. Final recommendation

**READY FOR PRE-GO-LIVE FIXES**

One confirmed P0 (member nested-button hydration/accessibility defect) and one P1 worth a product
decision (Settlement confirmation gap) stand between the current state and a clean Go-Live sign-off.
Both are small, isolated, well-understood, and do not require re-opening any Pilot, Wave, or Design
System architectural decision. Everything else in this review is either already-acceptable
intentional design (§5) or safely deferrable without user-facing risk (§4).
