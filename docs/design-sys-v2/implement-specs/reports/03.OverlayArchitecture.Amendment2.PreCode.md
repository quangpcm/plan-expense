# Overlay Architecture — Corrective Investigation / Amendment #2 — Pre-Code Manifest

**Scope:** bounded root-cause investigation only. No product source was modified. A throwaway
diagnostic route (`src/app/overlay-amend2-diag-temp/`) was created to empirically verify Bug 2's
mechanism against the real `ResponsiveModal`/`BottomSheet` components with Playwright, then fully
deleted — same disposable-harness method used throughout this whole initiative for root-cause work
(e.g. the original Focus Return Fix investigation). `git status` confirms no product file changed.

## 1. Executive finding

All three bugs are real, and all three have a **concrete, evidenced, non-speculative root cause**:

- **Bug 1** is caused by `ResponsiveModal` never opting its own scrollable content region out of
  vaul's default "allow drag-to-dismiss whenever the scroll position is at the top" heuristic. vaul
  already ships sophisticated `VisualViewport`-based keyboard/height handling — no new JS is needed
  for that part. The dismiss-on-scroll symptom has a precise, library-native fix
  (`data-vaul-no-drag`), and the keyboard-shift symptoms need real-iPhone confirmation (Playwright
  cannot exercise vaul's iOS-only code paths — see §2).
- **Bug 2** is caused by the legacy hand-rolled `BottomSheet` component sitting between two
  `ResponsiveModal` instances in one real Finance/Statistic flow. `BottomSheet` never registers with
  Radix's shared `DismissableLayerContext`, so it has no `pointer-events: auto` exemption when
  Radix sets `document.body.style.pointerEvents = 'none'` for its own modal coordination —
  confirmed empirically: **the `BottomSheet` becomes entirely non-interactive (not just the nested
  modal) the moment any `ResponsiveModal` is open anywhere in the tree**, on both desktop and
  mobile. Its hardcoded `z-50` (vs. `ResponsiveModal`'s shared `--z-index-overlay: 40` token) is a
  second, independent stacking defect. `ResponsiveModal`-in-`ResponsiveModal` nesting itself
  (Wave 1's proven case) remains fully correct — confirmed by direct measurement in this
  investigation, not just cited from the old report.
- **Bug 3** is real and, on inspection, **broader than the two named Wedding Guest examples**: 12 of
  roughly 30 current `ResponsiveModal` call sites pass no `className` at all and render fully
  unconstrained on desktop, spanning content from a single text input to multi-field forms. A
  `size` prop is justified by this evidence and by the fact that it directly supplies the size
  contract Pilot #3 already identified as the blocker for `WeddingGuestImportDialog`.

None of the three requires business logic, permission, or calculation changes. All three fixes are
additive/corrective to shared overlay primitives, not per-consumer visual patches.

## 2. Bug 1 root cause — mobile keyboard / drawer

### Source evidence

- `ResponsiveModal`'s mobile branch (`src/shared/components/ui/responsive-modal.tsx`) renders
  `Drawer.Root`/`Drawer.Content` from `vaul` with no `size`/`repositionInputs`/`disablePreventScroll`/
  `modal` overrides — every vaul default applies: `modal=true`, `disablePreventScroll=true`,
  `repositionInputs=true`, `dismissible=true`.
- `Drawer.Content`'s className is
  `"fixed inset-x-0 bottom-0 z-[var(--z-index-overlay)] flex max-h-[85vh] flex-col overflow-hidden ..."`;
  its children are wrapped in `<div className="mt-4 min-h-0 overflow-y-auto overscroll-contain pr-1">`
  — a real, correctly-detectable scrollable region (`overflow-y-auto`).
- The affected consumer, `TodoVendorForm`
  (`src/modules/todo/components/todo-vendor-form.tsx`), renders "Link tham khảo" and "Mô tả ngắn"
  as plain `<Input>`/`<Textarea>` (`src/shared/components/ui/input.tsx`,
  `.../textarea.tsx`) — real native `<input>`/`<textarea>` elements with no extra wrapping div, so
  they satisfy vaul's own `isInput()` check correctly.

### Library behavior (read directly from `node_modules/vaul/dist/index.mjs`)

- vaul already implements real, non-trivial iOS keyboard handling: an `onVisualViewportChange`
  listener (lines ~1111–1163) that shrinks `drawerRef.current.style.height` and shifts
  `drawerRef.current.style.bottom` by the keyboard height (`diffFromInitial`) whenever a focused
  input's visual viewport shrinks — this is an **inline style**, so it correctly overrides the
  static `max-h-[85vh]` Tailwind class (inline style wins on specificity). This directly targets
  "focused input remains usable" and "footer stays within the visible viewport," and is active by
  default (`repositionInputs=true`).
- A second mechanism, `preventScrollMobileSafari()` (lines ~181–275), applies a battery of
  Safari-only workarounds (input-focus transform trick, manual `scrollIntoView`, negative
  body-margin scroll pinning) — but it is gated by `if (isIOS())` (checked via user-agent
  sniffing), meaning **it never runs in a desktop-Chromium Playwright session regardless of
  viewport width set**. This is a hard verification-methodology limit: any automated check of this
  exact mechanism can confirm the code path exists and is wired correctly, but cannot substitute for
  a real iPhone/iOS Safari session.
- A third, separate mechanism — `shouldDrag(el, isDraggingInDirection)` (lines ~971–1020) — decides
  whether a touch-drag gesture should move the sheet (drag-to-dismiss) or be left alone (so the
  browser scrolls the content instead). Its relevant branch:
  ```js
  while (element) {
    if (element.scrollHeight > element.clientHeight) {
      if (element.scrollTop !== 0) {
        return false; // scrollable and not at top -> don't drag, let it scroll
      }
      if (element.getAttribute('role') === 'dialog') {
        return true;
      }
    }
    element = element.parentNode;
  }
  return true; // no scrollable ancestor found (or all at top) -> allow drag
  ```
  **When the scrollable content region is at `scrollTop === 0`, vaul treats a touch-drag inside it
  as "drag the sheet," not "scroll the content."** vaul does provide an explicit opt-out for this
  exact situation — `shouldDrag` checks `element.hasAttribute('data-vaul-no-drag') ||
  element.closest('[data-vaul-no-drag]')` and returns `false` (no drag) immediately if found — but
  `ResponsiveModal` never applies this attribute anywhere.

### Exact failure mechanism

1. **Dismiss-on-scroll (proven, not speculative):** `TodoVendorForm`'s fields are near the top of a
   fairly tall form. A user who taps into a field near the top (`Tên nhà cung cấp`, `Link tham
   khảo`) and then tries to scroll down to reach `Mô tả ngắn` or the submit button — especially
   right after opening, or after having scrolled back to the top — starts that gesture while the
   content wrapper's `scrollTop` is still `0`. vaul's `shouldDrag` then classifies the gesture as
   "drag the sheet," not "scroll the content," because `ResponsiveModal` never marks its content
   wrapper with `data-vaul-no-drag`. This exactly matches "attempting to scroll can dismiss/close
   the form unexpectedly."
2. **Keyboard-shift/footer symptoms (plausible, not yet device-confirmed):** the underlying
   mechanism (`onVisualViewportChange`) is well-designed and should generally work; a specific
   contributing factor worth flagging is that `ResponsiveModal` has **no sticky/pinned footer**
   pattern — the submit/cancel row is just a normal-flow child at the bottom of `children`, inside
   the same scrollable region as every field. If vaul's resize calculation is even slightly
   imperfect for a tall form (its own `isTallEnough = drawerHeight > totalHeight * 0.8` branch,
   `WINDOW_TOP_OFFSET = 26`, `KEYBOARD_BUFFER = 24` are all vaul-internal heuristics, not something
   `ResponsiveModal` controls or has tuned for its own content shapes), the user's only way to reach
   the footer is scrolling further inside a region that — per finding 1 above — can also accidentally
   trigger a dismiss. The two symptoms compound each other on a real device even though each has a
   distinct proximate cause.

**Category answer:** primarily **C (Vaul drag gesture vs. form scrolling)**, with **D
(keyboard/VisualViewport behavior)** as a secondary, not-yet-device-confirmed contributor, and
**A (viewport sizing)** ruled out as the primary cause — vaul does not rely on static `vh` units for
its runtime keyboard adjustment, it recalculates via `VisualViewport` and inline styles.

### Proposed architecture-level fix (not implemented)

- Add `data-vaul-no-drag` to `ResponsiveModal`'s content-scroll wrapper
  (`<div className="mt-4 min-h-0 overflow-y-auto overscroll-contain pr-1" data-vaul-no-drag>`) —
  this is vaul's own documented, supported extension point, not a workaround. The drag handle
  (`<div className="mx-auto mb-4 h-1.5 w-14 ...">`) and title/description block sit outside this
  wrapper and are unaffected, so dragging via the handle/header area to intentionally dismiss the
  sheet keeps working.
- Do not touch the `onVisualViewportChange`/height mechanism — no evidence it needs replacing, and
  the instruction is explicit not to introduce new `VisualViewport` JS (none is needed; vaul already
  owns this).
- Consider (not commit to, pending real-device evidence) whether the content wrapper needs a
  reserved bottom inset so the footer never sits flush against the shrunk viewport edge — this
  would need to be confirmed as necessary on a real device before being treated as required.

### Regression risks

- **Low.** `data-vaul-no-drag` only affects drag-vs-scroll disambiguation inside the wrapped region;
  it does not change any layout, does not affect the Dialog (desktop) branch at all, and does not
  change any existing consumer's visible behavior except removing the specific accidental-dismiss
  path. The one behavior it intentionally changes is: a user can no longer drag-dismiss the sheet by
  swiping down while their finger is directly over the form content (they still can via the handle
  or the explicit close button) — this is the correct trade-off per the bug report's own required
  target behavior ("scrolling textarea/form must not accidentally dismiss drawer... explicit
  legitimate drawer dismiss behavior still works").
- The keyboard-shift symptoms cannot be fully verified without a real iOS device — flagged plainly
  as a real limitation, not glossed over.

## 3. Bug 2 root cause — nested modal interaction

### DOM/Portal/stack model

Real reported path, confirmed by reading `src/app/(authenticated)/plans/[planId]/page.tsx`:

```
ResponsiveModal "Tổng quan tài chính" (showStatisticSheet)   — Radix Dialog / vaul Drawer
  → MemberSpendingList.onSelectMember → statisticMemberDrilldown
    → BottomSheet "Khoản chi của {member}"                  — hand-rolled, NOT Radix, NOT vaul
      → TimelineList.onSelectExpense → setDetailExpense
        → ResponsiveModal "Chi tiết khoản chi" (detailExpense) — Radix Dialog / vaul Drawer
```

`BottomSheet` (`src/shared/components/ui/bottom-sheet.tsx`) is explicitly `@deprecated` in its own
docstring ("use `ResponsiveModal` instead ... this component has neither" portal rendering, focus
lifecycle, nor Escape handling) — it is a plain `position: fixed` div with a hardcoded `z-50`
backdrop button, rendered in-place in the React tree (no `createPortal`).

### Exact event-ownership failure (empirically verified, not inferred)

Read directly from the installed Radix source
(`node_modules/@radix-ui/react-dialog/dist/index.mjs` line 153,
`node_modules/@radix-ui/react-dismissable-layer/dist/index.mjs`): Radix's `DialogContentModal` sets
`disableOutsidePointerEvents: context.open` — true whenever a modal `Dialog` (the default; `Dialog.Root`
is never given `modal={false}` anywhere in this codebase) is open. `DismissableLayer`'s effect then
does:

```js
if (disableOutsidePointerEvents) {
  if (context.layersWithOutsidePointerEventsDisabled.size === 0) {
    ownerDocument.body.style.pointerEvents = 'none';
  }
  context.layersWithOutsidePointerEventsDisabled.add(node);
}
```

and re-enables `pointer-events: auto` **only on DOM nodes that are themselves registered
`DismissableLayer` instances** (i.e., other Radix `Dialog`/`AlertDialog` content). `pointer-events`
is a normal inherited CSS property; `BottomSheet`'s own elements set no explicit `pointer-events`
value, so they inherit `none` from `<body>` — with no path back to `auto`, since `BottomSheet` never
registers with `DismissableLayerContext`.

**This was verified directly**, not just derived from source reading, with a disposable diagnostic
route mounting the real `ResponsiveModal`/`BottomSheet` components and driving them with Playwright:

| Check | Desktop (Dialog) | Mobile (Drawer) |
|---|---|---|
| `document.body.style.pointerEvents` after opening Layer A alone | `"none"` | `"none"` |
| Computed `pointer-events` on the `BottomSheet`'s own outer div while A is open | `"none"` | `"none"` |
| Real click on a button *inside* the `BottomSheet` while A is open | times out / not actionable | times out / not actionable |
| Once Layer C (`ResponsiveModal`) is genuinely open (forced open programmatically to isolate the question), a real coordinate-based click on a button/input inside it | **registers correctly**, `elementFromPoint` confirms the button itself is hit | **registers correctly** |

This produces a more precise and slightly different picture than the bug report's literal
step-by-step wording suggests: the measured defect is that **`BottomSheet` becomes fully inert the
instant *any* modal `ResponsiveModal` is open anywhere in the tree — before, during, or regardless
of which one opened first** — not narrowly "the innermost modal can't be reached." Once a
`ResponsiveModal` genuinely has focus/is open, its own interactivity is completely correct (matching
Wave 1's finding exactly). The practical, user-visible effect matches the report either way: reaching
or using the expense-detail modal from inside the Finance statistic sheet is broken, because the
`BottomSheet` in between cannot reliably hand off interaction once a Radix modal is anywhere in the
picture. (vaul's `Drawer` independently also sets `document.body.style.pointerEvents = 'none'` for
its own modal behavior — confirmed via source — so the same failure occurs on mobile too, not only
desktop.)

`bottomSheetOuter`'s measured `z-index` was `50`, vs. `ResponsiveModal`'s shared
`--z-index-overlay: 40` (`src/styles/globals.css`). This is a second, independent defect: even
where pointer-events were not the blocker, `BottomSheet`'s backdrop would still incorrectly outrank
any `ResponsiveModal` in raw stacking order.

### Why the Wave 1 nested `AttachmentPicker` case passed and this one fails

Wave 1's proof was `ResponsiveModal` nested **directly** inside `ResponsiveModal` — both layers are
real `Dialog.Root`/`Drawer.Root` instances that register with the *same* shared coordination system
(Radix's `DismissableLayerContext` on desktop; vaul's own internal stacking on mobile). That system
is specifically designed to disable the outer layer and enable the inner one correctly when both
participants are known to it — which this investigation re-confirmed still works.

The Finance case inserts a **third-party, non-participating layer** (`BottomSheet`) between two
`ResponsiveModal`s. `BottomSheet` was never part of Radix's/vaul's contract because it's a
completely independent, hand-rolled implementation — the deprecation notice on it is not
incidental, it is the exact reason this defect exists. The distinction is not "two modals vs. three
modals," it is **"all-Radix/vaul-native nesting" vs. "a non-participating overlay inserted into a
Radix/vaul-coordinated chain."**

### Proposed architecture-level fix (not implemented)

Not a z-index increase, not a new abstraction. The defect is that `BottomSheet` is structurally
unsafe as a participant in any interaction chain involving a `ResponsiveModal`, in either direction
(before, after, above, or below it). Given `BottomSheet` is already deprecated in favor of
`ResponsiveModal`, the correct fix is a **rule-level amendment to the overlay architecture guidance,
plus migrating the specific violating consumers**:

- Add an explicit rule: *"A `BottomSheet` instance that can itself open a `ResponsiveModal` (or that
  can be open at the same time as one), directly or via a further nested step, must be migrated to
  `ResponsiveModal`."* This voids the Wave 0 "KEEP — read-only drilldown" disposition specifically
  for the two statistic drilldowns (`statisticMemberDrilldown`, `statisticMilestoneMemberDrilldown`
  in `plans/[planId]/page.tsx`) — that KEEP was evaluated purely against the
  create/edit-form migration convention (`ui-modal-conventions.md` §4), not against nested-overlay
  safety, which is new evidence this investigation surfaced. It does **not** affect the other KEEP
  `BottomSheet` instances that never coexist with a nested `ResponsiveModal` (the Plan Detail Shell
  header menu, `PlanningTab`'s drilldown, `member-actions-menu.tsx`'s "⋮" menu) — those stay
  disposed exactly as already decided.
- Migrating those two drilldowns to `ResponsiveModal` brings them fully into the same coordinated
  layer system Wave 1 already proved correct, and is a natural, in-family fix (same component,
  same pattern already used successfully everywhere else), not a patch that hides the underlying
  defect.

### Regression risks

- **Medium.** This is a real migration (`BottomSheet` → `ResponsiveModal`) of two consumers, not a
  one-line change — it needs the same care as any other Wave (verify `TimelineList`'s rendering
  inside the new wrapper, verify the member/milestone-drilldown title logic, verify close/Escape
  behavior matches). It is, however, exactly the same class of migration already performed
  successfully many times over during Rollout (Waves 0/1/2/4/5), so the pattern itself carries low
  incremental risk — the medium rating is about scope/care, not about doing something unproven.
- No calculation, permission, or data logic is touched by this fix — `TimelineList`'s props and the
  drilldown state (`statisticMemberDrilldown`/`statisticMilestoneMemberDrilldown`) are unaffected by
  which overlay component renders them.

## 4. Bug 3 sizing analysis

### Current sizing contract

`ResponsiveModal`'s desktop (`Dialog.Content`) branch renders `className={cn('relative w-full
rounded-[28px] ...', className)}` inside a `flex items-center justify-center px-4` wrapper — with no
`className` passed, the dialog has **no max-width at all**, growing to the full viewport width minus
32px of page padding. The mobile (`Drawer.Content`) branch is always `inset-x-0` (full width) by
design and explicitly does **not** accept the caller's `className` for width purposes (existing code
comment in `responsive-modal.tsx` explains this is intentional) — so any `size` API's effect is
correctly confined to desktop by construction, with zero new work needed for the mobile requirement.

### Consumer evidence (full inventory, not just the two named examples)

Grepped every `<ResponsiveModal` usage repo-wide (~30 call sites). Existing explicit `className`
max-widths cluster into 4 real, already-in-use values:

| Existing value | Real consumers (representative) |
|---|---|
| `max-w-md` (448px) | Plan lock/passcode form |
| `max-w-lg` (512px) | Todo detail, expense detail, income detail, vendor form |
| `max-w-xl` (576px) | Expense form, income form, travel activity detail |
| `max-w-2xl` (672px) | Milestone form, todo form, edit-plan form, plan-settings, travel activity create/edit form, member avatar picker |
| `max-w-4xl` (896px) | "Tổng quan tài chính" statistic sheet, Wedding Guest full guest-list modal |

**12 call sites pass no `className` at all** and are therefore fully unconstrained on desktop today
— this is materially broader than the two Wedding Guest examples named in the bug report:

`CreatePlanForm` (`plans/page.tsx`), claim-invitation-link form (`member-list.tsx`), Wedding Guest
group manager / quick-add-guest / edit-guest / edit-invitation (`wedding-guest-panel.tsx`, 4
instances), Wedding Guest export (`wedding-guest-export-dialog.tsx`), debt counterparty quick-add
(`counterparty-picker.tsx`), debt custom date-range filter (`debt-native-detail.tsx`), the native
debt loan/repayment transaction form (`debt-native-tab.tsx`), passcode/security-code form
(`user/passcode-sheet.tsx`), display-name form (`user/display-name-sheet.tsx`), attachment
URL/upload picker (`storage/attachment-picker.tsx`).

### Proposed size API

```ts
type ResponsiveModalSize = 'sm' | 'md' | 'lg' | 'xl';
// new optional prop on ResponsiveModalProps: size?: ResponsiveModalSize
```

Applied only to the desktop `Dialog.Content` max-width (mobile untouched, per above).

### Proposed canonical widths (reusing only values already observed in real code — no invented pixels)

| Size | Width | Rationale |
|---|---|---|
| `sm` | `max-w-md` (448px) | Matches the one existing "simple form" precedent (passcode form). Fits: single-input or very short (1–3 field) workflows. |
| `md` | `max-w-xl` (576px) | Matches the existing "normal form" precedent (expense/income forms, travel activity detail); absorbs the very close, largely redundant existing `max-w-lg` (512px) bucket into the same semantic step — **this consolidation needs a quick visual confirmation at implementation time**, not locked in here. |
| `lg` | `max-w-2xl` (672px) | Matches the single most common existing value in the app (milestone/todo/edit-plan/travel-activity forms, member avatar picker) — the "complex form" bucket. |
| `xl` | `max-w-4xl` (896px) | Matches the two existing dense-content precedents (statistic sheet, Wedding Guest full list/table). Also directly supplies the size contract `WeddingGuestImportDialog` has been blocked on since Pilot #3 — that migration is **not** being done here, but this size would be the one it needs when it is eventually taken up. |

### Default behavior

**No default width change when `size` is omitted.** This is the zero-regression-risk choice:
existing consumers that already pass an explicit `className` max-width keep working completely
unchanged (they simply don't use `size`). The 12 currently-unconstrained consumers **stay
unconstrained** unless a follow-up step explicitly assigns them a `size` — per instruction, this
Pre-Code pass does not commit to migrating any of them wholesale. `size` is purely additive: a new
optional prop with no consumer required to adopt it.

### Candidate consumer mappings (classification only, not applied)

Per the bug report's specific request:

| Wedding Guest workflow | Candidate size | Why |
|---|---|---|
| Quick add guest (`WeddingGuestCreateForm`) | `md` | Multi-field identity + RSVP + gift form, not simple, not dense/table content. |
| Edit guest / edit invitation (`WeddingGuestEditForm`, `GuestInvitationForm`) | `md` | Same shape as quick-add. |
| Group manager (`WeddingGuestGroupList`) | `sm` | Short list of existing groups + a simple inline create-group mini-form; content is narrow regardless of list length. |
| Export (`WeddingGuestExportDialog`) | `sm` | One scope choice + a download button — the simplest content family in this whole inventory. |

Other current no-`className` consumers, classified for completeness (not proposed for migration in
this batch): `CreatePlanForm` → likely `lg` (comparable field count to the already-`2xl`-sized
milestone/edit-plan forms); claim-invitation-link, counterparty quick-add, date-range filter,
passcode form, display-name form, attachment URL picker → all `sm` (single input or very short);
native debt transaction form → likely `md` (comparable to expense/income forms already at `xl`).

## 5. Shared ResponsiveModal contract after amendment

```ts
type ResponsiveModalProps = {
  open: boolean;
  onOpenChange: (open: boolean) => void;
  title: string;
  description?: string | undefined;
  children?: ReactNode;
  className?: string | undefined;
  size?: 'sm' | 'md' | 'lg' | 'xl'; // NEW — optional, desktop-only, no default width change when omitted
};
```

- Bug 1's fix is internal to `ResponsiveModal`'s own markup (`data-vaul-no-drag` on the content
  wrapper) — no prop/contract change.
- Bug 2's fix does not change `ResponsiveModal`'s contract at all — it is a migration of two
  `BottomSheet` consumers to the existing `ResponsiveModal` API, plus a documentation-level rule
  addition about when `BottomSheet` is unsafe to keep.
- Bug 3's fix is the one actual public API addition, and it is purely additive/optional.

## 9. Implementation recommendation

**READY FOR AMENDMENT IMPLEMENTATION**

All three root causes are proven with direct source evidence and, for Bug 2, direct empirical
measurement against the real components — not assumption. Each proposed fix uses the affected
library's own supported extension point (`data-vaul-no-drag`, migrating to the already-proven
`ResponsiveModal`/Radix coordination system, an additive optional prop) rather than a timing hack,
a z-index escalation, or a per-consumer visual patch. The one open gap — full confirmation of Bug
1's keyboard-shift symptoms — is explicitly called out as requiring a real iOS device pass either
just before or just after the `data-vaul-no-drag` fix lands, not as a blocker to starting
implementation of the parts that are already fully proven.
