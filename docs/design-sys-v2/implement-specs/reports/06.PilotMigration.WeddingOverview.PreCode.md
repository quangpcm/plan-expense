## 4. Current Wedding Overview architecture

Confirmed by reading `overview-renderer.tsx`, `overview-tab.tsx`, `plan-type-config.ts`, and
`overview-widget-registry.wedding.tsx` in full — this is exactly the architecture Audit Decision
Record §22 (Overview Architecture — ACCEPTED/PROTECTED) requires to be preserved:

```text
plan-type-config.ts (per-PlanType widget list: widgetId + enabled + order)
        ↓
overview-renderer.tsx
   resolveOverviewWidgets(plan, props)
     → looks up config.overview.widgets for the plan's type
     → filters by widgetConfig.enabled
     → sorts by widgetConfig.order
     → maps widgetId → overviewWidgetRegistry[widgetId]
     → filters by widgetDefinition.isAvailable(props)
     → filters by resolveModuleAccess(currentMember, widgetDefinition.moduleId) !== 'hidden'
        (except moduleId === 'overview', which is never permission-gated)
   OverviewRenderer renders each resolved widget's `component` in order, inside
   <div className="space-y-6">
        ↓
overview-widget-registry.wedding.tsx (weddingOverviewWidgetRegistry)
   3 registry entries, each mapping a widgetId to: id, moduleId, component, isAvailable
        ↓
overview-widget-registry.tsx (base registry)
   merges weddingOverviewWidgetRegistry into the shared overviewWidgetRegistry object
   (confirmed: base file imports and spreads the wedding-specific registry — travel/debt/general
   plan types have their own equivalent widget sets in the same shared registry object)
```

For `planType: 'wedding'`, `plan-type-config.ts` configures exactly 3 widgets, in this order:

```text
order 0:  weddingAttentionSummary        moduleId: 'overview'      (never permission-hidden)
order 10: weddingMilestoneSnapshot       moduleId: 'planning'      (hidden if module access hidden)
order 20: weddingGuestFinanceSummary     moduleId: 'weddingGuests' (hidden if module access hidden)
```

`weddingGuestFinanceSummary`'s `component` (`WeddingGuestFinanceRowWidget`) itself renders two
sub-widgets side by side (`WeddingGuestSummaryWidget` + `WeddingFinanceSummaryWidget`), so the
**effective rendered content is 4 distinct widget bodies**, not 3.

**This wave's Pilot scope is exactly these files and nothing upstream/downstream of them**:
`overview-widget-registry.wedding.tsx` (all four widget components), and *possibly* the two
`SectionHeading`/`Card` uses immediately inside them. `overview-renderer.tsx`, `overview-tab.tsx`,
`plan-type-config.ts`, the Plan Detail Shell (`plans/[planId]/page.tsx`'s header, tab navigation,
and the rest of its ~2600 lines) are explicitly **not** in scope — see §11 disposition table and
the Non-Goals in §12.

## 5. Current sections/widgets (detailed)

### 5.1 `weddingAttentionSummary` → `WeddingAttentionSummaryWidget`

- **Header**: `SectionHeading` — eyebrow "Cần chú ý", title "Công việc", optional `description`
  (a computed summary string like "2 việc quá hạn · 1 việc đến hạn hôm nay"), `action` = a
  "Xem thêm ➔" button that calls `onOpenPlanningTodos` (switches the Plan Detail Shell's active
  tab to `planning` — not a route navigation).
- **Body** (inside one `Card`):
  - Sub-section "Cần xử lý ngay": a computed summary line, then either an inline "all clear"
    message (icon + text) when there are zero attention items, or up to 3 `AttentionItemRow`
    items (title, milestone name, priority label, a countdown badge colored by urgency) — desktop
    (`lg:`) renders these as a grid of bordered/shadowed cards, mobile renders them as a
    divided list with no per-row border/shadow.
  - Sub-section "Sắp tới": up to 3 more upcoming-todo rows (title, milestone name, countdown),
    excluding whatever already appeared in "Cần xử lý ngay", or a "no upcoming work" message if
    none.
- **Loading**: `isTodosLoading` → a single `Skeleton` (`h-56 rounded-[28px]`) replaces the whole
  Card body (header still renders).
- **Error**: `todoActionError` (a mutation-result error, not a fetch error) renders via
  `AuthFormMessage` above the Card, additively — does not replace the Card content.
- **Empty**: two independent empty sub-states inside the same widget — "Mọi việc đang trong tầm
  kiểm soát" (zero attention items) and "Không có công việc nào sắp đến hạn" (zero upcoming items)
  — both are true first-use/steady-state empties, not permission- or filter-driven.
- **Interaction**: every row and the header action are navigation-only (`onViewTodo` opens the
  Plan Detail Shell's existing `TodoDetailView` inside its existing `ResponsiveModal` — see §7.3;
  `onOpenPlanningTodos` switches tabs). No mutation happens inside this widget.

### 5.2 `weddingMilestoneSnapshot` → `WeddingMilestoneSnapshotWidget`

- **Header**: `SectionHeading` — eyebrow "Kế hoạch", title "Tiến độ kế hoạch", `action` = "Xem
  thêm ➔" calling `onOpenPlanningMilestones` (switches tab to `planning`, also sets a work-view
  mode — internal Shell state, not touched by this Pilot).
- **Body**: computes a "current" milestone (`in_progress`, or the first upcoming one) and a
  "next" milestone (the next non-cancelled milestone after current, by `orderIndex`), then renders
  0-2 `WeddingMilestoneCard`s side by side on desktop (`lg:grid-cols-2`), stacked on mobile. Each
  card shows: eyebrow ("Hiện tại"/"Tiếp theo"), milestone title, a status `Badge`
  (`warning`/`info` tone), a "`completed`/`total` công việc" count, and — for the *current*
  milestone only — a raw hand-built progress bar (`%` of todos completed) plus spent/estimated
  currency text; the *next* milestone shows spent/estimated currency text without the progress bar.
- **Loading**: `isMilestonesLoading` → `Skeleton` (`h-32 rounded-[28px]`) replaces the body.
- **Error**: `milestoneActionError` → `AuthFormMessage`, additive, same pattern as §5.1.
- **Empty**: `!currentMilestone` → a plain `Card` with "Không có mốc nào đang diễn ra hoặc sắp
  diễn ra." — the *only* one of the 4 widgets whose empty state is a bare `Card` + text rather
  than an icon+text composition.
- **Availability**: `isAvailable: (props) => !props.isPlanEnded` — this entire widget disappears
  once the plan is marked ended. This is a genuine product-state-driven visibility rule, not a
  permission rule — see §6 for why it's listed there anyway (it's a real conditional-visibility
  behavior the Pilot must preserve exactly).

### 5.3 `weddingGuestFinanceSummary` → `WeddingGuestFinanceRowWidget` (composes 2 sub-widgets)

Desktop (`lg:`): 2-column grid. Mobile: stacked, guest summary first.

**5.3.a `WeddingGuestSummaryWidget`**

- Fetches its own data via two hooks (`useGuestInvitations(planId)`, `useWeddingGuestGroups
  (planId)`) — this is the *only* one of the 4 widgets that fetches independently rather than
  receiving everything through `OverviewRendererProps`. Combines their loading/error states.
- **Header**: `SectionHeading` — eyebrow "Khách mời", title "Tình hình khách mời", `action` =
  "Xem thêm ➔" calling `onOpenWeddingGuests`.
- **Body** (inside one `Card`):
  - A leading icon + "`total` lời mời" (big number) + "`attendeeCount` người dự kiến" (supporting
    line) — **`total` (invitation count) and `attendeeCount` (expected-attendee count) are two
    different numbers computed from different aggregations; they are never the same field.** This
    is the guest-count-vs-attendee-count invariant (see §4.1 in the invariant table below).
  - RSVP breakdown: 3 rows (Đã xác nhận / Chờ phản hồi / Không tham dự), each with an icon, label,
    and count, using the app's existing success/warning/muted semantic tone convention (the file's
    own comment confirms this was deliberately aligned to the existing semantic tokens, not a
    one-off palette).
  - A single multi-segment progress bar (3 colored segments, one per RSVP status, sized by
    proportion) plus a "`X`% đã phản hồi" caption.
  - Conditionally, a "pending" callout box (only when `rsvpBreakdown.pending > 0`) naming the
    group with the most pending invitations.
  - Conditionally, a "Người tham dự" breakdown by guest group (top 3 groups by attendee count,
    each with a count `Badge`) — only rendered when at least one group has `attendeeCount > 0`.
  - **Explicitly does not show gift money/gold** — the file's own comment states this is
    intentional ("không đưa tiền/vàng mừng lên Overview, chỉ có ở tab Khách mời"). This is a scope
    boundary the Pilot must not cross.
- **Loading**: combined `isInvitationsLoading || isGroupsLoading` → `Skeleton` (`h-24
  rounded-2xl`) replaces the entire body (including the header's own description, which is
  hard-coded empty string here — i.e. this widget's `SectionHeading` never shows a description).
- **Error**: `invitationsError ?? groupsError` → inline red text *inside* the Card, replacing the
  whole body (different pattern from §5.1/§5.2, where errors are additive banners above an
  unaffected Card) — this is a real ErrorState candidate, see §11.
- **Empty**: `total === 0` → "Chưa có khách mời nào được thêm vào kế hoạch." inside the Card.

**5.3.b `WeddingFinanceSummaryWidget`**

- **Header**: `SectionHeading` — eyebrow "Tài chính", title "Ngân sách kế hoạch", `action` =
  "Xem thêm ➔" calling `onOpenFinance`.
- **Body** (inside one `Card`, no loading/error/empty state of its own — `statistic` and
  `estimatedTotal` are always-available numeric props, computed upstream in the Shell):
  - "Đã chi `spent` / `estimatedTotal`" text, a single-segment progress bar colored by budget
    health (`success` <70% used, `warning` 70-100%, `danger` >100%, computed by
    `getBudgetHealthTone`), a "`X`% ngân sách" caption (plus "— đã vượt dự kiến" suffix when
    over 100%), and "Còn dự kiến `remaining`" text.
  - Top-3 spending categories (icon, name, amount), only rendered when at least one category has
    `totalAmount > 0`.
- **Finance color invariant, already correctly implemented here**: ordinary amounts (`spent`,
  `estimatedTotal`, `remainingBudget`, category totals) render in neutral slate text — only the
  budget-health percentage/bar carries `success`/`warning`/`danger` color, and only because it
  represents a *state* (healthy/warning/over-budget), not because it's a monetary value. This
  widget is already compliant with the Finance Color Invariant from Wave 1 — the Pilot's job here
  is to preserve this exactly, not "fix" anything.

## 7. Permission-sensitive actions

Wedding Overview's own widgets contain **zero mutation actions and zero destructive actions**.
Every interactive element is either whole-widget visibility (resolved upstream, outside Pilot
scope) or a navigation callback. This is a genuinely low permission-complexity surface, which is
part of why it's a good first Pilot (06.PilotMigration.md §5/§6).

### 7.1 Whole-widget visibility (the only real permission-sensitive behavior in scope)

| Widget | Gating `moduleId` | Owner | Editor (default config) | Editor (module access overridden to `hidden`) | Viewer |
|---|---|---|---|---|---|
| `weddingAttentionSummary` | `'overview'` | Always visible | Always visible | Always visible (this moduleId is never gated) | Always visible |
| `weddingMilestoneSnapshot` | `'planning'` | Always visible (subject to `!isPlanEnded`) | Visible per `EDITOR_DEFAULT_MODULE_ACCESS.planning` | Hidden | Visible unless stored override is `hidden` |
| `weddingGuestFinanceSummary` (both sub-widgets together) | `'weddingGuests'` | Always visible | Visible per `EDITOR_DEFAULT_MODULE_ACCESS.weddingGuests` | Hidden | Visible unless stored override is `hidden` |

Note the coupling: guest info and finance info share **one** `moduleId` (`weddingGuests`) today —
hiding a member's Wedding Guests module access hides the Finance summary widget too, since they're
one registry entry (`WeddingGuestFinanceRowWidget`). This is existing behavior, not something to
"fix" — flagged here only so it's not mistaken for a migration bug later.

### 7.2 Navigation-only actions (not permission-gated beyond §7.1's whole-widget visibility)

```text
"Xem thêm ➔" (attention/todos)     → onOpenPlanningTodos      → switches Shell tab to 'planning'
"Xem thêm ➔" (milestones)          → onOpenPlanningMilestones → switches Shell tab, sets work-view mode
"Xem thêm ➔" (guests)              → onOpenWeddingGuests      → switches Shell tab to 'weddingGuests'
"Xem thêm ➔" (finance)             → onOpenFinance            → switches Shell tab to 'finance'
Attention/upcoming todo row click  → onViewTodo                → opens Shell's existing TodoDetailView modal
```

None of these five callbacks are conditionally rendered or disabled based on role — they're always
present when their parent widget is visible at all.

### 7.3 One integration point outside this Pilot's scope, flagged for awareness

`onViewTodo` opens `TodoDetailView` inside a `ResponsiveModal` that lives in the Plan Detail Shell
(`plans/[planId]/page.tsx`, not in the Overview widget files). *That* modal has real
permission-sensitive logic (`canManagePlan` from `hasCapability('planning.editAllTodo' | ...)`)
and a real destructive action (`onDeleteTodo`). **This Pilot does not touch that modal or
`TodoDetailView`** — it's Shell-owned, already `ResponsiveModal`-based (Wave 3), and out of scope
per the instruction not to migrate the Shell. It's listed here only as a regression-matrix
integration check: after migrating Overview's widgets, clicking a todo row must still open the
same modal with the same content and the same permission-resolved edit/delete affordances.

## 9. Current responsive behavior

Confirmed by reading the actual Tailwind breakpoint usage in all 4 widgets — **real, already-
existing mobile/desktop divergence** (a genuine V2 validation opportunity, not something to
invent):

```text
Attention items (§5.1):
  <1024px (Mobile + Tablet, since only `lg:` is used) → divided list, no per-row border/shadow
  ≥1024px (Desktop)                                    → grid of bordered/shadowed cards,
                                                          1-3 columns depending on item count

Milestone cards (§5.2):
  <1024px → stacked (1 column)
  ≥1024px → `lg:grid-cols-2` side by side (only when both current+next milestone exist)

Guest + Finance row (§5.3):
  <1024px → stacked, guest summary first
  ≥1024px → `lg:grid-cols-2` side by side
```

**Tablet currently renders identically to Mobile** in all three cases (nothing branches on the
768-1023px range specifically) — consistent with 01.Foundation.md §25 / 05.CorePatterns.md §31:
"Three-tier support does not require three separate...implementations." This is documented as
current behavior, not flagged as a defect; the Pilot should preserve it unless real evidence
during implementation shows Tablet needs its own treatment.

No horizontal scrolling, no hidden-on-mobile content, no feature-availability differences between
breakpoints were found in these widgets — every breakpoint difference is a *composition* change
(stack vs. grid, bordered-card vs. divided-list), consistent with capability parity
(06.PilotMigration.md §65).

## 16. Browser-level verification plan for Mobile / Tablet / Desktop

06.PilotMigration.md §80 explicitly states automation is insufficient for this phase and requires
manual verification. This sandbox currently has **no headless browser** (`chromium-cli`/
Playwright) — flagged honestly in every report since Wave 1, and 06.PilotMigration.md §55/§80 make
this a hard requirement for the Pilot specifically, not an optional nice-to-have like in prior
waves.

**Plan, to be executed once implementation begins:**

1. **Set up browser tooling before writing Pilot code**, not after — install/verify `chromium-cli`
   (or an equivalent headless-Chromium driver) in this environment, per the standing recommendation
   repeated in every report since Wave 1. If genuinely unavailable in this sandbox, that itself
   must be escalated for review rather than substituting source-reading for the required manual
   verification 06.PilotMigration.md §80 mandates.
2. **Representative widths** (per §55): 375px (mobile narrow), 428px (mobile large), 768px
   (tablet), 1024px (desktop), 1440px (wide desktop).
3. **Per-width checklist**, derived from §15's matrix:
   - All 4 widget bodies render with correct content for a seeded Wedding plan fixture covering:
     zero-state, mixed-urgency attention items, both milestones present, guests across all 3 RSVP
     states, budget in each of the 3 health tiers.
   - Attention items: divided-list at <1024px, bordered-card grid at ≥1024px, correct column
     count (1/2/3) for item count.
   - Milestone cards: stacked at <1024px, side-by-side at ≥1024px when both exist.
   - Guest+Finance row: stacked (guest first) at <1024px, 2-column at ≥1024px.
   - Long Vietnamese content (long todo titles, long milestone titles, long guest group names)
     wraps without breaking layout at every width.
   - Large currency values (9.500.000đ / 150.000.000đ / 1.250.000.000đ-scale) do not overflow or
     misalign the progress-bar/text layout.
4. **Keyboard walkthrough** (§51): Tab through each "Xem thêm" action and every attention/upcoming
   todo row; confirm focus-visible renders (canonical `--color-focus-ring`, per Wave 2/3) and that
   activating a todo row opens the Shell's `TodoDetailView` modal with focus entering it correctly
   (Wave 3's `ResponsiveModal` focus lifecycle — verify the *integration*, not the modal internals).
5. **Screen reader structure spot-check** (§52): page/section heading hierarchy (does adopting
   `Section` introduce or fix any heading-level issue versus the current raw `SectionHeading`
   usage — no regression expected either way, confirm), button/action names, status text (RSVP
   labels, budget %, milestone status) not conveyed by color alone (already true today per §6's
   invariant table — confirm it stays true post-migration).
6. **Touch target check** (§53): the "Xem thêm" buttons and todo/attention rows are the only
   interactive elements — confirm all satisfy the 44×44px intent already established as a
   Foundation-wide rule (Wave 1 §33).
7. **Record results directly in the eventual `06.PilotMigration.Report.md`**, per the required
   report structure (spec §97) — do not defer this to a follow-up document.
