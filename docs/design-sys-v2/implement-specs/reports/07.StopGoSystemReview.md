## 2. Finding #1 — Progress

### A. Evidence

```text
Wedding Overview (Pilot #1):
- Milestone progress: single-value % bar (completedTodoCount/todoCount), hand-rolled 2-div
  track+fill, WeddingMilestoneCard.
- Budget progress: single-value % bar (spent/estimated), hand-rolled, same visual recipe as
  milestone.
- RSVP breakdown: NOT a linear bar — a multi-segment composition (attending/pending/not_attending
  proportions), structurally different from the other two (it's closer to a stacked-bar chart than
  a single-value progress indicator).

Dashboard (Pilot #2):
- PlanCard progress: single-value % bar (varies by PlanType — budget-spent, saving-goal, milestone
  completion depending on plan-card-config.ts), hand-rolled, same 2-div track+fill recipe as
  Wedding Overview's milestone/budget bars, but with per-plan-type fill/track colors sourced from
  plan-card-visuals.ts (raw hex, frozen per Dashboard override #1 — see Finding #2).

Existing repository consumers beyond the two Pilots: not surveyed exhaustively in this review
(would require a repo-wide grep outside this review's evidence scope of "both Pilots' actual
migrated surfaces" — flagged as a gap in the evidence itself, see Decision below).

Repeated or isolated: the SINGLE-VALUE track+fill pattern is now repeated 3 times across 2 Pilots
(Wedding milestone, Wedding budget, Dashboard PlanCard) with byte-similar markup (`h-2` or similar
track height, `overflow-hidden rounded-full` track, absolutely-width-styled fill div). The
SEGMENTED pattern (RSVP breakdown) has exactly 1 occurrence — no repetition evidence at all.
```

### B. Semantic ownership

`CORE PRIMITIVE` for the single-value linear case — Design System V2 Section 11.29-11.30
(`11.GoPlanProductTheme.md`) explicitly anticipates this: **"Chúng ta nên có: Linear Progress cho
utility. Và: Journey Progress cho important plan-level moments."** This is a locked product-theme
decision (`TH-06` motif usage), not a fresh proposal — the spec already names the primitive and
positions it as Core-level infrastructure, with `JourneyProgress` explicitly scoped as a **Go Plan
Product Pattern, not Design System Core** (§11.30: *"`JourneyProgress` nên là Go Plan Product
Pattern, không phải Design System Core"*).

The segmented case (RSVP breakdown) has no equivalent anticipation in the spec and, with a single
occurrence, cannot yet be classified beyond `PRODUCT-SPECIFIC` / `INSUFFICIENT EVIDENCE`.

### C. Root cause

Missing Design System capability for the linear case (spec anticipated it, implementation never
built it — Core Primitives Wave (`02.CorePrimitives.Report.md`) did not include it, and neither
Pilot's Pre-Code manifest proposed inventing it mid-Pilot, correctly deferring per "don't invent,
defer instead").

### D. Decision

**Linear/single-value progress: AMEND DESIGN SYSTEM** (add a `Progress`/`ProgressBar` Core
Primitive) — but **not yet implemented by this review**, per explicit boundary instructions.
**Segmented progress (RSVP-style): KEEP PRODUCT-SPECIFIC / INSUFFICIENT EVIDENCE** — one
occurrence is not evidence of a reusable shape; forcing a `ProgressSegment` abstraction now would
violate the "don't design a large API without consumer evidence" instruction directly. The correct
model, per this evidence, is:

```text
Progress          (Core Primitive — single value, track + fill, tone-aware)
ProgressTrack /
ProgressSegment    NOT justified yet — defer until a second segmented-progress consumer appears
                    (Pilot #3's Wedding Guest RSVP list is a plausible second data point, since
                    Wedding Guest domain already has RSVP semantics — but that evidence does not
                    exist yet, so it cannot be assumed)
```

**Layer:** Core Primitive, not Structural Component. Reasoning: a linear progress bar is
anatomically closer to `Badge`/`Switch` (a small, tone-aware, non-compositional visual unit that
renders one piece of already-resolved state) than to `Card`/`Section`/`DataRow` (which arrange
*other* content). It takes exactly one resolved numeric ratio and a tone, the same shape as
`Metric` takes a resolved value — and `Metric` itself lives in Structural Components specifically
because it composes label+value+supporting, which Progress does not need to do. `04.
StructuralComponents.md` §4's explicit non-scope list does not mention Progress, and
`02.CorePrimitives.md`'s canonical scope (Button/Input/Textarea/Badge/Avatar/Date-Time/
DropdownSelect/Switch) is exactly the tier of "small, tone-aware, non-arranging" components
Progress belongs with.

### E. Timing

**NON-BLOCKING BEFORE PILOT #3.** Two consumers is real evidence and enough to *design* the
primitive, but nothing about Wedding Guest (Pilot #3) is known to depend on it yet — Wedding Guest
Pre-Code (not yet written) may or may not surface a third consumer. Building it now, before Pilot
#3's own Pre-Code evidence exists, risks guessing at an API shape neither Pilot actually needed
(the segmented case is a warning sign of exactly this risk — a superficially related but
structurally different progress shape). Recommended: build during **Rollout** once Pilot #3
either confirms the pattern a third time or doesn't.

### F. Required change (if/when amended — not implemented now)

```text
Layer: Core Primitive (new file, e.g. src/shared/components/ui/progress.tsx)
Spec: 02.CorePrimitives.md would need a new section (Button/Badge-adjacent placement)
Source code change: YES — new component + migrate 3 existing hand-rolled instances
  (WeddingMilestoneCard budget/milestone bars, PlanCard progress bar) to consume it
Documentation-only change: NO — this is a real component gap, not a documentation gap
Blast radius: 2 files (overview-widget-registry.wedding.tsx, plan-card.tsx) — small, both already
  reviewed/migrated once, low regression risk since only the DOM/class structure changes, not the
  computed percentage value
Regression requirement: value-diff (same % before/after) at 0%/partial/100% for each of the 3
  existing consumers, per the same discipline already used in both Pilots' regression matrices
```

## 3. Finding #2 — Plan-Type Expression colors

### A. Evidence

`plan-card-visuals.ts` defines, for all 9 `PlanType` values: `iconBgClassName` (raw Tailwind
gradient, e.g. `bg-gradient-to-br from-amber-500 to-orange-300`), `accentTextClassName` (raw hex,
e.g. `text-[#9a3412]`, `text-[#0c48d7]` — 8 of 9 types actually share the identical `#0c48d7`,
only `debt` differs), `progressTrackClassName`/`progressFillClassName` (raw hex). This is the
single largest concentration of non-token color in the two Pilots combined, frozen unchanged
through Dashboard per explicit user override.

`11.GoPlanProductTheme.md` §11.34 and `12.Plan-Type Expression.md` §12.5 both **already propose**
the exact token family needed:

```text
plan.wedding.accent / .surface / .text
plan.travel.accent / .surface / .text
plan.debt.accent / .surface / .text
plan.saving.accent / .surface / .text
plan.event.accent / .surface / .text
```

§12.4 explicitly states timing: *"Đây là direction, chưa khóa mã màu ở Section 12. Mã màu cụ thể
sẽ thuộc token implementation sau khi Pilot validate."* — token implementation was always meant to
follow Pilot validation. Dashboard is explicitly named as the validation ground: §12.53 *"Dashboard
là nơi nhiều PlanType xuất hiện cạnh nhau. Đây là test quan trọng nhất cho Plan-Type Expression."*

**We now have that validation**, and the result is encouraging at the architecture level:
Dashboard's actual implementation already follows §12.55's rule (*"Không: Wedding = whole pink
card... Ưu tiên: white/neutral surface + accent icon + small progress/accent"*) — confirmed by
direct inspection of the Dashboard browser-verification screenshots (populated scenario, §"Browser
Verification" in the Dashboard Report): every PlanCard is a white/neutral surface with the accent
confined to the icon badge, one metric's text color, and the progress fill — never a tinted whole
card. The *architecture* Section 12 asks for is already correct; only the *token layer* is
missing.

One concrete risk surfaces from this evidence that the spec itself anticipated and named: §12.28
warns Debt's accent must be a **"desaturated ochre"**, specifically *because* amber collides with
the semantic warning color, and says *"Phải đặc biệt thận trọng"* (must be especially careful).
Current implementation uses `from-amber-500 to-orange-300` for Debt's icon gradient and `#9a3412`
(a saturated dark-orange) for its accent text — Foundation's `--color-status-warning` is `#d97706`,
a genuinely close hue. No confusion has been observed or tested for in either Pilot's browser
verification (neither Pilot's regression matrix included a "does the Debt plan icon read as a
warning" check), so this is a real, named, spec-anticipated risk with no evidence either way yet.

### B. Semantic ownership

`PLAN-TYPE EXPRESSION` (the layer Section 12 defines) for the accent/token values themselves.
`FOUNDATION` only in the narrow sense that the *token mechanism* (CSS custom properties,
`--theme` block) is Foundation infrastructure — the *values* are explicitly Plan-Type Expression,
not generic Foundation semantic colors, per `04.StructuralComponents.md` §89 (*"Structural
components should generally not receive `planType`... Avoid `<Card planType="wedding" />`"*) and
Section 12's own architecture diagram (`Design System Core → Go Plan Product Theme → Plan-Type
Expression → Product Composition`).

### C. Root cause

Not a missing capability and not an incorrect contract — this is the **anticipated, intentional
sequencing** described by the spec itself (§12.4: tokenize *after* Pilot validation). The
underlying visual *architecture* (icon+accent, not whole-card tint) is already correct; what's
outstanding is purely the token-extraction step, which is explicitly downstream work, not a defect
being newly discovered.

### D. Decision

**AMEND DESIGN SYSTEM** — but the amendment is the *token extraction*, not a redesign, and it is
explicitly **not implemented by this review**. Ownership should live as a **Plan-Type Expression
token layer** (`plan.{type}.accent/.surface/.text`, per §12.5's own proposal), consumed *only* by
`plan-card-visuals.ts` (i.e., the product configuration file, not by `Card`/`Metric`/`Badge`
themselves) — this preserves `04.StructuralComponents.md` §89's hard rule that generic components
must never receive `planType`. Generic Structural/Core components remain completely unaware this
token family exists; only the product-owned visuals-config file would change what it points its
existing `accentTextClassName`/etc. fields at.

The Debt/warning-color proximity risk (§12.28) is recorded as a **sub-finding requiring explicit
attention at token-design time**, not resolved here — `KEEP PRODUCT-SPECIFIC` for now (i.e., no
action beyond flagging), since no evidence of actual user confusion exists and inventing a new
"desaturated ochre" hex value without contrast/perception testing would repeat exactly the kind of
unsourced-value invention this project's whole methodology exists to prevent.

### E. Timing

**NON-BLOCKING BEFORE PILOT #3.** The current raw-hex approach is not a Pilot #3 blocker because
Pilot #3 (Wedding Guest) is a single PlanType (`wedding`) — it does not exercise the cross-PlanType
comparison Dashboard already validated, and Wedding's own accent (`#0c48d7` in the current
`plan-card-visuals.ts`, shared with 7 of the other 8 types — itself worth noting as a separate,
smaller observation: only Debt currently has a genuinely distinct accent; the other 8 types
including Wedding are visually undifferentiated from each other today, which is its own quieter
piece of evidence that the token layer hasn't been designed with real per-type distinctiveness in
mind yet). Tokenizing now, before Pilot #3, would be introducing a new Foundation-adjacent
mechanism without a second Pilot's worth of validation on top of Dashboard's single data point —
appropriate for **Rollout**, once broader product surface evidence (ideally including Pilot #3)
confirms the token shape.

### F. Required change (if/when amended — not implemented now)

```text
Layer: Plan-Type Expression (new conceptual layer — likely a new CSS custom-property block in
  globals.css, namespaced e.g. --plan-{type}-accent, following the existing --color-* pattern)
Spec: 12.Plan-Type Expression.md §12.5's proposal would move from "proposed" to "locked" with
  actual hex values chosen (currently placeholders in the spec: "Rose/Warm Pink", "Sky/Cyan-Blue",
  "Amber/Ochre" etc. are directions, not hex codes)
Source code change: YES — src/styles/globals.css (new tokens) +
  src/modules/plan/constants/plan-card-visuals.ts (consume tokens instead of raw hex) — no other
  file needs to change, since plan-card-visuals.ts is already the single source PlanCard reads
  from
Documentation-only change: NO for the token definition; the spec's own "proposed → locked" status
  change IS a documentation change that should accompany it
Blast radius: 1 product file + 1 stylesheet — deliberately small, because the config-file
  indirection this project already has means no consumer of plan-card-visuals.ts needs to change
Regression requirement: visual diff across all 9 plan types (icon/accent/progress color must
  remain visually equivalent or be an explicitly reviewed/approved change, not an accidental
  drift), plus a specific contrast/distinction check for Debt against --color-status-warning
```

## 4. Finding #3 — Action primitive gaps

Evaluated independently, per instruction — these are three different findings with different
evidence strength, not one primitive.

### 3A. TextAction / text-link style action

**Evidence:** Wedding Overview only. `ViewAllAction` required `<Button variant="ghost">` with
`h-auto min-h-0 gap-0 rounded-none p-0` overrides — a near-total strip of Button's chrome to
reach a plain text-link shape. **Dashboard has zero occurrences of this pattern** — no "Xem thêm"
or equivalent text-link affordance exists anywhere in the Dashboard composition tree (confirmed by
direct inspection of `plans/page.tsx` and every component it renders; the closest thing, the FAB
and CreatePlanCard, are both full affordances with icon+label, not stripped-down text links).

**Semantic ownership:** `CORE PRIMITIVE` candidate (`Button variant="link"` or a small dedicated
`TextAction`), but **insufficient repeated evidence** — one Pilot, one consumer.

**Decision: DEFER TO ROLLOUT.** Exactly the same conclusion the Wedding Overview Pre-Code package
already reached, now reconfirmed by a second Pilot providing zero additional evidence. This is not
a regression in confidence — it is correct application of "don't invent, defer instead": Dashboard
genuinely didn't need it, so building it now would still be guessing from a single data point.

**Timing:** NON-BLOCKING / DEFERRED — wait for a second real consumer (plausible candidates:
Wedding Guest's likely "view all"/"see more" list actions in Pilot #3).

### 3B. IconButton

**Evidence:** Dashboard's notification bell (`plans/page.tsx`) is a raw `<button>` with hand-rolled
`size-11 rounded-full` chrome and tone-class branching — never composed from `Button` at all. This
is architecturally significant beyond "one more raw button": `02.CorePrimitives.md` §21 **already
canonically anticipates** a `Button` size named exactly `icon` (*"Canonical target: sm, md, lg,
icon"*), and the current `button.tsx` source contains an explicit, dated comment recording why it
was deliberately left out of Wave 2:

```text
// `icon` intentionally NOT added: unlike `sm`, there is no real icon-only Button consumer
// anywhere in the repo to derive/verify it against (accessible-name + 44x44 touch target can't
// be checked without one). ... add both only when a real consumer needs them.
```

Dashboard's bell button is precisely that consumer. This is the strongest-evidenced item in
Finding #3 — the spec pre-approved the primitive, Wave 2 explicitly deferred only for lack of a
consumer, and that consumer now exists with a real accessible-name requirement
(`aria-label="Thông báo"`) and touch-target size (`size-11` ≈ 44px, matching `02.CorePrimitives.md`
§14's 44×44px target almost exactly) to verify the size against.

**Semantic ownership:** `CORE PRIMITIVE` — specifically an extension of the *existing* `Button`
component (`size="icon"`), not a new component, per the spec's own framing.

**Decision: ADOPT NOW candidate** — evidence bar is met (spec pre-approved, real consumer exists
with concrete a11y requirements to verify against), but **not implemented by this review** per
explicit boundary. This is the one Finding #3 item strong enough to reasonably be pulled into
Pilot #3 prep work rather than deferred to Rollout, since Wedding Guest is highly likely to need
icon-only row actions (menu triggers, remove buttons) — the same primitive gap will otherwise
recur immediately.

**Timing:** **NON-BLOCKING BEFORE PILOT #3** but flagged as a strong Rollout-or-earlier candidate
— see Non-Blocking Amendments in §12.

### 3C. NotificationBadge

**Evidence:** Dashboard's bell icon + numeric count overlay (`plans/page.tsx:72-76`, raw
`absolute -right-1 -top-1` positioned span with `bg-rose-500`). **Single occurrence, single
Pilot.** No second consumer anywhere in either Pilot.

**Semantic ownership:** Ambiguous between `CORE PRIMITIVE` (a tiny positioned-badge-on-anchor
recipe) and simply a **composition pattern** documented in guidance rather than built as a
component — the entire "component" is a few Tailwind classes on a `<span>`, not obviously complex
enough to justify a dedicated abstraction the way `IconButton` (with its accessible-name and
touch-target contract) is.

**Decision: KEEP PRODUCT-SPECIFIC / INSUFFICIENT EVIDENCE.** One occurrence cannot justify a new
primitive, and unlike the IconButton case, the spec does not pre-anticipate this one. Building it
now would be inventing ahead of evidence.

**Timing:** DEFERRED UNTIL MORE EVIDENCE.

### Accessibility requirements (all three, for whichever amendment eventually proceeds)

```text
Accessible name    IconButton: mandatory aria-label (already true of the bell today — this
                    survives migration, not newly required)
Touch target        IconButton: verify 44×44px per 02.CorePrimitives.md §14; current bell
                    (size-11 = 44px) is already compliant, migration must not shrink it
Keyboard behavior   All three: native <button> semantics already used today (bell, FAB) — must
                    remain native buttons after any primitive adoption, not become divs
Focus-visible        All three: Button's existing focus-visible ring must carry over unchanged
```

## 5. Finding #4 — Radius / elevation

### A. Evidence

Canonical Foundation scale (`6.Foundation.md` §6.7, `FD-08`, confirmed in current
`globals.css`): **8 / 12 / 16 / 20 / full** (`--radius-ds-sm/md/lg/xl/full`). No 24, 26, or 28px
value exists anywhere in the canonical scale.

`11.GoPlanProductTheme.md` §11.19 gives an explicit target for major surfaces: *"Go Plan Theme nên
thiên về 12–16px cho major surfaces. Không cần 24–32px rounded card như nhiều consumer apps."* —
this is a locked-intent statement directly contradicting the current 24-28px values found in both
Pilots.

Current inventory across both migrated Pilots (grep-verified, this pass):

```text
20px   overview-widget-registry.wedding.tsx:276           — CANONICAL (--radius-ds-xl)
24px   card.tsx (base Card, --radius-card var)             — Wave 4 documented legacy debt
24px   plan-card.tsx:49 (PlanCard's Card override)          — reuses the same legacy value
24px   todo-attention-section.tsx:70 (row link)              — reuses the same legacy value
24px   overview-widget-registry.wedding.tsx:225              — reuses the same legacy value
24px   todo-attention-section.tsx (Skeleton loading, post-Pilot-#2) — reuses the same legacy value
24px   plans/page.tsx:142 (search-empty box)                — reuses the same legacy value
26px   overview-widget-registry.wedding.tsx:136 (lg: Card)   — NEW value, matches neither legacy
                                                                nor canonical
28px   todo-attention-section.tsx:40 (Card override)         — NEW value, matches neither
28px   create-plan-card.tsx:10                               — NEW value, matches neither
28px   plans/page.tsx:127-129 (Skeleton loading, ×3)          — NEW value, matches neither
28px   overview-widget-registry.wedding.tsx:234               — NEW value, matches neither
```

### B. Semantic ownership

`STRUCTURAL COMPONENT` for `Card`'s own default radius (governed by `04.StructuralComponents.md`
§21/§74). `MIGRATION-ONLY` for every per-consumer override value, since `04.StructuralComponents.md`
§67 explicitly makes per-consumer radius classification a **Pilot-time job**, not a Phase 4 job:
*"When migrating a consumer, classify each existing container: A — logical page grouping → Section
... "* — this classification exercise, for Card-role consumers specifically, has not yet happened
for any of the values above except the one 20px instance.

### C. Root cause

**A combination, and the two halves are genuinely different in severity:**

1. **24px is controlled, documented migration-compatibility debt.** Wave 4's implementation
   report and the `card.tsx` source comment (`TEMPORARY LEGACY COMPATIBILITY`) both explicitly
   record the decision, the reason (58 unreviewed Card consumers, avoiding an app-wide cascading
   visual change ahead of per-consumer review), and the fact that it is **not** the canonical
   target. This is exactly what `04.StructuralComponents.md` §108/§128 anticipated: Phase 4 should
   not broadly migrate consumers; that happens per-Pilot/Rollout. Every 24px instance found above
   is a direct or indirect reuse of this one documented, intentional decision — it is not spreading
   uncontrolled, it is being *correctly, consistently inherited* from Wave 4's frozen baseline.

2. **26px and 28px are uncontrolled visual drift.** Neither value has *any* basis in the canonical
   scale, the legacy `--radius-card` value, or any documented decision. They were introduced
   independently, ad hoc, by two different Pilots (26px once in Wedding Overview, 28px five times
   across both Pilots) with no cross-reference to each other or to Section 6.7. This is the kind
   of drift Wave 1's whole "don't invent, defer instead" discipline exists to prevent, and it
   happened anyway — inside components most exposed to exactly this discipline (`TodoAttentionSection`,
   `CreatePlanCard`, `Skeleton` loading blocks, all migrated or touched during Pilot #2's own
   "ADAPT" work, under close scrutiny, and still landed on a value with no basis).

### D. Decision

## 6. Finding #5 — ResponsiveModal focus return

This finding required the deepest investigation in this review, per its higher priority.

### 6.1 What was found in the Dashboard Pilot

Opening `CreatePlanForm`'s `ResponsiveModal` from the Dashboard FAB, then closing via Escape,
left focus on `<body>` instead of returning to the FAB. `responsive-modal.tsx` was not touched by
Pilot #2 (confirmed via `git diff` at the time), so the Dashboard Report correctly classified this
as pre-existing, not a regression.

### 6.2 Desktop behavior (Radix `Dialog`)

`ResponsiveModal`'s desktop branch is an unmodified, standard Radix `Dialog.Root` /
`Dialog.Portal` / `Dialog.Overlay` / `Dialog.Content` composition (`responsive-modal.tsx:36-67`),
with no `onOpenAutoFocus`/`onCloseAutoFocus` override anywhere. It relies entirely on Radix's
library default for both.

### 6.3 Mobile behavior (`vaul` `Drawer`)

`ResponsiveModal`'s mobile branch (`responsive-modal.tsx:70-112`) is similarly unmodified vaul
`Drawer.Root`/`Drawer.Content`, also with no `onOpenAutoFocus`/`onCloseAutoFocus` override.
Inspecting `node_modules/vaul/dist/index.mjs` confirms `vaul` is itself built directly on top of
`@radix-ui/react-dialog` (`import * as DialogPrimitive from '@radix-ui/react-dialog'`), so the
mobile branch inherits the *same* underlying Radix focus-scope mechanism as desktop, layered under
vaul's own `autoFocus` prop (default `false` — this is the mechanism `confirm-dialog.tsx` already
works around explicitly for its own `Drawer.Content`, per its code comment: *"Drawer has no
equivalent — it defaults autoFocus to false and focuses nothing at all — so Drawer.Content's own
onOpenAutoFocus extension point is used to focus Cancel explicitly."* **`ResponsiveModal` itself
has never received this same treatment** — only `ConfirmDialog` did, during Wave 3.

### 6.4 Is trigger/close focus restoration guaranteed?

Yes, by Radix's own default mechanism, *if* the consumer does nothing to prevent it —
`@radix-ui/react-focus-scope`'s `FocusScope` (which `Dialog.Content` renders internally) captures
`document.activeElement` as `previouslyFocusedElement` when its container mounts, and — unless
`onUnmountAutoFocus`'s dispatched event has `preventDefault()` called on it — restores focus to
that captured element (or `document.body` as fallback) via a `setTimeout(0)` in its cleanup
(`node_modules/@radix-ui/react-focus-scope/dist/index.mjs:76-106`). `ResponsiveModal` does not call
`preventDefault()` anywhere, so this default path should apply.

### 6.5 Root cause investigation (live verification performed this pass)

To rule out test-methodology artifacts before drawing a conclusion, an isolated harness (mounting
the real, unmodified `ResponsiveModal` with no other page state) was driven with **real keyboard
interaction** (`Tab` → `Enter` → `Escape`, not `.click()`, to avoid any ambiguity about synthetic
click-focus behavior) and `document.hasFocus()` was checked at every step to rule out a headless
browser window-focus artifact:

```text
document.hasFocus() before interaction:  true
After Tab   → activeElement = <button aria-label="Tạo kế hoạch">   (trigger correctly focused)
After Enter → activeElement = <button aria-label="Đóng">, hasFocus: true   (Radix's own
              onMountAutoFocus correctly moved focus into the dialog, to its first tabbable
              element — expected, working correctly)
After Escape → activeElement = <body>, hasFocus: true   (focus did NOT return to the trigger)
```

This was run **twice**: once against `next dev` (`reactStrictMode: true` in `next.config.ts`,
which double-invokes effects in development — a plausible confound for exactly this class of bug,
since the failure mode involves a `document.activeElement` capture inside a `useEffect`), and once
against a **production build** (`next build && next start`, where React's development-only
double-effect-invocation does not run regardless of the `reactStrictMode` config flag). **Both
runs produced an identical result.** This rules out React StrictMode's dev-only double-invocation
as the cause — the defect reproduces in the same code path real users will run.

**What this review could not fully isolate within a read-only investigation:** the exact internal
reason Radix's `previouslyFocusedElement` capture (which appears, from source inspection, to
correctly capture the trigger button given the effect's own internal ordering — see the full
reasoning trail in this session's working notes) does not end up restoring focus. A concrete,
testable hypothesis for whoever implements the fix: Radix's `Dialog.Content` is wrapped in a
`Presence`-driven exit-animation lifecycle (`data-[state=closed]:animate-content-hide` in
`responsive-modal.tsx:43`), which can delay actual DOM unmount (and therefore `FocusScope`'s
cleanup/restore timing) until the CSS animation completes — if some other focus-affecting event
happens in that window, or if the restore fires against a DOM node whose relationship to the
animation-driven unmount sequence differs from a plain instant-unmount, that would explain a
correct-in-isolation library mechanism failing in this specific animated composition. This was not
verified further, since doing so would require modifying `responsive-modal.tsx` (even temporarily)
to test with animations removed, which this review's boundaries do not permit.

### 6.6 Does our architecture bypass the primitive's normal trigger relationship?

Partially, structurally: `ResponsiveModal` is a fully **controlled** component (`open`/
`onOpenChange`, no `Dialog.Trigger` used anywhere) — consumers open it from arbitrary external
elements (a FAB, a menu item, etc.) rather than a `Dialog.Trigger`-wrapped button. This is an
explicitly *sanctioned* pattern in Radix's own API (controlled `Dialog.Root` without `Trigger` is
first-class, documented Radix usage, not a hack), and `03.OverlayArchitecture.md` §19 explicitly
requires preserving controlled-open-state architecture (*"Preferred product contract should
support controlled state where existing architecture uses it: open / onOpenChange... Do not
change state ownership merely for V2 consistency"*) — so this is not itself a violation of the
spec. But it does mean Radix's `document.activeElement`-based trigger-tracking (rather than a
literal trigger-element reference Radix is explicitly given) is the *only* mechanism available,
and the evidence in §6.5 shows that mechanism is not reliably restoring focus in our specific
composition.

### 6.7 Decision

**AMEND DESIGN SYSTEM.** Classified `OVERLAY ARCHITECTURE` — this is squarely
`ResponsiveModal`'s own responsibility per `03.OverlayArchitecture.md` §21/§23 (*"On close: focus
returns to the logical trigger when possible... The overlay primitive should preserve default
trigger restoration where possible"*), and per §78, *"Accessibility failure in the canonical
overlay is a Phase 3 blocker"* — meaning by the spec's own stated standard, a real, reproducible
accessibility gap in the canonical overlay is not something to defer casually, even though Phase 3
itself already completed. This is not `REJECT` (the gap is real and reproducible, confirmed
twice under different build modes) and not `KEEP PRODUCT-SPECIFIC` (it is the shared primitive,
not a product consumer, that owns this behavior). It is not yet `ADOPT NOW` in the sense of "we
know the fix" — the root cause needs one more level of instrumented investigation (§6.5) before a
correct, non-hacky fix (explicitly: **not** a `setTimeout`/`useEffect` manual focus hack, which
`03.OverlayArchitecture.md` §21 and this review's own instructions both prohibit) can be written.

### 6.8 Timing

**BLOCKING BEFORE PILOT #3 — but the blocking task is narrow and fast, not a redesign.**
Reasoning: Wedding Guest (Pilot #3) is explicitly flagged by its own eventual Pre-Code as needing
real overlay-heavy workflows — guest create/edit forms, likely delete confirmations, likely
import/export dialogs — all built on `ResponsiveModal`/`ConfirmDialog`. If this focus-return gap
is systemic to `ResponsiveModal`'s controlled/external-trigger pattern (which is the pattern every
one of those future consumers will also use), Pilot #3 will reproduce the same defect across many
more surfaces simultaneously, at exactly the point where regression-matrix scope is already
largest. Fixing (or definitively ruling out) this gap *before* Pilot #3 opens is cheaper than
discovering it repeated five times inside Pilot #3's own verification. The fix itself, once root
cause is confirmed, is expected to be narrow (a `ResponsiveModal`-internal change, likely either an
explicit `onCloseAutoFocus` handler mirroring `ConfirmDialog`'s existing pattern of manually
managing focus via the *primitive's own supported extension point* — not a manual
`setTimeout`/`useEffect` hack — or a fix to the animation/unmount timing interaction) — see §12
Blockers for the concrete, bounded task definition.

## 7. Metric/PlanCard finding (Pilot #2 rejection)

Pilot #2 evaluated composing `Metric`/`MetricGroup` into `PlanCard`'s core metric block and
rejected it, for three concrete, source-verified reasons (full detail in
`06.PilotMigration.Dashboard.Report.md` §7a): `Metric`'s fixed internal label/supporting color
roles are **inverted** relative to `PlanCard`'s original label/detail weighting; `Metric`'s closed
`tone` union cannot express `PlanCard`'s 9-way per-plan-type accent color; and `PlanCard`'s
per-field money-masking behavior needs full style-override control that `Metric`'s `value`/
`supporting` props don't cleanly provide.

**Evaluation: this indicates `PlanCard` is a legitimate product-specific composition, not that
`Metric`'s API is wrong.** `Metric`'s design intentionally keeps its tone system small and closed
(`04.StructuralComponents.md` §31: *"Metric may support a small generic tone system when
semantically justified: default/success/warning/danger/brand... Use tone for actual meaning, not
decoration"*) — widening it to accommodate 9 arbitrary per-plan-type hex values would be exactly
the kind of God-Component drift §8/§9 of the same spec warns against (*"When this happens: STOP
and reassess whether composition should remain in the product/pattern layer"*). `PlanCard` doing
its own thing here is the *correct* outcome of that guardrail working as designed, not a failure
of either component.

**Decision: not an open blocker.** No amendment recommended. This is recorded as a **positive
architecture signal** — evidence the Metric/MetricGroup boundary is holding under real pressure,
not evidence it needs to change. Should Pilot #3 (or a future PlanCard-adjacent surface) hit the
*same* rejection reason a second time with a *different* product component, that would become
worth reconsidering; one occurrence, with a well-reasoned rejection already on record, is not.

§3 item 2).

**Timing:** DEFERRED UNTIL MORE EVIDENCE. If Pilot #3 or Rollout produces a second
always-bottom-anchored, richer-header overlay need, that becomes real evidence for a new pattern;
until then, this remains correctly product-specific.

## 9. System-level review

**1. Did both Pilots preserve business invariants?**
Yes. Both Pilot reports carry explicit invariant-mapping tables (Wedding Overview: guest
count≠attendee count, money≠gold, finance neutral-by-default, milestone progress formula, RSVP
breakdown sum invariant, module-access-gated visibility; Dashboard: plan ordering, search
semantics, 5-site money masking, 9-way plan-type metric semantics, ended-plan branching, both Debt
sub-models, no-plan-limit-exists), each with a stated verification method, and both regression
manifests report all-NO across business logic/data model/permissions/routes/financial
calculations/filtering/sorting/validation/feature capability.

**2. Did shared V2 components remain domain-agnostic?**
Yes, with the Metric/PlanCard case (§7) as the clearest test of this under real pressure — the
boundary held by *not* being adopted where the fit was wrong, rather than being stretched to fit.
`04.StructuralComponents.md` §117's import boundary (no `modules/wedding`, `modules/plan`, etc.
inside Design System files) was checked directly for both Pilots' migrated files; none violate it.

**3. Did any God Component emerge?**
No. `MetricGroup`, `DataRow`, `Badge`, `ErrorState`, `Skeleton` all stayed at their Phase 4/5
contracts through two Pilots' worth of real usage pressure — the one place a component *could* have
grown a `planType` prop (Metric, under pressure from PlanCard) instead correctly stayed small and
had the product component decline to adopt it (§7).

**4. Did product components retain semantic ownership?**
Yes. `PlanCard`, `TodoAttentionSection`, `TodoNotificationScreen`, `CreatePlanCard`,
`WeddingMilestoneCard`, `WeddingGuestFinanceRowWidget` all remain their own components after
migration, composing V2 primitives/structural components internally rather than being replaced by
them or absorbed into a generic engine — consistent with ADR §4's canonical model and
`04.StructuralComponents.md` §64's explicit list of components that "must survive."

**5. Did V2 improve consistency without forcing bad abstractions?**
Largely yes, with the open findings above being exactly the honest exceptions: Progress and the
Plan-Type token layer are real, evidenced gaps *not yet forced into an ill-fitting shape* (both
Pilots correctly hand-rolled rather than stretching Metric/Card to cover them) — this is the
system working as intended, producing evidence for Rollout rather than premature abstractions.

**6. Did migration create meaningful regressions?**
One real regression was found and fixed *during* migration (Wedding Overview's
`WeddingMilestoneCard` truncate/`min-w-0` bug, confirmed pre-existing via `git diff` context lines,
not introduced by the Pilot, but caught and corrected before FINAL PASS). No unresolved regression
exists in either Pilot's final state per both regression manifests.

**7. Are temporary legacy compatibility decisions still controlled?**
Mostly yes (the 24px Card legacy value, §5C item 1), with one clear exception: the 26px/28px
drift (§5C item 2) is **not** a controlled decision — it has no documentation, no spec basis, and
happened inside the very Pilots meant to be exercising this project's "don't invent" discipline
most carefully. This is this review's clearest finding of process (not architecture) slippage.

**8. Is the architecture stable enough for a more complex Pilot #3?**
Yes, conditionally on Finding #5's blocker (see below). The two Pilots together exercised: 9-way
PlanType branching, cross-plan-type dashboard density, permission-display (role badges),
privacy-masking, multi-listener real-time data, two different overlay patterns, and one genuine
architecture-boundary stress test (Metric/PlanCard) that resolved correctly. Wedding Guest's
additional real complexity — dense filtered lists, forms, likely destructive confirmations, richer
permission gating — is not yet proven against V2, but nothing in either Pilot suggests the
architecture would buckle under it; the open findings are additive evidence-gathering items, not
structural warning signs, with the single exception of Finding #5's overlay-focus gap, which *is*
a structural risk specifically because Pilot #3 will exercise overlays far more heavily.

**9. Which findings must be fixed before Pilot #3?**
Finding #5 (ResponsiveModal focus-return) — see §12 for the bounded blocker task. The Pilot #3
Pre-Code radius-disclosure guardrail (§5E) is also required before Pilot #3's Pre-Code is written,
but is a review-process step, not a code fix, and costs essentially nothing to apply.

**10. Which findings should deliberately wait until Rollout?**
Progress primitive (Finding #1), Plan-Type Expression token layer (Finding #2), TextAction
(Finding #3A). IconButton (Finding #3B) is borderline — strong enough evidence to build now, but
not blocking; recommended as a **non-blocking amendment** that may reasonably be done either
immediately before Pilot #3 or during Pilot #3's own implementation once its Pre-Code confirms a
real icon-button consumer there too (very likely for a dense guest list's row actions).
