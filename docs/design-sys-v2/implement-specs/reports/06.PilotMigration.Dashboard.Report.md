### 7a. Why `Metric`/`MetricGroup` were evaluated and rejected for `PlanCard`

This is the one disposition that differs from a naive reading of "compose where clean" and is
worth recording precisely, since it wasn't obvious until checked against the actual component
source and token values:

1. **Label/detail color roles are inverted between the two systems.** `PlanCard`'s original
   label (`text-[var(--color-subtle)]`, lighter) and detail/footer text
   (`text-[var(--color-muted)]`, darker) intentionally put more visual weight on the detail than
   the label. `Metric`'s fixed internal recipe (`metric.tsx:50,52`) does the opposite: its
   `label` slot uses `--color-text-secondary` (→ `--color-muted`, darker) and its `supporting`
   slot uses `--color-text-muted` (→ `--color-subtle`, lighter). Composing `PlanCard`'s
   label/detail directly into `Metric`'s `label`/`supporting` props would silently **invert**
   which text reads as more prominent — a real visual hierarchy regression, not a neutral
   typography refresh. `Metric` has no `className` hook on its internal label/value/supporting
   elements to correct this (`...props` spreads only onto the outer wrapping `<div>`).
2. **`Metric`'s `tone` union has no slot for `PlanCard`'s 9-way per-plan-type accent color.**
   `tone?: 'default' | 'success' | 'warning' | 'danger' | 'brand'` cannot express
   `visual.accentTextClassName`'s 9 raw hex values (one per `PlanType`, from
   `plan-card-visuals.ts`, explicitly kept unchanged per override #1). Passing a pre-colored
   `<span>` as `value` would work around this, but only by re-implementing full manual color
   control inside `value` — at that point `Metric` contributes nothing except its outer
   `flex`/`gap` wrapper, while its label/supporting styling (point 1) is actively wrong for this
   consumer.
3. **Per-field masking doesn't map onto a single closed `tone` prop.** `getMaskedMoneyClassName`
   fully replaces the color/tracking classes on 5 independent call sites (primary value, primary
   detail, secondary value, progress label, progress secondary detail) depending on
   `plan.isLocked` combined with each field's own `isMonetary` flag. Preserving this exactly
   through `Metric` would again require passing pre-styled spans into `value`/`supporting`,
   which defeats the purpose of adopting the primitive.

Net: `Metric`/`MetricGroup` were composed only where they would provide real value with no loss
of fidelity; for `PlanCard`'s core metric block, that condition doesn't hold today. This is
recorded, not silently skipped — see §22 for how it feeds the Progress-primitive discussion
already pending from Pilot #1.

the FAB renders correctly `fixed`-positioned at the true bottom-right of the viewport — the

rendering issue.

**Coverage gap disclosed (same class as Wedding Overview's, not new):** TodoAttentionSection and

into that internal hook's real Firestore listener. Both consistently rendered their empty-state
branch during verification. This is a pre-existing architectural trait, not something this Pilot's
diff changed or could change within its file boundary — recorded per Pre-Code §14/Non-Goals.
