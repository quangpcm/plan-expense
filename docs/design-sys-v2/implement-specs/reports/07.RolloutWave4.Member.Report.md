## 5. Business / permission / data changes

**NO.** Role/permission/ownership rules, service calls, and mutation arguments are byte-identical
to before. Specifics:

- **Mutation call sites unchanged**: `onDelete?.(member)`, `onUnlinkAccount?.(member)`,
  `onReactivate?.(member)` / `onRemove?.(member)` — same optional-chaining calls, same arguments,
  same branch conditions (`isRemoved ? onReactivate : onRemove`), same order of operations
  (`await` the call, **then** close the dialog — unconditionally, regardless of success or
  failure).
- **The "always closes after await" behavior was deliberately preserved, not "fixed."** This
  component's page-level handlers (`handleDeleteMember`, `handleUnlinkAccount`,
  `handleReactivateMember`, `handleRemoveMember` in the page) catch their own errors internally and
  never re-throw (they surface failures via a separate `memberActionError` state rendered above
  `MemberList` in `members-tab.tsx`) — so `await onDelete?.(member)` always resolves, and the
  dialog closing unconditionally is the **existing** behavior, unrelated to this migration. This is
  a different pattern from Wave 0's page-level request/perform flows (which keep the dialog open
  and show `errorMessage` inline on failure) — I did not force this component into that other
  pattern; `ConfirmDialog`'s `errorMessage` prop was deliberately left unset here, matching what
  `member-list.tsx` already did (no local error surfacing at all).
- **Confirm-button color semantics preserved exactly, not normalized.** The original code was
  deliberate about severity: delete used inline `bg-red-600 text-white hover:bg-red-700` styling
  (confirmed byte-identical to `ConfirmDialog`'s `confirmVariant="destructive"` per that
  component's own code comment, harvested in Wave 2), while unlink and deactivate/reactivate used
  plain, non-red buttons. Mapped 1:1: `confirmVariant="destructive"` only for delete;
  `confirmVariant="default"` for unlink and deactivate/reactivate. I did not "upgrade" the other
  two to red for consistency — that would have been a business-severity judgment call outside this
  migration's scope.
- **`isLinked` branch**: when a member has linked financial records, the original UI showed no
  destructive button at all (only "Đóng"). Mapped by omitting `confirmLabel` entirely (not passing
  `confirmLabel={undefined}` — `exactOptionalPropertyTypes: true` rejects that; the prop is
  conditionally spread in instead) — `ConfirmDialog` renders no confirm button when `confirmLabel`
  is absent, reproducing the original's "info-only, no way to force the destructive action from
  here" behavior exactly.
- One additive-only `loading` delta, precedented by Wave 0: `isSaving` is now wired into
  `ConfirmDialog`'s `loading` prop for all three confirms. `ConfirmDialog` disables **both**
  Cancel and Confirm while `loading`, whereas the original `BottomSheet` version only disabled
  Confirm (`disabled={isSaving || ...}`) and left Cancel always clickable. This is a real,
  intentional-not-accidental delta — same trade-off Wave 0's report documented and the user
  approved for 6 other flows ("the same double-submit protection every other `ConfirmDialog` usage
  in this file already relies on"), reapplied here rather than newly invented. Flagging it
  explicitly rather than silently, per this wave's "if ambiguous, STOP" instruction — I judged this
  one not ambiguous (directly precedented, strictly additive protection, not a rule change) and
  proceeded; happy to revisit if you'd rather `member-list.tsx` diverge from that precedent.
- `MemberActionsMenu`'s `onSelect` callbacks (which open these dialogs) are untouched — no change
  to which actions are offered to which member, i.e. no permission-gating logic was touched.

## 9. Findings / deferred debt

- **Pre-existing, not introduced by this wave**: `member-list.tsx`'s `summary` block renders an
  avatar-change `<button aria-label="Đổi avatar của {nickname}">` **nested inside**
  `Collapsible`'s own toggle `<button>`. This is invalid HTML (a `<button>` cannot contain another
  interactive element); on the SSR'd page it causes a real "Hydration failed... Invalid HTML tag

  `git diff` — this migration never touches that block. Out of Wave 4's scope to fix (a structural
  a11y/hydration defect unrelated to overlay migration); flagging for awareness, not fixing
  opportunistically per this wave's explicit instruction.
