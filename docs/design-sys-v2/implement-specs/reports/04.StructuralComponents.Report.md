## 5. New canonical components

All six new components are pure presentation, zero business/domain imports (verified — none
import anything from `modules/*`, `services`, `repositories`, or Firebase), zero permission props,
zero PlanType branching, zero data fetching.

- **`Section`** — `{ eyebrow?, title?, description?, action?, children }`. Composes
  `SectionHeading` for its header; renders no surface (no background/border/shadow) of its own.
  `title` is optional so `Section` can also be used purely for spacing/grouping without a header.
- **`Metric`** — `{ label, value, supporting?, leading?, tone?, size? }`. `value` is `ReactNode` —
  the component never formats or calculates it. `tone` defaults to `default` (neutral); `success`/
  `warning`/`danger`/`brand` exist but nothing in the component ever infers a tone from the value
  itself — the finance neutral-by-default invariant is structurally enforced by the API shape, not
  by convention. Sizes map directly to Foundation's `metric-sm/md/lg` typography roles from Wave 1
  — no new typography invented here.
- **`MetricGroup`** — `{ columns?: 2|3|4, density?, children }`. Composition-only (`<MetricGroup><Metric
  .../><Metric .../></MetricGroup>`), no config array, no data prop. This is the component the
  review flagged as highest God-Component risk — see §8 for the boundary discussion in detail.
- **`DataRow`** — `{ leading?, main, status?, trailing?, selected?, disabled?, density?, onClick?, className? }`.
  Renders a `<div>` by default (non-interactive); becomes a real `<button>` only when `onClick` is
  passed. See §9 for the full boundary discussion.
- **`EmptyState`** / **`ErrorState`** — kept as two separate exported components (not one shared
  `State` component with a `type` prop) per §57's explicit instruction that empty/error semantics
  must stay distinct even though they share a visual recipe. Neither has a permission prop, a retry
  implementation, or error-parsing logic — see §10.

## 7. Section/Card boundary decisions

- `Section` never renders a surface. `Card` never implies page hierarchy. This is enforced
  structurally, not just by convention: `Section`'s markup literally has no background/border/
  shadow class anywhere in its implementation.
- **The Card default-shadow/radius change, and why it's reverted for now**: `Card` has **58
  consumers** across the repository (`grep -rl "from '@/shared/components/ui/card'"`). Changing
  its default shadow/radius is a single-file change that automatically applies to every one of
  them the next time each screen renders — no consumer file needs editing to achieve this. This
  isn't the kind of "mass migration" earlier waves avoided (no component was swapped for another),
  but it *is* a real, simultaneous, app-wide visual change, which is exactly why the review asked
  for it back out despite the target itself (`elevation.none` + canonical radius) being correctly
  derived from the spec (§21/§75/§121). The decision was well-evidenced but *staged too early*:
  each of the 58 consumers' surrounding hierarchy (nesting, whether that particular usage is even
  correctly a Card vs. should be a Section) hasn't been individually reviewed, so an app-wide
  cascade shouldn't happen until that review does. Reverted; recorded as `TEMPORARY LEGACY
  COMPATIBILITY` in `card.tsx` per §0/§4, to be resolved contextually — consumer by consumer —
  during Pilot/Rollout, not flipped back on globally in one shot even then.
- Proof consumer: `plans/archived/page.tsx`'s page-level `<Card><SectionHeading .../></Card>` was
  a textbook instance of the exact anti-pattern §14 names (`Page → Card → Card`, Card used as page
  section) — Category A "logical page grouping" per the §67 classification rule. Replaced with
  `<Section eyebrow title description />`. The individual `ArchivedPlanListItem` row's own Card
  wrapper was **not** touched at that level — a single archived-plan entry among a list is
  Category B "contained entity/surface," where Card remains the correct choice per Audit Decision
  Record §12.1.

## 8. Metric/MetricGroup boundary decisions

This is the section the review asked to see most clearly, so stated plainly:

- `Metric`'s prop type is `{ label: ReactNode; value: ReactNode; supporting?: ReactNode; leading?:
  ReactNode; tone?: 'default'|'success'|'warning'|'danger'|'brand'; size?: 'sm'|'md'|'lg' }`. That
  is the complete API surface — six props, all either presentation content or a closed enum of
  generic visual roles. None of them can carry a domain concept: there is no `finance`, `guest`,
  `debtDirection`, or similar prop, and none could be added without visibly breaking the "closed
  enum" shape of `tone`/`size`.
- `MetricGroup`'s prop type is `{ columns?: 2|3|4; density?: 'comfortable'|'default'|'compact';
  children }`. It receives `Metric` elements as `children` — it never receives a data array,
  domain collection, or config object. There is no code path in `MetricGroup` that reads a value
  out of its children or computes anything from them; it only applies grid/gap CSS classes.
- Neither component imports anything beyond `react`, `cn`, and (`Metric` only) nothing else at
  all. Verified by reading both files in full — `metric.tsx` imports `cn` and React types only;
  `metric-group.tsx` imports the same.
- **No live proof consumer was migrated for `Metric`/`MetricGroup` this wave.** Real label+value
  stat displays that could plausibly become `Metric` usage exist (e.g. the Wedding Overview widget
  registry's attendee/spend figures), but every candidate found sits inside a Wedding or Finance
  file — exactly what §109 says not to choose as a first proof ("Do not choose consumers that
  force: complex Wedding Guest behavior, Finance settlement logic"). Rather than force a marginal
  or contrived consumer just to have one, both components ship complete and spec-compliant with
  adoption deferred to Core Patterns/Pilot, which §108 explicitly allows ("Major product adoption
  begins in Core Patterns and Pilot waves"). This mirrors the same discipline already applied to
  Button's `size="lg"`/`size="icon"` in Wave 2 — no forced consumer just to check a box.

## 9. DataRow boundary decisions

- Prop type: `{ leading?: ReactNode; main: ReactNode; status?: ReactNode; trailing?: ReactNode;
  selected?: boolean; disabled?: boolean; density?: 'comfortable'|'compact'; onClick?: () => void;
  className?: string }`. `main` is the only required slot; everything else is either an optional
  slot or a generic presentation-state boolean. No prop named `Guest`, `Member`, `Debt`, `Expense`,
  `role`, or any domain concept exists, and none could be added without it being immediately
  visible as a violation of the slot-only shape.
- Interaction model follows the **exact pattern `settings-row.tsx` already established** in this
  codebase (`isInteractive = Boolean(onClick)`, conditionally rendering `<button>` vs. `<div>`) —
  harvested, not invented, and consistent with §46's requirement not to collapse every row into a
  clickable `<div>` regardless of whether it's actually interactive. Default is non-interactive
  (`<div>`), matching the explicit Test requirement in §100.
- `selected` is presentation-only (a boolean → background class); `DataRow` does not manage a
  selection collection, own multi-select state, or know what "selected" means for any entity —
  matching §47.
- Proof consumer: `archived-plan-list-item.tsx`'s top row (icon avatar + plan name + days-
  remaining subtitle) became a `DataRow` composition (`leading` = icon, `main` = title/subtitle).
  This is exactly the §110 pattern ("if a product component can internally replace repeated
  markup with a structural component without changing its public API or behavior, that may be a
  valid proof migration") — `ArchivedPlanListItem`'s own props, all business logic (`isOwner`,
  `handleRestore`, `handleDelete`, both error states, the delete-confirmation panel) are
  byte-for-byte unchanged; only the top row's markup source changed.
- `settings-row.tsx` itself was **not** touched or replaced by `DataRow` — it remains `REVIEW`-
  classified per Audit Decision Record §20.5, and forcing a disposition on it wasn't this wave's
  call to make.

## 10. Empty/Error boundary decisions

- Both components take `title` (required), `description?`, `visual?`, `action?`,
  `secondaryAction?` — six props total, no permission prop, no `cause`/`reason` enum, no retry
  implementation. `ErrorState` does not know what failed or why; the consumer supplies both the
  copy and the `action` (§58/§59 — no action is assumed to be "Thử lại").
- Kept as two separate components (not unified with a `variant="empty"|"error"` prop) per §57's
  explicit instruction — the internal visual recipe is intentionally near-identical (both files
  are ~35 lines, structurally the same layout), but they are distinct exports with distinct JSDoc
  intent, so a future reader/reviewer can't accidentally blur "nothing to show" with "something
  failed."
- Proof consumer: `plans/archived/page.tsx`'s inline empty-state `<div>` (`rounded-[24px]
  border-dashed ... Không có kế hoạch nào đã lưu trữ.`) became `<EmptyState title="..." />`. No
  `ErrorState` proof consumer was found or forced — the repository has **zero** existing
  "Không thể tải"/"Thử lại" error-surface patterns to migrate from (checked via grep across all
  `.tsx` files), meaning there was no low-risk real consumer to prove it against. Shipped complete
  and unconsumed, same reasoning as `Metric`/`MetricGroup` in §8.

## 15. Tests

`npm run test` — **149/149 pass**, 22 files (15 pre-existing + 7 new). Added per §0's second
required fix: basic contract tests for all seven Phase 4 canonical components.

**Approach — zero new dependencies.** The existing test setup (`vitest.config.ts`) runs under
`environment: 'node'` with no DOM, no jsdom, no React Testing Library — sufficient for the
pure-logic tests that existed before, but not for rendering React components. Rather than add a
new testing dependency (jsdom + `@testing-library/react`, which §95 doesn't forbid but which is
more infrastructure than "basic contract tests" needs), each new test renders components with
`renderToStaticMarkup` from `react-dom/server` — already an installed dependency (`react-dom` is a
direct `dependency`, not just a peer) — and asserts on the resulting HTML string. This needed only
one config change: widening `vitest.config.ts`'s `include` glob to also pick up `*.test.tsx` (was
`*.test.ts`-only). No new package was installed.

fixtures — generic strings like `"Label"`/`"Title"` throughout, per instruction):

## 16. Build

`npm run build` — **PASS** on the second attempt. First attempt failed with a real, legitimate
TypeScript error:

```text
src/shared/components/ui/section.tsx(21,17): error TS2375: Type '{ action: ReactNode; ... }' is
not assignable to type 'SectionHeadingProps' with 'exactOptionalPropertyTypes: true'.
```

Root cause: this repo's `tsconfig.json` has `exactOptionalPropertyTypes: true`, which distinguishes
"prop key absent" from "prop key present with value `undefined`." `Section` forwards its own
optional `eyebrow`/`description`/`action` props straight into `SectionHeading`, and when `Section`
is used without those props, they arrive as explicit `undefined` — which `SectionHeadingProps`
(typed as plain `eyebrow?: string`) rejected under this strict flag. Fixed by widening
`SectionHeadingProps`'s optional fields to `T | undefined` explicitly (the standard fix for this
exact pattern), not by changing `Section`'s own API or adding a runtime workaround. Re-ran
`build` clean afterward. This is the same category of finding as Wave 1's circular-`var()` bug and
Wave 3's initial-focus claim: caught by actually running the real verification command, not by
assuming a lighter command was equivalent — see §13.

**Compiled-CSS verification** (standing practice since Wave 1), re-run after the §0 revert:

```text
--radius-card:1.5rem;              (legacy value restored — 24px)
18px 54px ...                       (legacy shadow restored, confirmed present in output)
```

`brand-subtle` (DataRow's `selected` background) and the `text-metric-md`/`text-component-title`
typography classes (Metric/EmptyState/ErrorState) were also confirmed present in the compiled
bundle.
