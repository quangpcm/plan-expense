# Go Plan — Design System V2 Specification

# 15. Migration Rules & Strategy

**Status:** Proposed — Implementation Gate
**Dependency:** Sections 1–14 — Accepted
**Scope:** Migration principles · V1/V2 coexistence · component disposition · migration phases · pilot strategy · legacy retirement · rollback · AI implementation boundaries

---

## 15.1 Purpose

Sections 13–14 đã xác định:

```text
Section 13
WHAT MUST NOT CHANGE

Section 14
HOW TO CLASSIFY CHANGE
```

Section 15 trả lời:

> **Làm thế nào đưa Go Plan từ UI hiện tại sang Design System V2 mà không rewrite application và không làm business regress?**

## Go Plan đã có architecture tách UI → Hook → Service → Repository → Firebase, trong đó business logic thuộc Service và component không được gọi Firestore trực tiếp. Migration UI phải tận dụng boundary này thay vì chạm sâu xuống business layer.

# 15.2 Migration Principle

Không:

```text
V1
↓
REWRITE
↓
V2
```

Mà:

```text
V1
│
├── preserve business
│
├── introduce V2 foundation
│
├── migrate component
│
├── migrate pattern
│
├── migrate screen
│
└── retire legacy
        ↓
       V2
```

Core rule:

> **Progressive migration, not visual rewrite.**

Điều này cũng nhất quán với Modular Plan Architecture hiện tại: specification đã yêu cầu không rewrite toàn application cùng lúc và giữ backward compatibility cho existing Wedding data.

---

# 15.3 What Migration Is Allowed to Change

Migration được phép thay:

* design tokens;
* typography;
* spacing;
* radius;
* surface treatment;
* component visual anatomy;
* page composition;
* responsive layout;
* density;
* information hierarchy khi được classify L3;
* interaction presentation khi được classify L2;
* Plan-Type Expression.

Migration không mặc định được phép thay:

```text
Business Logic
Data Model
Service contracts
Repository
Firestore
Security Rules
Permission semantics
Entity lifecycle
Calculation
Cross-module relationships
```

Nếu cần:

> Section 14 L4 process.

---

# 15.4 Migration Unit

Không migrate theo:

```text
file-by-file
```

hoặc:

```text
page-by-page một cách ngẫu nhiên.
```

Migration unit ưu tiên:

```text
Foundation
    ↓
Primitive
    ↓
Component
    ↓
Pattern
    ↓
Screen family
    ↓
Product surface
```

Ví dụ:

```text
Spacing tokens
↓
Card / Section
↓
MetricGroup
↓
Overview metrics
↓
Wedding Overview
↓
Travel Overview
```

Nhờ đó một quyết định được validate trước khi lan rộng.

---

# 15.5 Dependency Direction

Migration phải đi từ low-level → high-level:

```text
Foundation
      ↓
Primitives
      ↓
Core Components
      ↓
Patterns
      ↓
Product Composition
      ↓
Plan-Type Expression
```

Không bắt đầu sửa 15 screens rồi sau đó mới quyết định:

* radius;
* section spacing;
* typography;
* button hierarchy.

---

# 15.6 Foundation First Rule

Trước Pilot phải implement đủ Foundation V2 tối thiểu:

```text
Color tokens
Typography tokens
Spacing
Radius
Elevation
Border
Icon sizing
Focus
Motion fundamentals
Responsive breakpoints
Density rules
```

Không cần implement toàn bộ Design System.

Chỉ cần đủ để Pilot không phải hard-code.

---

# 15.7 No Big Bang Migration

Cấm strategy:

```text
Replace entire UI
↓
Test at the end
```

Vì Go Plan đã có nhiều domain có coupling business quan trọng:

* Finance;
* Permissions;
* Wedding Guest;
* Travel Itinerary;
* Debt.

Architecture hiện cũng dùng Wedding như reference production model và yêu cầu existing Plans, Milestones, Todos, Expenses, Income, Members và Wedding Guests tiếp tục hoạt động sau refactor.

---

# 15.8 Component Disposition

Mỗi component hiện tại trước migration được classify:

```text
KEEP
ADAPT
REPLACE
MERGE
DEPRECATE
REMOVE
```

---

# 15.9 KEEP

Component:

* architecture tốt;
* semantic đúng;
* API phù hợp;
* chỉ cần token V2.

Ví dụ conceptual:

```text
Input
Checkbox
Avatar
Spinner
```

Action:

> giữ component, migrate styling.

---

# 15.10 ADAPT

Component đúng concept nhưng anatomy/API chưa hoàn toàn phù hợp V2.

Ví dụ:

```text
Button
Badge
Dialog
Tabs
```

Action:

> giữ identity/component contract nếu hợp lý, cải tiến internals.

Đây thường là nhóm lớn nhất.

---

# 15.11 REPLACE

Component cũ encode một pattern V1 không còn phù hợp.

Ví dụ:

```text
StandaloneMetricCard
```

có thể được thay bằng:

```text
MetricGroup
MetricItem
```

Nếu V2 đã quyết định giảm card fragmentation.

---

# 15.12 MERGE

Nhiều components thực chất giải cùng một UI problem.

Ví dụ:

```text
WeddingStatCard
TravelStatCard
FinanceSummaryCard
```

nếu khác nhau chủ yếu styling:

```text
↓
Metric / MetricGroup
```

Nhưng chỉ MERGE presentation.

Không merge business entities.

---

# 15.13 DEPRECATE

Component còn tồn tại để support V1 screen chưa migrate.

Rules:

```text
Can render existing screen
Cannot be used for new V2 work
Cannot receive new visual variants
```

Chỉ bug fix critical được phép.

---

# 15.14 REMOVE

Chỉ remove khi:

```text
0 usages
+
replacement stable
+
regression passed
```

Không remove ngay khi component mới được tạo.

---

# 15.15 Component Inventory

Trước implementation nên tạo registry:

| Component | Current usage | Decision | V2 target    | Priority |
| --------- | ------------: | -------- | ------------ | -------- |
| Button    |          High | ADAPT    | Button V2    | P0       |
| Card      |     Very High | ADAPT    | Surface/Card | P0       |
| StatCard  |          High | REPLACE  | MetricGroup  | P0       |
| Badge     |          High | ADAPT    | Badge V2     | P0       |
| Dialog    |          High | ADAPT    | Dialog V2    | P0       |
| Accordion |        Medium | REVIEW   | Disclosure   | P1       |

Tên thực tế phải lấy từ codebase khi implementation.

Section này không giả định component names chưa được audit.

---

# 15.16 Usage Mapping Before Replacement

Trước khi REPLACE một component:

```text
Find all usages
↓
Classify contexts
↓
Identify hidden variants
↓
Design V2 API
↓
Pilot
↓
Migrate
```

Không:

```text
create NewCard
↓
global search/replace OldCard
```

---

# 15.17 V1/V2 Coexistence

Trong migration, V1 và V2 sẽ tồn tại cùng lúc.

Đây là trạng thái hợp lệ.

Nhưng phải kiểm soát.

```text
V1 Components
→ legacy surfaces only

V2 Components
→ migrated surfaces + all new UI
```

---

# 15.18 One-way Migration

Migration chỉ đi:

```text
V1 → V2
```

Không tạo feature mới bằng V1 vì:

> "screen này chưa migrate."

Nếu feature mới nằm trên legacy screen:

ưu tiên dùng V2 component nếu không gây inconsistency nghiêm trọng.

---

# 15.19 No Dual Evolution

Không:

```text
ButtonV1 gets new variant
ButtonV2 gets another new variant
```

sau khi V2 Button được accepted.

Một khi V2 equivalent stable:

> V1 freezes.

---

# 15.20 Legacy Isolation

Đề xuất code organization conceptual:

```text
components/
    ui/
        button
        input
        badge

    patterns/
        metric-group
        section
        entity-list

    legacy/
        ...
```

Không bắt buộc đổi folder ngay.

Mục tiêu là có **ownership rõ**.

---

# 15.21 No `v2` Forever Rule

Có thể tạm thời dùng:

```text
ButtonV2
CardV2
```

trong Pilot.

Nhưng final architecture không nên tồn tại lâu dài:

```text
Button
ButtonV2
ButtonV3
```

Sau migration:

```text
ButtonV2
↓
Button
```

và legacy bị remove.

---

# 15.22 Migration Adapter

Cho phép temporary adapter khi V1 API khác V2.

Ví dụ:

```text
LegacyStatCard props
       ↓
adapter
       ↓
MetricItem
```

Adapter chỉ có nhiệm vụ mapping presentation.

Không:

* calculate business metric;
* query data;
* resolve permission.

---

# 15.23 Adapter Exit Rule

Adapter phải có:

```text
owner
migration target
deletion condition
```

Nếu không:

> adapter có nguy cơ trở thành architecture mới.

---

# 15.24 Token Migration

Hard-coded values nên migrate dần:

```text
#6366f1
↓
color.brand.primary
```

```text
16px
↓
space.4
```

Nhưng không mechanical replace tất cả numeric value.

Ví dụ:

```text
chart geometry
map coordinate
image ratio
```

không nhất thiết là design token.

---

# 15.25 Token Adoption Rule

New V2 component:

> **No arbitrary visual values unless explicitly justified.**

Allowed:

```text
token
```

Exception:

```text
documented local value
```

Không để Pilot tạo một second hidden token system.

---

# 15.26 CSS/Tailwind Migration

Vì current stack sử dụng TailwindCSS, migration nên giữ nguyên technology layer; Design System V2 không yêu cầu đổi styling technology.

Concept:

```text
Semantic tokens
↓
Tailwind/theme mapping
↓
Components
```

Không:

```text
Component
↓
random hex / arbitrary px everywhere
```

---

# 15.27 Business Hook Preservation

Một migrated component/page nên tiếp tục consume cùng business hooks/services khi có thể.

Before:

```text
useExpenses()
↓
Expense UI V1
```

After:

```text
useExpenses()
↓
Expense UI V2
```

Không mặc định:

```text
useExpensesV2()
```

chỉ vì visual mới.

---

# 15.28 Service Preservation

UI migration không tạo:

```text
StatisticServiceV2
ExpenseServiceV2
GuestServiceV2
```

nếu business behavior không đổi.

Architecture hiện quy định business logic nằm trong Service và Repository chỉ CRUD; đây là boundary cần được giữ nguyên.

---

# 15.29 Data Preservation

Migration V2 phải chạy trên existing data.

Không yêu cầu:

```text
recreate Plan
reset Plan
migrate all records
```

chỉ để UI mới hoạt động.

Backward compatibility đã là architecture requirement hiện tại.

# 15.40 Why Finance Later

Finance không phải vì ít quan trọng.

Ngược lại:

> **Finance quá quan trọng để dùng làm nơi thử nghiệm Foundation.**

Current SDD đã xác định SplitService, StatisticService và SettlementService là những đối tượng cần unit testing riêng, cùng Expense/Statistic flow ở integration testing.

Do đó khi migrate Finance:

> Design System primitives phải tương đối stable.

# 15.43 Wave 3 — Travel Itinerary

Travel kiểm tra:

```text
Timeline
Time-based grouping
Activity categories
Plan expression
Master-detail
```

Nhưng phải giữ architecture:

```text
Planning ≠ Itinerary
```

và Expense ↔ Activity chỉ là weak relationship.

Architecture test hiện tại đã quy định Activity không Expense vẫn valid, Expense không Activity vẫn valid, và một Expense có cả milestoneId + activityId không được double count ở Plan total.

# 15.44 Wave 4 — Finance

Finance migration chia nhỏ:

```text
Finance Overview
↓
Financial Timeline
↓
Expense Detail
↓
Create/Edit Expense
↓
Statistics
↓

```

Không migrate Finance như một mega task.

# 15.45 Create Expense Is Protected Flow

Create Expense là critical workflow.

Current UI requirement đặt mục tiêu tạo Expense nhanh, với các default để giảm thao tác.

Migration không được làm form đẹp hơn nhưng chậm hơn đáng kể.

Regression cần đo:

```text
steps
fields
defaults
time-to-complete
error rate
```

---

# 15.46 Finance Calculation Freeze

Trong Finance UI migration:

```text
Split algorithm
Statistic calculation
Settlement algorithm
```

được xem là frozen unless separate L4 task.

Current split implementation yêu cầu tổng participant amounts luôn khớp Expense amount, bao gồm largest-remainder distribution cho Percentage/Shares.

---

# 15.47 Wave 5 — Debt / Specialized

Debt chỉ migrate sâu khi business specification tương ứng đủ mature.

Không dùng Design System migration để “hoàn thiện” business còn chưa khóa.

Architecture hiện chỉ khóa rõ distinction giữa Debt balance và Finance cash flow, cùng yêu cầu không double count.

# 15.48 Legacy Retirement

Sau mỗi wave:

```text
Find legacy usage
↓
Migrate remaining usage
↓
Delete adapter
↓
Delete legacy component
↓
Remove obsolete styles/tokens
```

Không chờ cuối project mới cleanup toàn bộ.

---

# 15.49 Legacy Retirement Gate

Một component chỉ được retired khi:

```text
[ ] No active usages
[ ] No dynamic usage
[ ] Replacement documented
[ ] Regression pass
[ ] Story/example updated if used
[ ] Old tokens no longer needed
```

---

# 15.50 Dead Token Cleanup

Token V1 chỉ remove khi không còn consumer.

Không rename/remove token global trong cùng PR với 20 screen migrations nếu tránh được.

---

# 15.51 Rollback Strategy

Mỗi migration batch phải rollback được mà không rollback business/data.

Ideal:

```text
V2 presentation commit
↓
rollback
↓
V1 presentation restored

Business data unchanged
```

Nếu không thể:

> batch đang coupling quá nhiều.

---

# 15.52 Feature Flag

Không bắt buộc feature flag cho mọi component.

Nên cân nhắc flag khi:

* whole screen L2/L3;
* critical Finance flow;
* large user-facing interaction change;
* rollback bằng deploy khó.

Không dùng feature flags để duy trì V1/V2 vĩnh viễn.

---

# 15.53 Migration With Live Users

Khi Go Plan đã Go Live, strategy trở nên strict hơn:

```text
small batch
↓
regression
↓
release
↓
observe
↓
next batch
```

Không rollout 20 screens cùng lúc.

---

# 15.54 New Feature During Migration

New feature phải:

> **V2-first.**

Không xây feature mới hoàn chỉnh bằng V1 rồi migrate lại.

Nhưng business scope của feature vẫn tách khỏi Design System migration.

---

# 15.55 Bug Fix During Migration

Critical business bug:

> fix ngay ở correct layer.

Visual bug legacy:

* fix nếu blocking;
* nếu screen sắp migrate, tránh polish lớn V1.

# 15.58 AI Must Reuse Before Create

Implementation rule:

```text
Search existing V2 component
↓
Can reuse?
   ↓ yes
Reuse

   ↓ no
Can extend without breaking semantics?
   ↓ yes
Extend

   ↓ no
Propose new component
```

Không tự tạo:

```text
WeddingMetricCard2
TravelMetricCard2
```

---

# 15.59 No Opportunistic Refactor

AI/developer không được trong một migration task tự:

* rename unrelated files;
* rewrite hooks;
* reorganize services;
* optimize queries;
* change data model;
* fix unrelated business behavior.

Ghi thành separate task.

---

# 15.60 Migration Completion Definition

Design System V2 migration hoàn tất khi:

```text
V2 Foundation = canonical
V2 components = canonical
V2 patterns = canonical
Legacy component usage = 0
Legacy tokens = removed or explicitly retained
Pilot + rollout regression = pass
Business invariants = preserved
```

Không phải khi:

> “Các màn hình chính nhìn giống V2.”

---

# 15.61 Migration Failure Conditions

Migration FAIL nếu:

1. Rewrite toàn app.
2. V1/V2 cùng tiếp tục evolve.
3. ServiceV2 được tạo chỉ vì UI mới.
4. Schema đổi để component dễ render.
5. Existing Plan cần recreate.
6. Pilot chứa nhiều local visual hacks.
7. Foundation chưa stable nhưng rollout đã bắt đầu.
8. Finance được dùng để experiment Foundation.
9. Legacy component vẫn được dùng cho feature mới.
10. Adapter không có deletion plan.
11. UI migration thay business calculation.
12. AI task không có scope/invariants.
13. Một batch không rollback độc lập.
14. Mobile/desktop capability drift.
15. Migration “xong” nhưng legacy system vẫn tồn tại song song.

# 16. Regression Strategy

**Status:** Proposed — Release Safety Gate
**Dependency:** Sections 13–15 — Accepted
**Scope:** Visual · Responsive · Accessibility · Interaction · Business · Permission · Data · Cross-module · Lifecycle · Performance smoke · release gates

---

# 16.1 Purpose

Migration Strategy trả lời:

> Làm thế nào chuyển sang V2?

Regression Strategy trả lời:

> **Làm sao chứng minh V2 không làm Go Plan tệ hơn hoặc sai hơn?**

Regression không chỉ là:

```text
Screenshot before
vs
Screenshot after
```

Go Plan cần ít nhất:

```text
Visual correctness
+
UX correctness
+
Business correctness
+
Permission correctness
+
Data compatibility
```

Current SDD đã có testing direction gồm unit tests cho Split/Statistic/Settlement, integration tests cho Expense/Member/Statistic và manual testing cho upload, realtime, offline, permission và settlement. Section 16 mở rộng strategy đó cho Design System migration, không thay thế nó.

# 16.70 Regression Failure Protocol

Nếu test fail:

```text
FAIL
 ↓
Classify
 ├─ Visual V2 issue
 ├─ UX issue
 ├─ Business regression
 ├─ Permission regression
 ├─ Data compatibility
 └─ Existing bug discovered
```

Không tự động assume:

> V2 gây ra mọi bug.

Nếu bug đã tồn tại V1:

ghi:

```text
Pre-existing defect
```

và xử lý riêng nếu không blocking migration.

---

# 16.71 No “Fix While Here” Rule

Nếu regression phát hiện existing business bug:

Không silently fix trong DS task trừ khi:

* critical;
* được reclassified;
* scope được approve.

Điều này giữ Before/After comparison đáng tin.

---

# 16.72 Definition of Regression PASS

Một migrated surface PASS khi:

```text
Visual meets V2
+
Responsive behavior correct
+
Accessibility baseline passes
+
Interactions work
+
Business outputs preserved
+
Permissions preserved
+
Lifecycle states work
+
Existing data compatible
```

# Section 15–16 Combined Gate

Với hai Section này, chúng ta đã hoàn thành **Migration Safety Layer**:

```text
SECTION 13
Business Invariants
WHAT MUST NOT CHANGE
          │
          ▼
SECTION 14
Impact Classification
HOW RISKY IS THE CHANGE?
          │
          ▼
SECTION 15
Migration Strategy
HOW DO WE CHANGE IT?
          │
          ▼
SECTION 16
Regression Strategy
HOW DO WE PROVE IT IS SAFE?
```

Và toàn bộ Design System V2 lúc này bắt đầu có thể chuyển từ **design specification** sang **implementation specification** mà không cần một cuộc rewrite lớn.

## Recommended implementation sequence

```text
PHASE 0
Design System Audit
│
├── Existing component inventory
├── Token inventory
├── KEEP / ADAPT / REPLACE / MERGE
└── Legacy dependency map
        ↓
PHASE 1
Foundation V2
        ↓
PHASE 2
Core Components
        ↓
PHASE 3
Core Patterns
        ↓
PHASE 4
PILOT

Dashboard
   ↓
Wedding Overview
   ↓
Wedding Guest
        ↓
PHASE 5
PILOT REVIEW / SYSTEM FREEZE
        ↓
PHASE 6
Progressive Rollout
        ↓
PHASE 7
Legacy Retirement
        ↓
DESIGN SYSTEM V2
CANONICAL
```

Điểm tôi muốn **khóa mạnh** ở đây là `PHASE 5 — Pilot Review / System Freeze`.

Không nên vừa hoàn thành Wedding Guest rồi lập tức migrate toàn app. Ba Pilot phải được đặt cạnh nhau và review như **một system**:

```text
Dashboard
Wedding Overview
Wedding Guest
```

Nếu lúc đó chúng ta phát hiện:

* section spacing chưa ổn;
* card philosophy chưa nhất quán;
* typography hierarchy còn yếu;
* MetricGroup API chưa đủ;
* Inspector không scale;
* accent quá mạnh;
* density chưa đúng;

thì sửa **Design System một lần** trước khi rollout.

Đây chính là thời điểm Design System V2 chuyển từ:

> **Proposed System**

sang:

> **Implementation Baseline.**

Sau baseline đó, các màn hình còn lại chủ yếu phải là **migration**, không còn là nơi brainstorm lại visual language từ đầu. Điều này sẽ giúp mục tiêu quan trọng nhất của chúng ta đạt được: Go Plan có một hệ thống UI đủ nhất quán để Go Live, nhưng đồng thời bộ Design System này cũng đủ generic để sau này bạn tái sử dụng làm nền tảng cho các sản phẩm/web app khác.
