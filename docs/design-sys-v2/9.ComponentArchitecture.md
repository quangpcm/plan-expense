# Go Plan — Design System V2 Specification

## 9. Component Architecture

**Status:** Proposed
**Dependency:** Sections 1–8 — Accepted
**Scope:** Ownership layers · Component contracts · Composition rules · Reuse boundaries · State model · API principles

---

## 9.1 Core Architecture Principle

Design System V2 sử dụng 4 tầng:

```text
Primitive
    ↓
Component
    ↓
Pattern
    ↓
Product Composition
```

Mỗi tầng giải quyết một mức abstraction khác nhau.

Không được bỏ qua ranh giới giữa các tầng chỉ để code nhanh.

---

# 9.2 Layer 1 — Primitive

Primitive là building block thấp nhất của UI.

Nó biết về:

* tokens;
* accessibility;
* interaction state;
* structural styling.

Nó **không biết domain**.

Ví dụ:

```text
Button
IconButton
Input
Textarea
Select
Checkbox
Radio
Switch
Badge
Avatar
Divider
Progress
Skeleton
```

Primitive trả lời:

> “Một control cơ bản của system hoạt động và trông như thế nào?”

---

## 9.2.1 Primitive Contract

Primitive phải:

* sử dụng semantic tokens;
* support state đầy đủ;
* accessibility built-in;
* responsive-safe;
* không chứa business logic;
* không import service/repository;
* không biết PlanType/module/domain entity.

Ví dụ hợp lệ:

```tsx
<Button variant="primary" size="md">
  Lưu
</Button>
```

Không hợp lệ:

```tsx
<Button
  wedding
  canEditExpense={...}
  debtStatus="overdue"
/>
```

Nếu primitive biết `Wedding`, `Expense`, `Debt`, abstraction đã bị leak.

---

# 9.3 Layer 2 — Component

Component là tổ hợp reusable của primitives để giải quyết một UI problem phổ biến.

Ví dụ:

```text

Dialog
Drawer
BottomSheet
Tabs
Accordion
DropdownMenu
SearchField
FilterBar
Metric
MetricGroup
EmptyState
Alert
StatusBadge
AvatarGroup
```

Component trả lời:

> “Một cấu trúc UI có thể tái sử dụng hoạt động thế nào?”

Nó vẫn **không được sở hữu business semantic cụ thể**.

# 9.4 Layer 3 — Pattern

Pattern là cách nhiều components được compose để giải quyết một loại task hoặc information structure lặp lại.

Ví dụ:

```text
PageHeader
SectionHeader
MetricSection
EntityList
Inspector
Timeline
AttentionSection
SummaryPanel
FilterableList
MasterDetail
ActionFooter
```

Pattern trả lời:

> “Một loại experience phổ biến được tổ chức như thế nào?”

Pattern có thể biết semantic UI như:

* primary info;
* metadata;
* action;
* selected row;
* summary;
* detail.

Nhưng vẫn không nên biết:

```text
WeddingGuest
Expense
DebtTransaction
TravelActivity
```

# 9.5 Layer 4 — Product Composition

Đây là nơi domain được phép xuất hiện.

Ví dụ:

```text
WeddingGuestSummary
WeddingGuestRow
WeddingUpcomingMilestone

TravelUpcomingActivity
TravelDaySchedule

DebtBalanceSummary
DebtTransactionRow

FinanceSettlementSummary
```

Product Composition:

* dùng Components/Patterns;
* map domain data → presentation;
* quyết định copy/domain label;
* quyết định capability nào được hiển thị;
* có thể gọi product hooks/service facade qua container layer hiện tại.

Đây là nơi Go Plan “customize product experience”.

# 9.7 Genericization Rule

Một UI abstraction chỉ nên đưa vào core Design System khi đáp ứng ít nhất một trong các điều kiện:

1. xuất hiện ở nhiều domain/màn hình;
2. có behavior/accessibility phức tạp nên cần chuẩn hóa;
3. có visual contract cần consistency mạnh;
4. có khả năng rõ ràng được tái sử dụng ở product khác.

Nếu chỉ xuất hiện một lần và semantic rất đặc thù:

> giữ ở Product Composition.

Không generic hóa “để phòng tương lai”.

---

# 9.8 The “Third Use” Heuristic

Đề xuất sử dụng heuristic:

> **Lần 1: local implementation.
> Lần 2: observe similarity.
> Lần 3: consider extraction.**

Không phải rule tuyệt đối, nhưng giúp tránh premature abstraction.

Exception:

* Button/Input/Dialog/Accessibility primitives rõ ràng nên systemize ngay;
* Pattern có chiến lược thiết kế rõ từ đầu cũng có thể define sớm.

---

# 9.9 Shared Anatomy ≠ Shared Domain

Đây là một decision rất quan trọng.

Ví dụ:

```text
Todo
Guest
Expense
Activity
Debt Transaction
```

đều có thể trông giống “list row”.

Điều đó **không có nghĩa** phải tạo:

```tsx
<UniversalEntityRow entity={anything} />
```

Nên:

```text
DataRow pattern/component
        ↓
TodoRow
GuestRow
ExpenseRow
ActivityRow
```

Tức là:

> **reuse anatomy, preserve semantic ownership.**

---

# 9.10 Composition Over Configuration

Ưu tiên component composition hơn giant prop API.

Không tạo:

```tsx
<Card
  showHeader
  showFooter
  showBadge
  showProgress
  showAvatar
  showMetric
  compact
  wedding
  finance
  statusColor
  ...
/>
```

Ưu tiên:

```tsx
<Card>
  <CardHeader />
  <CardContent />
  <CardFooter />
</Card>
```

hoặc Pattern composition tương ứng.

Lý do:

* API dễ hiểu;
* ít conditional styling;
* dễ customize;
* reuse tốt hơn.

---

# 9.11 Avoid Boolean Prop Explosion

Nếu component có:

```text
isCompact
isHighlighted
isWarning
isSelected
isPremium
isHorizontal
isBorderless
isMuted
```

đó là dấu hiệu architecture cần review.

Ưu tiên semantic variant:

```text
variant="default | subtle | selected"
density="default | compact"
tone="neutral | success | warning | danger"
```

Nhưng variant chỉ nên tồn tại khi có semantic rõ ràng.

---

# 9.12 Variant Architecture

Variant được chia thành các dimension độc lập.

Ví dụ Button:

```text
variant
primary
secondary
ghost
danger

size
sm
md
lg

state
loading
disabled
```

Không:

```text
blueButton
redButton
weddingButton
financeButton
```

Color không phải API nếu semantic variant đã mô tả đủ.

---

# 9.13 Tone vs Variant

Cần phân biệt:

**Variant**

→ structural role.

```text
primary
secondary
ghost
```

**Tone**

→ semantic meaning.

```text
neutral
success
warning
danger
info
```

Ví dụ Alert:

```tsx
<Alert tone="warning" />
```

Button destructive:

```tsx
<Button variant="danger" />
```

Không để mỗi component tự hiểu màu khác nhau.

---

# 9.14 Density as a Shared Contract

Section 6–7 đã chốt:

```text
comfortable
default
compact
```

Component hỗ trợ density khi thực sự có value.

Ví dụ:

```tsx
<DataRow density="compact" />
```

Nhưng không bắt mọi component có cả 3 density.

Dialog chẳng hạn không cần `compact` chỉ để theo convention.

---

# 9.15 Responsive Responsibility

Trách nhiệm responsive được chia như sau.

### Primitive

Không overflow, touch/focus safe.

### Component

Biết cách reflow anatomy của chính nó.

### Pattern

Quyết định composition đổi theo viewport.

### Product Composition

Quyết định content priority theo business context.

Ví dụ:

```text
GuestRow
```

product layer có thể quyết định metadata nào secondary.

Nhưng breakpoint logic cơ bản của `DataRow` không nên copy ở mỗi domain.

---

# 9.16 State Ownership

Cần phân biệt 3 loại state.

### Visual state

Component sở hữu:

```text
hover
focus
pressed
open
```

### UI state

Pattern/container có thể sở hữu:

```text
selected row
expanded item
active tab
dialog open
```

### Business state

Product/domain sở hữu:

```text
todo.status
rsvp
expense.deleted
debt.overdue
```

Design System không biến business state thành internal component state.

---

# 9.17 Controlled vs Uncontrolled

Primitive/Component tương tác nên support chuẩn React phù hợp.

Ví dụ Dialog có thể hỗ trợ controlled API:

```tsx
open
onOpenChange
```

Không để component tự quản state nếu parent cần điều phối business flow.

Nhưng không cần ép mọi primitive thành controlled nếu không có value.

---

# 9.18 Business Logic Boundary

Design System component không được:

* tính settlement;
* resolve permissions;
* tính guest duplicate;
* quyết định Todo overdue theo business rule;
* query Firestore;
* gọi repository;
* mutate domain entity.

Ví dụ:

Sai:

```tsx
<DebtBadge debt={debt} />
```

nếu component tự tính overdue bằng business logic phức tạp.

Tốt hơn product layer resolve:

```tsx
<StatusBadge tone="danger">
  Quá hạn
</StatusBadge>
```

Business semantic được tính ngoài Design System.

---

# 9.19 Permission Boundary

Permission hiện được resolve bằng capability/service và enforce lại bằng Firestore Rules. 

Design System không được biết:

```text
owner
editor
viewer
canEditAllExpenses
```

Core component chỉ biết:

```text
disabled
hidden? → thường do parent quyết định render
```

Product layer quyết định:

```tsx
{canManageGuest && <Button>Thêm khách</Button>}
```

Button không tự resolve permission.

---

# 9.20 Data Formatting Boundary

Một số formatter generic có thể thuộc shared presentation utilities:

* date display;
* currency display;
* number compact;
* relative time.

Nhưng semantic interpretation vẫn thuộc product.

Ví dụ:

```text
41.900.000đ
```

formatting generic.

Nhưng:

```text
Cần thu 41,9 triệu
```

là product semantic.

# 9.21 Slot-Based Architecture

Với Components/Patterns phức tạp, ưu tiên slot/composition.

Ví dụ `PageHeader`:

```text

├── title
├── description
├── metadata
└── actions
```

Không tạo prop riêng cho từng use case.

Điều này giúp Dashboard, Finance, Wedding Guest reuse cùng grammar.

# 9.23 Pattern Anatomy Documentation

Pattern cần document thêm:

* information priority;
* interaction flow;
* when to use;
* when not to use.

# 9.40 Component API Stability

Core components phải được xem như public API nội bộ.

Khi đã migrate nhiều module, breaking change phải được quản lý.

Nguyên tắc:

> **prefer additive change over breaking change.**

Nếu cần breaking architecture change:

* document;
* migrate call sites;
* không để multiple legacy variants kéo dài vô hạn.

# 9.41 Escape Hatch Policy

Design System cần escape hatch, nhưng có kiểm soát.

Cho phép:

```text
className
```

hoặc equivalent styling hook khi cần layout-specific composition.

Nhưng:

> escape hatch không được dùng để override core visual contract thường xuyên.

Nếu 5 màn hình đều override cùng một thứ, system cần thêm official variant/token.

# 9.42 No Forking Rule

# 9.43 Existing Components Migration Strategy

Không rewrite một lần.

Mỗi component hiện có được phân loại:

```text
KEEP
ADAPT
REPLACE
PRODUCT-SPECIFIC
DEPRECATE
```

Ví dụ:

* component anatomy tốt → KEEP/ADAPT;
* component duplicate tokens → ADAPT;
* component business-specific nhưng đang nằm shared → PRODUCT-SPECIFIC;
* component trùng hoàn toàn với new primitive → REPLACE.

Đây là cách giảm regression risk.

# 9.44 Component Review Checklist

Một component chỉ được vào Design System core khi trả lời được:

```text
1. Problem generic là gì?
2. Ai sẽ reuse nó?
3. Nó thuộc Primitive, Component hay Pattern?
4. Domain nào bị leak vào không?
5. State matrix đầy đủ chưa?
6. Accessibility contract?
7. Responsive behavior?
8. Density behavior?
9. Semantic tokens nào dùng?
10. Có thể theme lại mà không sửa component không?
```

Không trả lời được #2 hoặc #4 → khả năng cao component nên ở product layer.

---

# 9.45 Failure Conditions

Component Architecture được xem là FAIL nếu:

1. Core component import Go Plan domain types.
2. Button/Card biết PlanType.
3. Một universal entity component phải chứa nhiều `if` theo domain.
4. Business logic chuyển vào Design System.
5. Permission được resolve bên trong primitive/component.
6. Core API có boolean prop explosion.
7. Mỗi screen override token/style riêng.
8. Product-specific copy bị hard-code trong core.
9. Responsive behavior duplicate ở mọi domain.
10. Component chỉ reuse được trong Go Plan nhưng vẫn bị gọi là generic system component.
11. Tạo duplicate V2 components thay vì migration rõ ràng.
12. Design System thay đổi business workflow để phù hợp component.

# 9.46 Proposed Architecture Decisions

| ID        | Decision         | Proposal                                              |
| --------- | ---------------- | ----------------------------------------------------- |
| **CA-01** | Layers           | Primitive → Component → Pattern → Product Composition |
| **CA-02** | Domain ownership | Product layer only                                    |
| **CA-03** | Reuse strategy   | Shared anatomy, preserve semantics                    |
| **CA-04** | API style        | Composition > configuration                           |
| **CA-05** | Props            | Avoid boolean explosion                               |
| **CA-06** | Permissions      | Resolved outside Design System                        |
| **CA-07** | Business logic   | Never in Design System                                |
| **CA-08** | State ownership  | Visual/UI/business separated                          |
| **CA-09** | Responsive       | Responsibility split by layer                         |
| **CA-10** | Theme            | Tokens change; core behavior stays                    |
| **CA-11** | Extraction       | Evidence-based, avoid premature abstraction           |
| **CA-12** | Migration        | KEEP / ADAPT / REPLACE / PRODUCT-SPECIFIC / DEPRECATE |
| **CA-13** | Escape hatch     | Allowed, monitored                                    |
| **CA-14** | Forks            | No permanent V1/V2 duplication                        |
