# Go Plan — Design System V2 Specification

## 7. Responsive & Density

**Status:** Proposed
**Dependency:** Sections 1–6 — Accepted

---

### 7.1 Responsive Principle

Go Plan không thiết kế theo tư duy:

> Desktop UI → thu nhỏ xuống Mobile.

Mà theo:

> **Same capability → appropriate presentation for each viewport.**

Business capability không được mất chỉ vì đổi viewport, trừ khi requirement của feature explicitly giới hạn platform.

Ví dụ:

```text
Desktop
Guest Detail → Inspector bên phải

Mobile
Guest Detail → Full-page / Bottom Sheet
```

Khác presentation, nhưng cùng capability.

Điều này tiếp tục direction mobile-first đã được PRD/UI-UX xác định từ đầu.  

---

### 7.2 Breakpoint Contract

Giữ compatibility với breakpoint hiện tại:

| Mode        |      Width | Primary intent                   |
| ----------- | ---------: | -------------------------------- |
| **Mobile**  |    0–767px | One-hand / single-column         |
| **Tablet**  | 768–1023px | Expanded mobile / transitional   |
| **Desktop** |    ≥1024px | Multi-column / information-dense |

Không tạo nhiều breakpoint chỉ để fix từng component.

Các breakpoint bổ sung chỉ được thêm khi có **layout behavior rõ ràng**, không vì một card cụ thể bị chật.

---

### 7.3 Breakpoint ≠ Device

Không suy luận:

```text
<768 = phone
>=1024 = mouse
```

Responsive behavior không được dựa vào giả định thiết bị.

Ví dụ desktop vẫn có thể:

* touch;
* zoom;
* keyboard-only;
* small browser window.

Do đó interaction không được phụ thuộc duy nhất vào hover.

---

### 7.4 Mobile Contract

Mobile là first-class experience.

Default:

```text
Single content column
Primary information first
Actions reachable
Minimal horizontal competition
Progressive disclosure
```

Mobile ưu tiên:

* vertical flow;
* stack;
* bottom sheet khi phù hợp;
* compact top-level navigation;
* contextual actions;
* ít side-by-side metrics hơn.

Không:

> desktop table bị scale nhỏ xuống.

---

### 7.5 Tablet Contract

Tablet không nên chỉ là “mobile rộng hơn”.

Nó là transition zone.

Có thể chuyển:

```text
1 column → 2 columns
```

nhưng tránh desktop complexity quá sớm.

Tablet đặc biệt phù hợp:

* metric grid;
* 2-column dashboard;
* content + compact secondary pane;
* horizontal tabs rộng hơn.

Inspector persistent chỉ dùng khi đủ không gian thực sự.

---

### 7.6 Desktop Contract

Desktop được phép tận dụng:

* multiple columns;
* persistent inspector;
* side filters;
* dense lists;
* contextual panels;
* wider comparative views.

Nhưng:

> desktop không được đồng nghĩa với "show everything".

Progressive disclosure vẫn áp dụng.

---

# 7.7 Container System

Không để từng page tự chọn width.

Đề xuất các layout container semantic:

```text
container.reading
container.standard
container.wide
container.full
```

### Reading

Form / settings / explanatory content.

### Standard

Dashboard / overview phổ biến.

### Wide

Planning / guest / finance / statistics.

### Full

Chỉ data-heavy workspace cần tận dụng viewport.

Điều này giúp tránh hiện tượng page A rộng 1200px, page B 1360px, page C full-width mà không có lý do.

---

# 7.8 Responsive Composition

Component nên thay đổi **composition** trước khi thay đổi kích thước chữ.

Ví dụ desktop:

```text
Metric A | Metric B | Metric C | Metric D
```

Mobile:

```text
Metric A | Metric B
Metric C | Metric D
```

hoặc:

```text
Metric A
Metric B
Metric C
Metric D
```

Không giải quyết bằng cách:

> thu font từ 16px xuống 10px để cố giữ 4 cột.

---

# 7.9 Responsive Priority

Khi thiếu không gian:

```text
1. Preserve critical content
2. Reflow layout
3. Collapse secondary information
4. Move optional action into contextual menu
5. Truncate only if acceptable
```

Không bắt đầu bằng:

```text
hide content
```

---

# 7.10 Information Preservation Rule

Responsive transformation không được thay đổi semantic.

Ví dụ Wedding Guest:

```text
Guest count ≠ attendee count
```

Hai metric này vẫn phải giữ distinction dù mobile layout khác. Business model hiện tại xác định rất rõ đây là hai số liệu khác nhau. 

Tương tự:

```text
Expense Paid
Expense Owed
Balance
```

không được gộp thành một con số chỉ vì màn hình nhỏ.

---

# 7.11 Tables

Table chỉ nên dùng khi comparison theo cột thực sự tạo value.

Desktop:

```text
Name | Paid | Owed | Balance
```

có thể phù hợp.

Mobile không mặc định horizontal-scroll table.

Ưu tiên transform:

```text
Name
Paid      ...
Owed      ...
Balance   ...
```

hoặc compact list row.

Horizontal scroll chỉ dùng khi preservation of column alignment thực sự quan trọng.

---

# 7.12 Inspector Pattern

Inspector là desktop pattern quan trọng cho Go Plan.

Use case:

* Todo;
* Milestone;
* Guest;
* transaction detail.

Responsive contract:

```text
Desktop → persistent side inspector
Tablet  → conditional side pane / overlay
Mobile  → page / sheet
```

Inspector không được tạo business flow riêng.

---

# 7.13 Dialog / Drawer / Bottom Sheet

Same intent, different presentation.

Concept:

```text
Simple confirmation
Desktop → Dialog
Mobile  → Bottom Sheet

Complex edit
Desktop → Dialog / Inspector
Mobile  → Full-screen sheet/page
```

Không ép mọi interaction thành modal.

UI/UX hiện tại cũng đã dùng Bottom Sheet cho destructive confirmation trên mobile-oriented flows. 

---

# 7.14 Navigation Responsiveness

Navigation phải preserve:

* module identity;
* active state;
* accessible labels;
* discoverability.

Không được biến navigation thành icon-only chỉ để tiết kiệm diện tích nếu icon không đủ rõ.

Vì navigation hiện được sinh từ module configuration, responsive presentation không được hard-code logic riêng theo Wedding/Travel/Debt. 

---

# 7.15 Density Model

Section 6 đã chốt:

```text
Comfortable
Default
Compact
```

Section 7 định nghĩa rõ semantic.

### Comfortable

Use:

* onboarding;
* authentication;
* empty state;
* Premium;
* short forms.

Characteristics:

```text
More whitespace
Larger vertical rhythm
Lower visible information count
```

### Default

Use:

* dashboard;
* overview;
* normal settings;
* normal cards.

Đây là density mặc định.

### Compact

Use:

* finance list;
* guest list;
* planning timeline;
* import preview;
* statistic tables;
* dense filters.

Characteristics:

```text
Reduced row padding
Reduced gaps
Preserve readable typography
Preserve touch/accessibility target
```

---

# 7.16 Density Is Not Font Scaling

Đây là rule bắt buộc.

`Compact` không được implement bằng:

```text
Body 14 → 11px
Icon 20 → 12px
Button height 44 → 28px
```

Density chủ yếu thay đổi:

* padding;
* gap;
* metadata arrangement;
* redundant labels;
* surface nesting.

Text readability và target size vẫn phải giữ.

---

# 7.17 Responsive Density

Density không map 1:1 với viewport.

Sai:

```text
Mobile = Compact
Desktop = Comfortable
```

Ví dụ:

Wedding Guest mobile vẫn có thể cần compact content.

Empty State desktop vẫn comfortable.

Density theo **task**, viewport chỉ ảnh hưởng composition.

---

# 7.18 Content Reordering

Responsive layout được phép reorder visually nếu semantic reading order vẫn hợp lý.

Rule:

> DOM/logical reading order phải ưu tiên accessibility và task flow.

Không sử dụng CSS order để tạo một UI nhìn đẹp nhưng keyboard/screen-reader đọc sai thứ tự.

---

# 7.19 Sticky UI

Sticky được phép cho:

* primary contextual actions;
* filters;
* navigation;
* inspector header.

Nhưng tránh:

```text
sticky header
+ sticky tabs
+ sticky filter
+ sticky footer
```

làm viewport thực tế quá nhỏ.

Mobile phải đặc biệt cẩn thận.

---

# 7.20 Content Truncation

Tên Plan, Guest, Todo, merchant... có thể dài.

Rule:

* critical identity: ưu tiên wrap;
* secondary metadata: có thể truncate;
* tooltip không được là cách duy nhất để xem nội dung trên touch device.

Không dùng ellipsis cho thông tin financial critical.

---

# 7.21 Responsive Testing Matrix

Mỗi Pattern/major screen phải test ít nhất:

```text
375px
768px
1024px
1440px
```

và thêm:

```text
Zoom 200%
Long Vietnamese text
Large numbers
Empty data
Dense data
```

Pilot screens:

* Dashboard;
* Wedding Overview;
* Wedding Guest.

---

# 7.22 Responsive Failure Conditions

Responsive được xem là FAIL nếu:

* horizontal overflow không chủ đích;
* action quan trọng biến mất;
* data semantic bị mất;
* font bị giảm dưới readability contract;
* desktop-only hover là cách duy nhất thao tác;
* mobile phải zoom để đọc;
* component cần custom breakpoint riêng chỉ để chữa layout;
* cùng một capability có behavior business khác nhau giữa viewport.

---

| ID        | Decision            | Proposal                                      |

| **RD-01** | Strategy            | Mobile-first                                  |

# 8. Accessibility

## 8.1 Accessibility Principle

Accessibility là một phần của correctness.

Không xem là:

> “support thêm cho một nhóm user”.

Một UI không keyboard-accessible, contrast kém hoặc state chỉ truyền qua màu là một UI chưa hoàn chỉnh.

UI/UX hiện tại đã đặt baseline gồm touch target ≥44px, text ≥14px và WCAG AA. V2 giữ tinh thần đó nhưng cần formalize sâu hơn. 

---

# 8.2 Accessibility Target

Design System V2 target:

> **WCAG 2.2 AA** cho các user flow chính.

Không đặt AAA làm mandatory toàn hệ thống vì có thể tạo constraint không cần thiết.

AA là production baseline.

---

# 8.3 Keyboard Accessibility

Mọi interaction desktop/web phải sử dụng được bằng keyboard khi interaction tương ứng có ý nghĩa.

Bao gồm:

* navigation;
* tabs;
* buttons;
* menus;
* forms;
* dialog;
* accordion;
* selectable rows;
* inspector controls.

Tab order phải predictable.

Không tạo clickable `div` không semantics khi có element native phù hợp.

---

# 8.4 Focus Visibility

Focus phải visible.

Foundation đã cấm:

```css
outline: none;
```

nếu không có replacement.

Focus state phải:

* đủ contrast;
* không chỉ đổi màu rất nhẹ;
* không bị overflow:hidden cắt mất;
* nhất quán giữa components.

---

# 8.5 Focus Management

Overlay interaction phải quản lý focus đúng.

### Dialog

Khi mở:

```text
focus → dialog
```

Trong dialog:

```text
focus trapped
```

Khi đóng:

```text
focus → trigger cũ
```

### Destructive confirmation

Focus mặc định không nên tự rơi vào destructive CTA nếu có nguy cơ accidental confirmation.

---

# 8.6 Touch Target

Baseline:

> **Minimum target 44 × 44px cho primary touch interaction.**

Tài liệu hiện tại cũng đã dùng chính rule này cho nút tạo Plan. 

Icon có thể 16–20px, nhưng clickable area vẫn 44px.

Không đồng nhất:

```text
icon size = hit area
```

---

# 8.7 Text Size

Baseline V2:

* body primary: khoảng 14px trở lên;
* metadata có thể 12px nếu contrast/readability tốt;
* critical content không xuống 12px chỉ để fit.

Điểm này refine requirement cũ “Text ≥14px”: V2 cho phép metadata nhỏ hơn khi không phải content chính, nhưng **không được dùng small text để giải quyết density**.

---

# 8.8 Contrast

Minimum target:

* normal text: WCAG AA;
* large text: WCAG AA;
* interactive controls/state boundaries phải đủ phân biệt;
* focus indicator phải đủ visible.

Không chọn token chỉ vì đẹp trên Figma/screenshot.

Token validation phải test trên actual background pair.

---

# 8.9 Color Is Not the Only Signal

Không truyền trạng thái chỉ bằng màu.

Sai:

```text
red amount = overdue
green amount = paid
```

Đúng hơn:

```text
Quá hạn · 1.200.000đ
```

với color hỗ trợ.

Điều này đặc biệt quan trọng trong Finance/Debt, nơi Section 6 cũng đã chốt semantic color không được lẫn với raw financial value.

---

# 8.10 Status Semantics

Status nên kết hợp:

```text
Label
+
Color
+
optional Icon
```

Ví dụ:

```text
● Quá hạn
✓ Hoàn thành
! Cần chú ý
```

Không bắt buộc cả ba mọi nơi, nhưng label không được biến mất ở critical state.

---

# 8.11 Forms

Form field phải có label semantic.

Placeholder không thay label.

Error phải:

* liên kết với field;
* mô tả cụ thể;
* không chỉ đổi border đỏ.

Ví dụ tốt:

```text
Số tiền phải lớn hơn 0.
```

không chỉ:

```text
Không hợp lệ
```

---

# 8.12 Required / Optional

Không làm user đoán field nào bắt buộc.

Nếu form chủ yếu optional, có thể label:

```text
Ghi chú — Không bắt buộc
```

Nếu phần lớn bắt buộc, required state phải được định nghĩa nhất quán.

---

# 8.13 Error Recovery

Accessibility không chỉ là screen reader.

Error UX phải giúp recovery.

Ví dụ upload lỗi:

* nói file nào lỗi;
* lý do;
* action tiếp theo.

Không để toast biến mất rồi user không biết record đã được lưu chưa.

SDD hiện xác định error từ Repository → Service mapping → UI feedback; Design System chỉ chịu trách nhiệm presentation rõ ràng, không thay error semantics/business. 

---

# 8.14 Loading

Loading phải preserve layout khi có thể.

Ưu tiên:

> skeleton / local loading state

thay vì spinner toàn màn hình.

UI/UX hiện tại cũng đã chốt Skeleton và không dùng full-screen spinner. 

Loading button phải:

* disable duplicate submit;
* giữ label/context;
* cho biết operation đang chạy.

---

# 8.15 Success Feedback

Success feedback phải tương xứng với action.

Ví dụ:

```text
Save preference
→ subtle feedback

Create Expense
→ toast / state update

Delete Guest
→ clear confirmation
```

Không animation celebration cho mọi save.

---

# 8.16 Destructive Actions

Destructive action phải:

* visually distinct;
* explicit label;
* confirmation khi hậu quả đáng kể;
* không đặt cạnh safe action mà dễ bấm nhầm.

Current business đã có Bottom Sheet confirm cho hard delete Member và giữ Deactivate khi có lịch sử liên quan. UI V2 phải preserve semantic distinction đó. 

---

# 8.17 Screen Reader Semantics

Use native semantics trước ARIA custom.

Examples:

```text
button → <button>
navigation → <nav>
form label → <label>
heading → h1/h2/h3 hierarchy
```

ARIA được bổ sung khi native semantics chưa đủ.

Không dùng ARIA để vá incorrect HTML structure.

---

# 8.18 Heading Hierarchy

Visual size không được quyết định heading semantic.

Ví dụ:

```text
Page Title → h1
Main Section → h2
Subsection → h3
```

dù Section title visually chỉ 18px.

Điều này rất phù hợp với V2 vì typography role và semantic HTML được tách riêng.

---

# 8.19 Icon-only Action

Icon-only action chỉ phù hợp khi meaning phổ biến hoặc context rất rõ.

Ví dụ:

* close;
* search;
* more menu.

Actions như:

* settlement;
* transfer ownership;
* sync guest;

không nên icon-only.

Icon-only button phải có accessible name.

---

# 8.20 Tooltips

Tooltip dùng để bổ sung, không được chứa critical information duy nhất.

Đặc biệt không dựa vào tooltip cho mobile.

---

# 8.21 Motion Accessibility

Respect:

```text
prefers-reduced-motion
```

Khi reduced motion:

* loại bỏ decorative transitions;
* giữ state transition clarity;
* không để interaction phụ thuộc animation.

Không dùng flashing/strobing effects.

---

# 8.22 Zoom & Text Reflow

User phải có thể zoom trình duyệt đến 200% mà core flow vẫn usable.

Expected:

* text reflow;
* controls không overlap;
* critical action accessible;
* không horizontal scroll toàn page nếu không cần thiết.

Data table có thể có local scroll nếu semantic yêu cầu.

---

# 8.23 Financial Readability

Finance/Debt cần accessibility riêng.

Require:

* dấu âm/dương rõ;
* unit rõ;
* không dựa hoàn toàn màu;
* alignment hợp lý;
* không truncate critical amount;
* paid/owed/receive/pay labels explicit.

Ví dụ:

```text
+1.250.000đ
Được nhận
```

tốt hơn chỉ một con số xanh.

---

# 8.24 Permissions and Accessibility

Disabled/hidden action không được làm sai security model.

Permission hiện được enforce ở Service + Firestore Rules, UI chỉ phản ánh capability. 

Accessibility không thay đổi rule đó.

Ví dụ viewer không có permission:

* có thể không render action;
* hoặc render disabled khi UX cần giải thích;

nhưng không được dựa vào disabled UI làm authorization.

---

# 8.25 Accessible Empty State

Empty State phải nói:

1. trạng thái là gì;
2. user có thể làm gì;
3. CTA nếu được phép.

Nếu user không có permission tạo:

không hiển thị CTA giả.

Ví dụ Viewer:

```text
Chưa có khoản chi nào.
```

khác Owner:

```text
Chưa có khoản chi nào.
[Thêm khoản chi]
```

---

# 8.26 Accessibility State Matrix

Mỗi interactive component phải review:

```text
Keyboard
Focus
Screen reader label
Touch target
Contrast
Disabled
Loading
Error
Reduced motion
Zoom
```

Không chỉ design:

```text
Default / Hover
```

---

# 8.27 Accessibility Testing

Minimum manual test:

```text
Keyboard-only navigation
200% browser zoom
Reduced motion
Light mode contrast
Long Vietnamese content
Mobile touch
```

Automated test nên cover:

* missing accessible names;
* invalid ARIA;
* common contrast/semantic issues khi tooling hỗ trợ.

Automated test không thay manual QA.

---

# 8.28 Accessibility Failure Conditions

Component/pattern FAIL nếu:

* action không keyboard reachable;
* focus invisible;
* state chỉ bằng color;
* touch target quan trọng <44px;
* placeholder đóng vai label;
* error không giải thích;
* modal mất focus;
* text critical bị truncate;
* zoom 200% phá core flow;
* hover-only action;
* permission action gây hiểu nhầm;
* reduced-motion preference bị bỏ qua.
