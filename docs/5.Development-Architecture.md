# 2. Nguyên tắc kiến trúc

Ứng dụng sử dụng kiến trúc:

```text
UI
↓
Feature Hook
↓
Service
↓
Repository
↓
Firebase Adapter
↓
Firebase SDK
```

Các nguyên tắc bắt buộc:

1. Component không gọi Firebase trực tiếp.
2. Component không chứa business logic.
3. Hook không tự xử lý nghiệp vụ phức tạp.
4. Service chịu trách nhiệm xử lý business logic.
5. Repository chỉ truy cập dữ liệu.
6. Firebase SDK chỉ được sử dụng trong Firebase Adapter hoặc Repository implementation.
7. Domain type không phụ thuộc trực tiếp vào Firestore SDK nếu không cần thiết.
8. Mỗi module tự quản lý code thuộc phạm vi nghiệp vụ của mình.
9. Shared code chỉ dùng cho phần thực sự dùng chung.
10. Không tạo abstraction khi chưa có nhu cầu thực tế.

# 6. Dependency Rule

Dependency hợp lệ:

```text
app
→ modules
→ shared
→ config
```

Bên trong module:

```text
component
→ hook
→ service
→ repository interface
→ repository implementation
→ Firebase adapter
```

Dependency không hợp lệ:

```text
repository
→ component
```

```text
service
→ page
```

```text
shared
→ module cụ thể
```

```text
expense module
→ internal file của settlement module
```

Khi một module cần sử dụng chức năng module khác, chỉ import từ public API của module đó.

Ví dụ:

```ts
import { calculateSettlementSuggestions } from "@/modules/settlement";
```

Không import sâu:

```ts
import { calculateSettlementSuggestions } from "@/modules/settlement/services/internal/settlement-calculator";
```

# 8. TypeScript Guideline

## 8.1 Strict mode

Bắt buộc bật:

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "exactOptionalPropertyTypes": true
  }
}
```

Nếu một option gây khó khăn quá lớn trong giai đoạn đầu, có thể tạm thời loại bỏ nhưng phải được ghi chú rõ.

---

## 8.2 Không sử dụng any

Không sử dụng:

```ts
const data: any = snapshot.data();
```

Sử dụng:

```ts
const data = snapshot.data() as ExpenseDocument;
```

Tốt hơn nữa là parse qua mapper hoặc Zod:

```ts
const expense = expenseDocumentSchema.parse(snapshot.data());
```

Nếu bắt buộc nhận dữ liệu chưa biết:

```ts
unknown;
```

Ví dụ:

```ts
function parseError(error: unknown): AppError {
  // Parse safely
}
```

---

## 8.3 Type và Interface

Sử dụng `type` cho phần lớn model và union:

```ts
type PlanStatus = "active" | "closed" | "archived";
```

```ts
type Plan = {
  id: string;
  name: string;
};
```

Sử dụng `interface` khi cần:

- Declaration merging.
- Implement bởi class.
- Public contract có khả năng mở rộng.

Ví dụ Repository:

```ts
interface ExpenseRepository {
  create(input: ExpenseDocument): Promise<void>;
}
```

---

## 8.4 Không dùng enum TypeScript nếu không cần

Không khuyến nghị:

```ts
enum PlanStatus {
  Active = "active",
  Closed = "closed",
}
```

Khuyến nghị:

```ts
export const PLAN_STATUS = {
  ACTIVE: "active",
  CLOSED: "closed",
  ARCHIVED: "archived",
} as const;

export type PlanStatus = (typeof PLAN_STATUS)[keyof typeof PLAN_STATUS];
```

Cách này nhẹ hơn, dễ serialize và phù hợp dữ liệu Firestore.

---

## 8.5 Nullable và Optional

Phân biệt:

```ts
note?: string
```

và:

```ts
note: string | null;
```

Quy ước:

- Form input có thể dùng optional.
- Firestore document dùng field cố định với `null`.
- Domain model nên nhất quán với DMS.

Ví dụ input:

```ts
type CreateExpenseInput = {
  note?: string;
};
```

Document:

```ts
type ExpenseDocument = {
  note: string | null;
};
```

---

## 8.6 Không dùng magic string

Không viết:

```ts
if (plan.status === "closed") {
}
```

Nên dùng constant:

```ts
if (plan.status === PLAN_STATUS.CLOSED) {
}
```

Đặc biệt với:

- Role.
- Status.
- Split method.
- Storage folder.
- Error code.
- Route path.

# 10. React Component Guideline

## 10.1 Component chỉ tập trung vào UI

Không làm:

```tsx
function ExpenseForm() {
  const db = getFirestore()

  async function handleSubmit() {
    await addDoc(collection(db, "expenses"), ...)
  }
}
```

Nên làm:

```tsx
function ExpenseForm() {
  const { createExpense, isSubmitting } = useCreateExpense();

  async function handleSubmit(values: ExpenseFormValues) {
    await createExpense(values);
  }
}
```

---

## 10.2 Phân loại component

### Page Component

Nằm trong `app/`.

Trách nhiệm:

- Nhận route params.
- Compose feature components.
- Xử lý route-level loading/error.
- Không chứa business logic.

### Feature Component

Nằm trong `modules/{feature}/components`.

Ví dụ:

- `ExpenseForm`.
- `SettlementSuggestionList`.
- `MemberList`.

### Shared Component

Nằm trong `shared/components`.

Ví dụ:

- Button.
- Input.
- Avatar.
- BottomSheet.
- EmptyState.

Không đưa feature-specific component vào `shared`.

---

## 10.3 Component size

Không áp dụng giới hạn cứng theo số dòng.

Khi component có nhiều trách nhiệm, nên tách.

Dấu hiệu cần tách:

- Có nhiều phần UI độc lập.
- Có nhiều state không liên quan.
- Có nhiều điều kiện render phức tạp.
- Có thể tái sử dụng.
- Khó test.

---

## 10.4 Props

Props phải có type rõ ràng:

```ts
type ExpenseCardProps = {
  expense: Expense;
  paidByName: string;
  onClick?: () => void;
};
```

Không truyền object quá lớn nếu component chỉ cần vài field.

Không truyền toàn bộ store vào component.

---

## 10.5 Event naming

Props callback dùng tiền tố `on`:

```ts
onSave;
onDelete;
onMemberSelect;
```

Handler nội bộ dùng tiền tố `handle`:

```ts
handleSave;
handleDelete;
handleMemberSelect;
```

---

## 10.6 Client Component

Chỉ thêm:

```ts
"use client";
```

khi component cần:

- React state.
- Event handler.
- Browser API.
- Zustand.
- Firebase client SDK.
- Firestore realtime listener.

Không biến toàn bộ layout thành Client Component chỉ vì một component con cần state.

# 12. Hook Guideline

## 12.1 Hook không chứa business logic phức tạp

Hook chịu trách nhiệm:

- Connect UI với service.
- Quản lý loading/error.
- Subscribe/unsubscribe realtime.
- Chuyển response thành state cho component.

Business logic như split, settlement, permission phải nằm trong service hoặc pure function.

---

## 12.2 Query hook

Ví dụ:

```ts
function useExpenses(planId: string) {
  // Subscribe realtime
  // Return data/loading/error
}
```

Return shape thống nhất:

```ts
type UseExpensesResult = {
  data: Expense[];
  isLoading: boolean;
  error: AppError | null;
};
```

---

## 12.3 Mutation hook

Ví dụ:

```ts
function useCreateExpense() {
  return {
    createExpense,
    isSubmitting,
    error,
  };
}
```

Không đặt tên mutation là `submit`.

Sử dụng tên nghiệp vụ cụ thể:

```ts
createExpense;
updateExpense;
removeMember;
confirmSettlement;
```

---

## 12.4 Cleanup realtime listener

Mọi hook realtime bắt buộc unsubscribe:

```ts
useEffect(() => {
  const unsubscribe = expenseService.watchExpenses(...)

  return unsubscribe
}, [planId])
```

Không tạo listener mới ở mỗi render.

# 13. Service Guideline

# 14. Repository Guideline

Repository là abstraction cho data access.

Repository interface:

```ts
interface ExpenseRepository {
  findById(planId: string, expenseId: string): Promise<Expense | null>;

  watchByPlan(
    planId: string,
    options: WatchExpensesOptions,
    onChange: (expenses: Expense[]) => void,
    onError: (error: unknown) => void,
  ): Unsubscribe;

  create(planId: string, expense: ExpenseDocument): Promise<void>;

  update(
    planId: string,
    expenseId: string,
    updates: ExpenseUpdateDocument,
  ): Promise<void>;
}
```

---

## 14.1 Repository chỉ truy cập dữ liệu

Repository được phép:

- Query Firestore.
- Convert snapshot.
- Create/update document.
- Run transaction.
- Run batch.
- Subscribe listener.
- Upload/delete Storage file.

Repository không được:

- Tính equal split.
- Tính member balance.
- Đề xuất settlement.
- Quyết định editor có được sửa hay không.
- Hiển thị toast.
- Điều hướng trang.

---

## 14.2 Repository interface và implementation

Interface:

```text
expense.repository.ts
```

Implementation:

```text
firestore-expense.repository.ts
```

Điều này giúp:

- Mock dễ hơn khi test.
- Có thể thay data source.
- Giảm Firebase coupling.

---

## 14.3 Mapper

Không để Firestore Timestamp lan truyền khắp UI nếu không cần.

Ví dụ mapper:

```ts
function mapExpenseDocument(id: string, data: ExpenseDocument): Expense {
  return {
    ...data,
    id,
    spentAt: data.spentAt.toDate(),
    createdAt: data.createdAt.toDate(),
    updatedAt: data.updatedAt.toDate(),
  };
}
```

Phân biệt:

- `ExpenseDocument`: dạng lưu Firestore.
- `Expense`: domain model dùng trong app.

# 17. Firestore Guideline

## 17.1 Timestamp

Tạo record:

```ts
createdAt: serverTimestamp();
updatedAt: serverTimestamp();
```

Khi UI cần optimistic data, có thể dùng client date tạm thời nhưng dữ liệu Firestore chính thức phải dùng server timestamp.

---

## 17.2 Transaction

Dùng transaction khi cần:

- Đọc dữ liệu hiện tại.
- Validate version.
- Cập nhật aggregate dựa vào giá trị cũ.
- Transfer ownership.
- Update expense amount và plan total.

Ví dụ:

```text
Update Expense
Read old expense
Validate version
Update expense
Update totalExpense
```

---

## 17.3 Batched Write

Dùng batch khi:

- Không cần đọc dữ liệu trước.
- Tạo plan cùng owner member.
- Tạo default category.
- Tạo userPlan index.
- Add guest và tăng memberCount.

---

## 17.4 Không lưu undefined

Firestore không chấp nhận `undefined` theo mặc định.

Trước khi write, input phải được normalize:

```ts
{
  note: input.note?.trim() || null;
}
```

---

## 17.5 Realtime Query

Realtime query phải:

- Có limit.
- Có order.
- Có cleanup.
- Không subscribe nhiều lần cùng dữ liệu.
- Không load toàn bộ lịch sử nếu chưa cần.

Timeline mặc định:

```ts
where("status", "==", "active");
```

6. Test trên Firebase Emulator hoặc staging.
7. Không sửa dữ liệu production trực tiếp bằng tay nếu có thể tránh.

Script migration không chạy tự động trong browser của user.

MVP chưa có Backend nên migration có thể là script Node.js riêng sử dụng Firebase Admin SDK, chỉ chạy bởi developer.

# 50. Security Guideline

- Không tin dữ liệu client.
- Không dựa vào việc ẩn button.
- Mọi write phải được Security Rules bảo vệ.
- Không cho client tự đặt owner.
- Không cho client tự sửa `createdByUserId`.
- Không lưu invitation token plain text.
- Không expose service account.
- Không lưu dữ liệu nhạy cảm vào log.
- Validate MIME type và size file.
- Storage Rules phải kiểm tra plan membership.
- Sử dụng Firebase App Check sau khi MVP ổn định.

---

# 51. Offline Guideline

Firestore offline được phép xử lý cache và pending write.

UI cần thể hiện:

- Đang lưu.
- Đã lưu local.
- Đang chờ đồng bộ.
- Đồng bộ lỗi.

Không tự xây queue trong MVP.

Các thao tác có nhiều bước như upload ảnh cần online.

Nếu offline:

- Có thể cho tạo draft local phase sau.
- MVP nên báo cần kết nối mạng khi upload attachment.

Expense không có attachment có thể tận dụng Firestore offline write nếu flow hỗ trợ ổn định.

# 55. Anti-pattern cần tránh

## Component gọi Firestore trực tiếp

Không làm.

## Business logic trong hook hoặc component

Không làm.

## Repository chứa logic chia tiền

Không làm.

## Copy server state sang nhiều store

Không làm.

## Một file service vài nghìn dòng

Cần tách theo use case hoặc domain helper.

## Shared folder chứa mọi thứ

Chỉ đưa code thực sự dùng chung vào shared.

## Import sâu vào internal module

Chỉ import qua public module API.

## Lưu float cho tiền

Không làm.

## Không cleanup realtime listener

Không làm.

## Dùng userId thay cho memberId trong expense

Không làm.

## Hard delete dữ liệu lịch sử

Không làm trong MVP.

## Chỉ kiểm tra permission trên UI

Không làm.

## Update nhiều document mà không dùng transaction hoặc batch

Không làm khi yêu cầu tính nhất quán.

# 57. Kết luận

Codebase phải tuân theo nguyên tắc trung tâm:

```text
UI không biết Firebase hoạt động như thế nào.

Repository không biết nghiệp vụ chia tiền hoạt động như thế nào.

Service không biết UI hiển thị như thế nào.

Domain function không phụ thuộc Firebase, React hoặc Next.js.
```

Việc phân tách này giúp:

- Business logic dễ test.
- UI dễ thay đổi.
- Firebase dễ thay thế.
- Dữ liệu dễ kiểm soát.
- Quyền hạn dễ audit.
- Codebase ít bị phụ thuộc framework.
- Dự án có thể mở rộng mà không cần viết lại từ đầu.

Đối với MVP, ưu tiên triển khai kiến trúc đủ rõ nhưng không quá trừu tượng. Chỉ tạo interface, service hoặc abstraction khi nó giúp tách business logic, tăng khả năng test hoặc giảm phụ thuộc Firebase.
