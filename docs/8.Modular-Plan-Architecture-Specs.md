Đúng. Ở thời điểm này tôi sẽ **tạm dừng việc mở rộng thêm PlanType** và coi đây là một **Architecture Gate**. Nếu nền `Plan Core + Module Registry + PlanType Configuration` không đứng vững với Wedding → Travel → Debt thì càng thêm feature càng khó sửa.

Tài liệu implement tôi đề xuất như sau.

# Go Plan — Modular Plan Architecture Specification

**Version:** 1.0
**Status:** Proposed Architecture Gate
**Scope:** Plan Core · Module Registry · PlanType Configuration · Overview Composition · Wedding / Travel / Debt validation

---

# 1. Mục tiêu

Go Plan cần hỗ trợ nhiều loại kế hoạch có nghiệp vụ khác nhau mà không phải xây dựng một ứng dụng riêng cho từng `PlanType`.

Kiến trúc phải đảm bảo:

* Các Plan chia sẻ một `Plan Core`.
* Chức năng phổ biến được đóng gói thành `Core Module`.
* Nghiệp vụ đặc thù được đóng gói thành `Extension Module`.
* `PlanType` quyết định cấu hình mặc định của Plan, không quyết định kiến trúc dữ liệu của toàn ứng dụng.
* Navigation được sinh từ cấu hình module.
* Overview được compose từ các widget.
* Module có thể được thêm mới mà hạn chế sửa code của module hiện có.
* Không generic hóa cưỡng ép những domain thực sự khác nhau.
* Existing Wedding Plan phải tiếp tục hoạt động sau migration.

Ba testcase kiến trúc bắt buộc:

1. **Wedding** — Plan phức tạp, sử dụng nhiều Core Module + Wedding extension.
2. **Travel** — chủ yếu sử dụng Core Module.
3. **Debt** — Plan khác biệt đáng kể, cần domain extension riêng.

Nếu kiến trúc không xử lý tốt cả ba testcase thì chưa được xem là hoàn thành.

# 4. Plan Core

`Plan` là entity gốc duy nhất.

Không tạo:

```text
WeddingPlan
TravelPlan
DebtPlan
```

Thay vào đó:

```ts
interface Plan {
  id: string;

  name: string;
  description?: string;

  type: PlanType;

  ownerId: string;

  startDate?: Timestamp;
  endDate?: Timestamp;

  status: PlanStatus;

  createdAt: Timestamp;
  updatedAt: Timestamp;
}
```

Ví dụ:

```json
{
  "id": "plan_001",
  "name": "Huế Gét Go",
  "type": "travel",
  "ownerId": "user_001",
  "status": "active"
}
```

`type` chủ yếu dùng để resolve configuration.

Không dùng `type` để hard-code toàn bộ UI.

# 9. Module ID

Module ID phải ổn định.

```ts
type PlanModuleId =
  | 'overview'
  | 'planning'
  | 'finance'
  | 'members'
  | 'weddingGuests'
  | 'debtTracking';
```

Module ID:

* Không phụ thuộc UI label.
* Không phụ thuộc PlanType.
* Được sử dụng trong registry/configuration.

# 11. Module Registry

Concept:


# 17. Dynamic Navigation

Plan navigation phải được generate.

Concept:

```ts
function getPlanNavigation(plan: Plan) {
  const config = getPlanTypeConfig(plan.type);

  return config.modules
    .filter(module => module.enabled)
    .sort((a, b) => a.order - b.order)
    .map(resolveNavigationItem);
}
```

Không maintain navigation riêng cho từng Plan page.

# 28. Cross-module Reference

Module có thể tham chiếu module khác nhưng phải loose coupling.

Ví dụ:

```text
Expense
   ↓
milestoneId?
```

được phép.

Nhưng Finance Module không được assume:

```text
mọi Expense bắt buộc có Milestone
```

Bởi Debt hoặc Personal Plan có thể sử dụng Finance mà không có Planning.

Do đó:

```ts
milestoneId?: string;
```

phải optional.

---

# 29. Critical Rule — Optional Module Dependency

Nếu module A không enabled:

```text
Planning = disabled
```

Finance vẫn phải hoạt động.

Không được crash vì:

```text
expense.milestoneId === undefined
```

Đây là testcase bắt buộc.

# 30. Module Dependencies

Nếu một module thực sự cần module khác, dependency phải khai báo rõ.

```ts
  optionalDependencies?: PlanModuleId[];
```

# 38. Failure Conditions

Architecture được xem là **FAIL** nếu xảy ra một trong các trường hợp:

### 1.

Thêm PlanType mới bắt buộc phải sửa nhiều `if/else` trong PlanDetail.

### 2.

Travel phải duplicate Wedding components chỉ để bỏ Wedding-specific features.

### 3.

Finance crash khi không có Planning.

### 4.

Overview phải copy thành:

```text
WeddingOverview
TravelOverview
DebtOverview
```

chỉ để thay đổi vài section.

### 5.

Plan entity chứa field của mọi extension.

### 6.

WeddingGuest bị generic hóa đến mức domain Wedding khó hiểu.

### 7.

Debt phải giả làm Expense/Income để hệ thống hoạt động.

### 8.

Thêm module mới buộc phải sửa generic navigation.

### 9.

Existing Wedding data không backward compatible.

### 10.

Module không thể test độc lập.

Chỉ cần một failure nghiêm trọng xuất hiện → dừng thêm PlanType và review architecture.

# 41. Architecture Gate

Sau Phase 9 phải tổ chức một architecture review với đúng ba câu hỏi:

### Gate 1 — Reusability

Travel có reuse được Wedding Core mà không copy domain/component không?

### Gate 2 — Extensibility

Debt có thêm được một domain hoàn toàn mới mà không phá Plan Core không?

### Gate 3 — Isolation

Wedding-specific logic có được cô lập khỏi Travel và Debt không?

Nếu cả ba đều:

```text
PASS
```

thì:

> **Modular Plan Architecture V1 được ACCEPTED.**

Khi đó mới bắt đầu thêm:

```text
Saving

```

# 43. Quyết định kiến trúc V1

Go Plan sẽ không phát triển theo mô hình:

> `PlanType → một bộ feature/page/entity riêng`.

Go Plan phát triển theo mô hình:

> **Plan Core → Modules → PlanType Configuration → Customized Experience.**

`Wedding` là reference implementation.

`Travel` là reuse validation.

`Debt` là extensibility validation.

Chỉ sau khi cả ba testcase vượt qua Architecture Gate mới tiếp tục mở rộng hệ sinh thái PlanType.

Tôi đánh giá tài liệu này nên đứng **trên DMS và UI/UX Specification hiện tại**, vì nó quyết định cách các tài liệu đó được chia module về sau.

Điểm tôi muốn đặc biệt giữ kỷ luật khi triển khai là **không làm Debt đầy đủ ngay**. Debt ở giai đoạn đầu chỉ là một *architecture probe*: đủ `Debt + Repayment + Remaining` để cố tình tạo ra một domain rất khác Wedding. Nếu nó cắm được vào Plan mà không phải sửa nát `PlanDetail`, `Finance`, `Overview` thì kiến trúc mới thực sự vượt qua bài kiểm tra.

Sau tài liệu này, tài liệu implement tiếp theo nên là **Module Contract & Folder Architecture Specification**: chốt interface TypeScript, registry thực tế, cấu trúc `/modules/planning`, `/modules/finance`, `/extensions/wedding-guests`, dependency direction, Firestore repositories và cách module đăng ký route/widget/navigation. Đó mới là tài liệu developer có thể bắt đầu refactor code theo từng phase mà không tự diễn giải architecture.
