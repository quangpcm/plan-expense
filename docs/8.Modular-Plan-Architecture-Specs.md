# Go Plan — Modular Plan Architecture Specification

**Version:** 1.1
**Status:** Proposed — Architecture Gate
**Scope:** Plan Core · Module Registry · PlanType Configuration · Dynamic Navigation · Overview Composition · Cross-module Integration
**Architecture validation:** Wedding → Travel → Debt

---

# 1. Mục tiêu

Go Plan cần hỗ trợ nhiều loại kế hoạch có nghiệp vụ khác nhau trong cùng một ứng dụng mà không phải xây dựng một hệ thống riêng cho từng `PlanType`.

Kiến trúc phải đảm bảo:

- Tất cả Plan chia sẻ một `Plan Core`.
- Chức năng phổ biến được đóng gói thành `Core Module`.
- Nghiệp vụ đặc thù được đóng gói thành `Extension Module`.
- `PlanType` đóng vai trò **preset/configuration**, không phải một domain model độc lập.
- Navigation được sinh từ cấu hình module.
- Overview được compose từ các widget.
- Module có thể được bật/tắt mà không phá module khác.
- Cross-module relationship phải có semantic rõ ràng.
- Không generic hóa cưỡng ép các domain thực sự khác nhau.
- Existing Wedding Plan phải tiếp tục hoạt động sau refactor.
- Việc thêm PlanType/Module mới không được yêu cầu sửa lại `PlanDetail` core.

Ba testcase kiến trúc bắt buộc:

```text
Wedding
→ Complex vertical + backward compatibility

Travel
→ Core reuse + extension + weak cross-module relationship

Debt
→ New domain + Finance integration
```

Nếu kiến trúc không xử lý tốt cả ba testcase thì chưa được xem là hoàn thành.

# 5. Plan Core

Không tạo:

```text

```

Sử dụng:

```ts
interface Plan {
  id: string;

  name: string;

  type: PlanType;

  ownerId: string;

  startDate?: Timestamp;
  endDate?: Timestamp;

  status: PlanStatus;
```

Ví dụ:


# 9. Core Modules

Core Module là capability có khả năng tái sử dụng ở nhiều PlanType.

V1.1:

```text
overview
planning
finance
members
```

## Planning

```text
Planning
│
├── Milestone
│
└── Todo
```

Semantic:

> Milestone tổ chức các mốc/giai đoạn của kế hoạch.

> Todo tổ chức công việc cần hoàn thành.

V1.1 Transitional Rule:

> `Milestone` hiện vẫn là technical anchor cho compatibility của Finance/Statistic/aggregate.

> Nếu Plan bật `planning` module, milestone hoạt động và hiển thị theo logic bình thường.

> Nếu Plan không bật `planning` module nhưng Finance vẫn cần tham chiếu milestone, hệ thống tự tạo đúng 1 `hidden default milestone` để dùng nội bộ.

## Finance

```text
Finance
│
├── Expense
├── Income
└── Settlement
```

## Members

```text
Members
│
├── PlanMember
├── PlanInvite
├── Guest Member
└── Permissions
```

## Hidden Default Milestone

V1.1 bổ sung một khái niệm kỹ thuật:

```text
hidden default milestone
```

Mục đích:

- giữ `milestone` làm compatibility anchor cho Finance
- không phá schema/service/statistic/aggregate/rules/tests hiện tại
- không bắt user của plan không có `planning` phải nhìn thấy milestone UI

Contract:

- mỗi milestone có thêm flag `isSystemHidden: boolean`
- `isSystemHidden = true` nghĩa là milestone được app tạo mặc định để dùng nội bộ
- mỗi plan không bật `planning` nhưng bật `finance` chỉ có đúng 1 hidden default milestone
- milestone này không được edit
- không được delete
- không được reorder
- không được hiển thị trong milestone list/search/dropdown cho user
- form tạo expense/income phải auto-fill milestone này ngầm trong code

# 15. Capability over PlanType Checks

Generic components nên hỏi:

```ts
hasModule(plan, 'finance');
```

không hỏi:

```ts
plan.type === 'wedding' || plan.type === 'travel';
```

Tương tự:

```ts
hasModule(plan, 'travelItinerary');
```

thay vì:

```ts
plan.type === 'travel';
```

PlanType-specific checks chỉ được phép nằm ở nơi resolve preset/configuration hoặc business logic thực sự thuộc PlanType.

# 20. Dynamic Navigation

Navigation phải được generate từ config.

```ts
function getPlanNavigation(plan: Plan) {
  const config = getPlanTypeConfig(plan.type);

  return config.modules
    .filter((module) => module.enabled)
    .sort((a, b) => a.order - b.order)
    .map(resolveNavigationItem);
}
```

Khi thêm:

```text
savingGoal
```

generic `PlanNavigation` không được yêu cầu sửa.

Chỉ:

```text
1. Register module
2. Add module vào PlanTypeConfig
```

# 34. Expense Semantic Model

Expense có ba dimension với semantic riêng:

```text
Expense
│
├── categoryId
│      → Đây là loại chi phí gì?
│
├── milestoneId
│      → Khoản chi được tính vào mốc kế hoạch nào?
│
└── activityId?
       → Khoản chi có liên quan đến hoạt động nào
         trong Travel Itinerary?
```

Concept:

```ts
interface Expense {
  id: string;
  planId: string;

  title: string;
  amount: number;

  categoryId: string;

  /**
   * Planning/accounting anchor.
   * Used for milestone aggregation.
   */
  milestoneId: string;

  /**
   * Optional weak reference to Travel Activity.
   * Used only for contextual Travel UX.
   */
  activityId?: string;

  // payer / participants / split...
}
```

---

# 35. Expense Dimensions không ngang hàng về semantic

### categoryId

Financial classification.

```text
Ăn uống
Di chuyển
Lưu trú
Vé
...
```

### milestoneId

Planning/accounting context.

Trả lời:

> Khoản chi này được tính vào mốc nào?

V1.1:

- Nếu Plan bật `planning`, `milestoneId` tham chiếu milestone hiển thị bình thường cho user.
- Nếu Plan không bật `planning` nhưng `finance` cần compatibility anchor, `milestoneId` tham chiếu `hidden default milestone`.

### activityId

Optional itinerary context.

Trả lời:

> Khoản chi này có liên quan đến hoạt động nào?

`activityId` không thay thế `milestoneId`.

`milestoneId` không thay thế `activityId`.

Không suy ra field này từ field kia.

# 36. Valid Expense Relationships

Tất cả các trường hợp sau đều hợp lệ:

| milestoneId | activityId | Ví dụ                                                  |
| ----------- | ---------- | ------------------------------------------------------ |
| Có          | Không      | Đặt khách sạn thuộc mốc Chuẩn bị                       |
| Có          | Có         | Expense vừa thuộc một milestone vừa liên quan Activity |
| Có(hidden)  | Không      | Debt expense dùng hidden default milestone             |
| Có(hidden)  | Có         | Travel/extension flow gắn activity nhưng planning UI bị tắt |

Trong transitional architecture V1.1:

- `Expense` không yêu cầu `activityId`.
- `Expense` vẫn luôn có `milestoneId`.
- Với plan không bật `planning`, `milestoneId` được app auto-fill bằng `hidden default milestone`.
- Hidden milestone không được expose ra planning UI/statistic UI khi `planning` module disabled.

# 40. activityId là Weak Reference

`Expense.activityId` có các đặc tính bắt buộc:

```text
optional

one-way

weak reference

không cascade delete

không cascade update

không ảnh hưởng milestone aggregation

không bắt buộc Activity còn tồn tại

có thể dangling sau khi Activity hard delete

một Activity có thể được nhiều Expense tham chiếu
```

Đây là Architecture Decision chính thức V1.1.

# 41. Activity Delete Lifecycle

V1.1 sử dụng **hard delete** Activity.

Không bắt buộc soft delete.

Flow:

```text
Delete Activity
       ↓
Delete Activity document
       ↓
Expense remains unchanged
```

Không:

```text
Delete Activity
       ↓
Delete related Expenses
```

Điều này bị cấm.

---

# 42. Dangling activityId

Sau hard delete:

```ts
Expense {
  activityId: 'deleted_activity_id'
}
```

được phép tồn tại.

Khi resolve:

```ts
const activity = await getActivity(expense.activityId);
```

nếu:

```text
activity == null
```

UI phải xử lý graceful.

Không crash.

Không ảnh hưởng Finance.

Không bắt buộc cleanup trong V1.1.

# 45. Finance Aggregation Invariants

Đây là rule bắt buộc.

## Plan total

```text
Plan Total Expense
=
SUM(all Expense.amount)
```

Không phụ thuộc Milestone hoặc Activity.

---

## Milestone total

```text
Milestone Total Expense
=
SUM(
  Expense.amount
  WHERE Expense.milestoneId == milestone.id
)
```

`activityId` không tham gia.

Nếu milestone là `isSystemHidden = true` và `planning` module đang disabled:

- aggregate vẫn tính bình thường ở data layer
- planning statistic UI không được expose milestone này cho user
- finance totals cấp plan/category/activity vẫn giữ nguyên

---

## Activity total

```text
Activity Total Expense
=
SUM(
  Expense.amount
  WHERE Expense.activityId == activity.id
)
```

`milestoneId` không tham gia.

---

## Category total

```text
Category Total Expense
=
SUM(
  Expense.amount
  WHERE Expense.categoryId == category.id
)
```

Không phụ thuộc Milestone hoặc Activity.

# 46. Finance Invariants

Các invariant sau không được vi phạm.

### Invariant 1

> Expense là source of truth của chi tiêu thực tế.

### Invariant 2

> Tổng chi Milestone chỉ được tính từ `Expense.milestoneId`.

### Invariant 3

> `Expense.activityId` không được sử dụng để tính hoặc suy ra Milestone total.

### Invariant 4

> Xóa Activity không được xóa Expense.

### Invariant 5

> Sửa Activity không được sửa Expense.

### Invariant 6

> Trong V1.1, Expense luôn có `milestoneId`; nếu Plan không bật `planning`, app phải gán `hidden default milestone`.

### Invariant 7

> Travel Itinerary có thể bị disable mà Finance vẫn hoạt động.

# Phase 9 — Debt Aggregate Prototype

Debt mode ở V1.1 không dùng entity `Debt` và `Repayment` như domain nhập liệu riêng.

Thay vào đó:

- `Finance` là source of truth cho cashflow công nợ
- `Expense` đại diện cho tiền tôi đã đưa ra để cho member khác mượn
- `Income` đại diện cho tiền member khác đã trả lại cho tôi
- `debtTracking` là module aggregate/view-model đọc từ finance theo từng member

Use case được hỗ trợ:

- quan hệ công nợ giữa `owner/current member` và từng member khác trong cùng plan
- không phân rã bắt buộc theo từng “khoản vay” riêng lẻ
- cho phép một member vay nhiều lần, trả nhiều đợt, chỉ cần biết tổng đã mượn / tổng đã trả / còn thiếu

Conceptual view model:

```ts
interface MemberDebtSnapshot {
  memberId: string;

  totalLentAmount: number;

  totalRepaidAmount: number;

  outstandingAmount: number;

  lastTransactionAt?: Timestamp;
}
```

Derived:

```text
Total Lent
Total Repaid
Outstanding
Last Transaction
```

Không làm full Debt product.

---

# Phase 10 — Debt ↔ Finance Relationship

Trong debt mode, `debtTracking` và `finance` không phải hai nơi nhập liệu song song.

`debtTracking` phải được suy ra từ finance:

```text
Expense (member-linked)
  -> Tôi đã cho member đó mượn bao nhiêu

Income (member-linked)
  -> Member đó đã trả lại cho tôi bao nhiêu
```

Ví dụ:

```text
Cho Minh mượn
5.000.000 đ
```

Finance:

```text
Expense
−5.000.000
```

DebtTracking aggregate:

```text
Minh
Đã mượn: 5.000.000
Đã trả: 0
Còn thiếu: 5.000.000
```

Sau đó:

```text
Minh trả
1.000.000 đ
```

Finance:

```text
Income
+1.000.000
```

DebtTracking aggregate:

```text
Minh
Đã mượn: 5.000.000
Đã trả: 1.000.000
Còn thiếu: 4.000.000
```

### Critical Requirement

- không double input giữa debtTracking và finance
- không double count trong statistic
- debtTracking là “balance view”, finance là “transaction ledger”

Architecture được xem là **FAIL** nếu xảy ra một trong các trường hợp:

1. Thêm PlanType mới yêu cầu thêm nhiều `if (plan.type === ...)` trong generic PlanDetail.

2. Travel phải duplicate `Milestone`, `Todo` hoặc `Expense`.

3. Finance crash khi Planning disabled.

4. Finance crash khi Travel Itinerary disabled.

5. Overview phải copy toàn bộ page cho từng PlanType chỉ để thay đổi sections.

6. `Plan` entity chứa data của extensions.

7. Wedding Guest bị generic hóa làm mất semantic domain.

8. Travel Activity bị ép trở thành Todo hoặc Milestone.

9. Activity bị ép thuộc Milestone mà không có business requirement rõ ràng.

10. Xóa Activity làm mất Expense.

11. Sửa Activity tự động rewrite Expense.

12. `activityId` được sử dụng để tính Milestone total.

13. Activity và Expense cùng lưu duplicated relationship hai chiều.

14. Debt phải giả làm Expense/Income để hoạt động.

15. Thêm module mới yêu cầu sửa generic navigation.

16. Existing Wedding data không backward compatible.

17. Module không thể test độc lập.

Chỉ cần một failure nghiêm trọng xuất hiện:

```text
STOP NEW PLAN TYPE DEVELOPMENT
```

và review architecture.

# 63. Architecture Decisions — V1.1

Các quyết định sau được xem là nền tảng và không được thay đổi trong implementation nếu chưa qua Architecture Review.

### ADR-01 — Single Plan Core

> Mọi PlanType sử dụng chung `Plan`.

Không tạo domain root riêng theo PlanType.

### ADR-02 — PlanType as Preset

> `PlanType` xác định configuration và experience, không xác định một architecture riêng.

### ADR-03 — Module-based Capabilities

> Capability được tổ chức theo Module.

Generic UI kiểm tra capability/module thay vì PlanType.

### ADR-04 — Extension Isolation

> Domain đặc thù được giữ trong Extension Module.

Không generic hóa cưỡng ép.

### ADR-05 — Config-driven Navigation

> Navigation được derive từ PlanType Configuration + Module Registry.

### ADR-06 — Widget-driven Overview

> Overview được compose từ reusable/specialized widgets.

### ADR-07 — Planning ≠ Itinerary

> Planning và Travel Itinerary là hai domain độc lập.

```text
Planning
→ Milestone → Todo

Travel Itinerary
→ Date → Time → Activity
```

### ADR-08 — Finance owns Expense

> Expense thuộc Finance.

Milestone và Activity không sở hữu Expense.

### ADR-09 — Independent Expense Dimensions

```text
categoryId
→ Financial classification

milestoneId
→ Planning/accounting context

activityId
→ Optional itinerary context
```

Ba dimension độc lập.

### ADR-10 — Weak Activity Reference

> `Expense.activityId` là optional, one-way, weak reference.

Không cascade lifecycle.

### ADR-11 — Expense is Actual Financial Truth

> Expense là source of truth cho chi tiêu thực tế.

`Activity.estimatedCost` chỉ là planned cost.

### ADR-12 — Module Isolation

> Một optional module bị disable hoặc không tồn tại không được làm module khác crash.

# 65. Final Architecture Statement

Go Plan V1.1 phát triển theo mô hình:

> **Plan Core → Modules → PlanType Configuration → Customized Experience**

Trong đó:

> **Wedding** là bài kiểm tra cho một vertical phức tạp và backward compatibility.

> **Travel** là bài kiểm tra cho khả năng reuse Core, bổ sung specialized extension và tạo weak cross-module relationships.

> **Debt** là bài kiểm tra cho khả năng thêm một domain hoàn toàn khác nhưng vẫn tích hợp với Finance Core.

Architecture chỉ được xem là thành công khi cả ba cùng hoạt động mà không làm generic Plan Core trở thành tập hợp các `if/else` theo PlanType.

**Không thêm PlanType mới trước khi Architecture Gate V1.1 PASS.**
